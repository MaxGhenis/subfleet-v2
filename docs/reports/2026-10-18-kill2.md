## Answers in brief

- **Why lockf 70848 was not recorded.** `/usr/bin/lockf` runs as an Apple platform
  binary with the hardened runtime. On this host (macOS 26.6.2) the kernel returns
  such a process's `KERN_PROCARGS2` buffer with its argv and no environment strings.
  So the installed marker read (`ps -axEww`) never sees its `SUBFLEET_ATTEMPT` and
  `SUBFLEET_ROOT`, and nor does release/217's raw read. It led its own session, so it
  was outside the group. Once its parent died it had ppid 1, so it was outside the
  walk. The installed census (c69757256) has no other source, and it keeps no record
  of a walk member it saw. git 75349 was found because git shows its environment
  (table below).
- **Release/217 finds it, conditionally, and only through responsibility (D-CEN1).**
  It does so when the attempt's guardian is a responsibility root, which needs a
  daemon that is its own responsible process at startup (C-5.1, a launchd-started
  daemon). The lockf names the guardian until the kill protocol's SIGKILL, and
  `_contain` records it and seeds later walks with it. With an unrooted guardian,
  release/217 misses it exactly as the installed release does.
- **Fix on this branch.** `Daemon._contain` now records every process any census
  counts (`counted_identities`), not just those seen naming the root. The kill
  protocol's first census runs before any signal and counts the lockf as the
  provider's child. That record keeps it counted after SIGTERM reparents it, rooted
  or not.
- **Does installing release/217 alone close D-KILL2 for the live daemon?** Only for
  attempts whose guardian recorded a root. That depends on the live daemon being
  self-responsible at startup; this job did not inspect the live daemon. Attempts
  started under the old daemon have no recorded root and keep three sources. With
  this branch, the incident's shape is closed for unrooted attempts too.
- **Question 2 (Codex).** A setsid'd child of a command run by Codex's own seatbelt
  launcher keeps the markers in its environment. The launcher passes them through,
  and a setsid'd python shows them in its buffer. A setsid'd lockf has them too, but
  the kernel hides its environment. It still names the disclaimed root as its
  responsible process. A real `codex exec` was not run: it needs the model service.
- **Question 5 (worktree cwd).** Yes, as a hold-only rule for job-owned worktrees,
  never for in-place workdirs. Measured cost: about 5 ms per census in process
  against a 62 to 78 ms census; `lsof` would cost about 320 ms. It was not
  implemented.

## Question 1: the shape reproduced with release/217's code

### The kernel fact under the incident

A probe (`probe_platform.py`, this job's scratch) started each binary setsid'd with
`SUBFLEET_ATTEMPT`, `SUBFLEET_JOB` and `SUBFLEET_ROOT` in its environment. It then
read its buffer in process (`procs.kernel.arguments`) and with `ps -Eww`:

| Binary as it runs | `csops` platform | `csops` runtime | Markers in `KERN_PROCARGS2` | Markers in `ps -E` |
|---|---|---|---|---|
| `/usr/bin/lockf` (waiting, and running a child) | yes | yes | no: argv only | no |
| `/bin/sleep`, `/bin/cat`, `/usr/bin/perl`, `/bin/zsh` | yes | yes | no: argv only | no |
| Xcode's `git` (via `/usr/bin/git`) | yes | no | yes | yes |
| Homebrew `git`, the venv's python | no | no | yes | yes |
| `bun`, Codex's native binary | no | yes | yes | yes |

Each hidden buffer held only the argv strings and the empty strings around them, for
example `['', '/usr/bin/lockf', '-k', '<lock>', '/bin/sleep', '60']`. The rule
observed over these ten binaries is hidden exactly when both flags are set in the
running process's code-signing status. The files' own signatures (`codesign -dv`)
carry no runtime flag, so the flag is the running process's. This is a correlation
over the binaries tested, not a kernel rule read from source. A platform binary
whose markers are hidden can never be found by C-5.5's marker source, whichever read
it uses.

## Question 2: a setsid'd child of a Codex command

A real `codex exec` needs the model service, so it was not run. Instead, Codex 0.159.0's
own launcher, `codex sandbox -P :workspace -C <scratch> -- /bin/sh -c …`, ran under
the following conditions:

- no model, and a dead HTTPS proxy;
- a scratch `CODEX_HOME` with no configuration;
- a parent started with responsibility disclaimed, carrying an attempt's markers.

Inside, the shell had `CODEX_SANDBOX=seatbelt` and `CODEX_SANDBOX_NETWORK_DISABLED=1`.
It had all of the parent's `SUBFLEET_*` variables. It started a setsid'd lockf and a
setsid'd python, then exited. Results (`probe_codex.py`):

- **lockf:** ppid 1, pgid = pid (its own session), responsible process = the
  disclaimed parent; markers invisible to both reads.
- **python:** the same shape, and markers visible to both reads.
- **release/217's census with the root alive:** lockf in `responsible_pids` only;
  python in `marker_pids` and `responsible_pids`.
- **The same census without the root:** no lockf.
- **After the root's SIGKILL:** lockf only when the census is seeded with the
  identity seen through responsibility.

So the launcher neither rewrites the environment nor disclaims responsibility for
what it starts; the kernel is what hides lockf's markers. What this did not exercise:
the lanes' own `config.toml` (`shell_environment_policy`) and the spawn path of
Codex's exec tool. That the incident's git 75349 carried the markers through a lane's
real Codex shows the lane's policy passes them.

A probe of late births (`probe_flags.py`) checked responsibility after the root dies.
Once the root had died, a surviving member named itself as responsible, and so did a
process that member started afterwards. Responsibility cannot be asked about after
the root's death; only a recorded identity can.

## Questions 3 and 4: release/217's reasons, and the fix

Release/217 misses an unrooted attempt's lockf for these reasons, all from
`procs.containment` and `Daemon._contain`:

1. **Group:** lockf leads its own session.
2. **Walk:** the walk follows parent links from the guardian, the child and recorded
   seeds. After SIGTERM, lockf's parent is init.
3. **Marker:** `_kernel_sources` reads the raw buffer, and lockf's holds no
   environment.
4. **Responsibility:** this applies only with a recorded root, and only while the root
   lives.
5. **Persistence:** `_contain` persisted only `responsible_pids` as seeds, so a walk
   sighting before SIGTERM was forgotten.

**The fix** (`subfleet/daemon.py`, `Daemon._contain`) works as follows:

- After each census, every live member counted by the group, the walk or its marker
  is persisted under the attempt's evidence `counted_identities`, with event
  `attempt.counted_recorded`. A probe keeps it in its record.
- Persisted members exclude the guardian and anyone recorded as responsible. A member
  is written only if its identity was captured and that birth isn't already kept in
  `owned_identities`, `responsible_identities` or `counted_identities`.
- Every later census gets these as recorded survivors, which seed the walk, as
  `responsible_identities` already did. A different birth at the same pid becomes a
  C-5.5 alternative.
- It is evidence only. `_kill_attempt` still signals only `owned_identities`, and
  `verified_empty` is unchanged: an unverifiable census is never contained (the M3 run
  below).

**What stays outside every source** (documented in C-5.5 and pinned by
`test_d_kill2_a_hidden_lockf_no_census_saw_is_invisible_without_a_root`, marked
`documented_limitation`):

- an unrooted attempt's hidden-marker process that leaves the group and the walk
  before any census counts it;
- a process started with responsibility disclaimed;
- after the root's death, a member no census saw.

The kill protocol's first census runs before any signal (`_kill_attempt`), so the
incident's order is covered. Turn jobs stop the provider before containment (D-13),
which this job did not examine.

**One gap remains for unrooted attempts that end by themselves.** If the provider
exits on its own while the lockf waits, the attempt's first full census is C-5.9's, at
finalization. By then the lockf may already have ppid 1. While the attempt runs,
`_inspect_running` records only group members (`_record_owned`, C-5.11). So an
unrooted attempt's hidden-marker process that left the group in a session of its own
is not seen. A rooted attempt is covered here as well: its guardian stays while the
lockf names it, and finalization's census counts it by responsibility.

**A possible follow-up** (not implemented): record walk descendants outside the group
from the same shared table `_inspect_running` already reads. That costs no extra
process read, but an evidence write whenever a new one appears. Under Codex, whose
commands lead sessions of their own, that write would come about once per inspection
interval, and the evidence would grow by one identity per command. Pruning seeds
proven dead would bound that.

## The invariant

For an attempt A, at the instant of a census that termination reports contained
(`verified_empty`):

1. no live process whose readable argument buffer holds A's `SUBFLEET_ATTEMPT` and
   `SUBFLEET_ROOT` strings exists;
2. no live process names A's recorded, still-live responsibility root as responsible;
3. no process that an earlier census of A counted, by any source, is alive under the
   identity it was counted with;
4. every read succeeded.

The first three hold only within the C-5.3 identity limit (same-second pid reuse).
Item 3 is what this branch adds for the group, walk and marker sources; release/217
had it for responsibility. The guarantee is not "no process carrying A's markers is
alive": a process whose markers the kernel hides, and which no census ever counted,
is outside all of 1 to 3.

Tests that state it:

- `test_d_kill2_property_every_counted_member_is_kept_once_and_seeds_the_next` (Hypothesis,
  40 derandomized examples) checks the recording half. Every live member other than the
  guardian, with a captured identity, ends in exactly one of `responsible_identities`
  and `counted_identities` under that identity. Each is passed to the next census as a
  recorded survivor. Nothing is added to `owned_identities`, and a repeated census
  writes nothing.
- The process and daemon tests check it end to end on the real kernel.

## Question 5: a worktree-cwd rule

**Should termination refuse "contained" while a marker-less process whose cwd is
inside the attempt's worktree lives?** For job-owned worktrees, yes. It is the one
signal that would have held 70848 with no root and no earlier sighting, since its cwd
was the job's worktree. It should be a hold-only source, never signal authority. It
should never apply to an in-place workdir.

**Measured** with `measure_cwd.py` on this host, 1,197 processes, load 22.5, 18 CPUs,
seven rounds, medians:

| Read | Time |
|---|---|
| Census, three sources | 62.0 ms (55 to 78) |
| Census, four sources | 77.6 ms (51 to 94) |
| Every process's cwd in process (`proc_pidinfo` `PROC_PIDVNODEPATHINFO`, 2,352 bytes per pid) | 5.1 ms (4.4 to 9.4) |
| `lsof -n -P -w -d cwd -Fn`, every process | 318.8 ms (296 to 662) |

Of the cwd reads, 867 succeeded, 328 were refused with EPERM (other users'
processes, which C-5.5 skips already) and 2 had gone. An in-process pass adds about
7% to a census. `lsof` would multiply it about five times.

**Over-inclusion, counted now:**

- 4 live processes had their cwd in this job's worktree: this job's own provider and
  tools.
- 18 had their cwd in `~/subfleet-v2`, where other sessions work. An in-place job
  there would be held by all 18.
- 0 had their cwd in the caller's lane checkout.

**Open before implementing:**

- whether a retried attempt of the same job reuses the worktree, in which case the
  new attempt's processes would hold the old one;
- that a process can `chdir` away, and one with its cwd elsewhere can still write
  into the worktree by absolute path.

So the rule would narrow the gap, not close it.

### Two causes

**1. The runner's kernel shows lockf's environment.** The runner image was
`macos-15-arm64` version 20260907.0337.1, on macOS 15.7.9 (24G830). There the daemon
test's lockf buffer carried its markers. On this host, macOS 26.6.2 (25G83, SIP
enabled), a probe on 2026-10-19 read a waiting `/usr/bin/lockf` as argc 7, the
executable path, one byte of padding and its seven argv strings, and nothing after
them. A python process started the same way showed its environment and the kernel's
strings. This is all that has been observed of which macOS versions hide a platform
binary's environment: 26.6.2 hides lockf's, 15.7.9 on the runner shows it. Whether
the difference is the version or the runner's configuration (a virtual machine
image, whose SIP status these logs don't show) is not established.

**2. #222's allowlist dropped the process tests' markers.** Since #222 (merged into
the branch at `976836695`), the guardian gives its provider only allowed names and
the names it is given with `--env-pass`. `SUBFLEET_ATTEMPT`, `SUBFLEET_JOB` and
`SUBFLEET_ROOT` are launch names (`launch_env.LAUNCH_NAMES`), which `Daemon._launch`
passes with `guardian_pass_args`. `FakeAttempt` passed none. So after the merge its
lockf and its python carrier carried no markers at all. The two carrier assertions
failed on CI, and would have failed on this host too. Every hidden-marker process
test passed only because there was no marker to hide. This cause has nothing to do
with macOS. Two observations show it: the premise test passed its "lockf shows no
`SUBFLEET_` string" assertion on a runner whose kernel shows lockf's environment,
and the daemon, which passes the markers by name, showed them on the same runner.
Of the other tests that start a real guardian with markers in its environment, only
this file lacked `--env-pass`.

### The fix

No Subfleet code changed: the fix is in the tests.

- **The stand-in, `tests/hidden_environment.py`.** `without_environment` cuts a
  `KERN_PROCARGS2` buffer after its argv, which is the shape 26.6.2 returns for lockf.
  `HidingKernel` wraps `procs.kernel` and applies that cut only to the pids it is
  given; every other read is the real one. `procs.kernel` is the reader every census
  uses (`_kernel_sources`), and the only place the census reads markers. `hiding_ps`
  does the same for the installed census's `ps -axEww` rows (a hidden pid's row
  becomes its argv). `published` reads a fixture's pid file.
- **The daemon test** (`tests/fake/test_census_escapers_daemon.py`):
  - The real-lockf test now skips where the host shows lockf's markers, with the
    reason `this host (macOS <version>) shows lockf's environment; the hidden-marker
    incident can't be reproduced with lockf here`. Where they are hidden it runs
    exactly as before; the body moved, unchanged, into `lockf_escaper_holds_the_attempt`.
  - A twin, `test_d_kill2_a_lockf_whose_markers_the_census_cannot_read_holds_the_attempt_on_any_macos[rooted|unrooted]`,
    starts the fake daemon with the new `--hide-environment-of <escaper pid file>`
    (`tests/fake/run_daemon.py`), so the daemon's own census cuts lockf's buffer.
    Every assertion is the real test's:
    - the attempt is quarantined;
    - lockf is in `live_pids` and `descendant_pids`, and never in `marker_pids` or
      `group_pids`;
    - its identity is in `counted_identities` (unrooted) or `responsible_identities`
      (rooted), and never in `owned_identities`;
    - `kill --confirm-dead` leaves the attempt quarantined while lockf lives, and
      releases it once lockf is gone.
  - `test_d_kill2_the_daemon_s_stand_in_hides_markers_the_host_shows` checks the
    flag where this host would otherwise hide the difference. The `retitled-nul`
    escaper's markers show on every macOS, and D-CEN1's regression counts it by them.
    With the flag, the census doesn't count it by them, and the rooted guardian still
    holds the attempt.
- **The process tests** (`tests/process/test_census_hidden_environment_process.py`):
  - `FakeAttempt` passes its environment with `guardian_pass_args`, as the daemon
    and `test_census_responsibility_process.py` do.

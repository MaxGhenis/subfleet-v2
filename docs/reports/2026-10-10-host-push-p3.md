The decision is to move the build out of admission. The same single push
executor serializes checkout construction and publication, so a build can delay
another push but cannot hold the admission pass or an ordinary pool worker.
At most one preparation is outstanding and one new build is offered per
detached pass, so every offer gets a fresh disk/admission look. Completed
results are consumed before unrelated holds: an unavailable pin cannot retain
the preparation slot. A completion observed after the disk sample also spends
that pass's offer budget. Preparing jobs hold no lane lease and have no attempt. A ready checkout is
renamed whole and recorded on the job before readiness is exposed; restart can
reuse it, and retention can still find it if a cancellation loses the future.
Cancellation during construction discards the unused checkout. A completed,
unused checkout stays tracked while its job waits on unrelated holds, so a
later cancellation still queues cleanup; after a lost tracker or restart,
`jobs.worktree` preserves retention ownership. Skipped and
discarded builds return false readiness, including cancellation after a pass
has captured its queued row. Admission passes the explicit prepared checkout
to its workspace helper; a checkout missing at the prepared-path validation
refuses with exit 7 and a notice. Even a later disappearance cannot invoke
that helper's synchronous direct-call fallback. Only the detached
pass owns the future map; the concurrent turn pass cannot cancel another pass's
build. Git's 60-second per-call limit remains, now outside admission; moving the
build does not extend supported repository sizes or provide a power-loss proof.

The 600 MB cap is two fifths of C-6.17's default decimal 1.5 GB placement reserve:
budgeting another 600 MB for a similarly sized Git clone object store leaves
nominal 300 MB checkout headroom. Git can change the object representation,
so the intake cap does not guarantee the combined allocation fits the reserve. The local
object store measured 502,183,981 bytes, so a 500 MB cap would refuse this checkout.
The cap remains fixed with disabled or customized disk policy. It bounds object
intake, not the expansion of arbitrary compressed checkout contents. APFS clones
count their logical size against it and do not allocate copied data blocks;
oversized concurrent-growth snapshots are discarded. Hardlinks are never used.

The read-only survey deduplicated 790 common Git configs from immediate local
repositories and one directory level below them, excluding hidden directories
and chief-of-staff. Median: 397 B; 95th percentile: 3,118 B; maximum: 143,067 B
(`PolicyEngine/policyengine-us`). The subfleet common config was 19,066 B. All
surveyed configs fit 256 KiB; this is 1/16 of the previous input limit.

The acceptance contract's C-6.5 refusal index and C-6.8/C-8.5 clauses now describe the bounds,
startup ordering, shared parse, asynchronous readiness, and error behavior.

## Fix round 1

Review #183 at `a22e72ec8` found that a SQLite ownership-write timeout froze
the build's Future and repeatedly stopped detached admission. The worker now
returns its checkout result without writing ownership. Admission completion
records ownership before exposing readiness, retains the result across
`SQLITE_BUSY`/`SQLITE_LOCKED` (including extended codes), and retries on later
passes while continuing other jobs. A permanent store failure fails only its
job; its cause remains pending until the failure and notice commit together.
Workspace refusal/deferral writes receive the same busy-store treatment, and
an unsuccessful deferral write does not consume the build retry budget.

The implementation is at `subfleet/daemon.py:3973` (construction), `:4014`
(completion), `:4058` (reaper), `:4111` (readiness), and `:6297`
(workspace retry accounting). Both consumers of the Future map use completion
recording. A failure or cancellation while construction is still running keeps
its slot until the worker stops, preserving the fresh disk look for another
build. Cancellation
rechecks the live row within the ownership transaction and discards an unused
checkout through the serialized executor. Cancellation also clears pending
store errors. Restart reuses a whole conventional-path checkout whose
ownership was not yet recorded; retention's existing `owned_worktree` lookup
still identifies that allocation if its job was cancelled before restart.
An already recorded path creates no second ownership audit event.

The bundled probe at `a098f20eb` was imported under the unique basename
`test_host_push_store_completion_pr183.py` and committed first. Its real
SQLite-lock regression retains the original input; after the fix, the lock
is held through admission's ownership-write timeout rather than requiring
that the construction worker write to SQLite. Its 80-example lifecycle
property also recognizes the existing conventional-path retention fallback.

`test_host_push_store_interleavings.py` adds a 120-example busy-write lifecycle
property (completion, cancellation, passes, pin holds, restart and crash),
including rollback at transaction start, each mutation, the audit write and
commit. Cancellation transactions share the generated fault schedule, and the
property rejects duplicate ownership audit events. A separate 20-example
property runs the complete production detached admission loop
with generated busy writes, completion and cancellation. Deterministic
production-Store regressions cover begin/update/audit/commit failures, extended
SQLite busy codes, permanent errors and notices, cancellation while recording
is pending, restart reuse, and refusal/deferral writes.

# What inspecting running attempts costs, 2026-09-24

On 2026-09-20 the laptop's closed-lid thermal guard SIGSTOPped the daemon from 17:18:38 to 19:22:13 EDT. The guard pauses the operator's command-line processes at or above 20% CPU while the lid is closed on battery, and the daemon qualified every time it looked. This report covers the process-inspection share of that cost and what C-5.12 changes. The admission share is a separate change.

## What was observed, 2026-09-20 and 2026-09-21

- With four attempts running and twelve jobs waiting, the daemon (release `20260920T211551Z`, source `4eb412f8`) sat at 90 to 101% of a core: seven CPU-minutes in its first twelve minutes. A three-second `sample` put its on-CPU time in `__fork`, the malloc locking a fork takes, and pipe reads.
- Polling its direct children for eight seconds showed about 120 of them, 15 a second, mostly `/bin/ps -axEww -o pid=,command=`, with `sysctl` and `/bin/ps -axo pid=,ppid=,pgid=,stat=`.
- By the next morning the daemon was at 1.0 GB resident with 40 threads. A `ps` started from a process of that shape costs the parent 8.2 ms of CPU when CPython forks and 0.17 ms when it uses `posix_spawn`: measured with a 1 GB heap and 40 idle threads, 40 runs each. At 50 MB the fork costs 0.85 ms.

## Where it went, from the code

- `_control` offers every live attempt to the worker pool every 50 ms. For a running attempt, `_process_attempt` called `procs.liveness` on every pass: `ps -p N -o lstart=`, `ps -p N -o stat=` and a `sysctl` for the boot identity, three processes each time, with nothing rationing them.
- Every 0.5 s it also ran a full census only to record the group's members as owned: two `ps` reads (one of them the environment scan), three more processes for every live pid found, then three more to re-check the guardian.
- Each tick asked `leases` once for every job the store had ever accepted.

## What changed (C-5.12)

- A healthy running attempt's processes are inspected at most once per `inspect_interval_s` (1 s), from one process table that every running attempt shares. The receipt, a cancel request and the wall clock are still read on every tick.
- A table expires 1 s after its read began, and an attempt falls due again when the table it was given expires, so each inspection is given a table read since its last. As first written, the next inspection was timed from before the read and fell just short of the table's expiry, so every other inspection reused a table: tables were read about every 2 s, and a death was seen up to about 2.5 s after it (found in review, 2026-09-25; `test_c5_12_each_inspection_is_given_a_table_read_since_its_last` pins the bounds on a fake clock, with `ps` taking from 0.02 to 1.5 s).
- Only the inspection that reads a table waits for `ps`, and for the table's boot identity, which it reads before any other attempt is given the table. One that finds a read running returns and asks again on its next tick, so a slow or hung `ps` or `sysctl` holds one of the pool's twelve workers rather than one per running attempt, and the other attempts' receipts are still read every tick (the attempts recorded with a legacy boot timestamp wait together for the table's one `kern.boottime` read). When `ps` takes longer than the 1 s interval, reads run back to back, one at a time; in the 2026-09-25 review a read that took 720 ms cost `ps` 26.5 ms of CPU, so the wait is the machine's load and not `ps` working. As first written, every inspection that asked during a read waited on its lock, for up to the 10 s cap. Until 2026-09-26 the same held for `sysctl`: each attempt given a table read its boot identity itself, behind the table's lock, so one 2 s `sysctl` held every inspecting worker for its length (found in the final review of PR #37; its probe, run again on 2026-09-27, is in `2026-09-24-process-inspection-cost/boot-wait.txt`: four attempts each waited about 2.1 s before this change, and three of them 0.0 s after). The reader is whichever attempt asks first once the table has expired, and the control loop offers attempts in the order the store lists them, so one attempt can be the reader interval after interval and wait out every slow read.
- The table is C-5.5's snapshot with `lstart` added. It answers the C-5.3 identity question for any number of pids, so a census is two `ps` reads instead of `2 + 3N`.
- A census no longer reads each pid its snapshot found a second time, so a process that exits just after the snapshot is still counted. That only ever holds on to an attempt: the kill protocol and C-5.9 re-read until the census empties, and start grace, which reads it once, now reads `start.json` and `exit.json` again after its census. Without that re-read, a guardian that finished while the census ran was quarantined here; before this change, with the pid dropped, it was recorded `starting-no-receipt` although its provider had exited 0, and its job could run again (found in review, 2026-09-25). The re-read counts a receipt only as the tick does, when its JSON value is neither empty nor false; testing that the file existed, it left an attempt whose `start.json` held `{}` or `null` in `starting`, with a full census on every tick (found in the final review of PR #37, 2026-09-26).
- The shared table can only say "alive", and only where `liveness` would. Anything else goes to a fresh `liveness`, and every census that decides anything is still read fresh. A guardian the table does not show but a fresh read finds alive has its group recorded from a table read for it alone: one `ps`, and one `kern.boottime` read for a legacy record, which that table matches itself. That used to happen once to most new attempts, which fell due as they first asked and were given a table another attempt had read before their guardian existed; an attempt the daemon launches now falls due an interval after it opened the guardian's launch gate, so its first table shows the guardian (found in the reviews of 2026-09-26).
- A guardian records a legacy `kern.boottime` timestamp when its UUID `sysctl` fails once as it starts, and its attempt keeps it for life. The shared table shows such a guardian alive when C-5.3 matches the timestamp to the table's `kern.boottime` seconds, which it reads once, for every legacy record it is asked about, and its group is recorded as owned from that table, as `same_process` would allow. As first written, owned recording wanted an exact boot match, so such an attempt paid five reads an interval and recorded nothing, and survivors of an abnormal guardian death were quarantined rather than killed (found in review, 2026-09-25). After that fix it still paid six: the table was asked without the legacy match, so the guardian was asked about afresh (two `ps -p` and a `kern.boottime`), and then read a table of its own and `kern.boottime` again to record its group. It now pays one `sysctl` per table (found in the final review of PR #37, 2026-09-26; `test_c5_12_the_legacy_match_says_alive_exactly_where_liveness_does` compares the two answers over 2,520 cases; the review's probe, run again on 2026-09-27, is in `2026-09-24-process-inspection-cost/legacy-reads.txt`: with the boot identity cached, an interval cost such an attempt six process starts before this change and two after, the table and `kern.boottime`, against one for an attempt recorded with the UUID).
- The shared table's reader reads its boot identity just after `ps`; any other table (a census's, or one read for a single attempt) reads it when it first describes a live pid. Either reads it once, and keeps whatever the read raised, as a table keeps its `kern.boottime` read. Until 2026-09-27 only a failed inspection was kept, so anything else either read raised would have been read again by each attempt that asked, one after another (found in the review of this PR's port). If that UUID read falls back to `kern.boottime` seconds, a guardian recorded with the UUID can only be unknown against it, so the inspection counts it as a failed read and decides nothing; otherwise one blip sent every running attempt to two `ps -p` reads and a table of its own. As first written, every table read it as soon as `ps` returned, so a failed `sysctl` made even an empty census unverifiable and blamed the enumeration (found in review, 2026-09-25).
- One boot-identity read is reused for 5 s, if it is the boot session UUID. The `kern.boottime` seconds that a failed UUID read falls back to are not kept: for as long as they were, every process recorded with the UUID would compare as unknown, and the kill protocol could not signal it (found in review, 2026-09-25). A boot mismatch is read again before it counts. A table read that fails is rationed like one that works, and while it stands no attempt asks about its guardian singly. As first written, each did, so an outage cost one capped read for the table and one per running attempt every interval (found in review, 2026-09-25).
- An inspection that raises, for instance on a store write that fails, gives back its interval. C-5.10's retry then repeats it, on the same table while that has not expired, and backs off as on `main`: 8 raises and 4 `daemon.log` lines in 120 s. Until 2026-09-27 the pass took its interval before the parts that can raise, so the retry found the attempt not due and returned normally, which C-5.10 counts as recovery. At the default 1 s interval a lasting cause then raised and was logged 119 times in 120 s, and an attempt whose guardian had died took a full census each time (found in the review of this PR's port to `main`, 2026-09-27; `tests/unit/test_inspection_pacing.py`). A retry that cannot inspect still returns normally and clears the count: one that finds another attempt's read running, or is given a failed table, an unreadable boot identity or a guardian whose liveness is unknown. The release line handles that case (`246926d`); here it is left for a follow-up.
- `ps` and `sysctl` are started with `posix_spawn`. That needs `close_fds=False`: CPython on macOS has no `POSIX_SPAWN_CLOSEFROM`, so with `close_fds=True` it forks (1.38 ms of parent CPU per start against 0.58 ms at a 512 MB heap and 40 threads, 2026-09-26; 35 ms against 0.49 ms at a fragmented 1.7 GB heap in the 2026-09-25 review). The cost is that a pipe or socket another thread is creating can be inherited, because macOS has no `pipe2` and no `SOCK_CLOEXEC` and Python marks it close-on-exec in a second step: beside two threads making pipes, 175 of 600 spawns inherited one, and 0 of 600 with `close_fds=True` (three runs of `tools/probe_fd_inheritance.py` on 2026-09-27 at a load average near 28, raw lines in `2026-09-24-process-inspection-cost/fd-inheritance.txt`). Only `ps` or `sysctl` holds it, for at most its 10 s cap, so at worst a close is seen that much later.
- The export check is one join driven from `leases`. `~/.claude.json` is parsed only when `stat` says it changed.

## What was measured

`tools/measure_idle_cost.py` runs a real `Daemon` with the production tick on a temp state root holding 300 accepted terminal jobs, with the timers switched off. It measures three states: idle; four running attempts (real sleeping processes as guardians) with twelve queued jobs; then every lane closed with the attempts ended. It takes 20-second windows and uses `getrusage` for the daemon and for the children it reaped. It was run from a checkout of each revision on 2026-09-24, with this Mac at a load average between 40 and 55, so the small numbers are upper bounds.

| | `origin/main` (3f155e5) | this change, as first written (845d663) |
|---|---:|---:|
| Idle: daemon | 7.8% | 0.5% |
| Four running, twelve waiting: daemon | 46.5% | 3.9% |
| Four running, twelve waiting: its `ps` children | 71.5% | 2.7% |
| Every lane closed, twelve waiting: daemon | 9.0% | 1.6% |

The measuring process is small (a fork from it is cheap), so the baseline column understates what a daemon at 1 GB paid.

Measured again on 2026-09-26, after the review's fixes, at a load average near 7, with the tool as it now is: each window starts once admission has settled, and the closed phase closes the lane before it ends the attempts. Twenty-second windows, one run of each revision:

| | `origin/main` (3f155e5) | as first written (845d663) | after the review |
|---|---:|---:|---:|
| Idle: daemon | 3.0% | 0.2% | 0.2% |
| Four running, twelve waiting: daemon | 29.0% | 1.6% | 1.9% |
| Four running, twelve waiting: its `ps` children | 49.3% | 1.8% | 2.1% |
| Every lane closed, twelve waiting: daemon | 3.8% | 0.7% | 0.7% |

After the review the table is read once a second, where the first version read it about every two seconds; the last two columns differ by 0.3 points of a core in each of the running rows.

`tests/fake/test_idle_cost.py` counts processes at the one seam every `subprocess` call goes through: four healthy attempts ticked twenty times cost one `ps` and one `sysctl`, and a guardian that dies is still found by a fresh read. Its smoke run of the measuring tool starts each window only once admission has settled: while the fleet is full a pass looks at one new job at most, so under load the first looks at a new queue, a decision row each, took seconds and landed in windows that began after a fixed pause (CI run 36016193771).

## What this does not change

- An abnormal guardian death is now noticed by the first table read that begins after it, which begins by the first 50 ms tick 1 s after the death (or as the read then running ends, when it takes longer than that), once that read (`ps` and the boot identity) and one fresh `liveness` read have run, and acted on once the census that decides between a loss and a kill has run; before, it was noticed at the next tick, once one `liveness` read had run, and acted on after the same census. In the 2026-09-25 review, at a load average of 40 to 60, one table read took 0.72 s and one `liveness` read 355 ms, so the worst case there was about 2.1 s, and more by a `sysctl` when the table's boot identity is not remembered. A normal end is unaffected, because it is read from `exit.json` on every tick, except for the attempt whose inspection is reading the table, which reads its receipt when that read returns, and the attempts recorded with a legacy boot timestamp, which wait for the table's one `kern.boottime` read. A new group member is recorded as owned by the next table read, not within 0.5 s. One missed is never signalled individually (C-5.4): while it stays in the group `killpg` reaches it with the rest, and one that has left the group before then is quarantined.
- The daemon's resident size (1.0 GB after fifteen hours on 2026-09-21) was not investigated.

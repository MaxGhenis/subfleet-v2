- **Detached resumes never move today.** `_resume_args` (daemon.py ~1890) pins `pinned_lane` and `pinned_model` to the source attempt. A pinned job waits while its lane is closed. C-11.8 holds it as stuck only if the closure ends more than `admission.pin_hold_far_s` out (7 days), and then fails it after `pin_grace_s`. A pinned job that hits a limit is not retried (daemon.py ~5865) and ends with rc 4. So on release/217 a resume already waits for its warm lane. Rule 2a's "otherwise move" would be new behaviour. It is possible only for Claude: all 18 live Claude lanes are `keychain-token` and share the default config directory, which is why C-26.2 can move turns. Codex lanes are `home` lanes, and a thread lives in its lane's home, so a Codex resume cannot move.
- **Cold moves happen today only on Claude conversation turns.** C-26.2 affinity (`scheduler.rank_key`, using `turn.affinity_lane` from the previous served message in `service._submit_turn`) puts the affinity lane first among candidates. A closed affinity lane is simply not a candidate, so the turn goes elsewhere. The only record of the move is the decision JSON. Nothing reaches the app (Timeline.swift `statusText`). C-26.7 failover continuations exclude the limited lane, so each of them is also a cold move.

- **The cache TTL bounds any useful wait.** Claude Code writes 1-hour cache entries (`ephemeral_1h_input_tokens` > 0, `ephemeral_5m` = 0 in the samples). Per Anthropic's prompt-caching documentation, each use refreshes an entry's lifetime. So waiting for a warm lane pays off only if it reopens before last use + TTL. A reopen after that loads cold on either account. Check how common 1-hour writes are across all attempts before relying on this.

## Design direction (to review before step 2)

- **Measurement.** Add `usage` to the adapter Outcome: raw provider fields plus a normalized `{prompt, cache_read, cache_write, output}`, with prompt = input + creation + read for Claude and prompt = input for Codex. Also record the first and last main-thread request and the cache TTL split. Store it in `attempts.evidence_json.usage`, which needs no schema change. Show it in `runs show` and in `status.json` (a per-lane share over a recent window). Add a `subfleet usage` report: cache-hit share per lane, per conversation and per resume chain, over a `--since` window. Older attempts are filled from retained stream artifacts and labelled as backfilled.
- **Warm wait for detached Claude resumes.** When the warm lane is closed only by a limit with a reported reopen time, wait iff reopen ≤ min(first warm-wait event + `admission.warm_wait_s`, last use + measured TTL). Otherwise move to a lane that shares the config directory, as an affinity rather than a pin. The resume launch must accept the new lane, which means amending C-11.2/C-12.3. Codex resumes wait as today, because they cannot move.
- **Turns.** Move as today. Record `moved_cold` (from, to, reason, warm lane's reopen time, measured context size) and show it in the turn status strip (Timeline.swift, plus the frontend probe tests). An optional per-message `wait_for_warm` is bounded by the same key.
- **Rank keys.** Leave them unchanged while the warm lane is open. #120 changes only the within-band tail of `rank_key`, after the `(desktop, affinity)` prefix. Keep this change in the prefix and in admission, and update `tests/reference_scheduler.py` (the differential reference).

## Replay of the live record (2026-10-04 02:50Z; `tools/warm_lane_replay.py`, summary in `2026-10-04-warm-lane-replay.json`)

Claude attempts since 2026-09-19: 2,237, of which 2,218 have a retained stream with usage.
- **TTL.** 2,004 attempts wrote only 1-hour cache entries, 112 wrote none, and none wrote 5-minute entries. The cache lifetime Subfleet runs under is 1 hour, measured.
- **Cache-hit share** (read / prompt, from `result.usage`): dispatch 0.978 (1,933 attempts), turns 0.972 (121), resumes 0.989 (11), gate reviews 0.897 (51).
- **Turns that stayed on their lane** (47). With a gap of 1 hour or less (26), the first request read a median 437k tokens and wrote 1.8k. With a gap over 1 hour (21), it read a median 0 and wrote 523k: cold on the same account. So the TTL, not the lane, decides warmth.
- **Turns that moved lane** (37). In 21 of them the previous turn ended within the hour, so staying would have read warm; they wrote 8.92M tokens cold in total. 19 of the 21 were C-26.7 failover continuations (`excluded` plus the limit closure) and 2 were `below-floor`. Their warm lane's reopen times: 18, 18, 63, 78, 79, 88, 90, 91, 91, 92, 138, 144, 178, 186, 191, 191, 228 minutes, plus two weekly closures (4.6 and 4.8 days). Only the two 18-minute cases reopened while the cache was still alive. They wrote 0.83M of the 8.92M.
- **Resumes** with the pinned lane closed at submit waited 726 to 9,004 s and then loaded cold anyway (for example `20260929-142213-triple-lock-paper`: 10k read, 274k written), because the wait outlived the TTL.

**Rule this supports.** Waiting helps only when the warm lane reopens before last use + TTL. The default `admission.warm_wait_s = 3600` equals the measured TTL. The effective bound per job is min(start of the warm wait + `warm_wait_s`, last use + measured TTL). A move after the TTL costs nothing extra, so the status should say "moved cold" only when the cache was still alive.

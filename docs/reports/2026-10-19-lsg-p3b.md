## Cause, as executed

### P3-1: the docstring's out-of-scope list did not match C-20.6

The new regression test parses both lists into items. It splits at semicolons outside parentheses and stops at the full stop that ends the sentence.

**Where it failed:**

- **As a pytest:** it failed at 473fe2941, in the first job's hold 1.
- **As text:** the second job applied the test's own parser (`out_of_scope`, taken from the head's test file) to each revision's docstring and C-20.6 clause, outside pytest. At 473fe2941 and at release 43f42d83d, which have the same docstring and clause, the result is:

- **Item count:** C-20.6 lists nine items, the docstring six.
- **Missing:** the docstring had no "a shell's script operand", no `DirEntry.stat` and no "native file access through `sqlite3`".
- **First item:** the docstring had "other PATH-searching programs, such as find -exec and interpreters". The clause adds `sudo`, `sandbox-exec` and `xcrun`, and says that nothing in this repository launches `find -exec`.
- **Symlink item, too broad:** the docstring said "path aliases, such as a symlink to /usr/bin or to the reader". That puts every symlink to the reader out of scope. But `_is_keychain_binary` (`subfleet/credentials.py:137`) compares the resolved path (`_fold`, `os.path.realpath`) and the file identity (`os.stat`). It does so for every direct launch's target (`_launch_targets`, `:175`) and for a wrapper's command given by path (`_unsafe_delegation`, `:433`). Of the symlinks to the reader, only one that a wrapper's bare command finds through PATH escapes. The property's `alias` program exercises the refused direct case: a bare alias name, found through PATH.
- **The clause's own wording:** release's C-20.6 says "or one to the reader that a wrapper's bare command finds through PATH". So it does not hold the brief's phrase either.
- **Why no test caught it:** the round-10 phrase test, `test_contract_and_docstring_state_the_command_word_and_nesting_rule`, checked neither phrase.

At this report's head, by the same computation, both lists have the same nine items. Both hold "a shell's script operand" and "a symlink to the reader that a wrapper's bare command finds through PATH".

### P3-2: the property never drew bytes, path-object or other argv words or programs

At 473fe2941, `launches()` in `tests/unit/test_live_store_guard_round10.py` built every argv word and program name as `str`. The guard handles other types like this:

- **Decoding:** it decodes the program and each argv word with `os.fsdecode`, which accepts text, bytes and path objects. The program is decoded at `credentials.py:447`, in `_launch_targets` and in `_find_program`. A wrapper's argv is decoded at `:456`.
- **Other types:** `os.fsdecode` raises `TypeError` on any other type, and either path refuses. A wrapper's argv word raises inside `_unsafe_delegation`'s `try`, which returns True (`:482`). A program raises before that `try` (`:447`; the guard calls `_unsafe_delegation` before `_launch_targets`), and the guard's own `except` refuses (`:515`).

Review r2 had this from reading the code only. The first job executed two things:

- **The typed property:** it passed with no failure, so there was nothing to minimize.
- **A scratch mutant run (its hold 3, GIL 3.14):** it showed the old inputs could not see this handling. Each of the three mutants below breaks it. Each passed the text-only property from 473fe2941, and each failed the typed one. The second job did not re-run this; its copy of the check was in the hold that never got the lock.

| Mutant (in `subfleet/credentials.py`) | Text-only property (473fe2941) | Typed property |
| --- | --- | --- |
| a wrapper's argv keeps only `str` words (`:456`) | passed | failed: `('/usr/bin/arch', ['/usr/bin/arch', b'<stand-in path>', …])` approved |
| a wrapper's argv word that is none of text, bytes or a path becomes `""` (`:456`) | passed | failed: `('/usr/bin/arch', [7, '-arm64', '-arm64', '/usr/bin/true'], None, None)` approved |
| `_find_program` treats a program that is not `str` as naming nothing (`:157`) | passed | failed: two distinct failures |

These argument types are real inputs, not just synthetic ones. The second job checked this on GIL 3.14.7 and 3.12.14, outside pytest, with only an audit hook installed. The hook raised on the first launch event, so nothing started. Both versions gave the same results:

| Launch | Reaches the hook | Then |
| --- | --- | --- |
| `subprocess.Popen([Path(…), b"x"])` | yes: program `PosixPath`, words `PosixPath`, `bytes` | |
| `subprocess.Popen` with an int argv word, program or `executable` | yes, the int unchanged | Popen raises `TypeError` once the hooks return |
| `os.execv(Path(…), [Path(…), b"x"])` | yes: program as `str`, words `PosixPath`, `bytes` | |
| `os.execv(b"…", [b"…"])` | yes: program as `bytes` | |
| `os.execv` with an int path or argv word | no | `TypeError` before any audit event |

- **Popen audits first:** it raises its audit event before it converts its arguments. So an int argv word or program reaches every audit hook, and only then does Popen raise `TypeError`.
- **Popen's typed words arrive unchanged:** a path object and a bytes word reach the hook as the original objects.
- **`os.execv` converts its path first:** a path-object program reaches the hook as text, and an int raises before any event. The property's `os.exec` events that carry an int, or a path-object program, are therefore synthetic. The guard judges them by the same rule regardless.

## Fix

1. **The docstring** (`install_keychain_exec_guard`, `credentials.py:547`) now lists C-20.6's out-of-scope items in the same words. It adds "a shell's script operand". Its symlink item reads "path aliases (a symlink to `/usr/bin`, or a symlink to the reader that a wrapper's bare command finds through PATH)". C-20.6's own item said "or one to the reader". It now says "or a symlink to the reader", so both texts carry the brief's phrase. That is the only change to the clause. The change log entry says "no behaviour change".
2. **The property's inputs:**
   - **Types:** each argv word and the program is drawn as text, bytes or a path object. That covers both direct and wrapped launches, `subprocess.Popen` and `os.exec` (`typed`, `round10.py:455`).
   - **Path objects:** a word is drawn as one only where it spells the word unchanged. `Path("./security")` is the bare name `security`, a different launch, and `Path("-C/")` is `-C`.
   - **Non-file words:** now and then one word is an int. Half of those times it is the program.
   - **Oracle:** the oracle (`expected_refusal`, `:509`) decodes what it is given. It refuses a wrapper launch with any word that names no file, and any launch whose program names no file. A direct launch's other words decide nothing, as before.
   - **Invariant:** unchanged. The test's one-line docstring states it: "Whatever types its words, PATH and directory have, a launch is refused exactly when C-20.6's rule refuses it."
   - **Events:** Hypothesis events record the forms drawn, so a run with `--hypothesis-show-statistics` shows the coverage.
3. **The mutation pins:** the three mutants above are pinned in `tests/unit/test_live_store_guard_round10_mutations.py` (`test_round10_property_fails_on_each_typed_word_mutant`, `:160`). Each must fail the typed property in a fresh child after an unmutated control passes. The text-only side is not committed, because it needs 473fe2941's file from git history.

# Codex pin 0.159.0 to 0.169.1 (D-CODEX-0169)

Base: `release/217`, `4aed7a3c9`. Reported 2026-11-17 by the Subfleet hub.

On 2026-11-17 Max asked the fleet to run GPT-6.2 Sol in place of GPT-6.1 Sol. When the hub found the guard's Codex pin in the way, he said "update the codex cli then!". On 0.159.0, the current lane pin, a ChatGPT-account request for `gpt-6.2-sol` fails with 400 `model_not_found`, and on 0.169.0 (`rust-v0.169.0`, released 2026-11-13) it gets an answer. The hub did not try versions 0.160 to 0.168. The guard preflight refuses every Codex launch whose `codex --version` differs from TRUST's `codex_version` (kind `version`, code 7), so the hub rolled back a 20:28Z install of 0.169.0 at 20:29Z.

This change pins 0.169.1 (`rust-v0.169.1`), which npm published at 22:26Z on 2026-11-17 and tagged `latest` (read at 23:27Z). One of its four commits adds `gpt-6.2-sol` and `gpt-6.2-astra` to Codex's bundled model catalog, two change Amazon Bedrock paths that Subfleet does not use, and one sets the version. Codex merges a remote catalog refresh with its bundled list, and the remote catalog lists `gpt-6.2-sol` (the hub read it from a ChatGPT-account Codex cache). Without the remote entry, 0.169.0 runs `gpt-6.2-sol` on generic fallback metadata, with direct tool calls and no `apply_patch`, while 0.169.1 runs it in code mode from its bundled entry.

This change moves the pin. It does not install anything and does not touch `policy.json`.

## What changes

- `private/guard/TRUST`: `codex_version` reads `codex-cli 0.169.1`, and `provenance` gains one dated sentence. `hook_sha256`, `hooks_trust_hash`, `override` and `reference_hook_path` do not change.
- `tests/unit/test_guard_subfleet_root.py` and `tests/unit/test_guard_overlay.py`: the new pin, the new TRUST digest, and the old-bytes rebuild with the version line undone.
- `tests/unit/test_publish_rule_round7.py`: a new version-independent test. Under `inherit="core"`, `codex sandbox` must drop the three git-denial variables without the launch's pins and pass exactly their values with them. It runs `env` only, and it skips where no Codex is installed, as on CI. The existing case that measured an actual push stays gated to 0.159, where the hub measured it, so it skips on 0.169.1.
- `tools/guard_pin_0169.py` and `tests/unit/test_guard_pin_0169.py`: the install kit (below).
- `docs/private-guard-overlay.md`: the new digest and a short section.

### App-server schema

The hub compared `codex app-server generate-json-schema` from 0.159.0 and 0.169.0 over what Subfleet uses: 25 v2 definitions and their closure (137 definitions), the four approval request and response pairs, `ServerRequest`, `ServerNotification` and `ClientRequest`. 0.169.1 generates the same 329 schema files as 0.169.0, byte for byte. Most changes add optional fields, enum values or methods. Subfleet reads the rest the same way on both versions:

- `CodexErrorInfo` moves its variants from `oneOf` to `anyOf` and adds `modelNotFound`, `policyCapacityUnavailable`, `inferenceHookDenied` and a catch-all string or object. `codex_turn._error_kind` reads a string code or the key of a one-key object and passes any code through. Only `usageLimitExceeded` and `rateLimitExceeded` count as limits, so the new codes stay unclassified. A follow-up should decide whether `policyCapacityUnavailable` counts as a limit.
- `MessagePhase` adds `partial_answer` and rewords its final-answer variant. Subfleet does not read message phases.
- An `imageGeneration` item's `result`, an audio `UserInput`'s `url` and an `input_audio` output part's `audio_url` each become one of two alternatives, a URL or a file id. Subfleet reads only the `type` of these: `codex_turn` counts an `imageGeneration` item as agent work, and `codex_brief` marks an `input_audio` part as media.
- `CommandExecutionApprovalKind` adds a managed-checkpoint variant. Codex sends it only to a client that declares the `requiredHumanApproval` initialize capability, and Subfleet does not declare it.
- `ReviewDelivery` drops `detached`, and `HookRunSummary.sourcePath` changes type. Subfleet never calls `review/start` and never reads `sourcePath`.

### Not verified before the move

- **No live model turn on 0.169.1.** A ChatGPT-account request for `gpt-6.2-sol` got an answer on 0.169.0. The first live turn on 0.169.1 comes in the post-install smoke (step 7 below), unless queued work reaches the smoke's lane first; step 7 says how to prevent that. Earlier pin moves ran a live denial before the move.
- **An `apply_patch` denial.** The hook's `apply_patch` branch has only the `hf-dest` rule. These runs showed the hook firing on an allowed patch, not a denial.
- **The measured `git push` case on 0.169.1.** Its push-free half is the new test.
- **The websocket transport.** The bundled entry prefers websockets, and the mock serves HTTP only, so the bundled-entry runs went over HTTP.
- **The `write_stdin` gap (C-23.6) stays as it was.** It exists on 0.159.0 too.

## Install (the hub)

The installed hook stays `e869dd4c…`, since D-SEARCH-REL1's hook `af5e7239…` needs its own decision. So the hub installs this branch's TRUST with the installed hook's hash in place of `af5e7239…`. `tools/guard_pin_0169.py stage` builds it from the installed TRUST (`36267abb…`) with this branch's two edits. It refuses unless the result equals this branch's TRUST with the hook hash swapped and its digest is the pinned `0224cb3f…`. The dry run at 23:40Z on 2026-11-17 staged `0224cb3f…` and verified it on all six Codex lanes.

Between the TRUST swap and the CLI upgrade (steps 4 and 5), and again between rollback steps 2 and 3, the guard refuses every Codex preflight with code 7. A job admitted then fails. A timer heal turn on a lane whose token reads as expired spends that epoch's only heal, and the lane then stays closed until someone logs in again. Caps and task holds do not stop timer heals, and task holds do not stop conversation turns. A lane hold stops both: a held lane is never a candidate, and no timer reads it. So the install first holds every Codex lane for twelve hours. A held lane launches nothing, so an install that stalls with the CLI and TRUST out of step does no harm until a hold ends.

If step 2, 3 or 4 fails, read the live TRUST's digest. If it is `0224cb3f…`, the swap went through, so carry on from step 5. If it is `36267abb…` and `TRUST.pre-0.169.1.bak` exists, rollback step 2 only moves the backup aside. Then stage into a fresh folder and try again, or end the holds as step 8 does. If any step after step 4 fails, or the install cannot finish well inside the holds, run the rollback at once, before ending any hold. If the rollback fails too, keep the lanes held, extending the holds as needed, until the CLI and TRUST agree.

A lane has at most one open operator hold. `subfleet lanes hold` on a held lane extends that hold, or keeps it when its end is later. `subfleet lanes release` ends it, whoever set it, and wakes admission at once, so queued work can take the lane before a new hold lands. So the install records the holds already in place (step 0), and at the end it releases only the lanes whose recorded hold has ended (step 8).

Run from a checkout of the merged commit, with the installed runtime. In these steps `PY` stands for `~/.local/share/subfleet/current/venv/bin/python -E -P`, and `$C1691` for a scratch 0.169.1 binary.

0. Check the preconditions and record the holds:
   - this branch has a review approval and has merged, and Max's go stands (2026-11-17);
   - the 1-minute load is under 60;
   - no Fleet ops booking forbids installs;
   - `codex --version` reads `codex-cli 0.159.0`;
   - `npm view @openai/codex dist-tags.latest` reads 0.169.1 or later. If a later release has come out, install 0.169.1 anyway and propose the later one in a new pin PR;
   - all six Codex lanes are enabled, since `doctor --live` skips a disabled lane;
   - save the output of `subfleet lanes list --json` to a file outside `~/.subfleet`. In it, a Codex lane's `closures` entry with `reason` `operator-hold` and no `released_at` is a hold in place. Note each one's `until_at` and `note`.
1. Hold every Codex lane:
   - pause or brake any controller that holds or releases lanes, so that it changes none until step 8;
   - run `subfleet lanes hold codex-N --until <twelve hours from now> --note D-CODEX-0169` for codex-1 to codex-6;
   - check that `subfleet lanes list` shows all six held to that time or later, and that `subfleet status` shows no Codex job or turn running.
2. Stage the new TRUST and preflight it on all six Codex lanes, one `--lane-home` each:
   `PY tools/guard_pin_0169.py stage --live ~/.subfleet/guard --stage ~/.subfleet/guard-stage-codex-0169 --codex $C1691 --lane-home ~/.subfleet/lanes/codex-1` (repeat `--lane-home` for codex-2 to codex-6).
   `stage` exits 1 unless every lane it was given verifies, and `swap` refuses a stage without the PREFLIGHT record that only a full pass writes. To try again, stage into a fresh folder and use that folder in steps 3 and 4.
3. Check the stage folder: `TRUST.sha256` must read `0224cb3f…`, and `PREFLIGHT` must list all six lane homes.
4. Swap the TRUST in. `swap` keeps the previous TRUST as `~/.subfleet/guard/TRUST.pre-0.169.1.bak`:
   `PY tools/guard_pin_0169.py swap --live ~/.subfleet/guard --stage ~/.subfleet/guard-stage-codex-0169`.
5. Upgrade the CLI straight away: `bun add -g @openai/codex@0.169.1`. If that fails, or `codex --version` then reads anything but `codex-cli 0.169.1`, run the rollback now.
6. Run `subfleet doctor --live`. It checks held lanes too and must verify all six Codex lanes. If it does not, run the rollback now.
7. Smoke on one Codex lane that has no step 0 hold in force; call it codex-K. If every lane's step 0 hold is still in force, wait for the earliest one to end while the install's holds stand, or roll back.
   - Save a copy of `~/.subfleet/policy.json` outside `~/.subfleet`. Add a `sol62` model entry for `gpt-6.2-sol`, outside the chains. Check that the file loads: `PY -c 'import sys; from subfleet.policy import load_policy; load_policy(sys.argv[1])' ~/.subfleet/policy.json`. The daemon reads `policy.json` only at startup and does not start on a policy it refuses, so restart it only after that check passes: `launchctl kickstart -k gui/$UID/com.subfleet.daemon`. Never use `subfleet daemon start`, which hands lanes the shell's environment (D-ENV1). Holds survive the restart.
   - Submit the smoke first: a writable job with no task, pinned to the entry and the lane, in a two-worktree scratch repo outside `/tmp` (`-m sol62 -H ~/.subfleet/lanes/codex-K -s workspace-write -C <repo>`). Then run `subfleet lanes release codex-K`. The release lets any older queued job that can run on codex-K start ahead of the smoke. To keep the smoke first, release only once `subfleet status` shows no such job and no open Codex conversation, or hold those jobs' tasks with `subfleet tasks hold`, which cannot stop the task-less smoke. A queued job without a task cannot be held that way. Otherwise, accept that such jobs may run first, under a guard that only preflight and the mock denials have checked on 0.169.1.
   - Once the smoke shows as running, hold codex-K again as in step 1. A hold leaves a running attempt alone.
   - The smoke must hit the `[stash-shared]` denial on `git stash` in its repo, with a line in the denial log. It must make one `apply_patch` edit there, and show `gpt-6.2-sol` attested in its rollout `turn_context`.
   - If the smoke fails, run the rollback.
8. End the holds. For each Codex lane, act on what step 0 recorded:
   - no hold, or one whose `until_at` has passed: run `subfleet lanes release codex-N`;
   - a hold whose `until_at` is at or after the end of the install's own hold: step 1 left that row as it was, so leave it;
   - a hold whose `until_at` is still ahead but before the end of the install's own hold: step 1 extended that row, so release it once the recorded `until_at` passes. Until then it carries the note `D-CODEX-0169`.

   Then restore the controllers paused in step 1. The hub moves the chains to the new entry in a separate step.

## Rollback

The rollback undoes this install and nothing later. It reads nothing from the checkout, so a checkout of any later commit that still has the kit can run it. Once a later guard change has replaced the hook or the TRUST, `rollback` refuses, and that change's own rollback applies.

1. Record the holds as install step 0 does, before holding anything. After a failed install, keep that install's step 0 record instead. Then hold every Codex lane as in install step 1 (after a failed install they are still held), and check that no Codex job or turn is running.
2. `PY tools/guard_pin_0169.py rollback --live ~/.subfleet/guard` writes the backup's bytes back over TRUST, then renames the backup to `TRUST.pre-0.169.1.bak.rolled-back-<UTC time>`. It refuses unless the backup is `36267abb…`, the live hook is `e869dd4c…` and the live TRUST is `0224cb3f…`, the one `swap` installs. After a `swap` that stopped before its rename, it leaves TRUST as it is and only moves the backup aside.
3. `bun add -g @openai/codex@0.159.0`, then confirm `codex --version` reads `codex-cli 0.159.0`. If either fails, keep the lanes held.
4. If install step 7 added the `sol62` entry, take it out, since 0.159.0 cannot serve it. If nothing else in `policy.json` has changed since step 7, restore step 7's copy. Otherwise, first move every chain and retired alias that names `sol62` to an entry 0.159.0 serves, then remove the entry. Check that the file loads and restart the daemon, as step 7 does.
5. Run `subfleet doctor --live`. Once it verifies all six Codex lanes, end the holds as in install step 8, using step 1's record. There, the install's own hold is the one this rollback's step 1 set. Then restore the controllers.

To install again after a rollback, stage into a fresh folder, since `stage` refuses an existing one. Keep each stage folder the install used until the next guard change.

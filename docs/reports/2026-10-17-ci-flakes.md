## D-2: stop dump loses the held frame, or loses the exit race

Read first: `ci-d2-stop-bound-3.14.log`, including the initial failure and retry. Both show the `subfleet-io_0` thread and `<invalid frame>`, with no `hold` frame. The supplied history also records exit `-14`.

The held worker belongs to `Daemon.workers`, a `ThreadPoolExecutor` with prefix `subfleet-io` (`subfleet/daemon.py:826`). `_process_attempt` reaches `_boundary("running", ...)`, which calls the harness's `hold` crash hook (`subfleet/daemon.py:1318`, `subfleet/daemon.py:7540`; `tests/e2e/conftest.py:69`). The hook repeatedly checks a release file and sleeps. The main thread is joining the worker pool in `close`, while retaining `daemon.lock`. This is the stop watchdog dump, not the SIGUSR1 diagnostic path.

The original `watch_stop` installed a kernel timer at grace + 3 s, then created a faulthandler watchdog with a fresh full-grace wait (base `subfleet/daemon.py:9607`, `subfleet/daemon.py:9613`). Setup time consumed the margin. Its C dumper also performed many individual writes before calling `_exit(1)`, so slow dumping could lose to SIGALRM.

CPython 3.14.7 source read:

- [`Modules/faulthandler.c`, `faulthandler_thread`, lines 603–630](https://github.com/python/cpython/blob/v3.14.7/Modules/faulthandler.c#L603): the native watchdog writes its header, walks interpreter stacks without acquiring the GIL, then exits.
- [`Python/traceback.c`, `dump_frame` and `dump_traceback`, lines 968–1085](https://github.com/python/cpython/blob/v3.14.7/Python/traceback.c#L968): invalid code, filename, line or name metadata makes `dump_frame` fail; the caller emits `<invalid frame>` and abandons that thread's outer frames. It explicitly anticipates frame memory changing during the dump.
- [`Include/internal/pycore_interpframe.h`, `_PyFrame_SafeGetCode`, lines 24–50](https://github.com/python/cpython/blob/v3.14.7/Include/internal/pycore_interpframe.h#L24): validity checks include missing globals/builtins/executable, freed-memory heuristics, and executable type. These are defensive checks, not proof that a worker has no stack.

The replacement API was checked too: [`Python/pystate.c`, `_PyThread_CurrentFrames`, lines 2457–2513](https://github.com/python/cpython/blob/v3.14.7/Python/pystate.c#L2457) runs as a Python/GIL caller, takes the runtime stop-the-world/thread-list protections, skips incomplete frames and puts managed frame objects in the returned dictionary. Retaining those objects avoids dereferencing raw frame storage that the target thread can clear.

Thus the watchdog can race the target thread's own frame changes, including the harness's repeated calls. The logs cannot identify which individual validity check failed. Retrying that unsynchronized walk would remain probabilistic.

Fix: the preexisting Python watcher captures managed frames with `sys._current_frames()`, formats only file/line/function/thread name, and writes the bounded snapshot through the descriptor reserved at startup (`subfleet/daemon.py:9552`). It exits 1 after the snapshot. Its wait is the remainder of the original monotonic grace, not another grace after C setup. No new Python thread is required at stop time. A follow-up resource regression found that escaping names through `unicode_escape` could import its codec after the process exhausted descriptors: the managed dump silently fell back to C (1/1 reproduced). Function names now use the already-loaded JSON encoder, thread names are capped at 100 characters, and no diagnostic codec needs opening. [`PyUnicode_AsEncodedString`](https://github.com/python/cpython/blob/v3.14.7/Objects/unicodeobject.c#L3680) confirms the codec-registry path; the host's codec is a filesystem module. The cold-codec regression and restoration mutation are queued after this correction.

The bounds are derived by dividing the existing diagnostic budget equally: Python at `G`, C fallback at `G + M/2`, kernel at `G + M`, with `G = 30 s`, `M = 3 s`: 30, 31.5, 33 s. External backstops remain 40 s. No timeout or margin was enlarged. The C watchdog remains independent of Python progress; the kernel still ends a blocked or failed diagnostic. Extreme scheduling delay or blocked output can still produce SIGALRM and incomplete diagnostics, as C-5.8a documents.

Deterministic regressions hide the C dump behind an injected `<invalid frame>` and delay C watchdog setup by `M + 0.25 s`. Before the fix both failed: respectively missing the held frame and exit `-14`. Both pass in the earlier complete watchdog suite after the fix; 20/20 repetitions of each have passed, with ten further repetitions of each queued. Mutation checks both failed as intended: replacing the managed snapshot with an exception failed both regressions (2/2), and restarting a whole grace after setup instead of waiting to the original deadline reproduced SIGALRM in the delayed-setup regression (1/1). These patches were confined to the owned watchdog child.

The unit expectations that a failed C timer necessarily implies SIGALRM were implementation assumptions: C-5.8a only requires the kernel to terminate a process still alive at its deadline. A working Python watcher may now exit first. The blocked-output injection now blocks both diagnostic paths and retains its SIGALRM assertion. The e2e assertions about the held frame, exit 1, ownership and adoption remain intact.

## D-RL1: child exit discards an exchange already applied

Read first: `ci-relay-child-exit-3.12.log`. The failing exchange is `client.send(1, "close", tag="end")`, which receives EOF instead of an acknowledgement.

Cause: `RelayServer.apply` closes the child's stdin before returning the close acknowledgement. The child can exit immediately; `guardian.run` observes `child.wait()` and calls `relay.stop()` (`subfleet/guardian.py:208`). The old stop path performed `shutdown(SHUT_RDWR)` on the connection, including its reply half, before the relay's `apply` → `_reply` exchange could finish (`subfleet/relay.py:230`, `subfleet/relay.py:298`). Its one-second join could also return with a reply still pending, letting the guardian exit and destroy the daemon relay thread.

The accept and read paths were inspected as well: a connection registered after stop's wakeup checks the stop flag before its first read. This already covers an idle accepted connection. A regression forces that ordering to guard the new exchange barrier; it is not a separately reproduced defect.

Fix (`subfleet/relay.py:231`, `subfleet/relay.py:297`): shutdown uses `SHUT_RD`, keeping the reply half alive. A dedicated exchange barrier spans `readline`, application and `_reply`; stop wakes an idle read before waiting on that barrier. It therefore cannot pass the gap between a completed application and its acknowledgement. The existing one-second thread join remains; reply writes use the same one-second budget, so the barrier cannot be held indefinitely by a client that does not read. Peer checking remains outside the barrier. Readers are closed with a context manager. C-26.4 and the top version-3 change bullet document the ordering; frame semantics are unchanged. Validation after the fix: all 14 relay unit cases pass; the repeated forced ordering runs pass 30/30 (10 close, 10 status, 10 accepted-but-unpublished). Restoring `SHUT_RDWR` inside the test process makes both reply cases fail again (2/2). The four real guardian tests skip on the process-inspection guard.

The forced close/status regression holds the response after `apply`, starts guardian-style stop, and allows `_reply` only after a socket proxy confirms that the real `shutdown` call has finished. This directly forces the read-but-unanswered window; no random scheduling or sleep is needed. Restoring the exact original `RelayServer.stop` fails all 20 strengthened reply repetitions with EOF (10 close, 10 status). The strengthened ordering passes all 20 reply repetitions after the fix, alongside 10 accepted-but-unpublished connection repetitions; the final complete relay rerun also passes all 14 unit cases with four guardian skips. Sequence numbers, hashes, fsync ordering, duplicate handling and failed-write handling are unchanged.

## D-TM1: short measurements misclassify linear work

Read first: `ci-timing-wrapper-flags-3.14.log`: 4.829 ms at 16 KiB versus 40.010 ms at 64 KiB, ratio 8.285 for 4× input. The code already consumes identifiers and flag runs in linear scans (`subfleet/sessions/handoff.py:179`, `subfleet/sessions/handoff.py:335`). The ordinary-identifier test averaged eight calls at 1/4 KiB; the wrapper test timed one call at 16/64 KiB. Neither selected the best repeated sample. Millisecond baselines were susceptible to transient host effects even with thread CPU time.

Fix: `tests/cpu_scaling.py` takes the minimum of five CPU batches at each size, calibrating an equal call count until the fastest smaller batch costs at least 20 ms of thread CPU. The CI wrapper sample's excess above 4× was 20.692 ms; a 20 ms base batch leaves `(8 - 4) × 20 = 80 ms` of noise headroom while preserving the 8× ceiling. The initial smoke and first four repetitions used an even larger 50 ms floor; it was reduced to keep the 50-run check practical on this heavily loaded host, retaining five minima and the larger inputs. The reported 50-run check uses the final 20 ms floor throughout: eight repetitions are serial, and the rest use four pytest workers within one invocation/lock hold. The earlier four 50 ms repetitions all passed and are supplemental. Both tests use 64/256 KiB, within the scrubber's 256 KiB work cap. Equal batches preserve the growth ratio; 4× linear work remains approximately 4×, quadratic work approximately 16×. The ceiling remains 8×, between linear 4× and quadratic 16× growth, and the wrapper's original absolute 0.5 s CPU bound remains at its original 64 KiB size. Child deadlines remain 60/120 s. The changed test assumption was stability of a tiny single/averaged CPU measurement; C-23.14 promises linear work, not that sampling assumption. Output assertions remain unchanged. No production scrubber behavior or C-23.x contract changes.

# PR #131, round-three review: REQUEST CHANGES

Head `12eb120aa032`; base `integrate/2111-features` (merge base `fcb16008`).
I reviewed the round-three commits `820c3712`, `0333f6df`, `6edab177`,
`eee8583b` and `12eb120a` against the round-two review, the fix-2 and fix-3
reports, and the hub's brief.

Host: macOS 26.6.2 (25G83) with SIP enabled. Unlike the builder's sandbox,
`/bin/ps`, `ps -E`, `sysctl kern.bootsessionuuid` and `lsof` all work here, so
every real-process test ran, with no constructor substitution. `sandbox_check`
returns 0 for this lane's processes and for the live daemon (pid 21233), so
`ps` runs here with the same privileges as the daemon's census.

## Verdict

**Parity holds.** The automatic path and `kill --confirm-dead` run the same
census and reach the same decision, the same boot included. A 150-example
differential property agrees, and it kills two parity mutants.

**Every round-two finding outside the residual is fixed in behaviour.** That
includes two cases checked with real processes: a real SIGKILL during child
publication, and the real 2.1.10 guardian code.

**Check 3 fails.** The residual is neither narrow nor documented honestly. On
this host, the C-5.5 marker source cannot see detached processes that keep
their markers:

- any Apple platform binary, such as `/bin/sh`, `/bin/bash`, `/bin/zsh`,
  `sleep` or `tail`;
- node with `process.title` set;
- `redis-server` in its default configuration.

Executed result: a real quarantine is released by both paths, within one pace,
while a detached `/bin/zsh` writer keeps appending to the job's folder. This
lane's own Claude Code Bash tool shells are exactly such processes.

The hub's decision rests on the premise that "the marker scan catches every
ordinary detached process … because each keeps its environment". That premise
is false here. The decision needs revisiting with this evidence, and the
contract text added in this round states a false mechanism.

- The residual docstring at `tests/fake/test_review_pr131_round2.py:168`.

**Real topology.** In this very lane:

- the guardian (52512) leads group 52512;
- the `claude` provider (52516) is a member of that group;
- each Bash tool shell (`/bin/zsh` 83516, then 25648) is a session leader in
  its own group.

So every tool shell is outside the attempt's group, and its markers are
invisible. Only the parent-link walk through the live provider finds it.

**Pre-existing at finalization.** `review_pr131_r3_finalize_probe.py` runs a
real guardian whose provider starts a new-session `/bin/zsh` writer and then
exits 0. After `exit.json`, the census is `verified_empty: true` while the
shell (ppid 1, its own group, `Ss`) keeps writing. The result is the same on
head and on base `fcb16008`. The base's import provenance was checked: it
imports `.review-tmp/base-fcb/subfleet/procs.py`.

What this PR adds is that quarantines are now released automatically. These
are precisely the attempts where something was observed alive. Before, they
waited for an operator, and 211 waited on 2026-10-05.

**Backstop limit.** Retention's `lsof` check protects a worktree only while
the writer has its cwd there or holds a file open. Its own test and the
existing cwd test pass. In
`test_real_lsof_protects_a_worktree_from_an_intermittent_invisible_writer`, the
writer appends and closes every 0.2 s from a cwd outside the tree. Retention
pruned the job (`pruned: ['job-intermittent']`, `bytes_after: 0`) while the
writer was still running.

**Change needed.** The hub should re-decide with these facts. The options
below are untested suggestions:

- **(a) Record lineage and its process groups.** At each steady-state
  inspection and at kill start, record the identity and process group of
  every parent-link descendant of the verified-live guardian or child. Store
  them as census roots, not as signal authority, because C-5.6 limits signals
  to group members. Then count live members of recorded groups.
  - This holds Claude tool shells and their children once they have been seen.
  - Still invisible: shells born and orphaned between two inspections, and
    double-forking servers whose markers are hidden (redis).
- **(b) Hold on a partial marker match** (see P2-1). This narrows the
  residual and errs only toward holding.
- **(c) Correct the documents regardless.** C-5.7, `design.md`, the residual
  docstring and the fix-3 report must stop saying that ordinary detached
  children stay held. The honest residual is any orphan outside the attempt's
  process group whose environment `ps -E` does not show. That covers Apple
  platform binaries such as shells and coreutils, processes that rewrite their
  process title, and processes that drop either marker.

### P2-1: the documented residual names two unnecessary preconditions

**Where:** `docs/acceptance-contract.md:193`, `docs/desktop/design.md:564`,
and `tests/fake/test_review_pr131_round2.py:168`. Each says the orphan "starts
a new session" and "scrubs both" markers.

- The census reads no session at all: `TABLE_ARGV` at `procs.py:199` has only
  pid, ppid, pgid, stat and lstart.
- The marker source requires both markers (`procs.py:507`), so dropping
  either one is enough to hide.

**Executed:** `test_only_the_full_documented_evasive_combination_escapes`, six
cases. Each uses the round-two fork-after-table-read shape and omits exactly
one documented precondition:

- a `setpgid` child that stays in the parent's session (stat `S`, not `Ss`);
- a child that drops only `SUBFLEET_ROOT`;
- a child that drops only `SUBFLEET_ATTEMPT`.

Each runs on both the automatic and the operator path. All six end `lost` with
leases `[]`.

**Change needed:** correct the text. Alternatively, treat a process carrying
`SUBFLEET_ATTEMPT=<id>` with no `SUBFLEET_ROOT` as ours, and reject only a
*different* root. That keeps the 2026-09-05 two-root disambiguation and errs
toward holding.

### P3-1: 2.1.10 guardians at install — SIGKILL escalation leaves a quarantine only `--force-release` or a reboot clears

**Where:** `subfleet/daemon.py:5901` (`child_unrecorded`) and `:6081` (owned
identities recorded at kill start).

**Executed:** `test_kill_escalation_against_each_guardian_version[2.1.10]`.

- It runs the real guardian from the installed release's `source_commit`
  `f832e6b8`, whose `guardian.py` is byte-identical to the PR base's.
- Its provider ignores SIGTERM.
- The head daemon's `_kill_attempt` escalates to SIGKILL. The result is
  `quarantined`, with the single error `guardian child publication
  unavailable`.
- The attempt stays held through an automatic pass, then `--confirm-dead`,
  then another automatic pass.
- The kill's first census, taken while the 2.1.10 guardian was verified alive,
  had already recorded the provider. The test prints
  `{"provider": 50989, "owned": ["50970", "50989"]}`.

The `[head]` case of the same test finalizes (`finalizing`). This is the
documented conservative hold, so it is safe. Its cost lands on every running
attempt at install, since no released guardian publishes a child, and each one
then needs `--force-release`.

**Suggestion:** discharge the legacy hold when a census taken while the
guardian was verified alive recorded the guardian's direct children. While the
guardian lives, its provider cannot leave the parent link, so the walk sees
the provider even if it left the group.

### P3-2: a gated guardian's publication crash is held like a legacy one

**Where:** `subfleet/guardian.py:152` (the first `start.json` carries no gate
marker) and `subfleet/daemon.py:5901`.

**Executed:** `test_sigkill_during_child_publication_never_executes_the_provider`.

- A real guardian is SIGKILLed while reading its launcher's identity, so none
  of its cleanup code runs.
- The launcher exits on EOF. `/usr/bin/touch provider-ran` never executes.
- `start.json` has no child fields, so the daemon cannot tell this receipt
  from a 2.1.10 one.
- The round-two tests show such receipts are held on both paths until a
  reboot.

**Suggestion:** add a `launch_gate` field to the first receipt. A gated
receipt without child publication, from a dead guardian, proves that no
provider ran.

### P3-3: the v6 migration fixture does not measure the legacy-publication hold on the live pile

`tests/fake/review_pr131_build_v6.py` creates empty attempt directories, so
the "152 of 211 release" result assumes there are no receipts at all. Live
quarantines from kill or loss paths have a legacy `start.json` and no
`exit.json`, and those stay held. I did not read `~/.subfleet`. Before
release, the hub could count those attempts read-only to set expectations.

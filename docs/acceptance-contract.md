## 1. Identifiers and vocabulary

- **C-1.1** A job id is `YYYYMMDD-HHMMSS-<slug>` in local time, the v1 format, unique in the store. `<slug>` is the `-n` name or the task name, lowercased, `[a-z0-9-]` only, at most 40 characters.
- **C-1.2** An attempt id is `<job id>/a<seq>` with `seq` starting at 1.
- **C-1.3** A lane id is `<provider>-<n>` (`codex-4`, `claude-3`). Lane ids are stable; a lane whose account or credential is rebound gets a new id and the old one is disabled.
- **C-1.4** An account key is `<provider>:<account id>`. For Codex the account id is the `account_id` from the home's `auth.json` claims when present, else the email; For Claude it is `<account_uuid>:<org_uuid>` as returned by the provider profile endpoint (C-10.6) for the lane's own credential; the email is a display label and never the key.
- **C-1.5** A request id is a caller-supplied string or a CLI-generated UUID4, at most 128 characters, printed back on submission.
- **C-1.6** Providers are exactly `codex` and `claude`. Model names in policy are short names (`astra`, `opus`) mapped to provider model ids in `policy.json`.
- **C-1.7** Timestamps in the store are ISO 8601 UTC with a `Z` suffix and second precision unless a column says otherwise. Epoch seconds from providers are converted on write.

## 3. Store

- **C-3.1** One SQLite database, `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, `busy_timeout=5000`. The schema is `subfleet/store_schema.sql`; `store.py` applies it and records `schema_version`. Migrations are additive and numbered.
- **C-3.2** Every state transition of a job, attempt, notice, lease, or action is one transaction, and every transaction that changes state also inserts an `events` row in the same transaction.
- **C-3.3** Transactions never span a subprocess call, a network call, a filesystem sync, or a sleep. Artifact copying, `ps`, `git`, and provider probes run outside transactions.
- **C-3.4** Readers other than the daemon (the CLI in offline mode, the menu bar app, Logpile) open the database read-only. Only the daemon and the guardian receipt path write, and the guardian writes files, not rows. The desktop app (section 29) never opens the database; it reads `status.json` and `catalog.json` and changes state only through daemon ops.
- **C-3.5** The CLI refuses to write to a store whose `schema_version` is newer than it knows (exit 1 with both versions).
- **C-3.6** The daemon says who holds a store lock too long and who waits too long for one. The main store's lock and the conversation store's lock are `lockwatch.WatchedLock`s: re-entrant locks that record the thread holding them and when its outermost hold began, and change nothing about who gets them or when. A hold longer than `HOLD_REPORT_S` (2 s) is written to `daemon.log` once, with the Python stack the holder is running at that moment (a `subfleet-lockwatch` thread samples every 0.5 s), and again when it ends, with its length; a hold no sample caught says, when it ends, where it was held. A thread that has waited `WAIT_REPORT_S` (5 s) for a lock writes one line naming itself, the number of threads waiting and the longest wait, the holder and how long it has held, the waiter's stack and the holder's live stack, and then keeps waiting. Each lock and kind of report (`hold`, `released`, `wait`) writes at most one line per `REPORT_EVERY_S` (60 s); the rest are counted, with the longest, in the next line, or in a summary line once the window has passed. SIGUSR1 makes the daemon write every thread's Python stack to `daemon.log` from `faulthandler`'s signal handler, so the dump arrives when every Python thread is stuck; it is registered as soon as the log is open (SIGUSR1's default action ends the process) and unregistered before the log closes. The daemon writes its identity to `daemon.lock` only once the handler is registered, with `"stack_dumps": true`, and rewrites it without the flag before it unregisters the handler; a daemon built on the main thread also sets SIGUSR1 to be ignored beneath the handler, so what `faulthandler` restores at close or at exit ends nothing. `subfleet daemon stacks` sends the signal only to the identity `daemon.lock` records, as `daemon stop` does (C-5.3, C-5.4), and only when that lock says `stack_dumps`, read again just before the signal; otherwise it signals nothing and exits 69 with the fix (restart the daemon on this version, or `sample <pid> 5`). A daemon built before the flag (the installed ad2c208 reports the same version, 2.0.0a0) is refused, not killed: the review of 5841d8b showed a process without the handler exits -30 on SIGUSR1. It waits up to `--wait` seconds (5) for the log to stop growing, and prints what was written; exit 69 when no daemon runs. Incident: 2026-09-25, a `list` whose statement takes 1 ms took 34-94 s, with 18 threads waiting on the store lock, and neither the log nor a native sample could say which Python code held it.
- **C-3.7** A read never waits for a writer. The daemon's store keeps `READ_CONNECTIONS` (6) read-only connections (`query_only`) beside its one writing connection, opened on first use. A read made outside a transaction (`Store.query`, `Store.one`) takes one of them for one statement instead of the store lock, so reads never queue behind a transaction, and SQLite steps them side by side. Snapshots may hold at most all but `STATEMENT_RESERVE` (2) of the read connections (`snapshot_share`, 4 of 6), so a one-statement read (a hook's lookup, the wait hub, the control loop) always has connections no snapshot can take. No read waits for a connection longer than `READ_WAIT_S` (1 s): after that it opens one of its own for that read alone and closes it after. Every such wait is counted (`daemon.status` `read_pool`) and written to `daemon.log` under C-3.6's rate limit (kind `read-pool`), naming the waiter, whether it opened its own, and every thread holding a read connection, for what and for how long. `Store.close()` closes a read connection only once its read has ended (it waits up to `CLOSE_WAIT_S`, 5 s; a read still going then closes its own when it ends) and refuses any read that starts after it. The write-ahead log is bounded: the writer sets `journal_size_limit` to `WAL_SIZE_LIMIT` (64 MiB), so each time SQLite restarts the log the file is cut back to that size, and the only checkpoints are SQLite's automatic ones, which are PASSIVE: a commit never waits for a reader, it checkpoints up to the oldest snapshot still open, and the commits after that snapshot ends checkpoint the rest and restart the log. The daemon runs no RESTART or TRUNCATE checkpoint, which would hold writers while it waited for readers. Since a long read holds the log back, a read connection in use longer than `HOLD_REPORT_S` (2 s) is written to `daemon.log` once with its thread's live stack (C-3.6's sampler, kind `read-hold`). A read made by a thread that holds the store lock goes to the writing connection, so a transaction still sees its own uncommitted rows. `Store.snapshot()` gives a block of reads one committed state without the store lock (inside a transaction, the transaction's state; a store without read connections holds the lock for the block instead). No transaction begins inside a snapshot on the same thread: it raises `SnapshotWriteError` before it writes, with or without read connections, because its reads would go to the snapshot and miss its own writes (the review of 5841d8b saw `add_artifact` record a duplicate that way); a commit that races a snapshot comes from another thread. `Timers.snapshot` and every capacity view read their rows inside one and build the view after it ends (`capacity.store_rows`, `Daemon._capacity_rows`, `Timers.view_rows`), so a view build holds no read connection; `Timers.snapshot` used to open a write transaction only to read, and the first version of this clause built each view inside its snapshot, so six views building at once held all six connections and every other read waited, with no bound and no log line (review of 5841d8b: 1.53 s with the store lock free). The hot reads are bounded by what they return, not by the history kept: a capacity view reads only the readings that can be the newest of their lane, scope and window (`Store.latest_reading_candidates`: per key, those at the greatest canonical `YYYY-MM-DDTHH:MM:SSZ` timestamp, plus every reading with another timestamp shape), not every reading; a probe record is one step of the partial index `events_probe_holder` (`json_extract(data_json,'$.holder')` over the `probe.state` payloads `json_valid` accepts), and a gate's state the newest matching event found by SQLite (`json_extract`, newest first, one row), not every `probe.state` or `gate.state` event parsed in Python; batch labels and submission records are looked up by job id (`+kind`, so SQLite uses `events_job`), not by walking every `job.submitted` event; `sessions` filters session events by session in SQL, or takes only the newest per kind and session; and a view reads the reset-credit history, its reconciliations and the lane rows once (`ResetCredits.override_context`), not once per lane. Each rewrite answers exactly what the old form did; differential tests over randomized stores pin that (`tests/unit/test_store_contention_queries.py`). A payload `json_valid` refuses is never filtered in SQL: a NaN or an Infinity, which `json.dumps` writes and `json.loads` reads, or a row that is not JSON at all. The partial index `events_not_json` hands every such row of the kinds asked to Python, which parses it as the old form did; a row that is not JSON, which no writer makes, is passed over where the old form raised. Both indexes are in `store_schema.sql`, so a store gets them the next time the daemon opens it, and neither can stop a store opening: `json_extract` is evaluated only for payloads `json_valid` accepts (an index on it alone fails to build over a single row that is not JSON). The store needs SQLite's JSON functions, built in since 3.38. `Timers` writes to the store only after releasing its own lock, which the control loop takes every tick. Incident: 2026-09-25, with the machine at load 85-100, a socket `list` whose statement takes 1 ms took 34-94 s while 18 daemon threads waited on the store lock; `docs/reports/2026-09-25-store-lock-contention.md` has the reproduction and the measurements.

## 4. Job and attempt state machines

- **C-4.1** Job states: `queued`, `running`, `waiting`, `succeeded`, `failed`, `cancelled`, `lost`. A `waiting` job has `wait_reason` in {`capacity`, `dependency`, `approval`, `uncertain`, `workspace`, `route`} and a `next_check_at`. Only `capacity` holds back the jobs behind it in its tier; a job waiting on its own `workspace` (C-6.8) or `route` (C-6.12) delays nothing else.
- **C-4.2** Attempt states and the boundary each one guards:

| State | Set when | Recovery if the daemon dies here |
|---|---|---|
| `reserved` | Lane lease, output lease, and any worktree lease taken; attempt row inserted | Release leases, mark attempt `failed` with class `unknown` and detail `reserved-no-launch`; the job may retry |
| `starting` | Guardian spawned; no `start.json` yet | If `start.json` exists, treat as `running`; else wait `start_grace_s` (10) then run containment (C-5.5) on the guardian pid; if empty, release and retry; if not verifiable, `quarantined` |
| `running` | `start.json` read: pid, pgid, boot id, proc start recorded | If `exit.json` exists, move to `finalizing`; else if the guardian is alive by (pid, boot id, proc start), re-adopt; if its identity cannot be inspected, leave the attempt for the next tick; if it is dead, read `exit.json` once more (the guardian writes the receipt and then exits, so a receipt can appear between the first read and the liveness check) and move to `finalizing` when it is there; else run containment; empty means `lost`, else kill survivors and re-check, else `quarantined`. A receipt present at finalization always wins over a `lost` verdict reached before it was read (incident: 2026-09-05, under a load average above 45 a job whose provider had exited 0 was recorded `lost` with its receipt on disk) |
| `finalizing` | `exit.json` read; classification, salvage, export, notice pending | Re-run finalization idempotently; every step checks for its own completed output before acting; a census that is not verified empty waits out `exit_settle_s` (C-5.9) before quarantining |
| `succeeded`, `failed`, `interrupted`, `lost`, `cancelled`, `quarantined` | Terminal | None; `quarantined` needs an operator action (C-5.7) |

- **C-4.3** A job has at most one `accepted_attempt_id`. Acceptance and the notice insert are one transaction. A result from an attempt whose `seq` is lower than the job's current attempt, or whose state is not `finalizing`, is never accepted.
- **C-4.4** A job whose final attempt ends without an rc is `lost`, never `succeeded`.
- **C-4.5** `max_attempts` default 3; a new attempt is admitted only for classes `limited` (next candidate), `transient` (same lane after 60 s, once, then next candidate), and `lost` on a read-only job. `auth-dead`, `cli-too-old`, `content-filter`, and any class on a writable job after the workspace changed require reconciliation first (C-13.3).
- **C-4.6** An attempt never changes lane or model. A new lane or model is a new attempt.

## 5. Process ownership and containment

- **C-5.1** The daemon spawns each attempt through `subfleet-guardian`, which calls `os.setsid()` so it leads a new session and process group, then spawns the provider command as its child with the same pgid, stdout and stderr redirected to the attempt directory, and an environment that contains the lane credential, the provider home, `SUBFLEET_ATTEMPT=<attempt id>`, `SUBFLEET_JOB=<job id>`, and `SUBFLEET_ROOT=<state root>`. The guardian never receives a secret in argv.
- **C-5.2** Before spawning the provider, the guardian writes `start.json` = {`guardian_pid`, `pgid`, `boot_id`, `proc_start`, `started_at`} via temp file and rename. After the provider exits it writes `exit.json` = {`rc`, `signal`, `finished_at`, `wall_s`, `child_pid`} the same way, then exits with the provider's rc. If the provider cannot be spawned, `exit.json` carries `rc: 127` and `spawn_error`.
- **C-5.3** Boot id is the stable `kern.bootsessionuuid` from `sysctl`; legacy receipts may carry `kern.boottime` seconds. Process start identity is the `lstart` column of `ps -p <pid> -o lstart=`. A pid is "the same process" only if both identities match. A legacy boot timestamp that differs from the current timestamp means unknown, not dead: macOS wall-clock correction can shift `kern.boottime` during one boot. Unknown identity never permits a signal or establishes death; a responsive daemon socket remains usable. Absent processes, reused start identities, and differing boot-session UUIDs still establish death.
- **C-5.4** The daemon may signal only a process group it recorded, and only after confirming the group leader's identity by C-5.3.
- **C-5.5** Containment enumeration collects live, non-zombie pids from three sources: the members of process group `<pgid>`; a walk of parent links descending from the guardian pid and the recorded child pid; and `ps -axEww -o pid=,command=` filtered on processes whose environment carries both `SUBFLEET_ATTEMPT=<attempt id>` and `SUBFLEET_ROOT=<state root>`. Attempt ids are a timestamp and a slug, so two daemons on one machine (or two test state roots) can mint the same id in the same second; the root is what tells their processes apart (incident: 2026-09-05, sleeping fakes from an earlier test quarantined a later test's attempt). "Verified empty" means all three returned zero live pids. If any `ps` call fails, the result is "unverifiable". The group and the walk are read from one `ps -axo pid=,ppid=,pgid=,stat=` snapshot, so a process cannot be present in one of them and absent from the other because it exited between two reads. The census records each live pid's parent, group, and state as evidence, never its command or environment.
- **C-5.6** Kill protocol: mark the cancel request; SIGTERM the pgid; wait `term_grace_s` (15); SIGKILL the pgid; enumerate (C-5.5); SIGKILL any survivors individually after re-checking identity; enumerate again, repeating for up to `kill_settle_s` (3) while the census is not verified empty, because signalled processes leave the process table only when the kernel finishes tearing them down and one read taken 50 ms after SIGKILL reports an exiting process as live under load (incident: 2026-09-05, two full-suite runs quarantined attempts that a rerun did not). The window ends early on the first verified-empty census and never widens what counts as contained. Verified empty releases the workspace and finalizes with `killed_by`. Anything else is `quarantined`.
- **C-5.7** A `quarantined` attempt keeps its leases (lane slot excluded), its workspace, and its worktree. `subfleet runs show` prints the evidence. Resolution is `subfleet kill <job> --confirm-dead` after the operator checks, which re-runs C-5.5 and releases only on verified empty, or `--force-release` which records the operator's override in `events`.
- **C-5.9** After `exit.json` is read, a census that is not verified empty does not quarantine at once. The daemon allows `exit_settle_s` (3), measured from the first such census, for the guardian, which writes the receipt just before it exits, and for processes it already reaped to leave the process table, re-running the census on each tick. Survivors or an unverifiable census past the window quarantine the attempt with detail `writers remain after exit receipt`.
- **C-5.8** The daemon holds an exclusive `fcntl.flock` on `daemon.lock` and writes its pid, boot id, proc start, and version there. A second daemon exits 69. The CLI treats a lock whose recorded identity is dead as no daemon.
- **C-5.10** A worker that raises is retried with backoff, not on the next tick. The control loop offers every live attempt, every pending export, and admission to the worker pool each tick (50 ms), and a worker that raised used to be eligible again at once, so a cause that fails fast (a repository git refuses, a store error) was retried, and logged, twenty times a second for as long as it lasted. Now a key the control loop offers (an attempt id, `export:<job>`, `admission`, `timer-recovery`, `retention`) is not run again until 0.5 s after its first consecutive failure, doubling to a 60 s ceiling; a success clears the count. A one-shot request is never paced: `resolve:<job>`, an operator's `kill --confirm-dead` or `--force-release`, is offered once, by the request itself, so holding it back would drop it after the caller was told it was accepted; it runs whenever it is asked for and its failure is logged each time. `daemon.log` gets the line on the 1st, 2nd, 4th, 8th (each power of two) consecutive failure, with the count and the next retry, and still only the exception's type, never its message (a provider or keychain error can carry a secret). The count is in memory: a restart forgives it, and recovery re-offers every live key as before (incident: 2026-09-20, `worker 20260920-081856-native-other-disability-opus/a1 failed: SalvageError` forty times in `daemon.log`; that cause was a git timeout, which paced itself at its own 15 s cap, and nothing in the daemon would have paced one that failed at once).
- **C-5.11** A running attempt or probe costs the daemon a bounded number of subprocesses, however often it is offered, and a tick costs a bounded number of store statements, however much history is kept. The control loop still offers every live attempt each tick (C-5.10) and still reads its exit receipt, its cancel request and its wall limit on each pass, but asks `ps` whether the guardian is still the recorded process (C-5.3) at most every `LIVENESS_INTERVAL_S` (1 s); a probe's wait loop does the same while it still reads its receipt, its job and its deadline every pass. A paced pass that raises leaves no pacing deadline, so the retry C-5.10 schedules repeats the inspection. The boot-session UUID is read once per daemon process; legacy `kern.boottime` seconds are read every time. The record of owned group members (C-5.4) reads C-5.5's group source alone, from one `ps -axo pid=,pgid=,stat=,lstart=` snapshot, runs inside the paced pass, and captures an identity (C-5.3) only for a member it has not recorded or whose start has changed; the three-source census, whose marker source reads every process's environment, is taken only to decide a release, kill, loss or quarantine. Pending exports are found with one statement (`PENDING_EXPORTS`), not a lease lookup per accepted job. A `wait` re-reads the store only as C-15.5 says, after a top-level transaction has committed a change or every `WAIT_RECHECK_S` (1 s), through one reader for all waiters; a worker pass wakes waiters only when the store's generation moved while it ran, and makes that decision before its key is released. Incident: 2026-09-24, the per-tick inspection (three subprocesses per running attempt per 50 ms tick, and every 0.5 s a census that dumped every process's environment, 2.3 MB), waiters re-reading their jobs on every worker pass, and an export sweep of 266 statements a tick saturated the store lock; `daemon.status` took 38.8 s, every client timed out, and shutdown hung until SIGKILL (docs/reports/2026-09-24-daemon-inspection-wedge.md).

## 6. Admission

- **C-6.1** Submission validates before touching the store: workdir exists and is not under `/tmp` unless allowed; prompt file readable; `-o` path's directory exists; sandbox in {`read-only`, `workspace-write`}; `--task`/`--tier` valid per policy or `-m`/`-a`/`-H` pins consistent; a read-only job with `-o` inside `-C` is allowed (the daemon writes it).
- **C-6.2** The payload digest is SHA-256 over the canonical JSON of: prompt bytes (as base64), resolved workdir, git head of the workdir or null, task, tier, pinned model, pinned lane, sandbox, sorted exclusions, resolved `-o` path or null, `allow_desktop`, policy hash. A repeated request id with the same digest returns the existing job id (exit 0); with a different digest, exit 2.
- **C-6.3** Admission of an attempt is one transaction that: chooses the lane and model from the decision (section 11), takes the lane slot lease `lane:<lane id>:slot:<n>`, takes the output lease `out:<resolved path>` if `-o` is set and not already held by this job, takes the worktree lease if writable (on the write target, C-6.5; a session is not a place and takes no lease), inserts the attempt as `reserved`, and records the decision. Launch happens after commit. The decision is evaluated just before the transaction, off the store lock, on rows read in one read snapshot (C-3.7), with the store's generation (C-5.11) noted first; the transaction reserves on it only if the generation has not moved, so no transaction has committed since and the decision rests on the very rows the reservation reads, and only if the evaluation began at most `ROUTE_REUSE_S` (5 s) earlier, which bounds how old its clock (reading freshness, closure ends) can be. Otherwise the transaction evaluates again inside, as it always did. An early evaluation that fails is dropped, and the transaction's own evaluation settles the job as C-6.12 says. `daemon.status` counts both outcomes under `admission.route_evaluations`, and why each evaluation was repeated: a commit since (`moved`), too old (`old`), or the early one failed (`failed`). Incident: with the daemon held to 5% of a core, evaluating a whole capacity view inside this transaction held the store lock for 13.5 s (`docs/reports/2026-09-25-store-lock-contention.md`).
- **C-6.4** Caps with defaults in `policy.json`: `max_active_attempts` 4 fleet-wide; `max_in_flight_per_lane` 2, and 1 while the lane has no `provider` reading fresher than `reading_ttl_s` (120); `max_wall_s` 21600 per job; `max_attempts` 3; `max_child_jobs` 8 per parent; `max_tokens_observed` optional per job; `workspace_git_timeout_s` 60, `worktree_add_timeout_s` 180, and `workspace_retry_max` 8 (C-6.8); `max_writable_per_session` 8 (C-6.5).
- **C-6.5** Refusals are exit 7 with the fix named: API-key home, workdir under `/tmp`, writable job that would write in a checkout on `main` or `master` (C-13.2), `-o` path held by a live job of another request id, a writable job for a session id that already has one running from another instance, a second writable job on the same worktree, a writable job beyond `caps.max_writable_per_session`, an isolated review (`-I`) that would inherit `CLAUDE_CODE_MANAGED_SETTINGS_PATH` or a remote managed-settings variable, and an isolated Codex review whose home carries managed requirements or a non-empty system or project config layer (C-23.3). This list is the index of refusals: a new refusal is added here, not in a clause of its own. What holds a writable job is where it writes. The write target of an in-place job is the real path of the checkout that contains its workdir (`git rev-parse --show-toplevel`), so `/repo` and `/repo/sub` are one target and two linked worktrees of one repository are two; the target of any other writable job is the worktree the daemon allocates for it (C-6.6), which no other job shares. One instance of a session may therefore hold any number of writable jobs on distinct targets, up to `caps.max_writable_per_session` (8), a backstop against a runaway caller and not a throttle (`max_active_attempts` bounds what runs). An instance is a process: the caller's pid with its boot id and start time (C-5.3), read by the daemon at submit and recorded with the target in the `job.submitted` event, so a recycled pid is never mistaken for it and no schema change is needed. A submission is refused when the session has a live writable job whose recorded instance is another process that is still running (the twin), and also whenever the two cannot be told apart: the submission carries no pid, either process cannot be inspected, or the live job recorded no instance. An instance that is provably gone (no such pid, or the pid now belongs to a later process) is not a second instance: a session resumed after a restart or an account switch is one instance whose detached jobs survived, and it may dispatch again. A revive is always another instance of the session it continues (C-23.54), so a revive and any other writable job of that session refuse each other as before. Both questions need `ps` or `git`, so they are answered under the submit lock before the inserting transaction, which re-checks with SQL alone and refuses any live job the submission was not cleared against (C-3.3) (incident: 2026-09-20, a session handing five stalled threads to parallel lanes was refused every writable job after the first with "caller_session is held by a live job", whichever worktree it named; the code compared session ids and never instances, so it refused the one instance this clause never meant to stop). Milestone 9 adds: a socket `submit` of `kind: "turn"` or a `turn:` request id (C-26.1); a person-only operation from an agent (C-25.6); a writable turn whose workspace contains the state root, `~/.claude`, `~/.codex`, a lane home, or the guard's directory, and a turn on `main` or `master` without `allow_main` (C-26.10).
- **C-6.6** A writable job runs in a worktree the daemon allocates under `worktrees/<job id>/` from the caller's repo at its current head, unless the caller passes `--in-place`, in which case the daemon takes the worktree lease `worktree:<realpath>` on the checkout that contains the caller's directory (C-6.5); the provider still starts in the directory the caller named. A Claude job in an allocated worktree starts at the caller's place in it (a job run from `repo/pkg` starts in `<worktree>/pkg`), that place named as git spells it (`git rev-parse --show-prefix`, so a directory given in another case, in decomposed Unicode or through the `/System/Volumes/Data` firmlink is the committed one), and a resume starts where its source attempt's launch started; a Codex job starts at the worktree's top, because Codex's workspace-write sandbox writes only under its working directory; a directory the caller's head does not hold (untracked or ignored) is not in the worktree, so the job starts at its top.
- **C-6.7** `prompt.md` holds the caller's prompt bytes exactly as submitted; it is the digest input and is never rewritten. Prepended text is applied in two places and recorded separately: at submit, the daemon prepends to a workspace-write job that is not in place a note naming its worktree, the caller's checkout it must never write and the caller's place in the repository (with or without `--no-preamble`), and before that the write template unless `--no-preamble` (the sandbox is known at submit); the manifest records whether the template was given (`preamble`), and a resume keeps its source's choice; at launch, the Claude adapter prepends the headless block unless the prompt already contains the marker line `<!-- subfleet:headless -->` (the provider is known only after routing). The adapter writes the text actually sent to `<attempt dir>/prompt.sent.md`, the launch's `stdin_path` points at it, and it is recorded as an artifact with role `prompt-sent`.
- **C-6.8** Workspace preparation (the main or master re-check, worktree allocation, reading HEAD, and the baseline snapshot) runs before every admission, so a waiting job repeats it on each pass and one slow pass must not end the job. Every git call in it is capped by `caps.workspace_git_timeout_s` (60; `git worktree add` by `caps.worktree_add_timeout_s`, 180); finalization's salvage uses the same cap, and a caller with no policy in hand reads `SUBFLEET_GIT_TIMEOUT_S`. A git call that did not finish is never read as an answer: a timed-out `rev-parse` is not "no HEAD" and a timed-out `symbolic-ref` is not "not on main". At submit it is exit 1 with nothing stored; at launch the attempt ends with the cause as its detail; at admission it is a failure classified here. Transient failures are a timeout and an `OSError` whose errno is EAGAIN, EINTR, ENOMEM, EMFILE, ENFILE, EBUSY, ETIMEDOUT, or ENOBUFS: the job moves to `waiting` with `wait_reason` `workspace` and a `next_check_at` 5 s out, doubling per consecutive failure to a 300 s ceiling, holds no lease, blocks no other job, and returns to `queued` on the first pass that succeeds, which also resets the count. After `caps.workspace_retry_max` (8) consecutive transient failures, or at once for any other failure (git exiting non-zero, a permission error), the job is `failed` with rc 1. Nothing is discarded: each deferral is a `job.workspace_deferred` event and the terminal failure a `job.workspace_failed` event, both carrying `error_type` (the underlying exception, so `TimeoutExpired` rather than its wrapper) and `error` (git's verb, the cap, and its stderr, or the OS error; a path and an errno, never a credential); the notice text ends with the same two fields; `show` returns the latest record as `workspace`; and `daemon.log` gets one line per deferral and per failure, naming the job. The consecutive count is held in memory, so a daemon restart forgives it while the events keep the history. A `worktrees/<job id>/` directory that is not a worktree (a `git worktree add` killed at its cap) is removed and rebuilt before the job is admitted; no attempt has run in it. The baseline snapshot seeds its temporary index from a copy of the real index (mtime kept) and reads the baseline with `read-tree -m`, so its entries are the baseline's while the stat data of every unchanged path carries over and `add -A` hashes only changed files; the copy's assume-unchanged and skip-worktree bits, which `read-tree -m` keeps, are cleared across the whole index before `add -A`, since `add -A` skips such paths and the empty-index read has none, so both reads give the same tree; bytes and mtime come from one open file; with no usable real index (none yet, unmerged entries, a copy git cannot read or clear) it reads the baseline into an empty index. Trusting stat data is git's own model: a rewrite that keeps size, mtime and inode is read as unchanged (incident: 2026-09-23, axiom-corpus, 59,822 tracked files and 14 GB: the empty-index snapshot took 39 to 51 s at a load average near 6 and timed out at the 60 s cap on all eight tries, so no writable job could be admitted there; seeded, the same tree took 0.5 s). A refusal raised during preparation (C-6.5) is still exit 7 with its fix and never waits (incident: 2026-09-20, under a load average near 10 a writable job went from queued to `failed` in 19 s with "workspace preparation failed", no attempt, and nothing in `daemon.log`; the same snapshot took 0.6 s minutes later and an identical resubmission ran; twelve jobs ended that way between 2026-09-19 and 2026-09-20, read-only ones after as long as 70 minutes in the queue, because the caps were 15 s and 5 s, the exception was discarded, and every failure was terminal).
- **C-6.9** Queued jobs are considered in tier order and, within a tier, oldest first (plan amendment 11). A job that cannot be placed on this pass (it is `waiting` on `capacity` with a `next_check_at` still ahead, its probe is pending, no lane is admissible, or a lease it needs is held) holds back the later jobs of its tier **that compete with it**, and no others. Two jobs compete when some model could serve both: a pinned job's models are its one pin; a task job's are its chain from its tier upward, exactly the chain routing walks (C-11.2); a job whose models cannot be told (a lane pin with no model) competes with every job. Lane pins narrow it further: two jobs pinned to different lanes never compete, whatever their models, because neither can take a slot the other waits for; a job with no lane pin, or a pin that cannot be resolved, could use any lane and so competes on models alone (incident: 2026-09-22, three Fable gate reviews pinned to three lanes; the oldest waited on its own lane's provider limit until 19:00Z and held the other two, whose lanes were open, for six hours). So an older Opus review keeps its place against later Opus work, including work that could promote into its chain, and a Fable-pinned job does not queue behind it. A job that passes an older waiting job of its tier leaves one active-attempt slot free (`max_active_attempts` minus one), so the older job starts the moment its capacity appears rather than waiting out the jobs that passed it; with nothing older waiting, the full cap applies. At `max_active_attempts` the pass ends: nothing later is evaluated. Tiers never hold each other, as before (incident: 2026-09-20, an Opus review that no lane would admit, every Claude lane `reserve:fable:unmeasured` and Astra closed until the next day, headed the `standard` tier; admission held the whole tier behind it, so three Fable-pinned jobs, tier-less and therefore `standard`, stayed queued beside eleven free Fable lanes and nothing at all was admitted for more than three hours).
- **C-6.10** A capacity wait is rechecked on a clock that backs off, and a recheck that reaches the verdict it reached last time adds no decision row. The first recheck is 1 s out (plan amendment 11); each consecutive recheck with the same verdict doubles it, to a 30 s ceiling; a reset the decision knows about (a closure's `until_at`, a reading's `resets_at`) that falls sooner is still checked on time. The verdict is the chain walked, the lane and model chosen, the policy hash, and each rejected lane with its reasons (`scheduler.verdict_signature`); readings, utilization, and `evaluated_at` are evidence and are left out, and so is `no-slot` on a lane that is rejected for another reason as well: a lane that is closed, reserved, or excluded is no nearer to taking the job when its slot empties, slots fill and empty all day, and a probe's reservation counts toward the fleet cap, so each probe cycle (C-18.1) marks every lane `no-slot` for the second it runs. A lane whose only reason is `no-slot` keeps it: that job is waiting for a slot, and that is its verdict. A changed verdict is recorded and restarts the clock at 1 s. The same doubling applies to three waits that are not on a closure or a reading, so the known-reset rule has nothing to say about them: a job waiting on a lease another job holds, which was a fixed 1 s; a job whose route could not be prepared with no clock set (its probe's slot is held, or the lane changed hands); and a job whose chosen lane and model changed after its probe. The last two had no clock at all and were prepared again, with a new probe directory, on every tick; a probe directory made for a reservation that then does not happen is removed, since no record names it and recovery would never collect it. Backing off is not meant to cost a start: each pass compares the leases no probe holds with those it saw on the pass before, counting the ones it took itself, and when one has gone (an attempt ended, a job released its worktree or its output path) every backed-off capacity wait other than a probe's own is looked at on that pass. Capacity that appears any other way (a fresh reading, a closure an operator lifts, a lane enrolled) is seen at the next recheck, so the most this clause can add to a start is 30 s. Only a capacity wait is brought forward. A job whose wait became `workspace` (C-6.8) loses its record and keeps that clock, because a look brought forward there spends one of `workspace_retry_max` retries, and eight unrelated releases would end the job. The 60 s wait after an inconclusive probe keeps its clock too, because bringing it forward would re-probe the provider on every release; it gets the other half of the rule, and a probe that ends the same way adds no second decision row. The record (verdict, consecutive rechecks, first and last look, and the latest hold in full) is held in memory per job, replaced whole on every look so that another thread never reads half of one, and dropped when the job is placed or ends. A restart therefore forgets it, as it forgets C-6.8's count: recovery makes every capacity wait due once, since what each was waiting for may have changed while no daemon ran and nothing else could bring a persisted wait forward, at the cost of one decision row per waiting job; `why` reports the record (C-6.11). C-11.5 is unchanged: the decision is still stored per attempt, and a waiting job still has the latest verdict it reached (incident: 2026-09-20, three jobs no lane would admit were each re-evaluated once a second for hours; every look prepared the workspace with git, scored every lane, and wrote a 22 KB decision row whose only new content was fresher readings: 1,628 rows in ten minutes with no attempt reserved, 29,923 rows and 681 MB of a 709 MB store, the file growing about 170 MB an hour, and the daemon at a full core; the decision said `earliest reset: 2026-09-20T22:20:00Z`, more than an hour off, on every one of them; by the next morning the store was 2.3 GB, 2.2 GB of it 98,014 decision rows. Replayed over the 80,996 rows of the six worst jobs, the verdict changed 74 times).
- **C-6.11** A job that is not placed always has a stated reason, and a fleet that places nothing says so. Each admission pass records, per job it leaves unplaced, why: `behind-older-job` with the older job's id and the tier (C-6.9); `fleet-full` with `max_active_attempts`; `slot-kept` with `kept_for`, `live`, and `max_active_attempts`, when a lane would take the job and the fleet is one short of its cap because C-6.9 keeps the last slot for an older waiting job of the tier (it is not reported as a full fleet, which an operator can see it is not); `parent-cap`; `lease-held` with the lease keys; `probe-pending`; `attempt-live` (an earlier attempt of the job is still live or quarantined); `approval`, `uncertain`, `workspace` (C-4.1); `route` with `error_type`, `error`, and `deferrals` (C-6.12), which is reported as that whatever else holds the job while its clock runs; otherwise the commonest first reason lanes rejected it for (`reserve:fable:unmeasured`, `closed:account`, `no-slot`, ...), with the `next_check_at` of any wait that has one. A wait that is a person's or a retry's to end (`approval`, `uncertain`, `workspace`) is reported as that even when the fleet is also full or an older job is also ahead of it. `hold` is the last pass's answer and `recheck` describes the last look (`recheck.label` is what that look found): the reason is the latest look's, not the first's, whether or not the verdict repeated; a look that ends without changing a verdict or a clock still refreshes it; and a pass that does not look at the job repeats the last hold in full (`leases`, `max_active_attempts`), so `why` never degrades between looks. A pass that raises publishes nothing: the holds and the `admission` snapshot stay as the last whole pass left them, because half a hold set would read as nothing left pending, and C-5.10 logs and paces the failure. When every lane has a standing reason the label is the commonest of those and not `fleet-full`: a probe's reservation counts toward the fleet cap, so such a job would otherwise read `fleet-full` for the second each probe runs. The record is in memory and replaced whole each pass. `subfleet why <job>` returns it as `job` (`state`, `tier`, `wait_reason`, `next_check_at`, `hold`, `recheck`, `decision_source`, `decided_at`) and as `queue`, the same in sentences, ahead of the decision. A queued or waiting job with no decision row (admission held it back, or no pass has reached it) is evaluated for the answer and marked `decision_source: evaluated-now`; no decision is recorded and no job changes, because answering is not admission. The evaluation asks who the desktop login is, as every evaluation does (C-10.3), and a newly verified identity is recorded as the `desktop.identity` event it would have been on the next pass. A job that ended without a decision prints its state and `No decision recorded.`, unless admission refused it (C-6.12), which prints `Refused at admission: <message>` in its place The CLI never prints `null`, also against a daemon that predates `queue`. `daemon.status` carries `admission`: `pending` (unplaced jobs other than those held as `approval`, `uncertain`, `workspace`, or `attempt-live`, which are a person's or a retry's to end), `placed_at`, `idle_for_s` and `idle_since` (null unless jobs are pending and none has been placed), `reasons` (count per reason), and `open_lanes`; it is one snapshot, replaced whole at the end of a pass, so a status request never reads half of an update. `open_lanes` is the lanes owned by v2, enabled, not the desktop login, identity not mismatched, under no account-wide closure, with a slot free and no probe holding it. Open means capacity exists, not that it fits: a job can still be refused an open lane by a model-scoped closure, the reserve, or its own exclusions, and the reasons say which. `subfleet status` prints one `admission:` line while `idle_for_s` is set, and its `running jobs:` count and table cover live jobs only. When jobs have been pending with none placed for 60 s, `daemon.log` gets one line (count, seconds idle, open lanes by id, reasons by count, and the first job in admission order), and one line when placing resumes or nothing is left pending. The line is a warning when a lane is open and some job is held for a reason other than ordinary queueing (`fleet-full`, `slot-kept`, `parent-cap`, `no-slot`, `lease-held`, `probe-pending`, `behind-older-job`); otherwise it is information, because with no lane open or a fleet at its cap waiting is the expected answer. The fleet is looked at again every 600 s while the stretch lasts: a warning is written each time, information at most every 3600 s, so a wait that was expected when it was first logged becomes a warning within ten minutes of becoming one (incident: 2026-09-20, fifteen jobs from six sessions sat queued for more than three hours beside open lanes; `subfleet why` printed `null` for every one of them, because a job admission skips gets no decision row and the CLI printed the missing value instead of the daemon's text; `subfleet status` said `running jobs: 519`, the size of the store, because `daemon.status` carries every job as `jobs`; and `daemon.log` had not gained a line since the daemon started).
- **C-6.12** A job whose route cannot be evaluated is that job's problem and never the pass's. Evaluating one job (`scheduler.evaluate`, and `scheduler.probe_required`, which checks an unmeasured-reserve authorization) is isolated from the rest of the pass, both where the route is prepared and inside the reserving transaction, which rolls back before the job is settled; a `ValueError` (a `PolicyError` is one), `KeyError`, `TypeError`, `AttributeError`, or `IndexError` from it settles that job and the pass goes on to the next, in its tier and every other. What it settles to depends on whose the error is. A `scheduler.RouteError` is the job's own: its pin names several lanes, its pin and its model are of different providers, or its authorization is not whole. No wait can fix that and only the caller can say what was meant, so the job is `failed` with rc 2, what submit would have answered, its `wait_reason` and `next_check_at` cleared (as for any job `_fail_queued` ends); its notice and a `job.route_refused` event carry the message (`error_type`, `error`), `daemon.log` gets one line naming the job and the message, `why` prints `Refused at admission: <message>` ahead of any decision recorded before it (`refused` in its result), and a worktree admission cut for it under `worktrees/<job id>/` that no attempt used is removed, since `jobs.worktree` is set only at reservation and retention would never collect it. Two of those errors can also come from a policy edit rather than the job: a provider conflict (a tier's chain moved to another provider under a job already pinned to a lane) and an authorization's model check. Those are refused only under the policy the job was accepted with (`jobs.policy_hash` equal to the running policy's); under any other they are treated as below. Anything else is not the job's: bad capacity data, a policy that no longer knows the job's task, tier, or model (submit checked each against the policy it ran under, so a policy edit is the operator's to fix), or a defect. That is never terminal, because a restart can bring the fix and failing it could fail every queued job at once: the job waits with `wait_reason` `route`, 5 s out doubling per consecutive failure to a 300 s ceiling, each deferral a `job.route_deferred` event carrying `error_type`, `error`, `deferrals`, and `next_check_at`, and a `daemon.log` line naming the job and the error's type only (C-5.10: the message is in the event and in `why`). A route wait is not a capacity wait: it holds back no other job (C-6.9) and no released lease brings it forward (C-6.10). While its clock runs its hold is `route` with the error (C-6.11), whatever else would hold the job; once the clock is due the job goes through the pass like any other, and a pass that evaluates its route resets the count. `why` names the error, from the hold and, when `why`'s own evaluation raises, in place of the decision (`route_error` in its result); `daemon.status` counts the hold under `admission.reasons`. The count is in memory; recovery makes every route wait due, as it does capacity waits. Route holds are not ordinary queueing, so beside an open lane the idle line (C-6.11) is a warning. A store error is not isolated: that is the pass's, and C-5.10 retries it. An accepted job is always evaluable as far as submit can tell: an empty task or tier is stored as none. A transient retry (C-4.5, C-9.5) is the daemon's choice of pair, not the job's, and is pinned to the last attempt's lane and model id only while that pair could run: the running policy resolves the id (a current id or a `retired` alias) to a model of the lane's provider, and the lane (or its re-enrolled successor) is enabled, v2-owned, and not identity-blocked. While it is pinned, its C-6.9 demand is that one model on that one lane; once a look has let the pin go, the job's demand is its own on that pass and while its clock runs, so it neither passes an older job it competes with nor is passed by a younger one (held behind one after a look, it waits on a C-6.10 capacity clock like any other held look, so the passes before that clock prepare no workspace and score no lane), and the next due look evaluates the pair again (a lane that recovered takes its one retry; a restart, which forgets the look, changes nothing). When the job is due, the pair is evaluated as admission would evaluate it. If the lane refuses it only for want of a slot (in flight, the fleet or a parent at its cap, a probe holding it), the retry waits for that lane. If the lane refuses it for anything a slot will not end (a closure, the desktop login, the job's own exclusions, a latched credential, the floor, the reserve), or the pair cannot be evaluated, the job routes as submitted, which is C-4.5's "then next candidate". Before this, a pinned retry waited on its lane until `max_wall_s` cancelled the job (incident: 2026-09-22, five jobs pinned by email, `-a max@axiom.org` and `-a max@thesisinstitute.org`, with a task and no model, named a Claude lane and a Codex lane at once in the capacity view (C-11.2); `resolve_lane` raised inside `_admit_pass`, which caught nothing per job, so every pass aborted at the first of them: `worker admission failed: ValueError (128 in a row)`, no attempt reserved between 14:45:05Z and 18:02:45Z (10:45 to 14:03 EDT), and every later job in every tier waited; `why` caught the same error and printed `No decision recorded.` for those five, so nothing pointed at the stalled pass. Admission resumed within a minute of the five pins being rewritten to `claude-11` and `claude-9` by hand. The same resolution had stalled admission once already that day: a gate review pinned `-a max@axiom.org -m fable` held every pass from its submission at 13:24:34Z until it was cancelled at 13:48:53Z, no attempt was reserved from 13:24:08Z to 13:50:32Z, and `daemon.log` shows the count reaching sixteen twice only because the lane-pins cutover restarted the daemon at 13:35:39Z).

## 7. Cancellation

- **C-7.1** `kill` inserts a cancel request in the job row (`cancel_requested_at`) in one transaction and returns; the daemon performs C-5.6 asynchronously. `kill --wait` blocks until terminal.
- **C-7.2** If the cancel commits before acceptance, the job becomes `cancelled` even if an attempt later reaches `finalizing`; that attempt's artifacts are kept and it is marked `interrupted`. If acceptance commits first, `kill` returns 0 and prints "already finished".
- **C-7.3** A parent's cancel cancels every child job not submitted with `--independent`, in the same transaction that records the parent's request.
- **C-7.4** A job that is `queued` when cancelled becomes `cancelled` immediately and releases its leases.

## 8. Artifacts and export

- **C-8.1** Every file the daemon publishes (deliverable, `-o` export, `manifest.json`, receipts) is written as: temp file in the destination directory, `os.fsync(fd)`, `os.rename`, `os.fsync` on the directory descriptor.
- **C-8.2** The deliverable is captured once at `finalizing` from the adapter (C-12.6) and recorded in `artifacts` with role `deliverable`, path, bytes, and SHA-256. The raw stream, stdout, stderr, and lane log are recorded with their own roles. Nothing appended to a transcript after the attempt's exit changes the deliverable.
- **C-8.3** The `-o` export is a copy of the accepted deliverable published by C-8.1 after acceptance. A failed export sets `export_error` on the job and emits an event; the job stays `succeeded`.
- **C-8.4** Retention: newest 500 jobs or 2 GiB (policy `retention.jobs`, `retention.bytes`), whichever binds, counted over jobs that are not conversation turns (turn jobs have their own budget, C-26.12), computed outside transactions in a maintenance pass; jobs that are active, `quarantined`, have unread notices addressed to a session, hold salvage refs referenced nowhere else, or are a gate's evidence are never pruned. A notice with no session can never be read, so it pins nothing (review IR-17). Probe and keepalive results live in `readings` and `events`, not in `jobs`.

## 9. Evidence labels and classification

- **C-9.1** Reading labels: `provider` (a server reported it; source and age recorded), `stale-provider` (the same beyond `reading_ttl_s`), `admission-observed` (this model recently succeeded or was rejected on this lane; remaining quota unknown), `local-backoff` (a routing decision with an explicit expiry and reason), `unknown`. No other label exists. A percentage is rendered only from a `provider` or `stale-provider` reading, and a stale one is marked stale.
- **C-9.2** Classification precedence is authentication, then admission, then quota, and the classifier records which evidence answered each. Outcome classes: `ok`, `limited`, `auth-dead`, `cli-too-old`, `content-filter`, `transient`, `unknown`. The raw rc and signal are always kept beside the class.
- **C-9.3** `auth-dead` requires a 401 from a usage endpoint, an explicit organisation-block message, or a refresh-token-revoked event. A 403 from the Claude usage endpoint on a setup token is expected scope and is not evidence. A limit-looking phrase with a successful `system/init` is `limited`, not `auth-dead`. A Codex conversation turn's `unauthorized` error is not evidence on its own: the turn is `unknown` and the lane's usage endpoint decides (design §7).
- **C-9.4** `limited` carries scope (`account` or a model id), the provider's reset clock when reported, else a guessed clock of now + 3600 s marked `clock_source: guessed`, and the evidence (event, stderr line, or rc). It writes a closure (C-9.6).
- **C-9.5** `transient` covers 5xx, stream disconnects, DNS and TLS failures, and "model at capacity" messages. It never writes a closure; it allows one same-lane retry after 60 s.
- **C-9.6** A closure is (lane, scope, until, reason, clock source, source event). A new closure on the same lane and scope extends `until` but never shortens it. Closures expire by clock; nothing else releases a provider-limit closure except a later `provider` reading that shows the window reset.
- **C-9.7** Codex windows are classified by duration (`window_minutes` 300 is `five_hour`, 10080 is `seven_day`, anything else keeps its minute count as the key), never by slot position.
- **C-9.8** Claude `rate_limit_event`: `unifiedWindows.<window>.utilization` is a fraction in [0, 1] and `resetsAt` is epoch seconds; `status: allowed` yields `provider` readings for the shared five-hour and weekly windows with scope `account`, and a scoped weekly Fable reading when `seven_day_overage_included` is present; over-cap utilization is stored as exhausted (1) with the original retained in evidence; `status: rejected` yields no utilization reading; it yields one `admission-observed` reading for the requested model whose `window` is the literal `admission` (the only value of `window` that is not a duration key), with `resetsAt` as the closure clock when present, and `errorCode` recorded. Named rejection types `seven_day_overage_included`, `seven_day_opus`, and `seven_day_sonnet` close their respective model scopes; shared and unknown limit types close the account. `overageStatus` is parsed independently and never treated as admission evidence.

## 10. Lanes and credentials

- **C-9.9** The Claude usage sensor that costs no model turn is `https://api.anthropic.com/api/oauth/usage`, read with the lane's own credential (source `oauth-usage`). It yields `provider` readings for the account windows `five_hour` and `seven_day` (scope `account`) and one `provider` reading per `limits[]` row of kind `weekly_scoped`, scope = the policy model id for the row's `scope.model.display_name`, window `seven_day`; utilization is normalised to a fraction. HTTP 429 yields no reading and the server's `Retry-After`, which the timer honours before asking that lane again; 401 is auth-dead; 403 is no-scope; anything else is unavailable and yields no reading. Reads are paced `reserve.usage_spacing_s` apart (3) because the endpoint penalises bursts (2026-09-06: fourteen back-to-back reads earned `Retry-After: 3035`). C-10.6 holds: the readings count only when the profile endpoint, asked with the same credential, binds the lane. The timer's periodic Claude probe is this read; a model turn is spent only by the pre-launch probe (C-11.4) and keepalive. A Claude home lane's login lives in the config directory's `.credentials.json` or, on macOS, in the keychain item `Claude Code-credentials-<sha256(CLAUDE_CONFIG_DIR)[:8]>` (observed 2026-09-06); its access token expires within hours and carries a refresh token the CLI renews when it runs. An access token past `expiresAt`, or a 401 on a home lane with a refresh token, is `expired-token`, never auth-dead: the timer spends one minimal turn under that home (C-23.47's heal, at most once per 20 minutes per credential epoch) and reads usage again.
- **C-10.1** A lane row is an immutable binding of provider, account key, credential reference, credential epoch, optional home, `owner` (`v1` or `v2`), and `desktop` flag. The credential reference is a keychain item name (`claude-quota-<email>`, as v1) or a home directory path; the store never holds a secret.
- **C-10.2** Enrolment probes before recording: Codex reads `auth.json`, refuses an API-key login and a free plan, and probes the usage endpoint; Claude runs one Haiku turn under the token with `--output-format stream-json --verbose` and reads the `rate_limit_event`.
- **C-10.3** A lane whose Claude identity (C-10.6) equals the identity of the desktop app's keychain credential is `desktop` and is never a candidate unless the job has `allow_desktop`. The desktop identity comes from the profile endpoint using the keychain credential itself, re-read each probe cycle; `~/.claude.json` `oauthAccount` is a hint that `doctor` compares against the profile and reports when they disagree, never the authority. While the desktop identity cannot be verified, every lane whose label matches either the cached email or the last verified desktop identity is treated as `desktop`. For Codex, `~/.codex` is observed and never a lane, and a numbered lane that shares the app's account is `app_shadowed`: dispatchable, ordered like any other lane, and last for automatic reset credits (C-23.46).
- **C-10.4** A lane with `owner: v1` is never a candidate. Ownership changes only by `subfleet lanes transfer <lane> --to v2` (or `--to v1`), which records an event. For a Codex lane the transfer also relocates the home: `~/.codex-<n>` moves to `<state root>/lanes/<lane id>/` on `--to v2`, before ownership flips, and back on `--to v1`, after it flips, each in one rename. v1 discovers Codex homes by directory glob from every caller (CLI, gates, launch agents) and reads no roster, so the relocation is the fence and the roster entry is the record. The lane keeps its id: the credential is unchanged, only its path moved. A transfer to v2 is refused while v1's ledger shows a run live on that home; a transfer back is refused while a v2 attempt is live on the lane.
- **C-10.5** The credential value is resolved inside the adapter's launch builder and placed only in the child's environment. It is never logged, never written to `lane.log`, never in `manifest.json`.
- **C-10.6** A Claude identity is the pair (`account_uuid`, `org_uuid`) returned by `https://api.anthropic.com/api/oauth/profile` when requested with exactly the credential that produces the lane's usage reading. A usage reading is recorded only when the profile identity equals the lane's recorded identity. When the profile is unavailable, the reading is stored with evidence `identity-unverified` and no windows; when it differs, with evidence `identity-mismatch` and no windows, and the lane is not a candidate until an operator re-enrols it. A setup-token lane whose token lacks profile scope keeps the identity recorded at enrolment, and its stream readings carry evidence `identity-enrolled`. Incident: on 2026-09-05 v1 attributed the Axiom account's usage to RulesAtlas because it trusted `~/.claude.json`; the evidence is `~/axiom-eng-briefs/opus-expiry-20260905/identity-fix-live-result.json`.
- **C-10.7** A desktop credential and an enrolled inference-token lane are distinct lanes even when their labels match; identity, not email, joins two credentials to one account, and `doctor` reports two enabled lanes with one identity as a defect (C-23.45).

## 11. Routing evaluation

- **C-11.1** `policy.json` is the routing data. Required keys: `tiers`, `chains` (task to ordered short-model list, one per tier), `fallback: "upward-only"`, `permissions` (task to sandbox; a submit that names no sandbox, `sandbox: "policy"`, gets its task's entry, else `*`, else read-only, and an isolated review or gate round always reads only; a writable result outside a git repository is refused with the fix `-s read-only`, never downgraded; d261, 2026-09-24), `models` (short name to provider, id, optional effort and scope), `retired` (alias to short name), `desktop_login: "never"`, `caps` (C-6.4), `reset_credits`. Optional `network: {codex_workspace_write: bool}` (d260, default false in code, true in the shipped policy): a writable, non-isolated Codex job gets `-c sandbox_workspace_write.network_access=true`, and a Codex conversation turn under `bypass` gets `networkAccess: true` (under `ask` and `accept-edits` a network command still reaches the person as an approval); wherever the network is granted the launch also carries `-c features.unified_exec=false` (C-23.6), because unified exec's `write_stdin` feeds a shell text the never-rules guard never sees; read-only and isolated launches never get the network. The file's SHA-256 is the policy hash on every job.
- **C-11.2** Evaluation for a `--task`/`--tier` job walks the chain from the tier's index upward. For each model, candidates are lanes of the model's provider that are enabled, `owner: v2`, not `desktop` (unless allowed), not in the job's exclusions, not under an unexpired closure for scope `account` or the model id, and with a free slot (C-6.4). The first model with a candidate wins. A `-m` pin evaluates one model and never falls back; `-a` or `-H` evaluates one lane. A pinned job evaluates one model, its `-m` model or else the first model of its task's chain from its tier, and so runs only on that model's provider. The pin is resolved to one lane id by `scheduler.resolve_lane` once, at submit, against the lanes admission evaluates named as the capacity view names them (each lane's row with its latest probe verdict merged in, as `Timers.enrich_view` merges it, so a Codex lane also answers to the email its usage probe reported, and keeps it through a probe that could not read the account; the same roster serves admission and recovery), and the job stores that lane id. The name as typed is kept in the `job.submitted` event (`pin.requested`, `pin.lane_id`) and, except for a job carrying an unmeasured-reserve authorization, in the request digest; a retry of an accepted request whose name no longer resolves to one lane is answered from the lane it was accepted on, so a retry still finds its job (C-6.2). An authorized job's digest binds the lane id it was granted for (C-11.7a), so its retry after the name comes to name another lane is refused as a different payload. A lane id matches only itself, except that a disabled lane whose credential an enabled lane now holds (a re-enrolment, C-10.2: the same account on the same credential) resolves to that lane, so a job pinned before a re-enrolment runs on its successor, and attempts on a lane and on its successor are attempts on one lane when retries and exclusions are counted (C-4.5: one same-lane retry, then the next candidate), a resume included, whose launch accepts the successor of the lane it recorded because the native session lives under the credential's home, not under a lane id (C-12.3); a job carrying an unmeasured-reserve authorization never follows, because the authorization names the lane id it was granted for (C-11.7). Any other name (an account key or its account part, a label, a Codex email, a home) may match several lanes, and narrowing drops only lanes that could never take the job: lanes of another provider than the job's, taken from the job's model or task, else from the flag that pinned it (`-a` a Claude account, `-H` a Codex home, sent as `pinned_provider`), a disabled lane when an enabled lane that also matches is bound to the same credential, and a lane whose credential proved to hold another account (C-10.6) when another lane of the same provider also matches (across providers the name stays ambiguous); such a lane keeps the email its probe read as `observed_email`, never as a name it answers to. A name given with `-a` or `-H` names a lane of that flag's provider only, so a job whose model runs on the other provider is refused at submit (exit 2), as v1 refused `-a` with a Codex model; a lane id says its own provider whatever flag carried it. A name that still matches several lanes is refused at submit with exit 2 naming the lane ids (`-a <lane id>` pins one). Resolving once means no later roster change (a probe reporting an email, a lane enrolled) can make an accepted pin ambiguous. A job accepted before this rule may still carry a name: each daemon start rewrites the pin of every unfinished job whose name resolves to one lane (`job.pin_canonicalized`, from and to; a job carrying an unmeasured-reserve authorization is never rewritten) and logs one line for each it leaves. One that names several lanes is refused at admission (C-6.12). One that names no lane waits as a pin to an unknown lane always has (`pinned lane ... is unknown`, C-17.3), which admission cannot settle, and `subfleet doctor` fails its `unfinished jobs pin lanes by id` row while any job carries such a pin; a repair that raises is logged and skipped, never holding up recovery. Exclusions (`-x`) are not narrowed: a name excludes every lane it matches, which errs toward not running.
- **C-11.3** Codex comparator: eligible when every `provider` window has utilization below `1 - headroom_floor` (floor default 0.15); ordered by `seven_day` reset ascending (soonest first), then lane id. In-flight counts never reorder Codex lanes. Claude comparator: eligible for a model by the same floor on the worst window of every scope that applies to that model; ordered first by the stranded term (a lane closed for a model the job does not need, typically Fable, sorts ahead of unstranded lanes so stranded capacity is spent first; C-23.37), then worst-window headroom descending, then in-flight ascending, then lane id. Lanes with no `provider` reading rank after measured lanes on both providers and are "eligible but unmeasured".
- **C-11.4** Before dispatching expensive work (writable, or tier `hard`) to an unmeasured lane, the daemon runs a probe with the model the job wants (C-10.2 style); a `limited` result closes the scope; `ok` records `admission-observed`. For other work the job's first attempt is the probe. A conversation turn never triggers a probe (C-26.9). A probe launch uses the fixed prompt `Reply with exactly OK. Do not use tools.` in a private read-only directory under the state root and carries `SUBFLEET_PROBE=1` in the child environment, so tooling and the fake providers can tell a probe from work.
- **C-11.5** The decision record is JSON: chain walked, per-model candidate list with each rejected lane and its reason, readings and closures consulted, chosen lane and model, and the policy hash. It is stored per attempt and printed by `subfleet why <job>`; `subfleet run --why` and `--dry-run` print it without dispatching.
- **C-11.6** The observed 06:33 case (excluded desktop lane, Opus chain exhausted) must evaluate to Astra with the reason "opus: no candidate lanes after exclusions; promoted".

## 12. Adapters

- **C-11.7** Reserve rule. A Claude Max account carries a shared weekly window (`seven_day`, all models) and a model-scoped weekly window for each reserved model (`reserve.models`, today `fable`). Use of the reserved model counts against both; use of any other model counts against the shared window only, so the shared window is what ends a week of the reserved model. For a job whose model is not reserved, a lane is a candidate only when fresh complete `oauth-usage` readings, or shared/scoped readings paired by event time and attempt from one `rate_limit_event`, give slack = (1 − shared utilization) − `reserve.cap_ratio` × (1 − reserved utilization) ≥ `reserve.min_slack`: a lane with no fresh paired measurement is rejected `reserve:<model>:unmeasured` unless an active provider-reported model-only exhaustion proves the reserved model cannot use capacity before its reset; that case requires a fresh supervised probe of the requested model and never overrides fresh measured reserve restrictions, a lane below the slack `reserve:<model>:reserved`, and a lane whose usage read shows no reserved window is free. Candidates are ordered by slack, so non-reserved work lands where the reserved bucket is most spent. `cap_ratio` is the reserved bucket's size relative to the shared one; the payload does not state it, so it is set above any ratio the observed accounts allow (2.0 on 2026-09-06, from an account at 94 shared and 49 reserved, which bounds it below 1.92) and lowered only from measurement. Incident: 2026-09-05, Opus lanes on two accounts exhausted their shared window and ended their Fable week with half the Fable bucket unused.
- **C-11.7a** An operator may explicitly authorize only an unmeasured reserve verdict for one new dispatch using `--allow-unmeasured-reserve REASON` with both lane and model pinned. ## 13. Salvage and workspaces

- **C-13.1** Salvage runs only for a writable job, only at `finalizing`, `lost`, or kill, and only when the worktree's tree hash differs from the baseline recorded at `reserved`. It builds a temporary index from the working tree (tracked and untracked, honouring `.gitignore`), `commit-tree` with the baseline as parent, and writes `refs/subfleet-salvage/<branch>-<utc>-<attempt seq>`. HEAD, the real index, and the working tree are untouched. The ref is recorded as an artifact with role `salvage`.
- **C-13.2** A private salvage ref may be written from any branch. What is refused, at submit, at admission and again at launch, is a writable job that would write in a checkout on `main` or `master`: an in-place job whose workdir is on one, and any job whose allocated worktree has been switched to one between attempts. A job that is not in place never writes where its caller stands: the daemon cuts it a detached worktree from the caller's head (C-6.6), so it may be submitted from a checkout on `main`, and the caller's HEAD, index and files are untouched. Any push of a salvage ref to a branch named `main` or `master` is refused.
- **C-13.3** Before a new attempt on a writable job, the daemon reconciles: salvage if dirty, record the salvage ref and the current head as the checkpoint, and start the next attempt from the same worktree with a prompt suffix naming the checkpoint. A limit hit after an hour of work loses nothing committed or salvaged.
- **C-13.4** Lane worktrees the daemon allocates live under `$SUBFLEET_HOME/worktrees/`, never `/tmp`. They are removed only after the job is terminal, its salvage ref exists if the tree was dirty, and retention selects them.

## 15. Notices and waiting

- **C-15.1** Every terminal job except a conversation turn writes a `notices` row for its caller session in the same transaction as the terminal state; a turn's outcome is its message's state (C-24.1), which the app shows. Notice text: job id, outcome class, rc, deliverable path, `-o` path if any, one summary line, and any uncertainty (`quarantined`, export failed, unattested).
- **C-15.2** Delivery layers, most to least reliable: `subfleet wait` in a background Bash call; a PostToolUse `asyncRewake` hook (milestone 4); SessionStart and UserPromptSubmit hooks surfacing rows with state `pending` or `offered` (inside a process Subfleet launched, only rows that name a job; C-26.13); a best-effort socket push through the v1 mechanism, kept until tickle, muster, and `ping` have tested replacements.
- **C-15.3** Notice states: `pending` (written), `offered` (a delivery attempt was made; transport recorded), `acknowledged` (`notice.ack` from the session, or the session ran `runs show <job>`), `surfaced` (printed by a hook). A notice may be offered more than once; it is acknowledged once.
- **C-15.4** `wait` is a server-side long poll with a per-call deadline of at most 60 s; the CLI loops until the job set is terminal or `--timeout` expires (exit 124). `wait` never wakes headless lanes and never targets a lane session.
- **C-15.5** `wait` has one reader, the wait hub (`subfleet/waits.py`). A waiter registers the jobs it waits on before its first read, reads its answer when it starts, and reads again only when the hub wakes it; it never re-reads on a timer or on another waiter's wake-up. The hub looks at the store's generation (C-5.11) when poked by `Daemon._notify` and otherwise every `WAIT_POLL_S` (0.1 s). When the generation has moved, a waiter has registered, or `WAIT_RECHECK_S` (1 s) has passed, it reads the state of every watched job and which of them hold an `out:` lease, one statement each whatever the number of waiters, and wakes each waiter whose jobs may all be returned: ended, a succeeded job's export done, or unknown to the store (the waiter then reports the unknown job, as it always did). So a wait returns within `WAIT_POLL_S` plus one read of the commit that ends its last job, poked or not; waiting costs one read per commit for all waiters together; and because registration comes before the first read, no wake-up is lost. A hub read that fails wakes every waiter to read for itself. A stopping daemon wakes every waiter, which answers `{"timeout": true}`. Incident: on 2026-09-25 ~21 PostToolUse hooks each held a `wait`, and every worker pass woke every waiter to re-read its jobs behind the store lock.
- **C-15.6** A hook costs one connection per question and no inspection. Its client does not check `daemon.lock` before connecting (`Client(verify_lock=False)`): that check costs a `ps` and a `sysctl` per process, and the PostToolUse hook runs on every Bash call of every session, while a hook exits 0 silently whichever way the daemon is down, which a refused connection already says. Its reads (`list`, `notice.pending`) are C-16.5's lookups.

## 16. Socket protocol

- **C-16.1** Unix domain socket at `daemon.sock`, mode 0600. Newline-delimited JSON, one request then one response per line. Request: `{"v": 1, "id": "<client string>", "op": "<op>", "args": {...}}`. Response: `{"v": 1, "id": "<same>", "ok": true, "result": {...}}` or `{"v": 1, "id": "<same>", "ok": false, "error": {"code": <exit code>, "message": "...", "fix": "..."}}`. The daemon raises its open-file soft limit to 4096 at start (never past the hard limit; launchd starts it with 256), serves at most 512 connections at once, each holding a reader until its client closes, and answers a connection past that at once with exit 69 and "try again shortly" rather than queueing it (logged at most once a minute); a `wait` has a thread for every connection that could send one. A client whose request write fails because the daemon already answered and closed still reads that answer. `accept` failing for want of descriptors or memory (EMFILE, ENFILE, ENOBUFS, ENOMEM), on a connection its client abandoned, or on an interrupted call, is logged at most once a minute and the daemon keeps serving; failing without a break for 300 s, the daemon exits so launchd starts a fresh one.
- **C-16.2** Ops: `submit`, `list`, `show`, `wait`, `kill`, `lanes`, `readings`, `why`, `notice.pending`, `notice.ack`, `notice.mark`, `ping`, `daemon.status`, `gate.start`, `gate.poll`, `gate.continue`, `sessions`, `pick`, `operations`, and the section 25 ops. Argument and result shapes are the dataclasses in `subfleet/protocol.py`, except the section 25 ops', which are design §5's (C-25.2); unknown fields are ignored, missing required fields are exit 2.
- **C-16.3** `submit` returns `{job_id, request_id, created: bool}` where `created: false` means an existing job matched the request id. `wait` returns the terminal states of the requested jobs or `{"timeout": true}` after the deadline.
- **C-16.4** The daemon serves requests on a thread pool; a request handler never blocks on a provider process, a probe, or `ps`. Long-running work is queued to workers with deadlines.
- **C-16.5** A liveness question and a hook's reads never queue behind slow requests. `ping` without `text` reads nothing and is answered on the connection's own thread. `list`, `show` and `notice.pending` (`LOOKUP_OPS`) run on their own 8-thread pool, `subfleet-read`; `wait` on the waiters' pool; `submit` and `gate.*` on the workers; conversation ops on the conversation pools; every other op on the 16-thread request pool, where view builds and writes that wait for the store lock stay. With C-3.7 none of the lookups waits for a transaction either, nor longer than `READ_WAIT_S` for a read connection, and snapshots cannot take the connections kept for them. Incident: 2026-09-25, all 16 request threads were busy and a `ping` took up to 90 s.

## 17. CLI

- **C-17.1** Verbs (v1 spellings permanent, plan amendment 1): `subfleet` and `subfleet status` (table), `run`, `runs [--mine] [--running] [--last N] [--kind K | --include-turns] [--json]` (turn jobs only when asked, C-26.12), `runs show <id> [--out|--err|--json]`, `runs reap` (reconcile now), `wait <id>... | --mine | --last [--timeout S]`, `kill <id> [--wait] [--confirm-dead|--force-release]`, `resume <id> [PROMPT]`, `lanes [list|probe|enroll <credential>|hold <lane> --until|release <lane>|transfer <lane> --to v1|v2]`, `why <id> | --task T --tier X`, `daemon [start|stop|status|logs|install]`, `doctor [--live]`, `ping [--session ID] TEXT`. Aliases: `jobs` for `runs`, `show` for `runs show`, `capacity` for `status`, `notify` for `ping`, `resume-codex` for `resume`. Also first-class and permanent, from v1: `gate [pr|plan|continue]` with its 0 to 5 exit codes, `sessions [list|continue|revive|mirror]`, and `handoff <session> --to <model>`; they dispatch to the `subfleet-gate` and `subfleet-sessions` entry points. `doctor --guard-check <payload>` runs the never-rules check as a dry run that writes no denial log (C-23.24). The bare `runs show <id>` keeps v1's output shape, which agents parse today: the metadata object, then a `--- out.md ---` line and the deliverable; `--out`, `--err`, and `--json` are v2's single-artifact forms and print one thing each.
- **C-17.2** `run` flags: `--task`, `--tier`, `-m`, `-a EMAIL` (a Claude account), `-H CODEX_HOME` (a Codex home; either may name a lane id instead, and the flag's provider narrows a name, C-11.2), `-C DIR`, `-p PROMPTFILE`, `-o OUT`, `-n NAME`, `-s SANDBOX`, `-x EMAIL` (repeatable), `--allow-desktop`, `--allow-tmp`, `--in-place`, `--independent`, `--parent JOB`, `--request-id ID`, `--wait`/`--attach`, `-d`/`--detach` (default inside a Claude session), `--batch FILE` (C-17.7), `--json`, `--dry-run`, `--why`, `--no-preamble`, `-I` (isolated review; requires `-s read-only` and `-D`; C-23.2), `-D REVIEW_ROOT`. Deprecated but accepted through milestone 8 with a stderr note: `-t CLASS`, `--overflow`, `-m sol` (remapped to `astra`).
- **C-17.3** Exit codes, one meaning each across every verb: 0 ok · 1 operational error · 2 invalid input · 3 no lane: no attempt could be admitted (message names the earliest reset) · 4 hard limit: the job's final attempt was `limited` and no candidate or attempt remained, whether or not a lane was pinned (message names the closure's clock) · 5 auth dead · 6 provider CLI too old · 7 refused (message names the rule and the fix) · 69 daemon unavailable · 75 queued (only with `--json` and `--no-wait-queue`) · 124 wait timeout · 125 job lost · 130 cancelled. `wait` and `--wait` return the job's rc when it is one of these; a provider rc outside the table maps to 1 with the raw rc in the message.
- **C-17.4** Stdout carries the contract (job id on `run`, the table on `runs`, the deliverable on `runs show --out`); human progress goes to stderr; `--json` emits one JSON object per line and no prose.
- **C-17.5** Offline mode: when the daemon is unavailable, `runs`, `runs show`, `status`, and `kill` work by reading the store read-only and the receipts, and `kill` signals the recorded pgid only after C-5.3 identity checks; everything else exits 69 and prints `subfleet daemon start`.
- **C-17.6** `run` inside a Claude Code session (detected as v1 does, by the session registry and env) defaults to detached and prints the four-line hint v1 prints (out path, log path, wait command, status command).
- **C-17.7** `run --batch FILE` submits every job in a manifest in one call and labels them as one batch. The manifest is TOML when the file ends `.toml` and JSON otherwise (both in the standard library; the package takes no dependency): an optional `label` (default: the file's stem), an optional `defaults` table, and `jobs`, a non-empty list of at most 256 tables; a bare JSON list is `jobs`. A table says nothing `run` cannot. Its keys are `task`, `tier`, `model` (`-m`), `account` (`-a`), `codex_home` (`-H`), `workdir` (`-C`), `prompt` (`-p`), `prompt_text`, `out` (`-o`), `name`, `sandbox`, `exclude`, `allow_desktop`, `allow_tmp`, `in_place`, `independent`, `parent`, `no_preamble`, and `allow_unmeasured_reserve`; an unknown key is exit 2. Precedence is the entry, then `defaults`, then the other flags on the same command line. Relative `workdir`, `prompt`, `out`, and `codex_home` paths resolve against the manifest's directory, so a folder of briefs moves whole. A job with no `name` is named after its prompt file. Every entry passes `run`'s own client-side checks before the first submit; if one fails, nothing is submitted and the message names the entry (exit 2, or 7 for a client-side refusal). After that the entries are independent: a submission the daemon refuses is reported and the rest still go, because a caller handing off K threads wants the K-1 that can run to run; the exit code is the first failure's, else 0. A daemon that stops answering ends the batch with exit 69 and the count already submitted. Stdout carries the job ids, one per line in manifest order, and with `--json` one object per entry (`batch`, `label`, `index`, `name`, `workdir`, `request_id`, `job_id`, `rc`, and `error` and `fix` for an entry that was not submitted) (C-17.4); stderr carries the table and the `wait` command for the whole batch. `--wait` and a synchronous `run` wait for every submitted job. `--dry-run`, `--why`, `-p`, and a positional prompt describe one job and are exit 2 with `--batch`. Without `--request-id` each entry gets a fresh request id. With `--request-id ID` the batch id is `ID` and entry n is `ID-n`, so submitting the same manifest again after a partial failure adds nothing twice (C-6.2); an in-place entry whose checkout has since moved is reported as a different payload rather than resubmitted, because the digest covers the git head. The daemon records `{id, label, index, size}` in the `job.submitted` event and in `manifest.json`, returns it as `batch` on `show` and on each labelled row of `list`, and refuses a malformed one with exit 2. It is a label for people and the menu bar app: it is not a column, not part of the payload digest, and never an input to routing; a daemon that predates it ignores the field (C-16.2).

## 18. Timers (milestone 5, interface only here)

- **C-18.1** Probe cycles wait `probe_interval_s` after the preceding cycle completes (default 60 seconds), with one probe per idle, enabled, unlatched lane per window (an `auth-dead` lane is not probed until re-enrolment and a revoked-token lane not until its credential epoch changes; C-23.44, C-23.47). - **C-18.2** `status.json` also carries `jobs`, so the menu bar app shows work as well as quota: `live` (every `running`, then `waiting`, then `queued` job, oldest first within a state), `recent` (the 8 most recently finished jobs), and `counts` by live state, all three of detached work only: a turn job (kind `turn`, C-26.1) is its conversation's (C-26.12) and is shown under `conversations` (C-29.6). [milestone 9; owner fake; module `subfleet/conversations/reconcile.py`]
- **C-24.7** (stop is scoped and ends the turn) `message.cancel` withdraws a message only before its job has an attempt, checked in the transaction that records the cancel. Withdrawing an id the daemon never received (naming its conversation) records a tombstone that is cancelled in the transaction that creates it; a later `message.submit` of that id returns the tombstone and nothing is dispatched (review IR-7). `turn.interrupt` targets only that message's attempt and escalates as design D-13: the provider's interrupt, SIGINT to the provider child through its guardian's relay, closing stdin, and only then C-5.6 containment. Each later step is taken only while the turn has no terminal event, at policy `conversations.stop_sigint_after_s`, `stop_close_after_s` and `stop_contain_after_s` seconds after the stop was requested (defaults 10, 20, 30); the policy loader refuses a value that is not a positive finite number and an order other than SIGINT before closing before containment. No other conversation, job, or process is signalled. [milestone 9; owner fake; module `subfleet/conversations/service.py`]
- **C-24.8** (an unfinished Claude turn blocks) A Claude attempt that ends without `result` after its message was delivered (C-24.6: acknowledged, or in the session transcript; review IR-5), including a stop that got no `result` and a driver's own stop (a model mismatch) that no `result` followed, sets the conversation `blocked_by: "unfinished-turn"`; a written message frame whose delivery is unknown blocks it as `delivery-unknown` (C-24.6), and a person's `message.resolve` of a Claude message as `delivered` turns that block into `unfinished-turn`; the next message waits for a person's `conversation.unblock` (`continue` or `leave`), recorded. `leave` sends a one-line note ahead of any queued message, so the next turn does not resume the stopped work; `continue` sends nothing. [milestone 9; owner fake; module `subfleet/conversations/reconcile.py`, `subfleet/conversations/service.py`]

## 25. Protocol additions

- **C-25.1** (discovery before mutation) `capabilities` returns protocol version 1, the daemon version, `conversation_schema` 1 (the version of the conversation ops' argument and result shapes, C-25.2, which is not the conversation store's schema, C-26.14), capability names and limits. A client sends no conversation op to a daemon that answers "unknown op", and sends a field whose silent omission would change an outcome only after the daemon advertised it. `PROTOCOL_VERSION` stays 1. [milestone 9; owner unit; module `subfleet/protocol.py`]
- **C-25.2** (the ops) The conversation ops are `capabilities`, `conversation.list`, `conversation.open`, `conversation.create`, `conversation.settings`, `conversation.unblock`, `conversation.history`, `conversation.events`, `conversation.watch`, `message.submit`, `message.status`, `message.cancel`, `turn.interrupt`, `message.resolve`, `approval.list`, `approval.get`, `approval.respond`, `attachment.add`, `catalog.refresh`, `models.list`, `conversation.runs`, `turn.diff` and `conversation.diff`, listed in `subfleet/protocol.py` (`CONVERSATION_OPS`) and answered by `subfleet/conversations/service.py`, with the arguments and results of design §5. Receipts from `conversation.open` and `message.status` carry the message's `text` (at most 20,000 characters, `text_truncated` when cut), so a client that did not send a message can show it. Errors are `ok: false` with an `Exit` code. An op added to this list is advertised by a `capabilities` name (`diff.v1` for the two diff ops, `runs.v1` for `conversation.runs`), not by a new `conversation_schema`. [milestone 9; owner unit; module `subfleet/protocol.py`]
- **C-25.3** (handlers never wait) A conversation op handler validates, writes at most one transaction per store (a worktree conversation's create writes its row, then its worktree), wakes the control loop, and returns. It never waits on a provider, a probe, `ps`, git, or a catalog scan (C-16.4), with two exceptions: `turn.diff` and `conversation.diff` run git (C-26.14), and `conversation.create` of a worktree conversation runs git to cut its worktree (C-26.10, design D-16). Those three ops (`conversation.create` whatever its workspace kind), file copies and transcript reads run on a dedicated bounded pool (the file pool), never on the pool the other ops and the session hooks use. [milestone 9; owner fake; module `subfleet/daemon.py`]
- **C-25.4** (a bounded cursor, batched writes) `conversation.events` returns events after a sequence number, long-polls at most 50 s, cuts a page at 256 KiB, and says `reset: true` exactly when the cursor is below the conversation's compaction floor (a cursor of 0 included), the highest sequence number compaction removed; each page carries the floor. Compaction removes an attempt's `text.delta` and `thinking.delta` rows, only once the job store has ended the attempt (not `quarantined`), no runner reads it, and its message has been terminal for `conversations.compact_after_s` (default 300 s), at most `conversations.compact_per_tick` (20) attempts per control-loop pass; a replay never stores a removed delta again (review IR-6). Driver output is written at most once per attempt per 250 ms or 64 KiB. It is polling with a wake-up, and no document calls it streaming. [milestone 9; owner fake; module `subfleet/conversations/events.py`]
- **C-25.5** (events and results carry only what a person may see) Events and op results hold user-visible text, provider-displayed reasoning, tool names, scrubbed input summaries of at most 500 characters and scrubbed result previews of at most 2 KiB; a credential-reading call is shown as hidden. Codex raw reasoning, Claude redacted thinking and signatures, and credentials never appear in them. Unscrubbed provider content at rest (attempt stdout, `stdin.jsonl`, prompts, message text) is 0600 in 0700 directories, retained under C-28.2, and never exported or put in a notice. Approvals are shown in full with token-shaped values masked in place (C-27.1). [milestone 9; owner unit; module `subfleet/conversations/redact.py`]
- **C-25.6** (person-only operations) `approval.respond`, `approval.get`, `message.resolve`, `conversation.unblock`, and any settings change that widens the permission policy or sets `allow_main` are refused (exit 7) when the caller (by `LOCAL_PEERPID`) or an ancestor is a live guardian's descendant or carries the C-5.1 markers, and accepted only from the installed app's executable (the kernel's path for the process, `proc_pidpath`, never a split command line) or a process with a controlling terminal; a daemon on any state root other than `~/.subfleet` also accepts the development build that `SUBFLEET_DEV_APP_EXECUTABLE` named when it started (design D-21). Approval nonces appear only in person-only results. [milestone 9; owner process; module `subfleet/conversations/peers.py`; design D-8]

## 26. Turns under admission

- **C-26.1** (a turn is a submission the daemon makes) Each turn is a job of kind `turn` with request id `turn:<message id>:<n>`, created only by the daemon's dispatcher through the ordinary submit validation, with `max_attempts` 1, no parent, `in_place` in the conversation's workspace, and the message digest as its payload digest. It is admitted by `evaluate` inside the reserving transaction like any job (C-6.3; C-23.54's one dispatch path). The socket `submit` op refuses `kind: "turn"` and request ids beginning `turn:`. A turn submit the daemon refuses before the job exists sent nothing: a refusal of the message as it is (exit 2 or 7, such as a checkout on `main` without `allow_main`, a missing attachment, or a model the fleet does not route) fails it `not-delivered: <reason>`; any other refusal (exit 1, such as git timing out while inspecting the workspace, or a store or file error) leaves it in its state with `state_reason` `deferred: <why>`, submitted again after 2 s, then 4 s, doubling to at most 300 s, never on every pass. A message withdrawn while its job is being submitted takes that job with it (C-24.7). [milestone 9; owner fake; module `subfleet/conversations/dispatch.py`, `subfleet/conversations/service.py`, `subfleet/daemon.py`]
- **C-26.2** (routing by provider) A Claude turn routes by model across Claude lanes whose credential resolves to the default config directory (`keychain-token`, `env`); a `home`-kind Claude lane is not a candidate (`config-dir`). A Claude turn prefers the lane that served the conversation's previous turn while that lane stays eligible, and each move is recorded with its reason. A Codex turn is pinned to the lane whose home holds its thread; a new Codex conversation's first turn routes by model and pins the conversation to the lane it ran on. [milestone 9; owner fake; module `subfleet/scheduler.py`]
- **C-26.3** (one writer per native session) A turn holds `conversation:<id>` and `native:<provider>:<native session id>` from reservation through finalization or quarantine. Resume, revive and handoff reservations wait while either is held, and `resume` refuses a `turn` source. A live process outside Subfleet holding the session (Claude: a pid in `~/.claude/sessions/*.json` naming it, without Subfleet markers and not an owned identity; Codex: the thread reports an active turn) is an admission wait `external-writer`, shown to the person. Conversation-bound sessions are never listed, nudged, revived, cold-swept or handed off by the sessions kit (C-26.13). [milestone 9; owner fake; module `subfleet/conversations/dispatch.py`, `subfleet/daemon.py`, `subfleet/sessions/`]
- **C-26.4** (the guardian relays, it does not interpret) A turn's guardian owns the provider's stdin as a pipe and accepts connections on `run/<16 hex>.sock` (0600 in a 0700 directory) only from the process `daemon.lock` names (pid, boot id, start time). Frames carry a number, a tag and the SHA-256 of their line; each is logged as an intent with fsync before the pipe write and then as `written` or `failed`. A resent number is acknowledged as a duplicate only when its hash matches a written frame; other content is a conflict; a failed or unfinished write is never reported as applied and ends relaying. It never parses provider messages. The relay advertises its version and frame cap in `start.json` and answers `status`, which is not a frame (no number, never logged, answered only after any frame being applied is logged), with the frames applied, whether stdin is closed, whether the child runs, and the cap. A runner asks for it before it sends or replays anything and then sends nothing on a guess: a relay whose count differs from its log, or whose log shows a frame not written, is not written to; a relay that answers `status` as a malformed frame (version 1) is read from its log as before. `message.submit` refuses a Claude message whose text and images cannot fit one frame (`capabilities` limit `relay_frame_bytes`); a frame over the cap is never sent, stdin is closed instead and the turn is reconciled (C-24.6). An unanswered frame or `status` is retried at most 5 times after doubling pauses; then, as after `conflict` or `failed`, nothing more is written and a turn without a terminal event is stopped as C-24.7 escalates, skipping the steps that need the relay. stdout and stderr remain files; `exit.json` still ends the attempt (C-5.1). [milestone 9; owner process; module `subfleet/relay.py`, `subfleet/guardian.py`, `subfleet/conversations/runner.py`]
- **C-26.5** (a turn's end) The provider's terminal event (Claude `result`; Codex `turn/completed`) ends the turn, after which the daemon closes stdin. Output after it is attached to the same message and never changes the outcome. A Claude turn launches with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=120000` and without `Monitor`, `CronCreate`, `ScheduleWakeup` and `RemoteTrigger`; a process alive policy `conversations.after_result_s` seconds after its terminal event (default 135: the ceiling plus 15 s) is stopped as C-24.7 escalates. [milestone 9; owner fake; module `subfleet/conversations/runner.py`]
- **C-26.6** (drivers replay) Turn drivers are pure: the daemon rebuilds one after a restart by replaying the attempt's stdout; a frame whose tag the relay log shows as written is not sent again; events are unique by `(attempt, source, position, ordinal)` with no NULL part and are not stored at or below the attempt's watermark. [milestone 9; owner unit; module `subfleet/conversations/claude_turn.py`, `codex_turn.py`, `runner.py`]
- **C-26.7** (limits end the turn; continuation is new) A limit or credit refusal after a message reached the provider ends the turn `failed` (`limited`); its closure is recorded at finalization (C-9.6) before anything else is submitted. With the conversation's `auto_continue` on, a Claude conversation gets a continuation message (new id, `origin: failover`, fixed text, excluding the limited lane), one per limited message and at most two per original message, written before the limited message shows `failed` (it cannot run while that message is live), ahead of any queued person message; the original message is never sent again. A Codex conversation waits for its lane. [milestone 9; owner fake; module `subfleet/conversations/dispatch.py`, `subfleet/conversations/service.py`]
- **C-26.8** (served facts, not requested ones) Each turn records the lane, account label, served model, effort, and Fast state the provider reported. Settings are validated against the provider's own catalog for that account before the message is sent (design D-19): the lane's claimed account is its email label (C-1.4), compared with the email Claude's `initialize` reports; a Claude model is a catalog value (`opus[1m]`) or a model id, resolved through the entry with that value or else the entry that resolves to the model admission routed to; a Codex turn always asks for the routed model id; a served model that differs from the request (after removing `[1m]`, ignoring `<synthetic>`) ends the turn `failed` (`model-mismatch`). A turn attempt is classified from structured provider evidence only (design §7), never from prose. `models.list` reports what each provider's catalog offers; a value not yet observed is checked by the driver before the message is sent. Claude Fast is shown as billing usage credits and needs a per-conversation confirmation; a served Fast state that differs from the request is a visible warning. [milestone 9; owner fake; module `subfleet/conversations/claude_turn.py`, `codex_turn.py`, `classify.py`]
- **C-26.9** (attended turns: first, not reserved) Turn jobs sort ahead of detached jobs of the same tier; a turn that is not placed never enters the detached jobs' waiters, holds none of them `behind-older-job`, and causes no `slot-kept`. Turns trigger no admission probe; a lane whose verdict would require one is not a candidate for a turn (`probe-required`). Turns have their own capacity, counted apart from detached jobs: at most `conversations.max_active_turns` (3) turns at once across the fleet and `conversations.turn_slots_per_lane` (1) on one lane; detached jobs count only detached attempts against `max_active_attempts` and `max_in_flight_per_lane`, and a full pool holds back only its own kind, so an attended turn never waits for a background job's slot (the installed daemon's first turn, 2026-09-24, waited on `no-slot` on every open Claude lane while detached jobs held them). A turn waiting on an approval longer than policy `conversations.approval_wait_s` (default 3600) is stopped with reason `approval-timeout`. [milestone 9; owner fake; module `subfleet/scheduler.py`, `subfleet/daemon.py`]
- **C-26.10** (attended workspaces) A conversation's workspace may be outside git. A checkout on `main` or `master` requires the conversation's `allow_main`, set by a person (C-25.6). A writable turn (Claude `accept-edits`, a writable Codex turn) is refused (exit 7) when its workspace equals or contains the state root, `~/.claude`, `~/.codex`, an enrolled lane home, or the guard hook's directory. Turn jobs write no salvage ref, at finalization or when a quarantined turn is released (C-5.7); the receipt records HEAD before and after, and a writable turn's working tree is written as tree objects at its start and end, with no ref (C-26.14). C-13.1 and C-13.2 keep binding every job that is not a turn. A worktree conversation (design D-16) is cut by `conversation.create` on branch `subfleet/<conversation id>` at `<state root>/worktrees/conversation-<conversation id>`; the store's update records the worktree on its row (path, branch, source directory, repository, base commit), every conversation view returns it, and the conversation's workspace is the worktree (the same subdirectory when the person picked one). Repeating the create with the same request id finishes a cut that failed or was interrupted, adopting a worktree already on that branch; until then the conversation refuses `message.submit` (`worktree-missing`) and never dispatches in the checkout it was to be cut from. [milestone 9; owner fake; module `subfleet/conversations/dispatch.py`, `subfleet/conversations/service.py`]
- **C-26.11** (the never-rules hook applies to turns) Every Claude turn outside `read-only` passes `--settings` with `"disableAllHooks": false`. Every Codex turn runs only after the C-14.2 preflight and the same-server `hooks/list` check of design D-10, and carries every guard flag an exec launch carries (C-23.6). Codex turns are `read-only` until a live test shows the hook denying a forbidden command and an `apply_patch` in an app-server turn. The Codex thread is opened read-only and a turn leaves no project-trust entry in a lane's `config.toml`. [milestone 9; owner live; module `subfleet/conversations/claude_turn.py`, `codex_turn.py`]
- **C-26.12** (turn jobs are the conversation's) A turn job creates no caller notice, exports no deliverable, and is retained under its own budget (policy `retention.turn_jobs`, default 2,000 jobs, and `retention.turn_bytes`, 4 GiB), separate from C-8.4's, so neither kind of job is pruned to make room for the other: pinned while its message is non-terminal, its conversation blocked, or a live runner reads its attempt (the conversation service answers, and retention asks again inside each delete transaction), and for `retention.turn_keep_days` (14) after it ends (review IR-17). It is not detached work: `list` leaves turn jobs out unless the request names a `kind` (`turn` lists only turns) or sets `include_turns`, and refuses a malformed filter (exit 2), so `runs`, `wait --mine` and `wait --last` never resolve to one; an explicit job id still reaches it, and `runs reap` still reconciles it. `status` shows live turns under their own line and heading, never as running or waiting jobs, and `why` names a turn as its conversation's. The daemon advertises the filter as the capability `jobs.kind.v1` (C-25.1), and `runs` sends `kind` and `include_turns` only after `capabilities` listed it. Against a daemon that does not (one older than `capabilities` answers "unknown op"), `runs --kind` exits 69 naming the restart without asking for the list, `runs --include-turns` sends neither field because such a daemon lists every kind, and `runs` drops the turn rows it returns (every row carries `kind`) and says on stderr that the list may be short when `--last` was applied first. `runs` also drops any row whose `kind` contradicts the request, whatever the daemon advertised. [milestone 9; owner unit; module `subfleet/retention.py`, `subfleet/conversations/service.py`, `subfleet/daemon.py`, `subfleet/cli.py`, `subfleet/offline.py`, `subfleet/render.py`]
- **C-26.13** (a conversation's session is not the sessions kit's) Inside a process Subfleet launched, one whose environment carries a C-5.1 marker (`SUBFLEET_ATTEMPT` or `SUBFLEET_JOB`), `subfleet hook SessionStart` hands no wake to the sessions kit, and `SessionStart` and `UserPromptSubmit` surface and mark `surfaced` (C-15.3) only the notices that name a job (C-15.1); a notice that names no job (a `ping`, a sessions-kit nudge, a timer alert, an imported v1 continuation) is neither printed nor marked there and stays pending. Every launch path sets `SUBFLEET_ATTEMPT`; the guardian passes the markers to the provider, and Claude Code passes them to its command hooks (observed with 2.1.280, new and resumed sessions, `-p` and stream-json input). A job that `subfleet run` submits from a turn's Bash tool names the session in `CLAUDE_CODE_SESSION_ID` as its caller (`cli.session_id`), the conversation's, so when it ends after the turn its notice reaches the conversation's next turn by this layer: `PostToolUse` (C-15.2 layer 2), which runs there unchanged, as does `PreToolUse`'s attached-runner guard (C-23.54), waits only on jobs still running, and a turn's process does not outlive its result by more than C-26.5 allows. The `sessions` op's `state` reports `conversation_sessions`: every native session id a conversation binds, archived or not, and every one a turn attempt ran; `lane_sessions` (C-23.31) still leaves turns out, because a turn may resume a session Subfleet did not create and is no lane run. A `state` reply without `conversation_sessions` comes from a daemon older than this clause, which may already run conversations (`PROTOCOL_VERSION` stays 1, C-25.1): every sessions-kit verb that reads it exits 69 with the fix `subfleet daemon stop && subfleet daemon start`, as for an op the daemon does not know, and never reads the silence as an empty list. The sessions kit never lists, nudges, revives, cold-sweeps or hands off one of these sessions, whatever `--all`, `--revive`, `--force` or `--dry-run` say. A request that names only such sessions, or only such sessions and headless lane runs (C-23.31), is refused (exit 7, under `--json` too) by `sessions continue` in every scope (v1's `tickle`, `muster` and `revive` spellings included), by `sessions revive` and by `handoff`, with the reason, checked before C-23.31's lane check, and the fix to continue it in the Subfleet app; a request that also names other sessions acts on those and reports each refused one with its reason. A cold handoff checks each canonical session id against the daemon's lists again at handoff, and a refusal there holds only that session. The daemon refuses the same continuations whatever client asks: a `resume` whose source job is a turn or whose native session is one of these, and a `revive` of one, are refused at submit (exit 7) with that fix and nothing stored, and one accepted before its session became a conversation's is failed with exit 7 by the admission pass that would have launched it, before any lease or attempt. A retry of a request the daemon already accepted is answered as C-6.2 answers any retry (its job id, exit 0; exit 2 for another payload), not refused: the refusal at submit applies only to a request id no job holds. [milestone 9; owner fake; module `subfleet/hooks.py`, `subfleet/sessions/`, `subfleet/daemon.py`]
- **C-26.14** (a turn's changes) A writable turn (any permission but `read-only`) whose workspace is a git checkout with a commit has two snapshots of its working tree, each a tree object written through a temporary index by the C-6.8 snapshot, with no ref and with HEAD, the real index and the files untouched: the start is the one admission takes (the attempt's `baseline_tree`); the end is taken at finalization before the turn's leases are released, or when a quarantined turn is confirmed dead, and a forced release with writers still live records that it has none. Both are kept per attempt in the conversation store (schema 2; an older store is migrated in place, a newer one refused) and in the attempt's receipt; recording the end writes one `conversation.watch` row for the message with `state` null, which, as for an approval asked or answered, tells a client to fetch the message again. While git fails transiently the end is tried at most three times in one daemon run (a restart counts again), and once when a quarantined turn is released (an operator's request is not offered again); then the failure is recorded and finalization goes on without an end snapshot. `turn.diff` compares a message's latest turn attempt's start and end snapshots (the attempt recorded last: C-24.5 runs one turn of a conversation at a time) or, before the end exists, its start with the working tree now, saying so (`to.live`); `conversation.diff` compares the start of the conversation's first writable turn (the first recorded) with the working tree now. Both run on the file pool (C-25.3), use git's plumbing with no external diff driver or textconv filter, list at most 1,000 changed files with status and line counts (the stats count every changed file, not only those listed; if git's listing passes 4 MiB they count the files it listed, say `complete: false`, and `files_truncated` is true) and at most 512 KiB of unified diff (the UTF-8 text returned, measured after decoding and scrubbing) cut at a line with `truncated: true`, scrub the diff text (C-25.5) one line at a time, a hunk's line without its `+`, `-` or space prefix, including private-key lines that a hunk's edge, the cut, or a hunk header's function context separates from the armour line at either end, each replaced in its line so every hunk keeps its line counts, and take `path` only relative to the checkout's top level, naming a file or a directory (then every changed file under it) (exit 2 otherwise). With nothing to compare they answer `available: false` in the same shape with a reason (`no-turn`, `read-only-turn`, `no-snapshot`, `snapshot-failed`, `snapshot-pruned`, or `workspace-gone` when git can no longer open the workspace as a checkout, which is never reported as a pruned snapshot). Neither commits, stages, checks out, or writes a ref. [milestone 9; owner fake; module `subfleet/conversations/diff.py`, `subfleet/daemon.py`, `subfleet/conversations/service.py`; design D-25]

## 27. Approvals

- **C-27.1** (real requests, bound replies) A provider permission or question request becomes one approval bound to its attempt and the provider's request id, with the exact request stored (0600) and its SHA-256, a random nonce, and options from design §8; the message becomes `approval-needed`. The display includes every field that changes what is granted. `approval.respond` requires the approval id, the nonce, the request SHA-256 the person saw, a live attempt, and a decision among the options; a reply to an answered, withdrawn, or mismatched approval is exit 2, and a duplicate of the recorded reply returns it unchanged. [milestone 9; owner fake; module `subfleet/conversations/approvals.py`]
- **C-27.2** (never granted by Subfleet) No approval is answered without a person's `approval.respond` (C-25.6). No answer grants more than the provider asked: no permission updates, execpolicy or network amendments, and no one-tap allow where the provider requires interaction. The only change Subfleet makes to a request's input is adding `answers` to a question. [milestone 9; owner unit; module `subfleet/conversations/claude_turn.py`, `codex_turn.py`]
- **C-27.3** (approvals outlive the daemon) After a daemon restart pending approvals are re-derived by replay and remain answerable; a request the provider re-announces is matched by its id. A stopped, ended, or timed-out turn withdraws its pending approvals. [milestone 9; owner process; module `subfleet/conversations/approvals.py`]
- **C-27.4** (unsupported requests are refused, visibly) Provider requests Subfleet does not support get the refusal of design §8 or JSON-RPC -32601 and an `error` event; credential requests are never answered with a credential. [milestone 9; owner unit; module `subfleet/conversations/claude_turn.py`, `codex_turn.py`]

## 28. Attachments and drafts

A message names at most 8 attachments by hash; the driver re-checks size and hash before building frames. [milestone 9; owner unit; module `subfleet/conversations/attachments.py`]

An attachment is deleted only in a transaction that re-checks that no non-terminal message references it and it is 30 days unused, then unlinked. [milestone 9; owner frontend; module `app/Sources/ConversationStore.swift`]

## 29. The desktop client

- **C-29.1** (an explicit endpoint) The app connects only to `<SUBFLEET_HOME or ~/.subfleet>/daemon.sock` and reads only `status.json` and `catalog.json` there. It never runs a v1 executable, never reads the v1 state directory, never starts a broker, and never falls back to either. [milestone 9; owner frontend; module `app/Sources/DaemonClient.swift`]
- **C-29.2** (unavailable is a state) A daemon that is down, lacks `capabilities`, or reports another conversation schema shows an actionable status; drafts stay editable and journaled ops stay queued. Reloading `status.json` is labelled as reloading a snapshot, never as a new observation (C-18.1). [milestone 9; owner frontend; module `app/Sources/`]

## 30. Catalog and legacy continuity

- **C-30.1** (catalog out of process) Discovery of existing native sessions runs in a separate process with a 20 s wall-clock cap per run, writes `catalog.json` atomically with titles and prompts scrubbed, re-reads only files whose size or mtime changed, indexes every session (exclusions of lane runs and Codex exec or subagent rollouts come before any limit), and never writes a native store. The daemon never scans the Claude projects tree or Codex session trees on a request or control thread. The conversation service starts a run every `conversations.catalog_interval_s` (default 60 s; 0 means only on `catalog.refresh`) and on request, never waits for one, and stops a run still alive after 60 s by its process group. `conversation.list` answers whether `catalog.json` is absent, damaged or old, and reports its `state` (`absent`, `unreadable`, `stale` when older than three intervals, `fresh`), `age_s`, `stale_after_s` and `refreshing` (design D-23). [milestone 9; owner fake; module `subfleet/conversations/catalog.py`, `subfleet/conversations/service.py`]
- **C-30.2** (what continues in place) A Claude session in the catalog is continuable when it is not a lane run; a live process outside Subfleet makes it wait (C-26.3). A Codex thread is continuable only in an enrolled lane's home; a thread in `~/.codex` continues only by labelled handoff (C-30.3), because no lane owns that home and C-10.3 keeps the desktop login out of admission. [milestone 9; owner unit; module `subfleet/conversations/catalog.py`]
- **C-30.3** (handoffs are labelled) A cross-provider or out-of-home continuation is a new conversation whose first message is a scrubbed continuity brief (C-23.14; Claude transcripts and Codex rollouts both have brief readers) and which records `handoff_from` (provider, native id, transcript path, brief SHA-256). It is never presented as the same native session. [milestone 9; owner unit; module `subfleet/conversations/service.py`]
- **C-30.4** (legacy cockpit import) The v1 `outbox.sqlite3` is the legacy cockpit's message outbox, not a notice outbox, and `cockpit-client/pending-messages.json` its client's journal of unacknowledged sends (manifest rows `outbox` and `cockpit`, milestone 9). Each outbox message is classified individually by its row status, the cockpit's own: `finished`, `error` and `cancelled` are terminal, every other status is not. A terminal message of a Claude session whose transcript is found becomes a read-only history row of that session's one `origin: legacy` conversation, which is bound to the native id and created from the transcript as `conversation.open` creates a native conversation (workspace the transcript's cwd, design D-9's settings); the row keeps the legacy message id, has origin `legacy`, state `complete` (finished), `failed` (error, or a cancelled unknown delivery a person marked handled) or `cancelled` (withdrawn before dispatch), no job and no predecessor, and settings holding only what the outbox recorded. A history row is never queued or dispatched, and is written only ahead of every other message of its conversation. A non-terminal message, and every journal entry whatever the outbox says of its id (an entry is a send the cockpit app has not seen acknowledged), keeps its legacy owner and is reported, and so does every message of its session; a journal that cannot be read (an OS error, not JSON, not an object keyed by session) is never read as empty: it holds every session, while a missing journal holds none. The import never moves, queues or sends one. A conversation an earlier pass bound (one holding legacy history, or created by the import) whose session a later pass finds held is blocked `legacy-owner`, which keeps every turn off it (C-24.5), and reported `bound-session-held`; the first pass that finds its session settled lifts that block and reports `bound-session-released`. A pass never replaces another block and never lifts one it did not set. A terminal message that a pass cannot place (its session held, its transcript not found, a session that cannot continue here, a conversation that already has messages of its own, a session that is not Claude's) is reported with that disposition and imported by a later pass once that changes. Every message and journal entry appears in the report with its disposition, by id and never by content. Repeated imports create nothing new: history is idempotent by legacy message id. Notices an earlier import made from outbox rows stay as they are. `python -m subfleet.importer --legacy-cockpit [--dry-run]` runs these two rows alone and opens no `state.sqlite3`; a real run holds `daemon.lock` for its whole length and is refused while a daemon holds it; a dry run imports into a scratch copy of `conversations.sqlite3`; neither writes under the v1 state or a native transcript. [milestone 9; owner unit; module `subfleet/importer.py`, `subfleet/conversations/legacy.py`, `subfleet/conversations/store.py`]

Version 2, 2026-09-05 (version 1 earlier the same day; section 23 and the amendments listed under Changes were added at 13:50 EDT). This document binds milestones 1 to 3 of `plan.md`. Code is built against it; tests cite its clauses by number (for example `C-5.4`). A clause changes only by editing this file in the same commit as the code and tests that depend on it. ## 1. Identifiers and vocabulary

- **C-1.1** A job id is `YYYYMMDD-HHMMSS-<slug>` in local time, the v1 format, unique in the store. `<slug>` is the `-n` name or the task name, lowercased, `[a-z0-9-]` only, at most 40 characters.
- **C-1.2** An attempt id is `<job id>/a<seq>` with `seq` starting at 1.
- **C-1.3** A lane id is `<provider>-<n>` (`codex-4`, `claude-3`). Lane ids are stable; a lane whose account or credential is rebound gets a new id and the old one is disabled.
- **C-1.4** An account key is `<provider>:<account id>`. For Codex the account id is the `account_id` from the home's `auth.json` claims when present, else the email; For Claude it is `<account_uuid>:<org_uuid>` as returned by the provider profile endpoint (C-10.6) for the lane's own credential; the email is a display label and never the key.
- **C-1.5** A request id is a caller-supplied string or a CLI-generated UUID4, at most 128 characters, printed back on submission.
- **C-1.6** Providers are exactly `codex` and `claude`. Model names in policy are short names (`astra`, `opus`) mapped to provider model ids in `policy.json`.
- **C-1.7** Timestamps in the store are ISO 8601 UTC with a `Z` suffix and second precision unless a column says otherwise. Epoch seconds from providers are converted on write.

## 2. State root and files

- **C-2.1** The state root is `$SUBFLEET_HOME`, default `~/.subfleet/`. Nothing is written outside it except: job workdirs and worktrees the caller named or the daemon allocated under `$HOME`, salvage refs inside the job's git repository, the `-o` export path, and `~/.claude/settings.json`, which only an explicit `daemon install --hooks` writes (C-23.25), never a job or a timer. The guard preflight's scratch home lives under `$SUBFLEET_HOME/tmp/` (C-23.23) and its verified-verdict markers under `$SUBFLEET_HOME/guard-cache/` (C-23.5), or under the directory `SUBFLEET_CODEX_GUARD_CACHE` names: an absolute value is the operator's explicit choice, a relative value must resolve inside the state root and is refused otherwise; the markers hold hashes, paths and timestamps only. The lane transfer (milestone 4, `docs/migration.md`) is the other exception: it edits the v1 roster it names, with a backup beside it, and relocates a transferred Codex home between `~/.codex-<n>` and `lanes/<lane id>/` under the state root (C-10.4).
- **C-2.2** Contents: `state.sqlite3` (plus WAL and SHM), `policy.json`, `lanes.json`, `daemon.sock`, `daemon.lock`, `daemon.log`, `jobs/<job id>/`, `lanes/<lane id>/` (provider homes when a lane has one), `worktrees/`.
- **C-2.3** `jobs/<job id>/` holds `prompt.md` (bytes as sent, written once), `manifest.json`, and per attempt `a<seq>/` with `stdout`, `stderr`, `start.json`, `exit.json`, `deliverable.md`, `lane.log`, and any provider raw stream. Files are created with mode 0600 and directories 0700.
- **C-2.4** A workdir under `/tmp` or `/private/tmp` is refused at submission (exit 7) unless `--allow-tmp`.

## 3. Store

- **C-3.1** One SQLite database, `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, `busy_timeout=5000`. The schema is `subfleet/store_schema.sql`; `store.py` applies it and records `schema_version`. Migrations are additive and numbered.
- **C-3.2** Every state transition of a job, attempt, notice, lease, or action is one transaction, and every transaction that changes state also inserts an `events` row in the same transaction.
- **C-3.3** Transactions never span a subprocess call, a network call, a filesystem sync, or a sleep. Artifact copying, `ps`, `git`, and provider probes run outside transactions.
- **C-3.4** Readers other than the daemon (the CLI in offline mode, the menu bar app, Logpile) open the database read-only. Only the daemon and the guardian receipt path write, and the guardian writes files, not rows.
- **C-3.5** The CLI refuses to write to a store whose `schema_version` is newer than it knows (exit 1 with both versions).

## 4. Job and attempt state machines

- **C-4.1** Job states: `queued`, `running`, `waiting`, `succeeded`, `failed`, `cancelled`, `lost`. A `waiting` job has `wait_reason` in {`capacity`, `dependency`, `approval`, `uncertain`, `workspace`, `route`} and a `next_check_at`. Only `capacity` holds back the jobs behind it in its tier; a job waiting on its own `workspace` (C-6.8) or `route` (C-6.12) delays nothing else.
- **C-4.2** Attempt states and the boundary each one guards:

| State | Set when | Recovery if the daemon dies here |
|---|---|---|
| `reserved` | Lane lease, output lease, and any worktree lease taken; attempt row inserted | Release leases, mark attempt `failed` with class `unknown` and detail `reserved-no-launch`; the job may retry |
| `starting` | Guardian spawned; no `start.json` yet | If `start.json` holds a receipt, treat as `running`, and take an `exit.json` that holds one as in the `running` row, `start.json` or not; else wait `start_grace_s` (10) then run containment (C-5.5) on the guardian pid and read `start.json` and `exit.json` again, because the guardian can write both and exit while the census runs: a receipt found then is taken on the next tick as above; else if the census is empty, release and retry; otherwise (not verifiable, or not empty) `quarantined`. A receipt is a file whose JSON value is neither empty nor false (`{}`, `[]`, `null`, `0`, `false` and `""` are none), on each tick and in this re-read alike. Each receipt is written atomically, as an object; one that is not JSON, a corrupt one holding any other value, or a `start.json` missing a field makes the attempt's pass raise each time C-5.10 lets it run (0.5 s after the first failure, doubling to 60 s), and decides nothing. The pass stops there, before the cancel and `max_wall_s` checks, so a `kill` is recorded but not acted on until the file is repaired |
| `running` | `start.json` read: pid, pgid, boot id, proc start recorded | If `exit.json` holds a receipt, move to `finalizing`; else if the guardian is alive by (pid, boot id, proc start), re-adopt; if its identity cannot be inspected, leave the attempt for the next tick; if it is dead, read `exit.json` once more (the guardian writes the receipt and then exits, so a receipt can appear between the first read and the liveness check) and move to `finalizing` when it is there; else run containment; empty means `lost`, else kill survivors and re-check, else `quarantined`. A receipt present at finalization always wins over a `lost` verdict reached before it was read (incident: 2026-09-05, under a load average above 45 a job whose provider had exited 0 was recorded `lost` with its receipt on disk) |
| `finalizing` | `exit.json` read; classification, salvage, export, notice pending | Re-run finalization idempotently; every step checks for its own completed output before acting; a census that is not verified empty waits out `exit_settle_s` (C-5.9) before quarantining |
| `succeeded`, `failed`, `interrupted`, `lost`, `cancelled`, `quarantined` | Terminal | None; `quarantined` needs an operator action (C-5.7) |

- **C-4.3** A job has at most one `accepted_attempt_id`. Acceptance and the notice insert are one transaction. A result from an attempt whose `seq` is lower than the job's current attempt, or whose state is not `finalizing`, is never accepted.
- **C-4.4** A job whose final attempt ends without an rc is `lost`, never `succeeded`.
- **C-4.5** `max_attempts` default 3; a new attempt is admitted only for classes `limited` (next candidate), `transient` (same lane after 60 s, once, then next candidate), and `lost` on a read-only job. `auth-dead`, `cli-too-old`, `content-filter`, and any class on a writable job after the workspace changed require reconciliation first (C-13.3).
- **C-4.6** An attempt never changes lane or model. A new lane or model is a new attempt.

## 5. Process ownership and containment

- **C-5.1** The daemon spawns each attempt through `subfleet-guardian`, which calls `os.setsid()` so it leads a new session and process group, then spawns the provider command as its child with the same pgid, stdout and stderr redirected to the attempt directory, and an environment that contains the lane credential, the provider home, `SUBFLEET_ATTEMPT=<attempt id>`, `SUBFLEET_JOB=<job id>`, and `SUBFLEET_ROOT=<state root>`. The guardian never receives a secret in argv.
- **C-5.2** Before spawning the provider, the guardian writes `start.json` = {`guardian_pid`, `pgid`, `boot_id`, `proc_start`, `started_at`} via temp file and rename. After the provider exits it writes `exit.json` = {`rc`, `signal`, `finished_at`, `wall_s`, `child_pid`} the same way, then exits with the provider's rc. If the provider cannot be spawned, `exit.json` carries `rc: 127` and `spawn_error`.
- **C-5.3** Boot id is the stable `kern.bootsessionuuid` from `sysctl`; legacy receipts may carry `kern.boottime` seconds. Process start identity is the `lstart` column of `ps -p <pid> -o lstart=`. A pid is "the same process" only if both identities match. A legacy boot timestamp that differs from the current timestamp means unknown, not dead: macOS wall-clock correction can shift `kern.boottime` during one boot. Unknown identity never permits a signal or establishes death; a responsive daemon socket remains usable. Absent processes, reused start identities, and differing boot-session UUIDs still establish death.
- **C-5.4** The daemon may signal only a process group it recorded, and only after confirming the group leader's identity by C-5.3.
- **C-5.5** Containment enumeration collects live, non-zombie pids from three sources: the members of process group `<pgid>`; a walk of parent links descending from the guardian pid and the recorded child pid; and `ps -axEww -o pid=,command=` filtered on processes whose environment carries both `SUBFLEET_ATTEMPT=<attempt id>` and `SUBFLEET_ROOT=<state root>`. Attempt ids are a timestamp and a slug, so two daemons on one machine (or two test state roots) can mint the same id in the same second; the root is what tells their processes apart (incident: 2026-09-05, sleeping fakes from an earlier test quarantined a later test's attempt). "Verified empty" means all three returned zero live pids. If any `ps` call fails, the result is "unverifiable". The group and the walk are read from one `ps -axo pid=,ppid=,pgid=,stat=,lstart=` snapshot, so a process cannot be present in one of them and absent from the other because it exited between two reads. The snapshot's `lstart` is each live pid's start identity (C-5.3), so a census is two `ps` reads however many processes it finds, and one boot-identity read when it finds any (a census that finds none needs no `sysctl`, so a failed one cannot make it unverifiable); a pid the snapshot cannot describe (a marked process born after it) is asked about singly, and leaves the census if it is gone. A pid the snapshot does describe is not asked about again, so a census can include a process that exited just after the snapshot, where each used to be read again and dropped if gone. That errs only toward holding on: the kill protocol and C-5.9 read the census again until it empties, `--confirm-dead` can be repeated, and start grace, which reads it once, reads the receipts again after it (C-4.2). The census records, as evidence, the parent, group, and state of each pid in the census that the snapshot shows, never a command or environment.
- **C-5.6** Kill protocol: mark the cancel request; SIGTERM the pgid; wait `term_grace_s` (15); SIGKILL the pgid; enumerate (C-5.5); SIGKILL any survivors individually after re-checking identity; enumerate again, repeating for up to `kill_settle_s` (3) while the census is not verified empty, because signalled processes leave the process table only when the kernel finishes tearing them down and one read taken 50 ms after SIGKILL reports an exiting process as live under load (incident: 2026-09-05, two full-suite runs quarantined attempts that a rerun did not). The window ends early on the first verified-empty census and never widens what counts as contained. Verified empty releases the workspace and finalizes with `killed_by`. Anything else is `quarantined`.
- **C-5.7** A `quarantined` attempt keeps its leases (lane slot excluded), its workspace, and its worktree. `subfleet runs show` prints the evidence. Resolution is `subfleet kill <job> --confirm-dead` after the operator checks, which re-runs C-5.5 and releases only on verified empty, or `--force-release` which records the operator's override in `events`.
- **C-5.7a** A quarantined probe (C-11.4's admission probe, a timer's turn, a re-enrolment's turn) keeps its one lease, the lane slot `lane:<lane id>:slot:0` it reserved, where a quarantined attempt gives its lane slot back (C-5.7), and only C-5.5's census ends that: verified empty contains it and releases the lease, and anything else, an unverifiable census included, leaves it quarantined. There is no operator override for a probe: `kill --confirm-dead` and `--force-release` act on attempts only. It is looked at again on its own clock, not on every admission pass: the look that quarantines it, and each later look that leaves it quarantined, puts the next look `probe_recheck_delay(n)` after the n-th, 1 s after the first and doubling to a 60 s ceiling (`PROBE_RECHECK_BASE_S`, `PROBE_RECHECK_CEILING_S`), and a pass before then neither takes a census nor asks whether the guardian is still the recorded process (C-5.3). Evidence that changed between looks is recorded but does not restart the clock: only a verified-empty census can end the quarantine, and a process tree that keeps changing must not buy back a census on every pass. A look writes only what changed. A `probe.state` record is written only when it differs from the newest one kept for its holder in something other than a live pid's run state (the `stat` of C-5.5's evidence, which reads `R` on one look at a busy survivor and `S` on the next and says nothing about containment), and no writer appends a record exactly equal to the newest one kept. A quarantined record and its job's hold (`waiting`, `uncertain`) commit in one `probe.quarantined` transaction, so neither is kept without the other; a look that finds the record current but the job not held, as a store an older daemon left half-written can be, holds the job. So an unchanged quarantine whose job is held costs one census and one identity check per interval, and no row, no transaction, and nothing for a waiter to wake on (the store's generation, C-5.11, does not move). Its job stays `uncertain` with the `next_check_at` the last recorded look set, which is no longer pushed a minute ahead on every pass, so `why` and `status.json` can show it in the past; admission holds an `uncertain` job whatever that clock says (C-6.11), so nothing is looked at sooner for it. The clock is in memory, as C-6.10's records are: a restart looks at each quarantined probe on its first pass, and that look writes nothing the record already says. A holder's newest record is found in one step of the partial index `events_probe_holder` (`json_extract(data_json,'$.holder')` over the `probe.state` payloads `json_valid` accepts) together with the `probe.state` payloads `json_valid` refuses (`events_not_json`, normally none: a NaN or an Infinity, which `json.dumps` writes and `json_extract` would read as JSON5), which are parsed in Python as before; never by parsing every `probe.state` event ever written. The two indexes and the query are the release line's (its C-3.7), character for character, because both lines open one store and `CREATE INDEX IF NOT EXISTS` keeps whichever definition came first. It answers as the old walk did for every holder a caller can ask, with three named exceptions: a payload carrying `holder` twice, which no writer makes, is indexed under its first value and hides that holder's older records; a payload that is not a JSON object, which no writer makes either, is passed over where the walk raised; and asking for no holder at all finds nothing, where the walk returned the newest payload without one (every caller passes a lease's holder, which the schema makes non-null, or a `probe:` string minted beside it). Incident: the two reviews of PR #40 (2026-09-24 and 2026-09-27) found that every pass re-ran the census on a quarantined probe, appended a record and committed a transaction, and found the record by parsing every `probe.state` event: 20 unchanged passes took 20 censuses, 20 guardian checks, 20 records and 20 quarantine transactions, and materialized 210 historical rows. On 2026-09-27 from 09:58 to 11:33Z the installed release line held four probes quarantined at once, on censuses `ps` could not complete, and wrote 58 `probe.quarantined` events for them.
- **C-5.9** After `exit.json` is read, a census that is not verified empty does not quarantine at once. The daemon allows `exit_settle_s` (3), measured from the first such census, for the guardian, which writes the receipt just before it exits, and for processes it already reaped to leave the process table, re-running the census on each tick. Survivors or an unverifiable census past the window quarantine the attempt with detail `writers remain after exit receipt`.
- **C-5.8** The daemon holds an exclusive `fcntl.flock` on `daemon.lock` and writes its pid, boot id, proc start, and version there. A second daemon exits 69. The CLI treats a lock whose recorded identity is dead as no daemon.
- **C-5.8a** A stopping daemon that has not ended `stop_grace_s` (30 s) after its stop was armed normally writes the Python stacks of up to 100 of its threads, newest first (faulthandler's cap), to `daemon.log` and calls `_exit(1)`. An independent kernel `ITIMER_REAL` timer, installed first, delivers SIGALRM with its default terminating action at `stop_grace_s + STOP_DUMP_MARGIN_S` (33 s). The nominal three-second margin normally lets a working faulthandler finish its dump and exit first. Scheduling or timer-installation delay, slow I/O, and blocked writes can consume that margin. SIGALRM ends any process still alive at the kernel deadline, including one whose ordinary dump is merely slow or descheduled, so diagnostics may be absent or incomplete even after successful faulthandler arming. It needs no GIL, successful `Event.set`, watcher wakeup, or new thread at stop time. If the kernel timer cannot be installed, arming exits 1 immediately instead of continuing without a bound. `close()` still releases `daemon.lock` only after every pool has drained, so the store keeps one writer. The bound ends the process instead of releasing the lock early, and the kernel frees the flock with the process. No guardian is signalled, and forked children do not inherit the interval timer; the next daemon adopts attempts still running (C-4.2), as after a SIGKILL. One nonblocking claim, created at startup and never released, permits only the first `arm` invocation to install the timers. A handler interrupting that invocation returns without setting the event until arming completes, so it cannot deadlock the owner before timer installation. Later invocations cannot replace either deadline. The stop is armed on the thread that begins it, before `stopping` is set: `close()` and the end of `serve_forever` call `arm` directly. A SIGTERM or SIGINT arms when the main thread runs its handler; a thread holding the GIL can delay that handler indefinitely. The handler skips `Event.set` once the event is set. A signal nested inside `set` remains bounded by the already installed timers. The startup watcher arms when anything else sets `stopping`; it is not the fallback. The stopping-line write follows timer installation and can itself block, so the line is not guaranteed to precede the dump. launchd's `ExitTimeOut` (which `daemon install` writes as `stop_grace_s` + 10 s; with none set, `launchctl print` reports 5 s) and `subfleet daemon stop` each wait `stop_grace_s` + 10 s for stops they initiate. After its wait, `daemon stop` re-verifies the identity (C-5.4) and sends SIGKILL. Raw signals and self-initiated stops do not start either external backstop. The grace outlasts probe containment during a stop: SIGTERM, up to `term_grace_s` of census polling, then SIGKILL and one census. The descriptor for the dump is opened when the daemon starts, so a daemon stopping because it ran out of descriptors can still write. A daemon built inside a test process arms nothing. The bound can end a stop that is slow but healthy, including the session mirror's flag publish, which is not crash-safe; launchd's SIGKILL, a crash or an operator's kill already cut that window. (Incident: 2026-09-25, pid 93697 shut its socket and then waited without a deadline on pool threads parked in `RLock.acquire`. It held the lock until a restart at 19:26Z, while every client was refused and every replacement exited 69; `docs/reports/2026-09-25-daemon-stop-wedge.md`.)
- **C-5.10** A worker that raises is retried with backoff, not on the next tick. The control loop offers every live attempt, every pending export, and admission to the worker pool each tick (50 ms), and a worker that raised used to be eligible again at once, so a cause that fails fast (a repository git refuses, a store error) was retried, and logged, twenty times a second for as long as it lasted. Now a key the control loop offers (an attempt id, `export:<job>`, `admission`, `timer-recovery`, `retention`) is not run again until 0.5 s after its first consecutive failure, doubling to a 60 s ceiling; a success clears the count. A running attempt whose inspection raised gives back its inspection interval, so the retry repeats it (C-5.11, C-5.12). Until an inspection runs to its end, a retry that cannot inspect, or stops at the pacing gate, is deferred and neither clears the count nor adds to it; a receipt, cancel or wall limit still ends a pass successfully. A one-shot request is never paced: `resolve:<job>`, an operator's `kill --confirm-dead` or `--force-release`, is offered once, by the request itself, so holding it back would drop it after the caller was told it was accepted; it runs whenever it is asked for and its failure is logged each time. `daemon.log` gets the line on the 1st, 2nd, 4th, 8th (each power of two) consecutive failure, with the count and the next retry, and still only the exception's type, never its message (a provider or keychain error can carry a secret). The count is in memory: a restart forgives it, and recovery re-offers every live key as before (incident: 2026-09-20, `worker 20260920-081856-native-other-disability-opus/a1 failed: SalvageError` forty times in `daemon.log`; that cause was a git timeout, which paced itself at its own 15 s cap, and nothing in the daemon would have paced one that failed at once).
- **C-5.11** A running attempt or probe costs the daemon a bounded number of subprocesses, however often it is offered, and a tick costs a bounded number of store statements, however much history is kept. The control loop still offers every live attempt each tick (C-5.10) and still reads its exit receipt, its cancel request and its wall limit on each pass, and inspects a running attempt's processes as C-5.12 says, from one table every running attempt shares. A probe's wait loop, which has no shared table, reads its receipt, its job and its deadline every pass, and asks `ps` whether its guardian is still the recorded process (C-5.3) once every `inspect_interval_s` (1 s), and once more in a check that finds a new or changed group identity, to confirm the leader before recording it (C-5.4). It records the probe's owned group members from C-5.5's group source alone, one `ps -axo pid=,pgid=,stat=,lstart=` snapshot, inside that check and at most every `OWNED_CENSUS_INTERVAL_S` (0.5 s, so with the default interval on every check), capturing an identity (C-5.3) only for a member not recorded under its current start and the current boot identity (so a reused pid, and a member recorded under another boot identity, such as legacy seconds once the boot UUID can be read or seconds a clock correction has since moved, are recorded afresh while still in the group); confirming the leader costs two more `ps` reads. A running attempt's inspection that raises leaves no due time, so the retry C-5.10 schedules repeats it in full, given the same table while that has not expired (C-5.12). The boot identity is read as C-5.12 says: only a boot-session UUID is reused for `BOOT_ID_TTL_S` (5 s), while legacy `kern.boottime` seconds are read afresh outside an existing table. The three-source census, whose marker source reads every process's environment, is taken only to decide a release, kill, loss or quarantine. Pending exports are found with one statement (`PENDING_EXPORTS`), not a lease lookup per accepted job. A `wait` re-reads the store only after a top-level transaction has committed a change, or every `WAIT_RECHECK_S` (1 s); a worker pass wakes waiters only when the store's generation moved while it ran, and makes that decision before its key is released. Incident: 2026-09-24, the per-tick inspection (three subprocesses per running attempt per 50 ms tick, and every 0.5 s a census that dumped every process's environment, 2.3 MB), waiters re-reading their jobs on every worker pass, and an export sweep of 266 statements a tick saturated the store lock; `daemon.status` took 38.8 s, every client timed out, and shutdown hung until SIGKILL (docs/reports/2026-09-24-daemon-inspection-wedge.md).
- **C-5.12** Inspection is rationed; decisions are not. Each tick (50 ms) reads a running attempt's `start.json` and `exit.json`, its cancel request and its wall clock, which are files and rows. Its processes are inspected at most once per `inspect_interval_s` (1), from one process table (C-5.5's snapshot) that every running attempt shares. A table expires one interval after its read began. An attempt falls due when the table it was last given expires (one this daemon launches, one interval after it opened the guardian's launch gate, so that its first table is read after the guardian started; one it recovered, when it first asks), and is given the last table read if that expires later, which means a table read after the one it last had and less than an interval before it fell due; otherwise it reads a new one, and that is the only time a read begins. So the table's `ps` begins at most once per interval however many attempts ask and however long it takes (when it takes longer than an interval, reads run back to back, one at a time), and only the inspection that reads waits for it, and for the table's boot identity, which the reader reads before any attempt is given the table: one that finds a read running returns and asks again on its next tick, so a slow or hung `ps` or `sysctl` holds one worker, not one per running attempt, and delays only the reading attempt's per-tick reads (except the `kern.boottime` read below, which the legacy attempts given the table wait for together). The reader is whichever attempt asks first once the table has expired, and the control loop offers running attempts in the order the store lists them, so one attempt can be the reader interval after interval and wait out every slow read. An abnormal guardian death is seen by the first table read that begins after it, which begins by the first tick one interval after the death that finds a free worker, or as the read then running ends if that read (`ps`, then the boot identity) is slower than that, once that read and one fresh read (below) have run, and is acted on once the fresh census that decides between a loss and a kill (C-5.5) has run too. A read that failed is rationed like one that worked, and an inspection given a failed read asks nothing singly and decides nothing, as a guardian that cannot be inspected decides nothing (C-4.2), so that a `ps` outage costs at most one capped read per interval rather than one per running attempt. An inspection that raises (a store write that fails, say) gives back its interval, so C-5.10's retry repeats it, given the same table while that has not expired, and backs off as for any worker; found not due, the retry would return, which C-5.10 counts as recovery. Until an inspection runs to its end, a retry that cannot inspect (another attempt's read is running, or the table, its boot identity or the guardian cannot be read), or stops at the pacing gate, is deferred: it neither clears C-5.10's count nor adds to it. An inspection that runs to its end clears the pending retry, and pacing state is pruned when the attempt is no longer live. The table says that the recorded guardian is alive (C-5.3), when it is, and lists the members of its group, whose identities are recorded as owned (C-5.6) only while that same table shows the recorded guardian alive and leading the recorded group; the environment scan is not run for this, because only group members are recorded. A shared table may say "alive" and nothing else, and says it only where `liveness` would (C-5.3): on an exact match of pid and start, and of the boot identity or, for a guardian recorded with a legacy boot timestamp (its UUID `sysctl` failed once as it started), a timestamp that C-5.3 matches to the table's `kern.boottime` seconds. A table reads those seconds the first time a legacy record needs them and keeps them for its life, whatever the answer, so every legacy attempt given the shared table shares one `sysctl`, and one that asks while it runs waits for it. A guardian it does not show alive is asked about afresh (C-5.3's own reads) before anything follows, and one that the fresh reads find alive has its group recorded from a table read for it alone, one `ps` outside the shared read and, for a guardian recorded with a legacy boot timestamp, that table's own `kern.boottime` read (rare, since a table read after the guardian started shows it); and every census that decides (start grace, a dead guardian, the kill protocol and its settle window, C-5.9's window, quarantine resolution, probe containment) is read fresh, never from the shared table. The shared table's reader reads its boot identity just after `ps`, and any other table (a census's, or one read for a single attempt) the first time a live pid needs it; each reads it once, whatever the answer (an error other than a failed inspection is a defect, kept and raised to every attempt that asks, whose passes C-5.10 retries): every attempt whose guardian the shared table shows shares that read, and when it fails none of them asks singly or is decided, as for a failed `ps` (one whose guardian the table does not show needs no boot identity and is asked about afresh, as above); a UUID read that fell back to `kern.boottime` seconds has failed for every attempt recorded with the UUID, which C-5.3 could only call unknown against them. One boot-identity read is reused for 5 s, and only a boot session UUID is: a failed read is not remembered, and neither are the `kern.boottime` seconds that a failed UUID read falls back to, against which every process recorded with the UUID would compare as unknown and so could not be signalled; a process whose start matches is never called dead on a boot-identity mismatch until a fresh read agrees. `procs` starts `ps` and `sysctl` without `fork` (`close_fds=False`, the condition under which CPython uses `posix_spawn` on macOS), because a fork costs in proportion to the daemon's memory; the daemon's other process starts (`git`, the guardian) still fork. Every descriptor the daemon opens is close-on-exec, but macOS has no `pipe2` and no `SOCK_CLOEXEC`, so a pipe or socket that another thread is creating at that instant can be inherited, by a `ps` or `sysctl` only, which holds it until it exits within its 10 s cap: the most that follows is a close seen that much later (`close_fds=True` would close it, but CPython on macOS then forks). The one descriptor this package hands down on purpose, the guardian's launch gate, is closed by the guardian before it inspects anything. The per-tick check for exports to retry is one query driven from `leases`, and the desktop login hint (C-10.3) is parsed only when `stat` says the file changed. What slows for every attempt is only how soon an abnormal guardian death is noticed and how soon a new group member is recorded as owned, and the attempt whose inspection is reading the table waits out that read, `ps` and `sysctl`, before its own per-tick reads, as a legacy attempt does the table's `kern.boottime` read; and a member missed is never signalled individually (C-5.4): while it stays in the group `killpg` reaches it with the rest, and one that has left the group is quarantined (incident: 2026-09-20, with four attempts running the daemon held a full core, about fifteen process starts a second: three to ask about each healthy guardian on every tick and a census of `2 + 3N` every 0.5 s; the laptop's thermal guard, which pauses the operator's command-line processes at or above 20% CPU while the lid is closed on battery, SIGSTOPped it for two hours; measured 2026-09-24 with `tools/measure_idle_cost.py`, production tick, timers off, `origin/main` and the first version of this clause (845d663): idle 7.8% and 0.5% of a core; four running attempts and twelve waiting jobs 46.5% and 3.9%, with the `ps` it started 71.5% and 2.7%; measured again 2026-09-26, after this clause's review, at a load average near 7: idle 3.0% and 0.2%; four running and twelve waiting 29.0% and 1.9%, with its `ps` 49.3% and 2.1%).

## 6. Admission

- **C-6.1** Submission validates before touching the store: workdir exists and is not under `/tmp` unless allowed; prompt file readable; `-o` path's directory exists; sandbox in {`read-only`, `workspace-write`}; `--task`/`--tier` valid per policy or `-m`/`-a`/`-H` pins consistent; a read-only job with `-o` inside `-C` is allowed (the daemon writes it).
- **C-6.2** The payload digest is SHA-256 over the canonical JSON of: prompt bytes (as base64), resolved workdir, git head of the workdir or null, task, tier, pinned model, pinned lane, sandbox, sorted exclusions, resolved `-o` path or null, `allow_desktop`, policy hash. A repeated request id with the same digest returns the existing job id (exit 0); with a different digest, exit 2.
- **C-6.3** Admission of an attempt is one transaction that: chooses the lane and model from the decision (section 11), takes the lane slot lease `lane:<lane id>:slot:<n>`, takes the output lease `out:<resolved path>` if `-o` is set and not already held by this job, takes the worktree lease if writable (on the write target, C-6.5; a session is not a place and takes no lease), inserts the attempt as `reserved`, and records the decision. Launch happens after commit.
- **C-6.4** Caps with defaults in `policy.json`: `max_active_attempts` 4 fleet-wide; `max_in_flight_per_lane` 2, and 1 while the lane has no `provider` reading fresher than `reading_ttl_s` (120); `max_wall_s` 21600 per job; `max_attempts` 3; `max_child_jobs` 8 per parent; `max_tokens_observed` optional per job; `workspace_git_timeout_s` 60, `worktree_add_timeout_s` 180, and `workspace_retry_max` 8 (C-6.8); `max_writable_per_session` 8 (C-6.5).
- **C-6.5** Refusals are exit 7 with the fix named: API-key home, workdir under `/tmp`, writable job that would write in a checkout on `main` or `master` (C-13.2), `-o` path held by a live job of another request id, a writable job for a session id that already has one running from another instance, a second writable job on the same worktree, a writable job beyond `caps.max_writable_per_session`, an isolated review (`-I`) that would inherit `CLAUDE_CODE_MANAGED_SETTINGS_PATH` or a remote managed-settings variable, an isolated Codex review whose home carries managed requirements or a non-empty system or project config layer (C-23.3), and a `lanes touch` that names a lane no touch may use: another owner's, disabled or superseded, the desktop login, identity-blocked, credential-latched, limited, closed for the account or the touch model, or running an attempt (C-18.3). This list is the index of refusals: a new refusal is added here, not in a clause of its own. What holds a writable job is where it writes. The write target of an in-place job is the real path of the checkout that contains its workdir (`git rev-parse --show-toplevel`), so `/repo` and `/repo/sub` are one target and two linked worktrees of one repository are two; the target of any other writable job is the worktree the daemon allocates for it (C-6.6), which no other job shares. One instance of a session may therefore hold any number of writable jobs on distinct targets, up to `caps.max_writable_per_session` (8), a backstop against a runaway caller and not a throttle (`max_active_attempts` bounds what runs). An instance is a process: the caller's pid with its boot id and start time (C-5.3), read by the daemon at submit and recorded with the target in the `job.submitted` event, so a recycled pid is never mistaken for it and no schema change is needed. A submission is refused when the session has a live writable job whose recorded instance is another process that is still running (the twin), and also whenever the two cannot be told apart: the submission carries no pid, either process cannot be inspected, or the live job recorded no instance. An instance that is provably gone (no such pid, or the pid now belongs to a later process) is not a second instance: a session resumed after a restart or an account switch is one instance whose detached jobs survived, and it may dispatch again. A revive is always another instance of the session it continues (C-23.54), so a revive and any other writable job of that session refuse each other as before. Both questions need `ps` or `git`, so they are answered under the submit lock before the inserting transaction, which re-checks with SQL alone and refuses any live job the submission was not cleared against (C-3.3) (incident: 2026-09-20, a session handing five stalled threads to parallel lanes was refused every writable job after the first with "caller_session is held by a live job", whichever worktree it named; the code compared session ids and never instances, so it refused the one instance this clause never meant to stop).
- **C-6.6** A writable job runs in a worktree the daemon allocates under `worktrees/<job id>/` from the caller's repo at its current head, unless the caller passes `--in-place`, in which case the daemon takes the worktree lease `worktree:<realpath>` on the checkout that contains the caller's directory (C-6.5); the provider still starts in the directory the caller named.
- **C-6.7** `prompt.md` holds the caller's prompt bytes exactly as submitted; it is the digest input and is never rewritten. Prepended text is applied in two places and recorded separately: at submit, the daemon prepends the write template to a workspace-write job unless `--no-preamble` (the sandbox is known at submit); at launch, the Claude adapter prepends the headless block unless the prompt already contains the marker line `<!-- subfleet:headless -->` (the provider is known only after routing). The adapter writes the text actually sent to `<attempt dir>/prompt.sent.md`, the launch's `stdin_path` points at it, and it is recorded as an artifact with role `prompt-sent`.
- **C-6.8** Workspace preparation (the main or master re-check, worktree allocation, reading HEAD, and the baseline snapshot) runs before every admission, so a waiting job repeats it on each pass and one slow pass must not end the job. Every git call in it is capped by `caps.workspace_git_timeout_s` (60; `git worktree add` by `caps.worktree_add_timeout_s`, 180); finalization's salvage uses the same cap, and a caller with no policy in hand reads `SUBFLEET_GIT_TIMEOUT_S`. A git call that did not finish is never read as an answer: a timed-out `rev-parse` is not "no HEAD" and a timed-out `symbolic-ref` is not "not on main". At submit it is exit 1 with nothing stored; at launch the attempt ends with the cause as its detail; at admission it is a failure classified here. Transient failures are a timeout and an `OSError` whose errno is EAGAIN, EINTR, ENOMEM, EMFILE, ENFILE, EBUSY, ETIMEDOUT, or ENOBUFS: the job moves to `waiting` with `wait_reason` `workspace` and a `next_check_at` 5 s out, doubling per consecutive failure to a 300 s ceiling, holds no lease, blocks no other job, and returns to `queued` on the first pass that succeeds, which also resets the count. After `caps.workspace_retry_max` (8) consecutive transient failures, or at once for any other failure (git exiting non-zero, a permission error), the job is `failed` with rc 1. Nothing is discarded: each deferral is a `job.workspace_deferred` event and the terminal failure a `job.workspace_failed` event, both carrying `error_type` (the underlying exception, so `TimeoutExpired` rather than its wrapper) and `error` (git's verb, the cap, and its stderr, or the OS error; a path and an errno, never a credential); the notice text ends with the same two fields; `show` returns the latest record as `workspace`; and `daemon.log` gets one line per deferral and per failure, naming the job. The consecutive count is held in memory, so a daemon restart forgives it while the events keep the history. A `worktrees/<job id>/` directory that is not a worktree (a `git worktree add` killed at its cap) is removed and rebuilt before the job is admitted; no attempt has run in it. The baseline snapshot seeds its temporary index from a copy of the real index (mtime kept) and reads the baseline with `read-tree -m`, so its entries are the baseline's while the stat data of every unchanged path carries over and `add -A` hashes only changed files; the copy's assume-unchanged and skip-worktree bits, which `read-tree -m` keeps, are cleared across the whole index before `add -A`, since `add -A` skips such paths and the empty-index read has none, so both reads give the same tree; bytes and mtime come from one open file; with no usable real index (none yet, unmerged entries, a copy git cannot read or clear) it reads the baseline into an empty index. Trusting stat data is git's own model: a rewrite that keeps size, mtime and inode is read as unchanged (incident: 2026-09-23, axiom-corpus, 59,822 tracked files and 14 GB: the empty-index snapshot took 39 to 51 s at a load average near 6 and timed out at the 60 s cap on all eight tries, so no writable job could be admitted there; seeded, the same tree took 0.5 s). A refusal raised during preparation (C-6.5) is still exit 7 with its fix and never waits (incident: 2026-09-20, under a load average near 10 a writable job went from queued to `failed` in 19 s with "workspace preparation failed", no attempt, and nothing in `daemon.log`; the same snapshot took 0.6 s minutes later and an identical resubmission ran; twelve jobs ended that way between 2026-09-19 and 2026-09-20, read-only ones after as long as 70 minutes in the queue, because the caps were 15 s and 5 s, the exception was discarded, and every failure was terminal).
- **C-6.9** Queued jobs are considered in tier order and, within a tier, oldest first (plan amendment 11). A job that cannot be placed on this pass (it is `waiting` on `capacity` with a `next_check_at` still ahead, its probe is pending, no lane is admissible, or a lease it needs is held) holds back the later jobs of its tier **that compete with it**, and no others. Two jobs compete when some model could serve both: a pinned job's models are its one pin; a task job's are its chain from its tier upward, exactly the chain routing walks (C-11.2); a job whose models cannot be told (a lane pin with no model) competes with every job. Lane pins narrow it further: two jobs pinned to different lanes never compete, whatever their models, because neither can take a slot the other waits for; a job with no lane pin, or a pin that cannot be resolved, could use any lane and so competes on models alone (incident: 2026-09-22, three Fable gate reviews pinned to three lanes; the oldest waited on its own lane's provider limit until 19:00Z and held the other two, whose lanes were open, for six hours). So an older Opus review keeps its place against later Opus work, including work that could promote into its chain, and a Fable-pinned job does not queue behind it. A job that passes an older waiting job of its tier leaves one active-attempt slot free (`max_active_attempts` minus one), so the older job starts the moment its capacity appears rather than waiting out the jobs that passed it; with nothing older waiting, the full cap applies. At `max_active_attempts` the pass ends: nothing later is evaluated. Tiers never hold each other, as before (incident: 2026-09-20, an Opus review that no lane would admit, every Claude lane `reserve:fable:unmeasured` and Astra closed until the next day, headed the `standard` tier; admission held the whole tier behind it, so three Fable-pinned jobs, tier-less and therefore `standard`, stayed queued beside eleven free Fable lanes and nothing at all was admitted for more than three hours).
- **C-6.10** A capacity wait is rechecked on a clock that backs off, and a recheck that reaches the verdict it reached last time adds no decision row. The first recheck is 1 s out (plan amendment 11); each consecutive recheck with the same verdict doubles it, to a 30 s ceiling; a reset the decision knows about (a closure's `until_at`, a reading's `resets_at`) that falls sooner is still checked on time. The verdict is the chain walked, the lane and model chosen, the policy hash, and each rejected lane with its reasons (`scheduler.verdict_signature`); readings, utilization, and `evaluated_at` are evidence and are left out, and so is `no-slot` on a lane that is rejected for another reason as well: a lane that is closed, reserved, or excluded is no nearer to taking the job when its slot empties, slots fill and empty all day, and a probe's reservation counts toward the fleet cap, so each probe cycle (C-18.1) marks every lane `no-slot` for the second it runs. A lane whose only reason is `no-slot` keeps it: that job is waiting for a slot, and that is its verdict. A changed verdict is recorded and restarts the clock at 1 s. The same doubling applies to three waits that are not on a closure or a reading, so the known-reset rule has nothing to say about them: a job waiting on a lease another job holds, which was a fixed 1 s; a job whose route could not be prepared with no clock set (its probe's slot is held, or the lane changed hands); and a job whose chosen lane and model changed after its probe. The last two had no clock at all and were prepared again, with a new probe directory, on every tick; a probe directory made for a reservation that then does not happen is removed, since no record names it and recovery would never collect it. Backing off is not meant to cost a start: each pass compares the leases no probe holds with those it saw on the pass before, counting the ones it took itself, and when one has gone (an attempt ended, a job released its worktree or its output path) every backed-off capacity wait other than a probe's own is looked at on that pass. Capacity that appears any other way (a fresh reading, a closure an operator lifts, a lane enrolled) is seen at the next recheck, so the most this clause can add to a start is 30 s. Only a capacity wait is brought forward. A job whose wait became `workspace` (C-6.8) loses its record and keeps that clock, because a look brought forward there spends one of `workspace_retry_max` retries, and eight unrelated releases would end the job. The 60 s wait after an inconclusive probe keeps its clock too, because bringing it forward would re-probe the provider on every release; it gets the other half of the rule, and a probe that ends the same way adds no second decision row. The record (verdict, consecutive rechecks, first and last look, and the latest hold in full) is held in memory per job, replaced whole on every look so that another thread never reads half of one, and dropped when the job is placed or ends. A restart therefore forgets it, as it forgets C-6.8's count: recovery makes every capacity wait due once, since what each was waiting for may have changed while no daemon ran and nothing else could bring a persisted wait forward, at the cost of one decision row per waiting job; `why` reports the record (C-6.11). C-11.5 is unchanged: the decision is still stored per attempt, and a waiting job still has the latest verdict it reached (incident: 2026-09-20, three jobs no lane would admit were each re-evaluated once a second for hours; every look prepared the workspace with git, scored every lane, and wrote a 22 KB decision row whose only new content was fresher readings: 1,628 rows in ten minutes with no attempt reserved, 29,923 rows and 681 MB of a 709 MB store, the file growing about 170 MB an hour, and the daemon at a full core; the decision said `earliest reset: 2026-09-20T22:20:00Z`, more than an hour off, on every one of them; by the next morning the store was 2.3 GB, 2.2 GB of it 98,014 decision rows. Replayed over the 80,996 rows of the six worst jobs, the verdict changed 74 times).
- **C-6.11** A job that is not placed always has a stated reason, and a fleet that places nothing says so. Each admission pass records, per job it leaves unplaced, why: `behind-older-job` with the older job's id and the tier (C-6.9); `fleet-full` with `max_active_attempts`; `slot-kept` with `kept_for`, `live`, and `max_active_attempts`, when a lane would take the job and the fleet is one short of its cap because C-6.9 keeps the last slot for an older waiting job of the tier (it is not reported as a full fleet, which an operator can see it is not); `parent-cap`; `lease-held` with the lease keys; `probe-pending`; `attempt-live` (an earlier attempt of the job is still live or quarantined); `approval`, `uncertain`, `workspace` (C-4.1); `route` with `error_type`, `error`, and `deferrals` (C-6.12), which is reported as that whatever else holds the job while its clock runs; otherwise the commonest first reason lanes rejected it for (`reserve:fable:unmeasured`, `closed:account`, `no-slot`, ...), with the `next_check_at` of any wait that has one. A wait that is a person's or a retry's to end (`approval`, `uncertain`, `workspace`) is reported as that even when the fleet is also full or an older job is also ahead of it. `hold` is the last pass's answer and `recheck` describes the last look (`recheck.label` is what that look found): the reason is the latest look's, not the first's, whether or not the verdict repeated; a look that ends without changing a verdict or a clock still refreshes it; and a pass that does not look at the job repeats the last hold in full (`leases`, `max_active_attempts`), so `why` never degrades between looks. A pass that raises publishes nothing: the holds and the `admission` snapshot stay as the last whole pass left them, because half a hold set would read as nothing left pending, and C-5.10 logs and paces the failure. When every lane has a standing reason the label is the commonest of those and not `fleet-full`: a probe's reservation counts toward the fleet cap, so such a job would otherwise read `fleet-full` for the second each probe runs. The record is in memory and replaced whole each pass. `subfleet why <job>` returns it as `job` (`state`, `tier`, `wait_reason`, `next_check_at`, `hold`, `recheck`, `decision_source`, `decided_at`) and as `queue`, the same in sentences, ahead of the decision. A queued or waiting job with no decision row (admission held it back, or no pass has reached it) is evaluated for the answer and marked `decision_source: evaluated-now`; no decision is recorded and no job changes, because answering is not admission. The evaluation asks who the desktop login is, as every evaluation does (C-10.3), and a newly verified identity is recorded as the `desktop.identity` event it would have been on the next pass. A job that ended without a decision prints its state and `No decision recorded.`, unless admission refused it (C-6.12), which prints `Refused at admission: <message>` in its place The CLI never prints `null`, also against a daemon that predates `queue`. `daemon.status` carries `admission`: `pending` (unplaced jobs other than those held as `approval`, `uncertain`, `workspace`, or `attempt-live`, which are a person's or a retry's to end), `placed_at`, `idle_for_s` and `idle_since` (null unless jobs are pending and none has been placed), `reasons` (count per reason), and `open_lanes`; it is one snapshot, replaced whole at the end of a pass, so a status request never reads half of an update. `open_lanes` is the lanes owned by v2, enabled, not the desktop login, identity not mismatched, under no account-wide closure, with a slot free and no probe holding it. Open means capacity exists, not that it fits: a job can still be refused an open lane by a model-scoped closure, the reserve, or its own exclusions, and the reasons say which. `subfleet status` prints one `admission:` line while `idle_for_s` is set, and its `running jobs:` count and table cover live jobs only. When jobs have been pending with none placed for 60 s, `daemon.log` gets one line (count, seconds idle, open lanes by id, reasons by count, and the first job in admission order), and one line when placing resumes or nothing is left pending. The line is a warning when a lane is open and some job is held for a reason other than ordinary queueing (`fleet-full`, `slot-kept`, `parent-cap`, `no-slot`, `lease-held`, `probe-pending`, `behind-older-job`); otherwise it is information, because with no lane open or a fleet at its cap waiting is the expected answer. The fleet is looked at again every 600 s while the stretch lasts: a warning is written each time, information at most every 3600 s, so a wait that was expected when it was first logged becomes a warning within ten minutes of becoming one (incident: 2026-09-20, fifteen jobs from six sessions sat queued for more than three hours beside open lanes; `subfleet why` printed `null` for every one of them, because a job admission skips gets no decision row and the CLI printed the missing value instead of the daemon's text; `subfleet status` said `running jobs: 519`, the size of the store, because `daemon.status` carries every job as `jobs`; and `daemon.log` had not gained a line since the daemon started).
- **C-6.12** A job whose route cannot be evaluated is that job's problem and never the pass's. Evaluating one job (`scheduler.evaluate`, and `scheduler.probe_required`, which checks an unmeasured-reserve authorization) is isolated from the rest of the pass, both where the route is prepared and inside the reserving transaction, which rolls back before the job is settled; a `ValueError` (a `PolicyError` is one), `KeyError`, `TypeError`, `AttributeError`, or `IndexError` from it settles that job and the pass goes on to the next, in its tier and every other. What it settles to depends on whose the error is. A `scheduler.RouteError` is the job's own: its pin names several lanes, its pin and its model are of different providers, or its authorization is not whole. No wait can fix that and only the caller can say what was meant, so the job is `failed` with rc 2, what submit would have answered, its `wait_reason` and `next_check_at` cleared (as for any job `_fail_queued` ends); its notice and a `job.route_refused` event carry the message (`error_type`, `error`), `daemon.log` gets one line naming the job and the message, `why` prints `Refused at admission: <message>` ahead of any decision recorded before it (`refused` in its result), and a worktree admission cut for it under `worktrees/<job id>/` that no attempt used is removed, since `jobs.worktree` is set only at reservation and retention would never collect it. Two of those errors can also come from a policy edit rather than the job: a provider conflict (a tier's chain moved to another provider under a job already pinned to a lane) and an authorization's model check. Those are refused only under the policy the job was accepted with (`jobs.policy_hash` equal to the running policy's); under any other they are treated as below. Anything else is not the job's: bad capacity data, a policy that no longer knows the job's task, tier, or model (submit checked each against the policy it ran under, so a policy edit is the operator's to fix), or a defect. That is never terminal, because a restart can bring the fix and failing it could fail every queued job at once: the job waits with `wait_reason` `route`, 5 s out doubling per consecutive failure to a 300 s ceiling, each deferral a `job.route_deferred` event carrying `error_type`, `error`, `deferrals`, and `next_check_at`, and a `daemon.log` line naming the job and the error's type only (C-5.10: the message is in the event and in `why`). A route wait is not a capacity wait: it holds back no other job (C-6.9) and no released lease brings it forward (C-6.10). While its clock runs its hold is `route` with the error (C-6.11), whatever else would hold the job; once the clock is due the job goes through the pass like any other, and a pass that evaluates its route resets the count. `why` names the error, from the hold and, when `why`'s own evaluation raises, in place of the decision (`route_error` in its result); `daemon.status` counts the hold under `admission.reasons`. The count is in memory; recovery makes every route wait due, as it does capacity waits. Route holds are not ordinary queueing, so beside an open lane the idle line (C-6.11) is a warning. A store error is not isolated: that is the pass's, and C-5.10 retries it. An accepted job is always evaluable as far as submit can tell: an empty task or tier is stored as none. A transient retry (C-4.5, C-9.5) is the daemon's choice of pair, not the job's, and is pinned to the last attempt's lane and model id only while that pair could run: the running policy resolves the id (a current id or a `retired` alias) to a model of the lane's provider, and the lane (or its re-enrolled successor) is enabled, v2-owned, and not identity-blocked. While it is pinned, its C-6.9 demand is that one model on that one lane; once a look has let the pin go, the job's demand is its own on that pass and while its clock runs, so it neither passes an older job it competes with nor is passed by a younger one (held behind one after a look, it waits on a C-6.10 capacity clock like any other held look, so the passes before that clock prepare no workspace and score no lane), and the next due look evaluates the pair again (a lane that recovered takes its one retry; a restart, which forgets the look, changes nothing). When the job is due, the pair is evaluated as admission would evaluate it. If the lane refuses it only for want of a slot (in flight, the fleet or a parent at its cap, a probe holding it), the retry waits for that lane. If the lane refuses it for anything a slot will not end (a closure, the desktop login, the job's own exclusions, a latched credential, the floor, the reserve), or the pair cannot be evaluated, the job routes as submitted, which is C-4.5's "then next candidate". Before this, a pinned retry waited on its lane until `max_wall_s` cancelled the job (incident: 2026-09-22, five jobs pinned by email, `-a max@axiom.org` and `-a max@thesisinstitute.org`, with a task and no model, named a Claude lane and a Codex lane at once in the capacity view (C-11.2); `resolve_lane` raised inside `_admit_pass`, which caught nothing per job, so every pass aborted at the first of them: `worker admission failed: ValueError (128 in a row)`, no attempt reserved between 14:45:05Z and 18:02:45Z (10:45 to 14:03 EDT), and every later job in every tier waited; `why` caught the same error and printed `No decision recorded.` for those five, so nothing pointed at the stalled pass. Admission resumed within a minute of the five pins being rewritten to `claude-11` and `claude-9` by hand. The same resolution had stalled admission once already that day: a gate review pinned `-a max@axiom.org -m fable` held every pass from its submission at 13:24:34Z until it was cancelled at 13:48:53Z, no attempt was reserved from 13:24:08Z to 13:50:32Z, and `daemon.log` shows the count reaching sixteen twice only because the lane-pins cutover restarted the daemon at 13:35:39Z).

## 7. Cancellation

- **C-7.1** `kill` inserts a cancel request in the job row (`cancel_requested_at`) in one transaction and returns; the daemon performs C-5.6 asynchronously. `kill --wait` blocks until terminal.
- **C-7.2** If the cancel commits before acceptance, the job becomes `cancelled` even if an attempt later reaches `finalizing`; that attempt's artifacts are kept and it is marked `interrupted`. If acceptance commits first, `kill` returns 0 and prints "already finished".
- **C-7.3** A parent's cancel cancels every child job not submitted with `--independent`, in the same transaction that records the parent's request.
- **C-7.4** A job that is `queued` when cancelled becomes `cancelled` immediately and releases its leases.

## 8. Artifacts and export

- **C-8.1** Every file the daemon publishes (deliverable, `-o` export, `manifest.json`, receipts) is written as: temp file in the destination directory, `os.fsync(fd)`, `os.rename`, `os.fsync` on the directory descriptor.
- **C-8.2** The deliverable is captured once at `finalizing` from the adapter (C-12.6) and recorded in `artifacts` with role `deliverable`, path, bytes, and SHA-256. The raw stream, stdout, stderr, and lane log are recorded with their own roles. Nothing appended to a transcript after the attempt's exit changes the deliverable.
- **C-8.3** The `-o` export is a copy of the accepted deliverable published by C-8.1 after acceptance. A failed export sets `export_error` on the job and emits an event; the job stays `succeeded`.
- **C-8.4** Retention: newest 500 jobs or 2 GiB, whichever binds, computed outside transactions in a maintenance pass; jobs that are active, `quarantined`, have unread notices, hold salvage refs referenced nowhere else, or are a gate's evidence are never pruned. Probe, keepalive, and touch (C-18.3) results live in `readings` and `events`, not in `jobs`.

## 9. Evidence labels and classification

- **C-9.1** Reading labels: `provider` (a server reported it; source and age recorded), `stale-provider` (the same beyond `reading_ttl_s`), `admission-observed` (this model recently succeeded or was rejected on this lane; remaining quota unknown), `local-backoff` (a routing decision with an explicit expiry and reason), `unknown`. No other label exists. A percentage is rendered only from a `provider` or `stale-provider` reading, and a stale one is marked stale.
- **C-9.2** Classification precedence is authentication, then admission, then quota, and the classifier records which evidence answered each. Outcome classes: `ok`, `limited`, `auth-dead`, `cli-too-old`, `content-filter`, `transient`, `unknown`. The raw rc and signal are always kept beside the class. An attempt the daemon signalled (`killed_by` set: an operator's kill, the wall limit, recovery of a dead guardian's group) is never `ok`, whatever its rc and deliverable: finalization records it `unknown` with the detail `stopped by <killed_by>: exit <rc> after the daemon's signal is not a finished deliverable`. The daemon decides this, not the adapter, so it holds for every provider; like C-12.6's empty-deliverable rule it is recomputed from the attempt row on every finalization while `finalization.json` keeps the adapter's verdict, and whenever either rule overrides that verdict the attempt's evidence keeps it as `provider_verdict` (incident: 2026-09-24, three running Codex jobs were cancelled; Codex exited 0 after the SIGTERM and left its last interim progress message, 32 to 61 words such as "I am checking the newer validation code before finalizing", in `last.md`, which the adapter classified `ok`, "Codex completed with a deliverable").
- **C-9.3** `auth-dead` requires a 401 from a usage endpoint, an explicit organisation-block message, or a refresh-token-revoked event. A 403 from the Claude usage endpoint on a setup token is expected scope and is not evidence. A limit-looking phrase with a successful `system/init` is `limited`, not `auth-dead`.
- **C-9.4** `limited` carries scope (`account` or a model id), the provider's reset clock when reported, else a guessed clock of now + 3600 s marked `clock_source: guessed`, and the evidence (event, stderr line, or rc). It writes a closure (C-9.6).
- **C-9.5** `transient` covers 5xx, stream disconnects, DNS and TLS failures, and "model at capacity" messages. It never writes a closure; it allows one same-lane retry after 60 s.
- **C-9.6** A closure is (lane, scope, until, reason, clock source, source event). A new closure on the same lane and scope extends `until` but never shortens it. Closures expire by clock; nothing else releases a provider-limit closure except a later `provider` reading that shows the window reset.
- **C-9.7** Codex windows are classified by duration (`window_minutes` 300 is `five_hour`, 10080 is `seven_day`, anything else keeps its minute count as the key), never by slot position.
- **C-9.8** Claude `rate_limit_event`: `unifiedWindows.<window>.utilization` is a fraction in [0, 1] and `resetsAt` is epoch seconds; `status: allowed` yields `provider` readings for the shared five-hour and weekly windows with scope `account`, and a scoped weekly Fable reading when `seven_day_overage_included` is present; over-cap utilization is stored as exhausted (1) with the original retained in evidence; `status: rejected` yields no utilization reading; it yields one `admission-observed` reading for the requested model whose `window` is the literal `admission` (the only value of `window` that is not a duration key), with `resetsAt` as the closure clock when present, and `errorCode` recorded. Named rejection types `seven_day_overage_included`, `seven_day_opus`, and `seven_day_sonnet` close their respective model scopes; shared and unknown limit types close the account. `overageStatus` is parsed independently and never treated as admission evidence.

## 10. Lanes and credentials

- **C-9.9** The Claude usage sensor that costs no model turn is `https://api.anthropic.com/api/oauth/usage`, read with the lane's own credential (source `oauth-usage`). It yields `provider` readings for the account windows `five_hour` and `seven_day` (scope `account`) and one `provider` reading per `limits[]` row of kind `weekly_scoped`, scope = the policy model id for the row's `scope.model.display_name`, window `seven_day`; utilization is normalised to a fraction. HTTP 429 yields no reading and the server's `Retry-After`, which the timer honours before asking that lane again; 401 is auth-dead; 403 is no-scope; anything else is unavailable and yields no reading. Reads are paced `reserve.usage_spacing_s` apart (3) because the endpoint penalises bursts (2026-09-06: fourteen back-to-back reads earned `Retry-After: 3035`). C-10.6 holds: the readings count only when the profile endpoint, asked with the same credential, binds the lane. The timer's periodic Claude probe is this read; a model turn is spent only by the pre-launch probe (C-11.4) and keepalive. A Claude home lane's login lives in the config directory's `.credentials.json` or, on macOS, in the keychain item `Claude Code-credentials-<sha256(CLAUDE_CONFIG_DIR)[:8]>` (observed 2026-09-06); its access token expires within hours and carries a refresh token the CLI renews when it runs. An access token past `expiresAt`, or a 401 on a home lane with a refresh token, is `expired-token`, never auth-dead: the timer spends one minimal turn under that home (C-23.47's heal, at most once per 20 minutes per credential epoch) and reads usage again.
- **C-10.1** A lane row is an immutable binding of provider, account key, credential reference, credential epoch, optional home, `owner` (`v1` or `v2`), and `desktop` flag. The credential reference is a keychain item name (`claude-quota-<email>`, as v1) or a home directory path; the store never holds a secret.
- **C-10.2** Enrolment probes before recording: Codex reads `auth.json`, refuses an API-key login and a free plan, and probes the usage endpoint; Claude runs one Haiku turn under the token with `--output-format stream-json --verbose` and reads the `rate_limit_event`.
- **C-10.3** A lane whose Claude identity (C-10.6) equals the identity of the desktop app's keychain credential is `desktop` and is never a candidate unless the job has `allow_desktop`. The desktop identity comes from the profile endpoint using the keychain credential itself, re-read each probe cycle; `~/.claude.json` `oauthAccount` is a hint that `doctor` compares against the profile and reports when they disagree, never the authority. While the desktop identity cannot be verified, every lane whose label matches either the cached email or the last verified desktop identity is treated as `desktop`. For Codex, `~/.codex` is observed and never a lane, and a numbered lane that shares the app's account is `app_shadowed`: dispatchable, ordered like any other lane, and last for automatic reset credits (C-23.46).
- **C-10.4** A lane with `owner: v1` is never a candidate. Ownership changes only by `subfleet lanes transfer <lane> --to v2` (or `--to v1`), which records an event. For a Codex lane the transfer also relocates the home: `~/.codex-<n>` moves to `<state root>/lanes/<lane id>/` on `--to v2`, before ownership flips, and back on `--to v1`, after it flips, each in one rename. v1 discovers Codex homes by directory glob from every caller (CLI, gates, launch agents) and reads no roster, so the relocation is the fence and the roster entry is the record. The lane keeps its id: the credential is unchanged, only its path moved. A transfer to v2 is refused while v1's ledger shows a run live on that home; a transfer back is refused while a v2 attempt is live on the lane.
- **C-10.5** The credential value is resolved inside the adapter's launch builder and placed only in the child's environment. It is never logged, never written to `lane.log`, never in `manifest.json`.
- **C-10.6** A Claude identity is the pair (`account_uuid`, `org_uuid`) returned by `https://api.anthropic.com/api/oauth/profile` when requested with exactly the credential that produces the lane's usage reading. A usage reading is recorded only when the profile identity equals the lane's recorded identity. When the profile is unavailable, the reading is stored with evidence `identity-unverified` and no windows; when it differs, with evidence `identity-mismatch` and no windows, and the lane is not a candidate until an operator re-enrols it. A setup-token lane whose token lacks profile scope keeps the identity recorded at enrolment, and its stream readings carry evidence `identity-enrolled`. Incident: on 2026-09-05 v1 attributed the Axiom account's usage to RulesAtlas because it trusted `~/.claude.json`; the evidence is `~/axiom-eng-briefs/opus-expiry-20260905/identity-fix-live-result.json`.
- **C-10.7** A desktop credential and an enrolled inference-token lane are distinct lanes even when their labels match; identity, not email, joins two credentials to one account, and `doctor` reports two enabled lanes with one identity as a defect (C-23.45).

## 11. Routing evaluation

- **C-11.1** `policy.json` is the routing data. Required keys: `tiers`, `chains` (task to ordered short-model list, one per tier), `fallback: "upward-only"`, `permissions` (task to sandbox), `models` (short name to provider, id, optional effort and scope), `retired` (alias to short name: a retired short name or exact id and the current model that takes its work; an alias re-targets dispatch, never a usage scope or a recorded model, so a retired model's own weekly window and the runs that asked for it keep its own id), `desktop_login: "never"`, `caps` (C-6.4), `reset_credits`. The file's SHA-256 is the policy hash on every job.
- **C-11.2** Evaluation for a `--task`/`--tier` job walks the chain from the tier's index upward. For each model, candidates are lanes of the model's provider that are enabled, `owner: v2`, not `desktop` (unless allowed), not in the job's exclusions, not under an unexpired closure for scope `account` or the model id, and with a free slot (C-6.4). The first model with a candidate wins. A `-m` pin evaluates one model and never falls back; `-a` or `-H` evaluates one lane. A pinned job evaluates one model, its `-m` model or else the first model of its task's chain from its tier, and so runs only on that model's provider. The pin is resolved to one lane id by `scheduler.resolve_lane` once, at submit, against the lanes admission evaluates named as the capacity view names them (each lane's row with its latest probe verdict merged in, as `Timers.enrich_view` merges it, so a Codex lane also answers to the email its usage probe reported, and keeps it through a probe that could not read the account; the same roster serves admission and recovery), and the job stores that lane id. The name as typed is kept in the `job.submitted` event (`pin.requested`, `pin.lane_id`) and, except for a job carrying an unmeasured-reserve authorization, in the request digest; a retry of an accepted request whose name no longer resolves to one lane is answered from the lane it was accepted on, so a retry still finds its job (C-6.2). An authorized job's digest binds the lane id it was granted for (C-11.7a), so its retry after the name comes to name another lane is refused as a different payload. A lane id matches only itself, except that a disabled lane whose credential an enabled lane now holds (a re-enrolment, C-10.2: the same account on the same credential) resolves to that lane, so a job pinned before a re-enrolment runs on its successor, and attempts on a lane and on its successor are attempts on one lane when retries and exclusions are counted (C-4.5: one same-lane retry, then the next candidate), a resume included, whose launch accepts the successor of the lane it recorded because the native session lives under the credential's home, not under a lane id (C-12.3); a job carrying an unmeasured-reserve authorization never follows, because the authorization names the lane id it was granted for (C-11.7). Any other name (an account key or its account part, a label, a Codex email, a home) may match several lanes, and narrowing drops only lanes that could never take the job: lanes of another provider than the job's, taken from the job's model or task, else from the flag that pinned it (`-a` a Claude account, `-H` a Codex home, sent as `pinned_provider`), a disabled lane when an enabled lane that also matches is bound to the same credential, and a lane whose credential proved to hold another account (C-10.6) when another lane of the same provider also matches (across providers the name stays ambiguous); such a lane keeps the email its probe read as `observed_email`, never as a name it answers to. A name given with `-a` or `-H` names a lane of that flag's provider only, so a job whose model runs on the other provider is refused at submit (exit 2), as v1 refused `-a` with a Codex model; a lane id says its own provider whatever flag carried it. A name that still matches several lanes is refused at submit with exit 2 naming the lane ids (`-a <lane id>` pins one). Resolving once means no later roster change (a probe reporting an email, a lane enrolled) can make an accepted pin ambiguous. A job accepted before this rule may still carry a name: each daemon start rewrites the pin of every unfinished job whose name resolves to one lane (`job.pin_canonicalized`, from and to; a job carrying an unmeasured-reserve authorization is never rewritten) and logs one line for each it leaves. One that names several lanes is refused at admission (C-6.12). One that names no lane waits as a pin to an unknown lane always has (`pinned lane ... is unknown`, C-17.3), which admission cannot settle, and `subfleet doctor` fails its `unfinished jobs pin lanes by id` row while any job carries such a pin; a repair that raises is logged and skipped, never holding up recovery. Exclusions (`-x`) are not narrowed: a name excludes every lane it matches, which errs toward not running.
- **C-11.3** Codex comparator: eligible when every `provider` window has utilization below `1 - headroom_floor` (floor default 0.15); ordered by `seven_day` reset ascending (soonest first), then lane id. In-flight counts never reorder Codex lanes. Claude comparator: eligible for a model by the same floor on the worst window of every scope that applies to that model; ordered first by the stranded term (a lane closed for a model the job does not need, typically Fable, sorts ahead of unstranded lanes so stranded capacity is spent first; C-23.37), then worst-window headroom descending, then in-flight ascending, then lane id. Lanes with no `provider` reading rank after measured lanes on both providers and are "eligible but unmeasured".
- **C-11.4** Before dispatching expensive work (writable, or tier `hard`) to an unmeasured lane, the daemon runs a probe with the model the job wants (C-10.2 style); a `limited` result closes the scope; `ok` records `admission-observed`. For other work the job's first attempt is the probe. A probe launch uses the fixed prompt `Reply with exactly OK. Do not use tools.` in a private read-only directory under the state root and carries `SUBFLEET_PROBE=1` in the child environment, so tooling and the fake providers can tell a probe from work.
- **C-11.5** The decision record is JSON: chain walked, per-model candidate list with each rejected lane and its reason, readings and closures consulted, chosen lane and model, and the policy hash. It is stored per attempt and printed by `subfleet why <job>`; `subfleet run --why` and `--dry-run` print it without dispatching.
- **C-11.6** The observed 06:33 case (excluded desktop lane, Opus chain exhausted) must evaluate to Astra with the reason "opus: no candidate lanes after exclusions; promoted".

## 12. Adapters

- **C-11.7** Reserve rule. A Claude Max account carries a shared weekly window (`seven_day`, all models) and a model-scoped weekly window for each reserved model (`reserve.models`; Fable until its retirement on 2026-09-27, none in the shipped policy since). Use of the reserved model counts against both; use of any other model counts against the shared window only, so the shared window is what ends a week of the reserved model. For a job whose model is not reserved, a lane is a candidate only when fresh complete `oauth-usage` readings, or shared/scoped readings paired by event time and attempt from one `rate_limit_event`, give slack = (1 − shared utilization) − `reserve.cap_ratio` × (1 − reserved utilization) ≥ `reserve.min_slack`: a lane with no fresh paired measurement is rejected `reserve:<model>:unmeasured` unless an active provider-reported model-only exhaustion proves the reserved model cannot use capacity before its reset; that case requires a fresh supervised probe of the requested model and never overrides fresh measured reserve restrictions, a lane below the slack `reserve:<model>:reserved`, and a lane whose usage read shows no reserved window is free. Candidates are ordered by slack, so non-reserved work lands where the reserved bucket is most spent. `cap_ratio` is the reserved bucket's size relative to the shared one; the payload does not state it, so it is set above any ratio the observed accounts allow (2.0 on 2026-09-06, from an account at 94 shared and 49 reserved, which bounds it below 1.92) and lowered only from measurement. Incident: 2026-09-05, Opus lanes on two accounts exhausted their shared window and ended their Fable week with half the Fable bucket unused.
- **C-11.7a** An operator may explicitly authorize only an unmeasured reserve verdict for one new dispatch using `--allow-unmeasured-reserve REASON` with both lane and model pinned. The daemon resolves the lane to its enrolled ID, persists the reason/evidence (nonblank, at most 2,000 characters), includes it in request idempotency and audit data, and requires a fresh same-model admission probe before reserving the work attempt, even for standard read-only jobs or previously observed admissions. The decision continues to call reserve capacity unmeasured. This exception never overrides measured reserve restrictions, account/model closures, identity or desktop protection, ownership, exclusions, or capacity caps; never rotates accounts or promotes models; and is not inherited by subsequent jobs or resumes. Dry-run remains side-effect free. An unsuccessful or identity-unbound probe cannot authorize work. Tests: `tests/unit/test_scheduler.py`, `tests/fake/test_reserve_authorization.py`.
- **C-12.1** `subfleet/adapters/base.py` defines the interface; adapters return data and never touch the store. Methods: `enroll(credential) -> LaneInfo`, `probe(lane) -> list[Reading]`, `build_launch(job, attempt, lane, credential_env) -> Launch`, `classify(attempt_dir, exit_info) -> Outcome`, `attest(attempt_dir, launch) -> Attestation`, `deliverable(attempt_dir, launch) -> bytes | None`, `resume_launch(job, attempt, lane, prompt) -> Launch | None`.
- **C-12.2** A `Launch` is argv, env additions, cwd, and the paths for stdout, stderr, and any raw stream file, plus `native_session_id` when the adapter chose it up front (Claude `--session-id`).
- **C-12.3** Codex launch mirrors v1's `bin/subfleet-codex` argument construction: `codex exec --json -m <model id>`, effort via `-c model_reasoning_effort=<effort>` when the model has one, `--sandbox <read-only|workspace-write>`, `-c hooks=<guard override>` when the guard is armed, `--output-last-message <attempt dir>/last.md`, the prompt on stdin, `CODEX_HOME=<home>`, `CODEX_API_KEY` and `OPENAI_API_KEY` removed from the environment. The thread id is read from the `thread.started` event. `codex exec resume <thread id>` on the same home is the resume launch. A probe launch (C-11.4), which is also how every Codex timer turn runs (heal, touch), adds `--skip-git-repo-check`: its private directory under the state root is never a repository, and `codex exec` exits 1 in an untrusted directory without the flag (observed 2026-09-25 with codex-cli 0.153.3: "Not inside a trusted directory and --skip-git-repo-check was not specified"). Work keeps codex's own repository check.
- **C-12.4** Claude launch: `claude -p --model <model id> --session-id <uuid4> --output-format stream-json --verbose`, permission flags per sandbox as v1 `bin/subfleet-claude` builds them, `CLAUDE_CODE_OAUTH_TOKEN=<token>` (or `CLAUDE_CONFIG_DIR=<home>` for a lane home), `ANTHROPIC_API_KEY` removed from the environment, the prompt on stdin. `claude -p --resume <session id>` is the resume launch.
- **C-12.5** Attestation: Codex from the rollout's model field; Claude from the transcript located by session uuid under `~/.claude/projects/`, per-message `model` within the attempt's recorded byte range, exactly one transcript match required. Result is `attested`, `mismatch` (with served model), or `unattested`; never a false positive.
- **C-12.6** Deliverable: Codex from `last.md` when present, else the last `item.completed` agent message in the JSON stream. Claude from the transcript's final assistant text within the attempt's range (v1 `prefer_transcript_text` rule), else the stream's `result` text. An empty deliverable with rc 0 is class `unknown`, not `ok`.
- **C-12.7** Fixtures: `tests/fixtures/<provider>/<case>/` with `stdout`, `stderr`, `rc`, and `expected.json`; cases at minimum: success, hard limit with clock, hard limit without clock, model-scoped limit, credits rejection (the experiment-0 Fable payload), auth dead, refresh-token revoked, CLI too old, content filter, stream disconnect, model downgrade (Claude), spawn failure. Fixtures are redacted: no tokens, no cookies, no `Authorization` values.

## 13. Salvage and workspaces

- **C-13.1** Salvage runs only for a writable job, only at `finalizing`, `lost`, or kill, and only when the worktree's tree hash differs from the baseline recorded at `reserved`. It builds a temporary index from the working tree (tracked and untracked, honouring `.gitignore`), `commit-tree` with the baseline as parent, and writes `refs/subfleet-salvage/<branch>-<utc>-<attempt seq>`. HEAD, the real index, and the working tree are untouched. The ref is recorded as an artifact with role `salvage`.
- **C-13.2** A private salvage ref may be written from any branch. What is refused, at submit, at admission and again at launch, is a writable job that would write in a checkout on `main` or `master`: an in-place job whose workdir is on one, and any job whose allocated worktree has been switched to one between attempts. A job that is not in place never writes where its caller stands: the daemon cuts it a detached worktree from the caller's head (C-6.6), so it may be submitted from a checkout on `main`, and the caller's HEAD, index and files are untouched. Any push of a salvage ref to a branch named `main` or `master` is refused.
- **C-13.3** Before a new attempt on a writable job, the daemon reconciles: salvage if dirty, record the salvage ref and the current head as the checkpoint, and start the next attempt from the same worktree with a prompt suffix naming the checkpoint. A limit hit after an hour of work loses nothing committed or salvaged.
- **C-13.4** Lane worktrees the daemon allocates live under `$SUBFLEET_HOME/worktrees/`, never `/tmp`. They are removed only after the job is terminal, its salvage ref exists if the tree was dirty, and retention selects them.

## 15. Notices and waiting

- **C-15.1** Every terminal job writes a `notices` row for its caller session in the same transaction as the terminal state, after that transaction has written the state; a notice for a job whose row is not yet terminal is refused. The first line is `<job id>: <state>; rc=<rc>; deliverable=<path>; out=<-o path>`, read from the job row inside that transaction: the job's terminal state and rc, the pair `wait`, `runs` and `runs show` report, never the final attempt's outcome class and rc. The deliverable and `-o` paths name files only for an accepted job (`succeeded` with an `accepted_attempt_id`); for any other job both are `-`, whatever its attempt left on disk. The PostToolUse hook's line for a job with no notice row (C-15.2 layer 2) is rendered from the job row by the same function, so one terminal state has one rendering; likewise `wait`'s line names an `-o` file or deliverable only for a `succeeded` job, and `runs show` falls back to the `-o` path only for one. Then the summary: for a job whose last attempt reached finalization, `attempt a<seq>: <class>, rc=<rc>: <detail>`, and when the job did not accept that attempt's non-empty deliverable, `output kept, not accepted: <path>`, with `; -o <path> was not written` when the job has an `-o` path; for a job that ended without one, why (cancelled before launch, quarantined with its census, the refusal, the workspace error of C-6.8). Then any uncertainty (`quarantined`, export failed, unattested) (incident: 2026-09-24, three running Codex jobs were cancelled and correctly became `cancelled` with rc 130, their attempts `interrupted`, nothing accepted and nothing exported, but each notice was written from the attempt, `ok; rc=0; deliverable=<path>; out=<-o path>` and "Codex completed with a deliverable", so the session was told the job had succeeded and where its output was; the hook fallback later announced the same jobs `cancelled; rc=130` from the job row).
- **C-15.2** Delivery layers, most to least reliable: `subfleet wait` in a background Bash call; a PostToolUse `asyncRewake` hook (milestone 4); SessionStart and UserPromptSubmit hooks surfacing rows with state `pending` or `offered`; a best-effort socket push through the v1 mechanism, kept until tickle, muster, and `ping` have tested replacements.
- **C-15.3** Notice states: `pending` (written), `offered` (a delivery attempt was made; transport recorded), `acknowledged` (`notice.ack` from the session, or the session ran `runs show <job>`), `surfaced` (printed by a hook). A notice may be offered more than once; it is acknowledged once.
- **C-15.4** `wait` is a server-side long poll with a per-call deadline of at most 60 s; the CLI loops until the job set is terminal or `--timeout` expires (exit 124). `wait` never wakes headless lanes and never targets a lane session.

## 16. Socket protocol

- **C-16.1** Unix domain socket at `daemon.sock`, mode 0600. Newline-delimited JSON, one request then one response per line. Request: `{"v": 1, "id": "<client string>", "op": "<op>", "args": {...}}`. Response: `{"v": 1, "id": "<same>", "ok": true, "result": {...}}` or `{"v": 1, "id": "<same>", "ok": false, "error": {"code": <exit code>, "message": "...", "fix": "..."}}`.
- **C-16.2** Ops: `submit`, `list`, `show`, `wait`, `kill`, `lanes`, `readings`, `why`, `notice.pending`, `notice.ack`, `ping`, `daemon.status`. Argument and result shapes are the dataclasses in `subfleet/protocol.py`; unknown fields are ignored, missing required fields are exit 2.
- **C-16.3** `submit` returns `{job_id, request_id, created: bool}` where `created: false` means an existing job matched the request id. `wait` returns the terminal states of the requested jobs or `{"timeout": true}` after the deadline. A client that connected and sent a request but read no complete, decodable response line (a timeout while sending or reading, a reset or broken pipe, a close with no line, a line past the size cap or one that does not decode) does not know the request's outcome and never reports it as not done: the daemon may have committed it and answered after the client stopped reading, and even a failed send may have delivered the whole line. A refused connection is the one failure that proves nothing was sent (exit 69, C-17.3). `submit` and `kill` are idempotent (C-6.2, C-7.1), so the CLI and the sessions kit send the identical request once more, the same arguments under the same request id, with a 60 s deadline, and its answer is the outcome: `created: false` there is the job the first, unanswered request created, which a request id the CLI minted makes this invocation's own (`created: true` in its output), and a kill answered "already finished" is followed by `show`, because the first kill may be what finished the job, and the CLI prints the job's state and rc. Only if the re-send is also unanswered is the outcome reported as unknown (exit 1, C-17.3), naming the request id and the command that settles it: the same command with `--request-id <id>`, which never creates a second job, or `subfleet kill <job>` again, which is safe; stdout then carries no job id, and a job whose kill is unknown is not waited on. A re-sent submit that is refused does not prove the first created nothing, because submit validates before it looks up the request id and a moved HEAD is a different payload (C-6.2), so the client looks the request id up: `list` accepts `request_id`, and the client filters the rows itself as well, for a daemon that ignores the field (C-16.2). A job found is the answer when the CLI minted the id and is named in the refusal otherwise; none found, the refusal stands; a lookup that fails leaves the outcome unknown. The different-payload refusal names the job that holds the request id. A daemon gone before the re-send leaves a submit's outcome unknown and sends a kill to offline mode (C-17.5). A re-send answered only `busy` (C-16.7) was never read and settles nothing: a submit is still looked up by request id, and a job found is the answer when the CLI minted the id; otherwise, and for a kill, the outcome is reported as unknown, never as busy, since exit 69 would read as nothing sent. The message also names `subfleet runs --request-id <id>`, which finds the job whoever its caller session is (a revive's job belongs to the session it continues, so `runs --mine` would miss it); every id in a printed command is shell-quoted, so pasting it cannot change the id. A quarantine resolution (`--confirm-dead`, `--force-release`) whose outcome is unknown is to be repeated with its own flag and note, not as a plain `kill`, which would answer "already finished" and resolve nothing. `revive` and `handoff` tell the settle whether their request id was minted for the call, as `run` does; the CLI mints it before calling them, because the staged prompt is named after it, so it says so explicitly, and only `handoff --request-id` is the operator's. A handoff's brief is rebuilt from a transcript that keeps growing, so for it the lookup is named first and a re-run is said to risk a refusal as a different payload, which names the job and creates none. The unknown entry of a batch names the lookup as well. A dry run creates nothing and is not re-sent (incident: 2026-09-24, a `subfleet run --batch` entry printed "no response from the daemon within 15s" and "NOT submitted" while the daemon had committed it at 11:47:04Z, about a second before the client's 15 s deadline (event 581051); a manual `subfleet run` retry minted a fresh request id and created a duplicate job at 11:50:38Z (event 581065); a kill reported failed three times, with "no response from the daemon within 15s" and then "daemon closed the connection without a response", had committed its cancel at 11:59:01Z (event 581283)).
- **C-16.4** The daemon serves requests on a thread pool; a request handler never blocks on a provider process, a probe, or `ps`. Long-running work is queued to workers with deadlines.
- **C-16.6** The daemon does not exit because `accept` failed for want of a resource. `EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM`, `ECONNABORTED`, `EINTR` and `EAGAIN` are waited out (50 ms, doubling to 2 s, reset by the next connection accepted; by sleeping, never by waiting on the stop event, whose lock the signal handler that sets it would meet held on the same thread) and logged on the 1st, 2nd, 4th, 8th consecutive failure with the count of open connections and descriptors; any other `accept` error still ends `serve_forever`. On macOS the kernel drops the connection whose `accept` failed, so its client reads end of stream ("closed the connection without a response"): waiting out protects the process and the next client, and C-16.7 is what keeps a client from meeting `EMFILE` at all. At start, before anything else, the daemon raises its soft `RLIMIT_NOFILE` to 65536 (`subfleet/descriptors.py`), never above the hard limit and never lowering it, trying 32768, 16384 ... 1024 in turn if `setrlimit` refuses, and logs the effective soft and hard limits and what the raise achieved. `daemon install` writes `SoftResourceLimits.NumberOfFiles` (65536, or `kern.maxfilesperproc` if lower) into the launchd plist, so even a daemon that cannot raise its own limit does not start at launchd's 256. `daemon.status` reports `descriptors`: the soft and hard limits (`null` is unlimited), the descriptors open now, and the C-16.7 connection counts. (Incident: `~/.subfleet/daemon.log` holds 14 tracebacks of `OSError: [Errno 24] Too many open files` from `self._socket.accept()` in `serve_forever`, 2 on 2026-09-24 and 12 on 2026-09-25, some a few log lines apart as launchd restarted a daemon that failed again at once. Each ended the process, and every client waiting on a reply lost it. launchd had started the daemon at a soft limit of 256, and every client connection held a descriptor.)
- **C-16.7** Client connections are bounded and never wait for a reader. The daemon holds at most `max(4, min(512, (soft limit - 64) // 2))` client connections at once: 64 descriptors stay reserved for its own work, including the store, the log, the lock, the listener and its children's pipes, and each connection is allowed two. Each connection it holds has a reader thread of its own, started at `accept`, so no connection waits for a reader; requests can still wait for a thread of the request pools, and those waits are bounded by the cap. `close()` waits at most 2 s in all for readers to return, then closes every connection it still holds. One accepted past the cap gets `{"ok": false, "error": {"code": 69, "message": "the daemon is busy: ...", "fix": "try again shortly; ..."}}` at once, before its request is read, and is closed; nothing else the daemon sends over the socket carries 69. The client reads that answer even if its request met the closed socket, and because nothing was read, `Client.call` sends the same request again after 50 ms doubling to 1 s (less up to half at random), but only while less than half its deadline has passed, so a retry the daemon does read still has at least half the deadline to answer and a clean busy never becomes an unknown outcome (C-16.3); after that it reports busy. The first try has the whole deadline, and a lost answer's message names the caller's deadline. A caller with a faster answer than waiting takes busy at once (`Client(retry_busy=False)`): the prompt hooks read the store offline instead. A connection for which no reader thread can be started is answered busy as well, since nothing was read. Reads time out: a connection with no request outstanding that has sent nothing and received no reply for 60 s is closed at its next read timeout (so after 60 to 120 s of silence), and the same 60 s bounds sending one reply, so a client that stops reading frees its thread; after a reply that failed part way nothing more is sent on that connection. A request line (newline included) over 1 MiB is answered once with exit 2 and the rest of that line is discarded, and one that nests past the JSON parser's depth is answered exit 2 too; framing does not depend on how the bytes arrive. A read-only request (`list`, `show`, `wait`, `readings`, `why`, `pick`, `daemon.status`, `notice.pending`, `ping` without text, and `lanes` listing, with no action or `list`; they may record observations such as the desktop identity, nothing a caller relies on) whose client has closed its whole socket is not run: when the reader sees the client leave, such requests not yet started are cancelled, so the connection and its place under the cap go at once, and one a thread reaches later is dropped. A `wait` whose client leaves ends at its next poll. On macOS `getpeername` tells a closed client apart from one that shut down only its write half, which still gets its reply. A request that writes still runs after its client leaves, because a client disconnect cannot cancel its durable job (C-5.2). The listen backlog is `socket.SOMAXCONN` (128, macOS's default `kern.ipc.somaxconn`), since a connect refused on a full backlog reads to the CLI as no daemon at all. Refusals, idle closes and dropped requests are counted in `daemon.status` and logged on the 1st, 2nd, 4th, 8th occurrence; accept failures are counted there too and logged per consecutive run as C-16.6 says. (Before this clause every connection held one of 32 reader threads for its whole life, so 40 clients in `wait` left no reader for anyone else; `tests/unit/test_daemon_connections.py` holds that load and requires a ping answered within 2 s.)

## 17. CLI

- **C-17.1** Verbs (v1 spellings permanent, plan amendment 1): `subfleet` and `subfleet status` (table), `run`, `runs [--mine] [--running] [--last N] [--request-id ID] [--json]`, `runs show <id> [--out|--err|--json]`, `runs reap` (reconcile now), `wait <id>... | --mine | --last [--timeout S]`, `kill <id> [--wait] [--confirm-dead|--force-release]`, `resume <id> [PROMPT]`, `lanes [list|probe|enroll <credential>|hold <lane> --until|release <lane>|transfer <lane> --to v1|v2|touch [<lane>|--all] [--dry-run]]` (touch: C-18.3), `why <id> | --task T --tier X`, `daemon [start|stop|status|logs|install]`, `doctor [--live]`, `ping [--session ID] TEXT`. Aliases: `jobs` for `runs`, `show` for `runs show`, `capacity` for `status`, `notify` for `ping`, `resume-codex` for `resume`. Also first-class and permanent, from v1: `gate [pr|plan|continue]` with its 0 to 5 exit codes, `sessions [list|continue|revive|mirror]`, and `handoff <session> --to <model>`; they dispatch to the `subfleet-gate` and `subfleet-sessions` entry points. `doctor --guard-check <payload>` runs the never-rules check as a dry run that writes no denial log (C-23.24). The bare `runs show <id>` keeps v1's output shape, which agents parse today: the metadata object, then a `--- out.md ---` line and the deliverable; `--out`, `--err`, and `--json` are v2's single-artifact forms and print one thing each.
- **C-17.2** `run` flags: `--task`, `--tier`, `-m`, `-a EMAIL` (a Claude account), `-H CODEX_HOME` (a Codex home; either may name a lane id instead, and the flag's provider narrows a name, C-11.2), `-C DIR`, `-p PROMPTFILE`, `-o OUT`, `-n NAME`, `-s SANDBOX`, `-x EMAIL` (repeatable), `--allow-desktop`, `--allow-tmp`, `--in-place`, `--independent`, `--parent JOB`, `--request-id ID`, `--wait`/`--attach`, `-d`/`--detach` (default inside a Claude session), `--batch FILE` (C-17.7), `--json`, `--dry-run`, `--why`, `--no-preamble`, `-I` (isolated review; requires `-s read-only` and `-D`; C-23.2), `-D REVIEW_ROOT`. Deprecated but accepted through milestone 8 with a stderr note: `-t CLASS`, `--overflow`. Retired models are accepted with a stderr note and replaced by their successor, whatever the running policy still lists: `-m sol` (`astra`) and `-m fable` or `-t fable` (`opus`, since 2026-09-27); batch manifests, `why -m`, `pick --model`, `sessions handoff --to`, `sessions revive --model`, and `gate --peer` do the same.
- **C-17.3** Exit codes, one meaning each across every verb: 0 ok · 1 operational error · 2 invalid input · 3 no lane: no attempt could be admitted (message names the earliest reset) · 4 hard limit: the job's final attempt was `limited` and no candidate or attempt remained, whether or not a lane was pinned (message names the closure's clock) · 5 auth dead · 6 provider CLI too old · 7 refused (message names the rule and the fix) · 69 daemon unavailable · 75 queued (only with `--json` and `--no-wait-queue`) · 124 wait timeout · 125 job lost · 130 cancelled. `wait` and `--wait` return the job's rc when it is one of these; a provider rc outside the table maps to 1 with the raw rc in the message. Exit 1 also covers an outcome the CLI could not learn (C-16.3): the message says the outcome is unknown and names the request id, and such an outcome is never reported as refused, failed, or not submitted.
- **C-17.4** Stdout carries the contract (job id on `run`, the table on `runs`, the deliverable on `runs show --out`); human progress goes to stderr; `--json` emits one JSON object per line and no prose.
- **C-17.5** Offline mode: when the daemon is unavailable, `runs`, `runs show`, `status`, and `kill` work by reading the store read-only and the receipts, and `kill` signals the recorded pgid only after C-5.3 identity checks; everything else exits 69 and prints `subfleet daemon start`.
- **C-17.6** `run` inside a Claude Code session (detected as v1 does, by the session registry and env) defaults to detached and prints the four-line hint v1 prints (out path, log path, wait command, status command).
- **C-17.7** `run --batch FILE` submits every job in a manifest in one call and labels them as one batch. The manifest is TOML when the file ends `.toml` and JSON otherwise (both in the standard library; the package takes no dependency): an optional `label` (default: the file's stem), an optional `defaults` table, and `jobs`, a non-empty list of at most 256 tables; a bare JSON list is `jobs`. A table says nothing `run` cannot. Its keys are `task`, `tier`, `model` (`-m`), `account` (`-a`), `codex_home` (`-H`), `workdir` (`-C`), `prompt` (`-p`), `prompt_text`, `out` (`-o`), `name`, `sandbox`, `exclude`, `allow_desktop`, `allow_tmp`, `in_place`, `independent`, `parent`, `no_preamble`, and `allow_unmeasured_reserve`; an unknown key is exit 2. Precedence is the entry, then `defaults`, then the other flags on the same command line. Relative `workdir`, `prompt`, `out`, and `codex_home` paths resolve against the manifest's directory, so a folder of briefs moves whole. A job with no `name` is named after its prompt file. Every entry passes `run`'s own client-side checks before the first submit; if one fails, nothing is submitted and the message names the entry (exit 2, or 7 for a client-side refusal). After that the entries are independent: a submission the daemon refuses is reported (`NOT submitted`, which names only an entry the daemon refused with an error response) and the rest still go, because a caller handing off K threads wants the K-1 that can run to run; the exit code is the first failure's, else 0. An entry whose answer is still lost after its re-send (C-16.3) is reported with its outcome unknown and its request id, and it ends the batch, because a daemon that answered neither is not answering: every later entry is reported as not sent and is not sent, the exit code is 1 unless an earlier failure's code stands, and stderr prints `subfleet run --batch <file> --request-id <batch id>`, which settles every entry and creates none twice. A daemon that refuses the connection ends the batch the same way, with exit 69, the count already submitted, and the same command. A batch that stopped waits for nothing. Stdout carries the job ids, one per line in manifest order, and with `--json` one object per entry (`batch`, `label`, `index`, `name`, `workdir`, `request_id`, `job_id`, `rc`, `outcome` (`created`, `existing`, `refused`, `unknown`, or `not-sent`), and `error` and `fix` for an entry that was not submitted, where the `fix` of an unknown or unsent entry is the command that settles it) (C-17.4); stderr carries the table and the `wait` command for the whole batch. `--wait` and a synchronous `run` wait for every submitted job. `--dry-run`, `--why`, `-p`, and a positional prompt describe one job and are exit 2 with `--batch`. The batch id is `ID` with `--request-id ID` and a fresh UUID4 without it, and entry n is always `<batch id>-n`, which must fit C-1.5's 128 characters (exit 2 before anything is sent), so submitting the same manifest again with `--request-id <batch id>` after a partial failure or a lost answer adds nothing twice (C-6.2) (incident: 2026-09-24, entries of a batch without `--request-id` each had an unrelated fresh request id, so no re-run could name them, C-16.3); an in-place entry whose checkout has since moved is reported as a different payload rather than resubmitted, because the digest covers the git head. The daemon records `{id, label, index, size}` in the `job.submitted` event and in `manifest.json`, returns it as `batch` on `show` and on each labelled row of `list`, and refuses a malformed one with exit 2. It is a label for people and the menu bar app: it is not a column, not part of the payload digest, and never an input to routing; a daemon that predates it ignores the field (C-16.2).

## 18. Timers (milestone 5, interface only here)

- **C-18.1** Probe cycles wait `probe_interval_s` after the preceding cycle completes (default 60 seconds), with one probe per idle, enabled, unlatched lane per window (an `auth-dead` lane is not probed until re-enrolment and a revoked-token lane not until its credential epoch changes; C-23.44, C-23.47). The default leaves refresh headroom within the 120-second reading TTL; configured intervals remain authoritative, and busy or delayed lanes still display stale readings honestly. Keepalive is `admission-observed` evidence every 5 h 05 m; reset-credit policy is an action (C-19) with v1's rule set; a cycle starts idle Codex weekly clocks before it publishes (C-18.3); alerts fire on transition and at most every 6 h while persisting; retention runs every hour; `status.json` is published for the menu bar app every probe cycle.
- **C-18.2** `status.json` also carries `jobs`, so the menu bar app shows work as well as quota: `live` (every `running`, then `waiting`, then `queued` job, oldest first within a state), `recent` (the 8 most recently finished jobs), and `counts` by live state. Each row has `job_id`, `name`, `state`, `wait_reason` and `next_check_at` (only while `waiting`, so a finished job never shows a stale reason), `sandbox`, `workdir` (the allocated worktree once there is one), `model` and `lane_id` from the job's latest attempt (the pinned model before any attempt), `attempts`, the three timestamps, `rc`, and `batch` (C-17.7) or null. Batch labels are read from `job.submitted` events for the displayed jobs only. The section is always present, empty when nothing is running. The app keeps a batch's jobs together under one heading (`<label> · <size> jobs`) where the first of them appears, shows a waiting job's reason (`waiting: workspace`; any reason other than `capacity` is a warning), shows a failed job's exit code, and decodes a snapshot that has no `jobs` key, so an app newer than its daemon still works. The section is as fresh as the snapshot, one probe cycle (C-18.1); `subfleet runs` remains the live ledger.

- **C-18.3** Weekly clocks start on first use, so the daemon starts idle ones. A ChatGPT-subscription Codex account's weekly window starts at its first real request after a reset (a global reset, a redeemed reset credit, or natural expiry), not at the reset. Until then the usage endpoint reports the window at 0% with a `reset_at` that slides to (the read + the window's length) on every read. C-11.3 orders Codex candidates by `seven_day` reset ascending, and an unstarted window always reads the latest possible reset, so an idle lane ranks last and nothing routed starts it: every idle day moves that lane's next reset a day later, and with the fleet spending a week in about 48 hours the next reset is the binding constraint (Max, 2026-09-14: "If you know the reset starts when using it, we should touch it immediately."). *Detection* (`capacity.clock_unstarted`) reads the lane's own readings and adds no label (C-9.1): every account-wide window at least a day long (C-9.7) must be a fresh `provider` reading at exactly 0% whose `resets_at` lies within 600 s of `observed_at` plus the window's length; a long window that is stale, unread, or without a reset says nothing. The capacity view derives each Codex lane's `weekly_clock`: `not-started` on that evidence; `touched` when the evidence was read no more than 600 s after a request reached the lane, either a touch that succeeded (unless the lane's previous successful touch did not start this clock either) or a work attempt that sent one (C-23.19's rule for which attempts did), because the endpoint can still show a just-started window sliding for a few minutes and a tiny request rounds to 0%; otherwise none. *Eligibility*: no touch uses a lane that is another owner's, superseded or disabled, the desktop login (C-10.3), identity-blocked (C-10.6), credential-latched or auth-dead (C-23.44, C-23.47), limited (`limit_reached` or `allowed: false`), under an unexpired closure for the account or the touch model, or running an attempt, which is itself the first request. *The touch* is a timer turn like heal and keepalive, not a job (C-8.4, C-23.54): the probe reservation (`lane:<lane id>:slot:0` held by a `probe:timer:` holder, so admission sees the lane unavailable and counts the reservation toward `max_active_attempts`, C-6.4), then one read-only turn with the fixed probe prompt (C-11.4) through the daemon's guardian path (C-5.1), with the Codex home's API-key refusal (C-6.5), the guard trust preflight and its override (C-14.2), the API-key variables removed (C-12.3), and containment and recovery as for any probe (C-5.4 to C-5.7); a turn refused before launch leaves no probe directory. It runs the touch model, `timers.touch_model` (default `luna`, `gpt-5.6-luna`; a policy with no `models.luna` still uses that id), with a deadline of `timers.touch_timeout_s` (120). Only a Codex turn metered on the weekly window starts the clock; Spark meters on a bucket of its own and would report success while starting nothing, so `load_policy` refuses a Spark or non-Codex touch model and a retired alias (`sol` would mean Astra at `ultra` effort). A turn classified `auth-dead` disables the lane (C-23.44), and one classified `limited` writes its closure (C-9.4); every other contained turn is then re-probed under the same reservation, and the re-probe is persisted before the lease is released, so the published snapshot shows the reset the touch fixed. A re-probe that fails is recorded beside the turn's verdict (`probe_status`), never over it: the turn reached the provider. A touch is not C-23.27's refresh probe: it runs only on a lane whose credential answered, and its re-probe is that cycle's second usage read of the home, as the heal's is. *Automatically*, each probe cycle, after its verdicts are persisted and before its snapshot, reset-credit pass, alerts, and `status.json` (C-23.27), touches the eligible lanes whose fresh probe in that cycle answered `ok` with an unstarted clock and whose last touch's spacing, `timers.touch_spacing_s` (3600), has passed; the spacing absorbs the minutes the endpoint lags a new window. One pass touches at most as many lanes as there are lane workers (`keepalive_workers`, 4); the rest are touched on the next cycle. It skips a lane a probe reservation holds (`held`: a quarantined probe keeps its lease) rather than wait, rechecks the spacing once it holds the lane (another touch may have finished meanwhile), and publishes and releases each lane as its own turn finishes. One lane's failure to publish (a store that refuses its event) is that lane's `error_type`, and its verdict still stands in memory; every other lane is still published and released. An offline cycle touches nothing; `timers.touch_unstarted: false` stops automatic touches without removing the verb; a touch pass that raises is recorded as a `timer.error` and the cycle still publishes. *Records*: each touch that reserved its lane is recorded as a `timer.touch` event with status `touching` before its turn starts, so a daemon that dies mid-turn still spaces the next one and recovery records how the turn ended (and disables or closes the lane as the live path would); a turn that had already settled when the daemon stopped (its probe record `completed`) only has its lease released, and its record reads `interrupted` once the deadline plus 300 s has passed, so the next cycle may touch again; the result is a second `timer.touch` event (lane, mode `auto` or `operator`, model, status, `requested_at`, the weekly reset before and after, `ineffective`, the number of successful touches of this unstarted clock in one idle stretch (a clock read running after a touch ends the stretch, so an unstarted clock after an early or global reset is a new window, and a warning about a touch before that run is dropped), counted across any failed ones between, that left it unstarted (a forced touch of a running clock does not count), and `previous`, the lane's last touch with a verdict) and one `daemon.log` line (`lane touch ... status=...`), which never carries a provider message. A touch the daemon's own stop cut short is recorded `cancelled`, and a `touching` record older than the deadline plus 300 s reads `interrupted`; neither is a verdict on the lane, so neither spaces the next touch nor warns, and while a touch is running, cut short, or interrupted the lane's clock state and warning stand on its `previous` touch, so an operator's touch in flight neither clears a warning nor re-raises it. An automatic pass that starts clocks sends one service notice, "codex: weekly clock started on N lane(s)", naming each lane's new reset; a repeat touch of a clock the last one did not start is not announced. A lane whose clock is still not started after its touch failed, after a successful touch did not start it, or while automatic touches are off raises the warning `codex-clock:<home>` naming `subfleet lanes touch <lane>`; while the touch model is closed on it, the warning names the closure's clock and `subfleet status`. C-23.52's re-alert and recovery rules apply. *The verb*: `subfleet lanes touch [<lane>|--all] [--dry-run] [--json] [--no-wait] [--timeout S]`. A named lane (a lane id, its number, or any name C-11.2 resolves to one Codex lane; a superseded id resolves to the lane that replaced it) is touched whatever its readings and spacing say; a lane eligibility excludes is refused with exit 7 and the fix (C-6.5), and a name that is no Codex lane is exit 2. With no lane or `--all`, every eligible lane whose clock is `not-started` and whose spacing has passed is touched. An operator's pass waits up to 30 s for a lane a probe is reading. `--dry-run` prints the plan (each Codex lane's action, reason, clock, reset, and last touch) from the capacity view with the cached desktop identity, calls no provider, and writes nothing. The daemon runs the touches on its timer workers (C-16.4); the CLI collects them with `touch-status` long polls of at most 30 s, which the daemon serves from its waiter pool as it serves `wait` (C-15.4) and, for a request it no longer holds in memory (after a restart), from the last `timer.touch` event per lane; it prints `<lane>: touched · weekly reset now <instant>` for each (and `<lane>: not touched (<reason>)` for a named lane that changed state before its turn), and exits 0 when every touch succeeded, 7 if one was refused, 5 if one found its credential dead, 1 for any other failure or a named lane left untouched, and 124 when `--timeout` (300 s) passes with the touch still running in the daemon. `subfleet status` and `lanes list` mark a lane `clock not started` (or `clock touched HH:MMZ`, `clock started by a job HH:MMZ`) and count the unstarted ones; `status.json` carries `weekly_clock` and v1's `window_unstarted` for each Codex home and `unstarted` for the fleet. Incident: codex-4 (max@policyengine.org) redeemed its banked reset at 2026-09-22 20:09 ET and sat unstarted, ranked last, until a manual touch at 2026-09-23 15:52 ET, about 20 hours of weekly clock lost. v1 carried this as `subfleet touch codex` on an unmerged branch; its launchd bridge `~/bin/codex-window-touch` retires itself once `subfleet lanes --help` lists `touch`. Tests: `tests/unit/test_timers_touch.py` (including the C-11.3 regression: an unstarted lane ranks last, its reset slides a day per idle day, and only the touch fixes it), `tests/fake/test_lanes_touch_daemon.py`, `tests/unit/test_cli_lanes_touch.py`, `tests/e2e/test_lanes_touch.py`.

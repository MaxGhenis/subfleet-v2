## 3. Store

- **C-3.1** One SQLite database, `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, `busy_timeout=5000`. The schema is `subfleet/store_schema.sql`; `store.py` applies it and records `schema_version`. Migrations are additive and numbered.
- **C-3.2** Every state transition of a job, attempt, notice, lease, or action is one transaction, and every transaction that changes state also inserts an `events` row in the same transaction.
- **C-3.3** Transactions never span a subprocess call, a network call, a filesystem sync, or a sleep. Artifact copying, `ps`, `git`, and provider probes run outside transactions.
- **C-3.4** Readers other than the daemon (the CLI in offline mode, the menu bar app, Logpile) open the database read-only. Only the daemon and the guardian receipt path write, and the guardian writes files, not rows. The desktop app (section 29) never opens the database; it reads `status.json` and `catalog.json` and changes state only through daemon ops.
- **C-3.5** The CLI refuses to write to a store whose `schema_version` is newer than it knows (exit 1 with both versions).
- **C-3.6** The daemon says who holds a store lock too long and who waits too long for one. The main store's lock, the conversation store's lock and its file-write guard (`conversation-files`, held across a file write's fsyncs, C-25.3) are `lockwatch.WatchedLock`s: re-entrant locks that record the thread holding them and when its outermost hold began, and change nothing about who gets them or when. A hold longer than `HOLD_REPORT_S` (2 s) is written to `daemon.log` once, with the Python stack the holder is running at that moment (a `subfleet-lockwatch` thread samples every 0.5 s), and again when it ends, with its length; a hold no sample caught says, when it ends, where it was held. A thread that has waited `WAIT_REPORT_S` (5 s) for a lock writes one line naming itself, the number of threads waiting and the longest wait, the holder and how long it has held, the waiter's stack and the holder's live stack, and then keeps waiting. Each lock and kind of report (`hold`, `released`, `wait`, and C-3.7's `read-pool` and `read-hold`) writes at most one line per `REPORT_EVERY_S` (60 s); the rest are counted, with the longest, in the next line, or in a summary line once the window has passed. A report that raises is dropped: it never fails an acquire, and never makes a release raise after what the lock guarded is done (the review of 5841d8b found an error in a report could make `transaction()` raise after its rows were committed). SIGUSR1 makes the daemon write every thread's Python stack to `daemon.log` from `faulthandler`'s signal handler, so the dump arrives when every Python thread is stuck; it is registered as soon as the log is open (SIGUSR1's default action ends the process) and unregistered before the log closes; a daemon built in a process where an earlier one still holds the registration (tests build several) takes it over, since registering over a live registration would leave SIGUSR1 ignored. The daemon writes its identity to `daemon.lock` only once the handler is registered, with `"stack_dumps": true`, and rewrites it without the flag before it unregisters the handler; a daemon built on the main thread also sets SIGUSR1 to be ignored beneath the handler, so what `faulthandler` restores at close or at exit ends nothing. `subfleet daemon stacks` sends the signal only to the identity `daemon.lock` records, as `daemon stop` does (C-5.3, C-5.4), and only when that lock says `stack_dumps`; otherwise it signals nothing and exits 69 with the fix (restart the daemon on this version, or `sample <pid> 5`). It reads the lock again just before the signal, and when the lock has changed since (a daemon that began to stop has dropped the flag) it signals nothing and exits 1, asking to run it again. A daemon built before the flag (the installed ad2c208 reports the same version, 2.0.0a0) is refused, not killed: the review of 5841d8b showed a process without the handler exits -30 on SIGUSR1. It waits up to `--wait` seconds (5) for the log to stop growing, and prints what was written; exit 69 when no daemon runs. Incident: 2026-09-25, a `list` whose statement takes 1 ms took 34-94 s, with 18 threads waiting on the store lock, and neither the log nor a native sample could say which Python code held it.
- **C-3.7** A read never waits for a writer. The daemon's store keeps `READ_CONNECTIONS` (6) read-only connections (`query_only`) beside its one writing connection, opened on first use. A read made outside a transaction (`Store.query`, `Store.one`) takes one of them for one statement instead of the store lock, so reads never queue behind a transaction, and SQLite steps them side by side. Snapshots may hold at most all but `STATEMENT_RESERVE` (2) of the read connections (`snapshot_share`, 4 of 6), so a one-statement read (a hook's lookup, the wait hub, the control loop) always has connections no snapshot can take. No read waits for a connection longer than `READ_WAIT_S` (1 s): after that it opens one of its own for that read alone and closes it after. Every such wait is counted (`daemon.status` `read_pool`) and written to `daemon.log` under C-3.6's rate limit (kind `read-pool`), naming the waiter, whether it opened its own, and every thread holding a read connection, for what and for how long. `Store.close()` closes a read connection only once its read has ended (it waits up to `CLOSE_WAIT_S`, 5 s; a read still going then closes its own when it ends) and refuses any read that starts after it, and one that was still opening a new pooled connection, which it does not wait for: that read closes the connection it opened. The write-ahead log is bounded: the writer sets `journal_size_limit` to `WAL_SIZE_LIMIT` (64 MiB), so each time SQLite restarts the log the file is cut back to that size, and the only checkpoints are SQLite's automatic ones, which are PASSIVE: a commit never waits for a reader, it checkpoints up to the oldest snapshot still open, and the commits after that snapshot ends checkpoint the rest and restart the log. The daemon runs no RESTART or TRUNCATE checkpoint, which would hold writers while it waited for readers. Since a long read holds the log back, a read connection in use longer than `HOLD_REPORT_S` (2 s) is written to `daemon.log` once with its thread's live stack (C-3.6's sampler, kind `read-hold`). A read made by a thread that holds the store lock goes to the writing connection, so a transaction still sees its own uncommitted rows. `Store.snapshot()` gives a block of reads one committed state without the store lock (inside a transaction, the transaction's state; a store without read connections holds the lock for the block instead). No transaction begins inside a snapshot on the same thread: it raises `SnapshotWriteError` before it writes, with or without read connections, because its reads would go to the snapshot and miss its own writes (the review of 5841d8b saw `add_artifact` record a duplicate that way); a commit that races a snapshot comes from another thread. `Timers.snapshot` and every capacity view read their rows inside one and build the view after it ends (`capacity.store_rows`, `Daemon._capacity_rows`, `Timers.view_rows`), so a view build holds no read connection; `Timers.snapshot` used to open a write transaction only to read, and the first version of this clause built each view inside its snapshot, so six views building at once held all six connections and every other read waited, with no bound and no log line (review of 5841d8b: 1.53 s with the store lock free). The hot reads are bounded by what they return, not by the history kept: a capacity view reads only the readings that can be the newest of their lane, scope and window (`Store.latest_reading_candidates`: per key, those at the greatest canonical `YYYY-MM-DDTHH:MM:SSZ` timestamp, plus every reading with another timestamp shape), not every reading; a probe record is one step of the partial index `events_probe_holder` (`json_extract(data_json,'$.holder')` over the `probe.state` payloads `json_valid` accepts), and a gate's state the newest matching event found by SQLite (`json_extract`, newest first, one row), not every `probe.state` or `gate.state` event parsed in Python; batch labels and submission records are looked up by job id (`+kind`, so SQLite uses `events_job`), not by walking every `job.submitted` event; `sessions` filters session events by session in SQL, or takes only the newest per kind and session; and a view reads the reset-credit history, its reconciliations and the lane rows once (`ResetCredits.override_context`), not once per lane. Each rewrite answers exactly what the old form did; differential tests over randomized stores pin that (`tests/unit/test_store_contention_queries.py`). The one exception is a payload with a repeated key, which no writer makes (every payload is `json.dumps` of a dict): SQLite reads the key's first value and Python its last, so such a payload is found only under its first value, and Python checks what it parsed, so it is never returned or counted as another holder's or session's (review of 1516f3b). A probe record lookup takes only the newest row the index holds for a holder, so such a payload also hides its first value's older records: that holder gets none where the old walk found its previous one (review of 0e43105). A payload `json_valid` refuses is never filtered in SQL, and never given to `json_extract` (the session query guards it with `CASE`, since SQLite does not promise to test WHERE terms in the order written): a NaN or an Infinity, which `json.dumps` writes and `json.loads` reads, or a row that is not JSON at all. The partial index `events_not_json` hands every such row of the kinds asked to Python, which parses it as the old form did; a row that is not JSON, which no writer makes, is passed over where the old form raised. Both indexes are in `store_schema.sql`, so a store gets them the next time the daemon opens it, and neither can stop a store opening: `json_extract` is evaluated only for payloads `json_valid` accepts (an index on it alone fails to build over a single row that is not JSON). The store needs SQLite's JSON functions, built in since 3.38. `Timers` writes to the store only after releasing its own lock, which the control loop takes every tick. Incident: 2026-09-25, with the machine at load 85-100, a socket `list` whose statement takes 1 ms took 34-94 s while 18 daemon threads waited on the store lock; `docs/reports/2026-09-25-store-lock-contention.md` has the reproduction and the measurements.

## 4. Job and attempt state machines

- **C-4.1** Job states: `queued`, `running`, `waiting`, `succeeded`, `failed`, `cancelled`, `lost`. A `waiting` job has `wait_reason` in {`capacity`, `dependency`, `approval`, `uncertain`, `workspace`, `route`} and a `next_check_at`. Only `capacity` holds back the jobs behind it in its tier; a job waiting on its own `workspace` (C-6.8) or `route` (C-6.12) delays nothing else.
- **C-4.2** Attempt states and the boundary each one guards:

| State | Set when | Recovery if the daemon dies here |
|---|---|---|
| `reserved` | Lane lease, output lease, and any worktree lease taken; attempt row inserted | Release leases, mark attempt `failed` with class `unknown` and detail `reserved-no-launch`; the job may retry |
| `starting` | Guardian spawned; no `start.json` yet | If `start.json` holds a receipt, treat as `running`; else wait `start_grace_s` (10) then run containment (C-5.5) on the guardian pid and read `start.json` and `exit.json` again, because the guardian can write both and exit while the census runs: a receipt found then is taken on the next tick, `start.json` as above and `exit.json` as in the `running` row; else if the census is empty, release and retry; otherwise (not verifiable, or not empty) `quarantined`. A receipt is a file whose JSON value is neither empty nor false (`{}`, `[]`, `null`, `0`, `false` and `""` are none), on each tick and in this re-read alike |
| `running` | `start.json` read: pid, pgid, boot id, proc start recorded | If `exit.json` holds a receipt, move to `finalizing`; else if the guardian is alive by (pid, boot id, proc start), re-adopt; if its identity cannot be inspected, leave the attempt for the next tick; if it is dead, read `exit.json` once more (the guardian writes the receipt and then exits, so a receipt can appear between the first read and the liveness check) and move to `finalizing` when it is there; else run containment; empty means `lost`, else kill survivors and re-check, else `quarantined`. A receipt present at finalization always wins over a `lost` verdict reached before it was read (incident: 2026-09-05, under a load average above 45 a job whose provider had exited 0 was recorded `lost` with its receipt on disk) |
| `finalizing` | `exit.json` read; classification, salvage, export, notice pending | Re-run finalization idempotently; every step checks for its own completed output before acting; a census that is not verified empty waits out `exit_settle_s` (C-5.9) before quarantining |
| `succeeded`, `failed`, `interrupted`, `lost`, `cancelled`, `quarantined` | Terminal | None; `quarantined` needs an operator action (C-5.7) |

- **C-4.3** A job has at most one `accepted_attempt_id`. Acceptance and the notice insert are one transaction. A result from an attempt whose `seq` is lower than the job's current attempt, or whose state is not `finalizing`, is never accepted.
- **C-4.4** A job whose final attempt ends without an rc is `lost`, never `succeeded`.
- **C-4.5** `max_attempts` default 3; a new attempt is admitted only for classes `limited` (next candidate), `transient` (same lane after 60 s, once, then next candidate), and `lost` on a read-only job. `auth-dead`, `cli-too-old`, `content-filter`, and any class on a writable job after the workspace changed require reconciliation first (C-13.3).
- **C-4.6** An attempt never changes lane or model. A new lane or model is a new attempt.

## 5. Process ownership and containment

- **C-5.1** The daemon spawns each attempt through `subfleet-guardian`, which calls `os.setsid()` so it leads a new session and process group, then spawns the provider command as its child with the same pgid, stdout and stderr redirected to the attempt directory, and an environment that contains the lane credential, the provider home, `SUBFLEET_ATTEMPT=<attempt id>`, `SUBFLEET_JOB=<job id>`, and `SUBFLEET_ROOT=<state root>`. The guardian never receives a secret in argv. It starts the provider only after it reads the byte `1` from its launch gate, the read end of a pipe the daemon passes it above descriptor 2, where the guardian's /dev/null standard streams cannot replace it. The daemon writes that byte only after it has recorded the guardian's identity; a guardian that reads anything else there, end-of-file included, starts nothing, writes neither `start.json` nor `exit.json` (C-5.2) and exits 127. A probe (C-11.4) and the turn a Claude lane's re-enrolment runs pass their guardians the same launch gate. The daemon runs at the default QoS: `daemon install` writes launchd `ProcessType` `Interactive`, because `Standard` clamps the daemon and every process it starts to the `utility` QoS (priority 20, which no thread can raise), and `Adaptive`, which launchd moves out of Background only on XPC activity (launchd.plist(5)), runs it darwinbg (priority 4), since its clients use a Unix socket. The guardian keeps its daemon's QoS and starts the provider under a `utility` QoS clamp (`/usr/sbin/taskpolicy -c utility`), which the provider and every process it starts inherit and none can raise, so agent work stays below the operator's apps however the daemon is scheduled; a thread's own QoS and `nice` reach no child, so neither would do. taskpolicy execs the provider in its own place: its pid, process group, environment and argv are those it would have had unclamped. When taskpolicy cannot spawn the provider it exits 66 with `taskpolicy: posix_spawn: <reason>` as the first line of the provider's standard error, and the guardian records that as C-5.2's spawn failure, rc 127 and a `spawn_error` in the words Popen's own failure has, and empties that standard error, as that failure leaves it, so no adapter reads taskpolicy's reason as the provider's. `SUBFLEET_PROVIDER_QOS=inherit` in the daemon's environment runs providers at the guardian's QoS instead, as does a host without taskpolicy.
- **C-5.2** Before spawning the provider, the guardian writes `start.json` = {`guardian_pid`, `pgid`, `boot_id`, `proc_start`, `started_at`} via temp file and rename. After the provider exits it writes `exit.json` = {`rc`, `signal`, `finished_at`, `wall_s`, `child_pid`} the same way, then exits with the provider's rc. If the provider cannot be spawned, `exit.json` carries `rc: 127` and `spawn_error`.
- **C-5.3** Boot id is the stable `kern.bootsessionuuid` from `sysctl`; legacy receipts may carry `kern.boottime` seconds. Process start identity is the `lstart` column of `ps -p <pid> -o lstart=`. A pid is "the same process" only if both identities match. A legacy boot timestamp that differs from the current timestamp means unknown, not dead: macOS wall-clock correction can shift `kern.boottime` during one boot. Unknown identity never permits a signal or establishes death; a responsive daemon socket remains usable. Absent processes, reused start identities, and differing boot-session UUIDs still establish death.
- **C-5.4** The daemon may signal only a process group it recorded, and only after confirming the group leader's identity by C-5.3.
- **C-5.5** Containment enumeration collects live, non-zombie pids from three sources: the members of process group `<pgid>`; a walk of parent links descending from the guardian pid and the recorded child pid; and `ps -axEww -o pid=,command=` filtered on processes whose environment carries both `SUBFLEET_ATTEMPT=<attempt id>` and `SUBFLEET_ROOT=<state root>`. Attempt ids are a timestamp and a slug, so two daemons on one machine (or two test state roots) can mint the same id in the same second; the root is what tells their processes apart (incident: 2026-09-05, sleeping fakes from an earlier test quarantined a later test's attempt). "Verified empty" means all three returned zero live pids. If any `ps` call fails, the result is "unverifiable". The group and the walk are read from one `ps -axo pid=,ppid=,pgid=,stat=,lstart=` snapshot, so a process cannot be present in one of them and absent from the other because it exited between two reads. The snapshot's `lstart` is each live pid's start identity (C-5.3), so a census is two `ps` reads however many processes it finds, and one boot-identity read when it finds any (a census that finds none needs no `sysctl`, so a failed one cannot make it unverifiable); a pid the snapshot cannot describe (a marked process born after it) is asked about singly, and leaves the census if it is gone. A pid the snapshot does describe is not asked about again, so a census can include a process that exited just after the snapshot, where each used to be read again and dropped if gone. That errs only toward holding on: the kill protocol and C-5.9 read the census again until it empties, `--confirm-dead` can be repeated, and start grace, which reads it once, reads the receipts again after it (C-4.2). The census records each live pid's parent, group, and state as evidence, never its command or environment.
- **C-5.6** Kill protocol: mark the cancel request; SIGTERM the pgid; wait `term_grace_s` (15); SIGKILL the pgid; enumerate (C-5.5); SIGKILL any survivors individually after re-checking identity; enumerate again, repeating for up to `kill_settle_s` (3) while the census is not verified empty, because signalled processes leave the process table only when the kernel finishes tearing them down and one read taken 50 ms after SIGKILL reports an exiting process as live under load (incident: 2026-09-05, two full-suite runs quarantined attempts that a rerun did not). The window ends early on the first verified-empty census and never widens what counts as contained. Verified empty releases the workspace and finalizes with `killed_by`. Anything else is `quarantined`.
- **C-5.7** A `quarantined` attempt keeps its leases (lane slot excluded), its workspace, and its worktree. `subfleet runs show` prints the evidence. Resolution is `subfleet kill <job> --confirm-dead` after the operator checks, which re-runs C-5.5 and releases only on verified empty, or `--force-release` which records the operator's override in `events`.
- **C-5.9** After `exit.json` is read, a census that is not verified empty does not quarantine at once. The daemon allows `exit_settle_s` (3), measured from the first such census, for the guardian, which writes the receipt just before it exits, and for processes it already reaped to leave the process table, re-running the census on each tick. Survivors or an unverifiable census past the window quarantine the attempt with detail `writers remain after exit receipt`.
- **C-5.8** The daemon holds an exclusive `fcntl.flock` on `daemon.lock` and writes its pid, boot id, proc start, and version there. A second daemon exits 69. The CLI treats a lock whose recorded identity is dead as no daemon.
- **C-5.8a** A stopping daemon that has not ended `stop_grace_s` (30 s) after its stop was armed normally writes the Python stacks of up to 100 of its threads, newest first (faulthandler's cap), to `daemon.log` and calls `_exit(1)`. An independent kernel `ITIMER_REAL` timer, installed first, delivers SIGALRM with its default terminating action at `stop_grace_s + STOP_DUMP_MARGIN_S` (33 s). The nominal three-second margin normally lets a working faulthandler finish its dump and exit first. Scheduling or timer-installation delay, slow I/O, and blocked writes can consume that margin. SIGALRM ends any process still alive at the kernel deadline, including one whose ordinary dump is merely slow or descheduled, so diagnostics may be absent or incomplete even after successful faulthandler arming. It needs no GIL, successful `Event.set`, watcher wakeup, or new thread at stop time. If the kernel timer cannot be installed, arming exits 1 immediately instead of continuing without a bound. `close()` still releases `daemon.lock` only after every pool has drained, so the store keeps one writer. The bound ends the process instead of releasing the lock early, and the kernel frees the flock with the process. No guardian is signalled, and forked children do not inherit the interval timer; the next daemon adopts attempts still running (C-4.2), as after a SIGKILL. One nonblocking claim, created at startup and never released, permits only the first `arm` invocation to install the timers. A handler interrupting that invocation returns without setting the event until arming completes, so it cannot deadlock the owner before timer installation. Later invocations cannot replace either deadline. The stop is armed on the thread that begins it, before `stopping` is set: `close()` and the end of `serve_forever` call `arm` directly. A SIGTERM or SIGINT arms when the main thread runs its handler; a thread holding the GIL can delay that handler indefinitely. The handler skips `Event.set` once the event is set. A signal nested inside `set` remains bounded by the already installed timers. The startup watcher arms when anything else sets `stopping`; it is not the fallback. The stopping-line write follows timer installation and can itself block, so the line is not guaranteed to precede the dump. launchd's `ExitTimeOut` (which `daemon install` writes as `stop_grace_s` + 10 s; with none set, `launchctl print` reports 5 s) and `subfleet daemon stop` each wait `stop_grace_s` + 10 s for stops they initiate. After its wait, `daemon stop` re-verifies the identity (C-5.4) and sends SIGKILL. Raw signals and self-initiated stops do not start either external backstop. The grace outlasts probe containment during a stop: SIGTERM, up to `term_grace_s` of census polling, then SIGKILL and one census. The descriptor for the dump is opened when the daemon starts, so a daemon stopping because it ran out of descriptors can still write. A daemon built inside a test process arms nothing. The bound can end a stop that is slow but healthy, including the session mirror's flag publish, which is not crash-safe; launchd's SIGKILL, a crash or an operator's kill already cut that window. (Incident: 2026-09-25, pid 93697 shut its socket and then waited without a deadline on pool threads parked in `RLock.acquire`. It held the lock until a restart at 19:26Z, while every client was refused and every replacement exited 69; `docs/reports/2026-09-25-daemon-stop-wedge.md`.)
- **C-5.10** A worker that raises is retried with backoff, not on the next tick. The control loop offers every live attempt, every pending export, and admission to the worker pool each tick (50 ms), and a worker that raised used to be eligible again at once, so a cause that fails fast (a repository git refuses, a store error) was retried, and logged, twenty times a second for as long as it lasted. Now a key the control loop offers (an attempt id, `export:<job>`, `admission`, `timer-recovery`, `retention`) is not run again until 0.5 s after its first consecutive failure, doubling to a 60 s ceiling; a success clears the count; a running attempt's pass that stops at its pacing gate or cannot inspect, while an inspection that raised has not yet run to its end, is neither (C-5.11). A one-shot request is never paced: `resolve:<job>`, an operator's `kill --confirm-dead` or `--force-release`, is offered once, by the request itself, so holding it back would drop it after the caller was told it was accepted; it runs whenever it is asked for and its failure is logged each time. `daemon.log` gets the line on the 1st, 2nd, 4th, 8th (each power of two) consecutive failure, with the count and the next retry, and still only the exception's type, never its message (a provider or keychain error can carry a secret). The count is in memory: a restart forgives it, and recovery re-offers every live key as before (incident: 2026-09-20, `worker 20260920-081856-native-other-disability-opus/a1 failed: SalvageError` forty times in `daemon.log`; that cause was a git timeout, which paced itself at its own 15 s cap, and nothing in the daemon would have paced one that failed at once).
- **C-5.11** A running attempt or probe costs the daemon a bounded number of subprocesses, however often it is offered, and a tick costs a bounded number of store statements, however much history is kept. The control loop still offers every live attempt each tick (C-5.10) and still reads its exit receipt, its cancel request and its wall limit on each pass, and inspects a running attempt's processes as C-5.12 says, from one table every running attempt shares. A probe's wait loop, which has no shared table, reads its receipt, its job and its deadline every pass, and asks `ps` whether its guardian is still the recorded process (C-5.3) once every `inspect_interval_s` (1 s), and once more in a check that finds a new group member, to confirm the leader before recording it (C-5.4). It records the probe's owned group members from C-5.5's group source alone, one `ps -axo pid=,pgid=,stat=,lstart=` snapshot, inside that check and at most every `OWNED_CENSUS_INTERVAL_S` (0.5 s, so with the default interval on every check), capturing an identity (C-5.3) only for a member it has not recorded or whose start has changed. A running attempt's inspection that raises leaves no due time, so the retry C-5.10 schedules repeats it in full: it asks for a table at once, and is given the last one while that is less than an interval old (C-5.12). Until an inspection has run to its end, a pass that could not inspect (another attempt's read was running; the table, its boot identity or a table to record the group from could not be read; the guardian's liveness was unknown) or that stops at the pacing gate returns `DEFERRED`, which neither clears C-5.10's count nor adds to it, so a cause that lasts is retried and logged on C-5.10's backoff (review of the merge, 2026-09-26: such a pass returned normally, which counted as recovery, so whenever a `ps` read took 0.5 s or more each retry landed inside the next read and the count went 1, 0, 1). The boot identity is read as C-5.12 says; the three-source census, whose marker source reads every process's environment, is taken only to decide a release, kill, loss or quarantine. Pending exports are found with one statement (`PENDING_EXPORTS`), not a lease lookup per accepted job. A `wait` re-reads the store only as C-15.5 says, after a top-level transaction has committed a change or every `WAIT_RECHECK_S` (1 s), through one reader for all waiters; a worker pass wakes waiters only when the store's generation moved while it ran, and makes that decision before its key is released. Incident: 2026-09-24, the per-tick inspection (three subprocesses per running attempt per 50 ms tick, and every 0.5 s a census that dumped every process's environment, 2.3 MB), waiters re-reading their jobs on every worker pass, and an export sweep of 266 statements a tick saturated the store lock; `daemon.status` took 38.8 s, every client timed out, and shutdown hung until SIGKILL (docs/reports/2026-09-24-daemon-inspection-wedge.md). (Merged 2026-09-26 with C-5.12, which replaced this clause's per-attempt `LIVENESS_INTERVAL_S` pacing of running attempts with the shared table.)
- **C-5.12** Inspection is rationed; decisions are not. Each tick (50 ms) reads a running attempt's `start.json` and `exit.json`, its cancel request and its wall clock, which are files and rows. Its processes are inspected at most once per `inspect_interval_s` (1), from one process table (C-5.5's snapshot) that every running attempt shares; an inspection that raised is repeated at C-5.10's backoff, on the same table while it is less than an interval old (C-5.11). A table expires one interval after its read began. An attempt falls due when the table it was last given expires (one this daemon launches, one interval after it started the guardian, so that its first table is read after the guardian started; one it recovered, when it first asks), and is given the last table read if that expires later, which means a table read after the one it last had and less than an interval before it fell due; otherwise it reads a new one, and that is the only time a read begins. So the table's `ps` begins at most once per interval however many attempts ask and however long it takes (when it takes longer than an interval, reads run back to back, one at a time), and only the inspection that reads waits for it, and for the table's boot identity, which the reader reads before any attempt is given the table: one that finds a read running returns and asks again on its next tick, so a slow or hung `ps` or `sysctl` holds one worker, not one per running attempt (except the `kern.boottime` read below, which the legacy attempts given the table wait for together), and delays only the reading attempt's per-tick reads. The reader is whichever attempt asks first once the table has expired, and the control loop offers running attempts in the order the store lists them, so one attempt can be the reader interval after interval and wait out every slow read. An abnormal guardian death is seen by the first table read that begins after it, which begins by the first tick one interval after the death that finds a free worker, or as the read then running ends if that read (`ps`, then the boot identity) is slower than that, once that read and one fresh read (below) have run. A read that failed is rationed like one that worked, and an inspection given a failed read asks nothing singly and decides nothing, as a guardian that cannot be inspected decides nothing (C-4.2), so that a `ps` outage costs at most one capped read per interval rather than one per running attempt. The table says that the recorded guardian is alive (C-5.3), when it is, and lists the members of its group, whose identities are recorded as owned (C-5.6) only while that same table shows the recorded guardian alive and leading the recorded group; the environment scan is not run for this, because only group members are recorded. A shared table may say "alive" and nothing else, and says it only where `liveness` would (C-5.3): on an exact match of pid and start, and of the boot identity or, for a guardian recorded with a legacy boot timestamp (its UUID `sysctl` failed once as it started), a timestamp that C-5.3 matches to the table's `kern.boottime` seconds. A table reads those seconds the first time a legacy record needs them and keeps them for its life, failed or not, so every legacy attempt given the shared table shares one `sysctl`, and one that asks while it runs waits for it. A guardian it does not show alive is asked about afresh (C-5.3's own reads) before anything follows, and one that the fresh reads find alive has its group recorded from a table read for it alone, one `ps` outside the shared read (rare, since a table read after the guardian started shows it); and every census that decides (start grace, a dead guardian, the kill protocol and its settle window, C-5.9's window, quarantine resolution, probe containment) is read fresh, never from the shared table. The shared table's reader reads its boot identity just after `ps`, and a census's table the first time a live pid needs it; each reads it once, whatever the answer: every attempt given the shared table shares that read, and when it fails no attempt asks singly and nothing is decided, as for a failed `ps`; a UUID read that fell back to `kern.boottime` seconds has failed for every attempt recorded with the UUID, which C-5.3 could only call unknown against them. One boot-identity read is reused for 5 s, and only a boot session UUID is: a failed read is not remembered, and neither are the `kern.boottime` seconds that a failed UUID read falls back to, against which every process recorded with the UUID would compare as unknown and so could not be signalled; a process whose start matches is never called dead on a boot-identity mismatch until a fresh read agrees. `procs` starts `ps` and `sysctl` without `fork` (`close_fds=False`, the condition under which CPython uses `posix_spawn` on macOS), because a fork costs in proportion to the daemon's memory; the daemon's other process starts (`git`, the guardian) still fork. Every descriptor the daemon opens is close-on-exec, but macOS has no `pipe2` and no `SOCK_CLOEXEC`, so a pipe or socket that another thread is creating at that instant can be inherited, by a `ps` or `sysctl` only, which holds it until it exits within its 10 s cap: the most that follows is a close seen that much later (`close_fds=True` would close it, but CPython on macOS then forks). The one descriptor this package hands down on purpose, the guardian's launch gate, is closed by the guardian before it inspects anything. The per-tick check for exports to retry is one query driven from `leases`, and the desktop login hint (C-10.3) is parsed only when `stat` says the file changed. What slows for every attempt is only how soon an abnormal guardian death is noticed and how soon a new group member is recorded as owned, and the attempt whose inspection is reading the table waits out that read, `ps` and `sysctl`, before its own per-tick reads; and a member missed is never signalled individually (C-5.4): while it stays in the group `killpg` reaches it with the rest, and one that has left the group is quarantined (incident: 2026-09-20, with four attempts running the daemon held a full core, about fifteen process starts a second: three to ask about each healthy guardian on every tick and a census of `2 + 3N` every 0.5 s; the laptop's thermal guard, which pauses the operator's command-line processes at or above 20% CPU while the lid is closed on battery, SIGSTOPped it for two hours; measured 2026-09-24 with `tools/measure_idle_cost.py`, production tick, timers off, `origin/main` and the first version of this clause (845d663): idle 7.8% and 0.5% of a core; four running attempts and twelve waiting jobs 46.5% and 3.9%, with the `ps` it started 71.5% and 2.7%; measured again 2026-09-26, after this clause's review, at a load average near 7: idle 3.0% and 0.2%; four running and twelve waiting 29.0% and 1.9%, with its `ps` 49.3% and 2.1%).

## 6. Admission

- **C-6.1** Submission validates before touching the store: workdir exists and is not under `/tmp` unless allowed; prompt file readable; `-o` path's directory exists; sandbox in {`read-only`, `workspace-write`}; `--task`/`--tier` valid per policy or `-m`/`-a`/`-H` pins consistent; a read-only job with `-o` inside `-C` is allowed (the daemon writes it).
- **C-6.2** The payload digest is SHA-256 over the canonical JSON of: prompt bytes (as base64), resolved workdir, git head of the workdir or null, task, tier, pinned model, pinned lane, sandbox, sorted exclusions, resolved `-o` path or null, `allow_desktop`, policy hash. A repeated request id with the same digest returns the existing job id (exit 0); with a different digest, exit 2.
- **C-6.3** Admission of an attempt is one transaction that: chooses the lane and model from the decision (section 11), takes the lane slot lease `lane:<lane id>:slot:<n>` (a turn's is `lane:<lane id>:slot:turn-<n>`, C-26.9), takes the output lease `out:<resolved path>` if `-o` is set and not already held by this job, takes the worktree lease if writable (on the write target, C-6.5; a session is not a place and takes no lease), inserts the attempt as `reserved`, and records the decision. Launch happens after commit. The decision is evaluated before the transaction, off the store lock, on rows read in one read snapshot (C-3.7); the evaluation `_prepare_route` makes to decide on a probe is the one reserved on, so a job is evaluated once, not twice, before its reservation (a transient retry's pinned pair is also evaluated, as before, by `_retry_waits_on_a_slot`). The transaction never builds or reads a capacity view, reads no table whole but the small lane, lease and reset-credit ones, and never calls `evaluate`. It checks the decision on rows it reads with a few small queries (`Daemon._route_rows`, `route_check.still_stands`): every lane row, marked and merged as a view marks and merges them (`capacity.mark_desktop`, `Timers.merge_lane`, `capacity.credential_latched`); the attempts in flight (`attempts_live`); the probe leases; the readings added since the snapshot, by id (a reading id is reused only after the newest reading is deleted, so while the snapshot's newest reading stands, every reading added since has a greater id); the closures not released (`closures_active`, and by id any the snapshot held with an empty `released_at`); the lanes a confirmed reset-credit override (C-23.17) covers now, decided for the lane rows now at a view's clock (`Actions.override_context`), since whether one covers a lane turns on the lane's account key and home, so a lane enrolled or moved since can gain or lose one with no action changing (the review of 9dd4f35 found a `hard` job placed without its probe on a lane enrolled meanwhile); and the parents of the jobs a parent cap counts. The decision looks at the lanes of the models it walks (`scheduler.model_lanes`: each model's provider's, or the one lane the job's pin names), and only those are judged. A lane whose values of the fields `evaluate` reads (`scheduler.LANE_FACTS`), readings, open closures, attempts in flight in the job's pool, slot block and override are what they were, and whose own clock has not reached its horizon, is judged as it was; each other lane is judged again, alone, in memory, at the check's clock (`scheduler.judge_lane`), and ranked against the candidates that did not change (`scheduler.rank_key`). A lane's horizon (`capacity.lane_horizons`, recorded off the lock with the early decision) is the first instant at which the clock alone could change how that lane is judged: a reading it counted as fresh stops being so (its `observed_at` plus `reading_ttl_s`, or its `resets_at`), a reading observed after the view's clock becomes fresh, or a closure ends. `scheduler.evaluate` reads the clock through nothing else (`fresh_provider`, a closure's `until_at`), so before its own horizon a lane whose rows did not change is judged as it was, whatever any other lane's clock does. Each of these can close a lane, not only open one: the review of 5841d8b found a reading going stale, and the review of f48df54 an override ending (the lane's reading, held out, is below the floor) and a reported closure on a reserved model ending (the lane's slack behind a probe becomes `unmeasured`, C-11.7). `Timers.enrich_view`, which relabels an overridden lane's readings, and `_pick`, which holds them out, both decide an override at the view's clock, so one view never does the one without the other; a lane whose override began or ended since is judged again with its readings held out or put back. A fleet or parent cap that began or ended refuses or frees every lane alike, so every lane of the walk is judged again then; and when the model the decision chose has no candidate now and the chain goes on, the next models' lanes are judged, as `evaluate` walks them. The check then makes the decision an evaluation of the rows the transaction sees, at its clock, would make, exactly and in `evaluate`'s order (`route_check.as_now`): each changed lane's verdict, detail and evidence put in place, each reading it carries aged and labelled at the check's clock (a `provider` reading past `reading_ttl_s` is `stale-provider`), `evaluated_at` that clock's second; so the probe a lane needs (C-11.4) is read from now's detail, and a wait recorded on the decision is clocked by now's verdict (C-6.10). It goes on with that decision, the same lane or another, or none. It does not decide, and the transaction rolls back before it has written anything, only when it cannot rebuild what the decision rests on: the job's pin now names another lane (a re-enrolment moved the binding it follows, C-11.2); an evaluation now would raise, as the one made again off the lock then does; a policy loaded since; a clock earlier than the instant the early decision's view was built at (a clock that stepped back); a reading the snapshot held that was deleted (retention deletes readings only with a pruned job's attempts); or a row it cannot read (a timestamp that does not parse), which the evaluation made again then settles as C-6.12 says; a check that raises on every try settles the job so too (a `route` wait naming the error, backed off), never leaving it `route-moved`. Then the route is evaluated again, off the lock, and checked again, up to `ROUTE_TRIES` (3) times in one pass; then the job keeps its place (`route-moved`, C-6.11: the later jobs it competes with wait behind it, C-6.9) and the next pass, which follows at once, looks again. A clock or a row on a lane the decision does not look at never sends it back: on d04b8b3 the check refused any decision past the fleet-wide horizon, and sixty Claude lanes' staggered readings, refreshed on a 120 s cycle, refused every check of a Codex job three seconds after its evaluation, thirty passes running (review of d04b8b3); on 5d14f98 it refused a cap that began or ended, and a timer probe's lease (which counts toward the detached fleet's cap, C-6.4) held at each evaluation and gone at each check refused a job every try (review of 5d14f98). Age alone voids nothing: `ROUTE_REUSE_S` (5 s), which sent every evaluation older than that to be made again inside, is gone, since the check is exact and, on 2026-09-26, the store lock was waited for longer than that. The transaction also finds the job no attempt in flight or quarantined before it reserves one (C-26.9's two passes never take the same job, and this makes that a rule of the store). Two changes the check does not see, as the evaluation it replaces did not: `Timers` updates its in-memory probe status (`Timers.metadata`) just after the commit that records the probe, so a check made between the two reads the status from before the probe; and a commit by another process, which C-3.4 allows only as a hand edit of a running daemon's store. `daemon.status` counts under `admission.route_evaluations`: checks that kept the early decision's choice, a lane or none (`reused`), and checks that chose again from the lanes judged again (`rechosen`); evaluations made again after a check could not decide (`again`), and why (`moved`: a pin that names another lane now, an evaluation that would raise, or what the check rests on could not be rebuilt; `old`: a clock earlier than the view's; `error`: the check raised); jobs left for the next pass (`deferred`); and the lanes checks judged again (`rejudged`). Incidents: with the daemon held to 5% of a core, evaluating a whole capacity view inside this transaction held the store lock for 13.5 s (`docs/reports/2026-09-25-store-lock-contention.md`); on 2026-09-26, at load 110 to 170 with 48 jobs queued, it held it for 7.7 to 12.6 s at a time while other threads waited up to 43 s, because some commit had landed since the early evaluation nearly every time (`docs/reports/2026-09-26-admission-latency.md`).
- **C-6.4** Caps with defaults in `policy.json`. The concurrency caps are `max_active_attempts` (attempts in flight across the fleet, a probe's reservation included), `max_in_flight_per_lane` (detached attempts on one lane), `max_in_flight_unmeasured` (on a lane with no `provider` reading fresher than `reading_ttl_s`, 120; with it unset, `max_in_flight_per_lane` applies there too) and `max_active_attempts_per_parent` (attempts under one ancestor, C-6.9). The submit counts are `max_child_jobs` (children one parent may create in all) and `max_writable_per_session` (live writable jobs one session may hold, C-6.5). Each of these six is null by default, which is no cap, and the shipped policy says so; a positive whole number sets one, and anything else is refused naming the key. Until 2026-09-27 the concurrency caps were 4, 2 and 1, a fixed 1 beneath the unmeasured cap that no policy could raise, and a parent cap of 1 that the policy did not show (Max: "we should uncap everything and instead use prioritization"); until 2026-09-28 the submit counts were 8 and 8 (Max: "remove *all* caps"). `policy.cap` and `policy.lane_slot_cap` are their only readers. What bounds the fleet without them is the providers' own limits and `headroom_floor` (C-11.3, C-4.5), and C-11.3's load band, which spreads work without refusing it; the machine guard (C-6.13) can be turned on. The other bounds are not counts and keep their defaults: `max_wall_s` 21600 per job; `max_attempts` 3; `max_tokens_observed` optional per job; `workspace_git_timeout_s` 60, `worktree_add_timeout_s` 180, and `workspace_retry_max` 8 (C-6.8).
- **C-6.5** Refusals are exit 7 with the fix named: API-key home, workdir under `/tmp`, writable job that would write in a checkout on `main` or `master` (C-13.2), `-o` path held by a live job of another request id, a writable job for a session id that already has one running from another instance, a second writable job on the same worktree, a writable job beyond `caps.max_writable_per_session` when a policy sets it (none by default, C-6.4), a child beyond `caps.max_child_jobs` when a policy sets it (none by default), an isolated review (`-I`) that would inherit `CLAUDE_CODE_MANAGED_SETTINGS_PATH` or a remote managed-settings variable, and an isolated Codex review whose home carries managed requirements or a non-empty system or project config layer (C-23.3). This list is the index of refusals: a new refusal is added here, not in a clause of its own. What holds a writable job is where it writes. The write target of an in-place job is the real path of the checkout that contains its workdir (`git rev-parse --show-toplevel`), so `/repo` and `/repo/sub` are one target and two linked worktrees of one repository are two; the target of any other writable job is the worktree the daemon allocates for it (C-6.6), which no other job shares. One instance of a session may therefore hold any number of writable jobs on distinct targets, with no count unless a policy sets `caps.max_writable_per_session`, a backstop against a runaway caller and not a throttle (C-6.4: no count bounds what runs by default). An instance is a process: the caller's pid with its boot id and start time (C-5.3), read by the daemon at submit and recorded with the target in the `job.submitted` event, so a recycled pid is never mistaken for it and no schema change is needed. A submission is refused when the session has a live writable job whose recorded instance is another process that is still running (the twin), and also whenever the two cannot be told apart: the submission carries no pid, either process cannot be inspected, or the live job recorded no instance. An instance that is provably gone (no such pid, or the pid now belongs to a later process) is not a second instance: a session resumed after a restart or an account switch is one instance whose detached jobs survived, and it may dispatch again. A revive is always another instance of the session it continues (C-23.54), so a revive and any other writable job of that session refuse each other as before. Both questions need `ps` or `git`, so they are answered under the submit lock before the inserting transaction, which re-checks with SQL alone and refuses any live job the submission was not cleared against (C-3.3) (incident: 2026-09-20, a session handing five stalled threads to parallel lanes was refused every writable job after the first with "caller_session is held by a live job", whichever worktree it named; the code compared session ids and never instances, so it refused the one instance this clause never meant to stop). Milestone 9 adds: a socket `submit` of `kind: "turn"` or a `turn:` request id (C-26.1); a person-only operation from an agent (C-25.6); a writable turn whose workspace contains the state root, `~/.claude`, `~/.codex`, a lane home, or the guard's directory, and a turn on `main` or `master` without `allow_main` (C-26.10).
- **C-6.6** A writable job runs in a worktree the daemon allocates under `worktrees/<job id>/` from the caller's repo at its current head, unless the caller passes `--in-place`, in which case the daemon takes the worktree lease `worktree:<realpath>` on the checkout that contains the caller's directory (C-6.5); the provider still starts in the directory the caller named. A Claude job in an allocated worktree starts at the caller's place in it (a job run from `repo/pkg` starts in `<worktree>/pkg`), that place named as git spells it (`git rev-parse --show-prefix`, so a directory given in another case, in decomposed Unicode or through the `/System/Volumes/Data` firmlink is the committed one), and a resume starts where its source attempt's launch started; a Codex job starts at the worktree's top, because Codex's workspace-write sandbox writes only under its working directory; a directory the caller's head does not hold (untracked or ignored) is not in the worktree, so the job starts at its top.
- **C-6.7** `prompt.md` holds the caller's prompt bytes exactly as submitted; it is the digest input and is never rewritten. Prepended text is applied in two places and recorded separately: at submit, the daemon prepends to a workspace-write job that is not in place a note naming its worktree, the caller's checkout it must never write and the caller's place in the repository (with or without `--no-preamble`), and before that the write template unless `--no-preamble` (the sandbox is known at submit); the manifest records whether the template was given (`preamble`), and a resume keeps its source's choice; at launch, the Claude adapter prepends the headless block unless the prompt already contains the marker line `<!-- subfleet:headless -->` (the provider is known only after routing). The adapter writes the text actually sent to `<attempt dir>/prompt.sent.md`, the launch's `stdin_path` points at it, and it is recorded as an artifact with role `prompt-sent`.
- **C-6.8** Workspace preparation (the main or master re-check, worktree allocation, reading HEAD, and the baseline snapshot) runs before every admission, so a waiting job repeats it on each pass and one slow pass must not end the job. Every git call in it is capped by `caps.workspace_git_timeout_s` (60; `git worktree add` by `caps.worktree_add_timeout_s`, 180); finalization's salvage uses the same cap, and a caller with no policy in hand reads `SUBFLEET_GIT_TIMEOUT_S`. A git call that did not finish is never read as an answer: a timed-out `rev-parse` is not "no HEAD" and a timed-out `symbolic-ref` is not "not on main". At submit it is exit 1 with nothing stored; at launch the attempt ends with the cause as its detail; at admission it is a failure classified here. Transient failures are a timeout and an `OSError` whose errno is EAGAIN, EINTR, ENOMEM, EMFILE, ENFILE, EBUSY, ETIMEDOUT, or ENOBUFS: the job moves to `waiting` with `wait_reason` `workspace` and a `next_check_at` 5 s out, doubling per consecutive failure to a 300 s ceiling, holds no lease, blocks no other job, and returns to `queued` on the first pass that succeeds, which also resets the count. After `caps.workspace_retry_max` (8) consecutive transient failures, or at once for any other failure (git exiting non-zero, a permission error), the job is `failed` with rc 1. Nothing is discarded: each deferral is a `job.workspace_deferred` event and the terminal failure a `job.workspace_failed` event, both carrying `error_type` (the underlying exception, so `TimeoutExpired` rather than its wrapper) and `error` (git's verb, the cap, and its stderr, or the OS error; a path and an errno, never a credential); the notice text ends with the same two fields; `show` returns the latest record as `workspace`; and `daemon.log` gets one line per deferral and per failure, naming the job. The consecutive count is held in memory, so a daemon restart forgives it while the events keep the history. A `worktrees/<job id>/` directory that is not a worktree (a `git worktree add` killed at its cap) is removed and rebuilt before the job is admitted; no attempt has run in it. The baseline snapshot seeds its temporary index from a copy of the real index (mtime kept) and reads the baseline with `read-tree -m`, so its entries are the baseline's while the stat data of every unchanged path carries over and `add -A` hashes only changed files; the copy's assume-unchanged and skip-worktree bits, which `read-tree -m` keeps, are cleared across the whole index before `add -A`, since `add -A` skips such paths and the empty-index read has none, so both reads give the same tree; bytes and mtime come from one open file; with no usable real index (none yet, unmerged entries, a copy git cannot read or clear) it reads the baseline into an empty index. Trusting stat data is git's own model: a rewrite that keeps size, mtime and inode is read as unchanged (incident: 2026-09-23, axiom-corpus, 59,822 tracked files and 14 GB: the empty-index snapshot took 39 to 51 s at a load average near 6 and timed out at the 60 s cap on all eight tries, so no writable job could be admitted there; seeded, the same tree took 0.5 s). A refusal raised during preparation (C-6.5) is still exit 7 with its fix and never waits (incident: 2026-09-20, under a load average near 10 a writable job went from queued to `failed` in 19 s with "workspace preparation failed", no attempt, and nothing in `daemon.log`; the same snapshot took 0.6 s minutes later and an identical resubmission ran; twelve jobs ended that way between 2026-09-19 and 2026-09-20, read-only ones after as long as 70 minutes in the queue, because the caps were 15 s and 5 s, the exception was discarded, and every failure was terminal).
- **C-6.9** Queued jobs are considered in priority order: class, then tier in the policy's declared order, then oldest first (plan amendment 11). The classes, first to last (2026-09-27, Max: "uncap everything and instead use prioritization"): `attended`, a conversation turn from the Subfleet app (it has a pass of its own, which runs first, C-26.9); `session`, a detached job someone is waiting on now: a gate round, or a job whose caller's Claude Code session is live (a `~/.claude/sessions` row names its `caller_session`, in either case, and the row's pid is still the process that wrote it: `registry.validated` compares the row's `procStart` with one process-table read) or whose parent job is unfinished; a caller's pid alone (`caller_pid`) is not evidence, since a live pid proves a process, not the caller; and `background`, every other job (a caller that has exited, a launchd or cron submission, a batch whose dispatcher is gone). A batch a live session submits is `session`. Liveness is read once per pass, off the store lock but for one indexed query (`Daemon._liveness`), and `scheduler.priority_class` and `scheduler.ordered_jobs` are pure functions of it; with no liveness to read every detached job is `session`. The hold-back below applies only while the job's pool has a count cap (`scheduler.hold_scope`: for a detached job `max_active_attempts`, `max_in_flight_per_lane` or `max_in_flight_unmeasured`, and then behind any older competing job; for a turn either turn cap, likewise; for a job with a parent whose only count is `max_active_attempts_per_parent`, only behind an older competing job that shares an ancestor with it, since that count is shared only within a family). In an uncapped pool, the default, no job waits behind another: a later job never takes a slot an older one needs, because there are no slots to take, and a job no lane admits waits on its own clock (C-6.10) without holding anyone. Two scarce things keep their order with no cap at all. A lease: C-26.9's queue, which asks no job's kind (submit refuses a second writable job in one checkout and a second job on one output path, C-6.5, so detached contention is rare); a job is never queued for, nor held behind, nor kept from the last slot for (capped or not), a job waiting for a lease the first job holds itself: a retry keeps its job-held leases, and the waiter moves only once the retry has run (review of PR #72: two read-only resumes of one native session, the retrying one `background` and the waiter `session`, each waited for the other until `max_wall_s`). And a lane's probe lease: a detached attempt takes the lowest free `lane:<lane id>:slot:<n>` from n = 1, so `slot:0` is the admission probe's alone (C-11.4) and a probe waits for no attempt (review of the uncap plan: with no per-lane cap a busy lane nearly always had an attempt on `slot:0`, and an older writable job waiting to probe it lost the slot to each later job that needed no probe). A job that cannot be placed on this pass (it is `waiting` on `capacity` with a `next_check_at` still ahead, its probe is pending, no lane is admissible, or a lease it needs is held) holds back the later jobs of its tier **that compete with it**, and no others. Two jobs compete when some model could serve both: a pinned job's models are its one pin; a task job's are its chain from its tier upward, exactly the chain routing walks (C-11.2); a job whose models cannot be told (a lane pin with no model) competes with every job. Lane pins narrow it further: two jobs pinned to different lanes never compete, whatever their models, because neither can take a slot the other waits for; a job with no lane pin, or a pin that cannot be resolved, could use any lane and so competes on models alone (incident: 2026-09-22, three Fable gate reviews pinned to three lanes; the oldest waited on its own lane's provider limit until 19:00Z and held the other two, whose lanes were open, for six hours). So an older Opus review keeps its place against later Opus work, including work that could promote into its chain, and a Fable-pinned job does not queue behind it. With `max_active_attempts` set, a job that passes an older waiting job of its tier leaves one active-attempt slot free (`max_active_attempts` minus one), so the older job starts the moment its capacity appears rather than waiting out the jobs that passed it; with nothing older waiting, the full cap applies; and at `max_active_attempts` the pass ends: nothing later is evaluated. In a capped pool the order above still decides who is older: a waiting `session` job holds back the later `background` jobs of its tier that compete with it. Tiers never hold each other, as before (incident: 2026-09-20, an Opus review that no lane would admit, every Claude lane `reserve:fable:unmeasured` and Astra closed until the next day, headed the `standard` tier; admission held the whole tier behind it, so three Fable-pinned jobs, tier-less and therefore `standard`, stayed queued beside eleven free Fable lanes and nothing at all was admitted for more than three hours).
- **C-6.10** A capacity wait is rechecked on a clock that backs off, and a recheck that reaches the verdict it reached last time adds no decision row. The first recheck is 1 s out (plan amendment 11); each consecutive recheck with the same verdict doubles it, to a 30 s ceiling; a reset the decision knows about (a closure's `until_at`, a reading's `resets_at`) that falls sooner is still checked on time. The verdict is the chain walked, the lane and model chosen, the policy hash, and each rejected lane with its reasons (`scheduler.verdict_signature`); readings, utilization, and `evaluated_at` are evidence and are left out, and so is `no-slot` on a lane that is rejected for another reason as well: a lane that is closed, reserved, or excluded is no nearer to taking the job when its slot empties, slots fill and empty all day, and a probe's reservation counts toward the fleet cap, so each probe cycle (C-18.1) marks every lane `no-slot` for the second it runs. A lane whose only reason is `no-slot` keeps it: that job is waiting for a slot, and that is its verdict. A changed verdict is recorded and restarts the clock at 1 s. The same doubling applies to three waits that are not on a closure or a reading, so the known-reset rule has nothing to say about them: a job waiting on a lease another job holds, which was a fixed 1 s; a job whose route could not be prepared with no clock set (its probe's slot is held, or the lane changed hands); and a job whose chosen lane and model changed after its probe. The last two had no clock at all and were prepared again, with a new probe directory, on every tick; a probe directory made for a reservation that then does not happen is removed, since no record names it and recovery would never collect it. Backing off is not meant to cost a start: each pass compares the leases no probe holds (the turn pass also those admission probes hold, C-26.9) with those it saw on the pass before, counting the ones it took itself, and when one has gone (an attempt ended, a job released its worktree or its output path) every backed-off capacity wait other than a probe's own is looked at on that pass. Capacity that appears any other way (a fresh reading, a closure an operator lifts, a lane enrolled) is seen at the next recheck, so the most this clause can add to a start is 30 s. Only a capacity wait is brought forward. A job whose wait became `workspace` (C-6.8) loses its record and keeps that clock, because a look brought forward there spends one of `workspace_retry_max` retries, and eight unrelated releases would end the job. The 60 s wait after an inconclusive probe keeps its clock too, because bringing it forward would re-probe the provider on every release; it gets the other half of the rule, and a probe that ends the same way adds no second decision row. The record (verdict, consecutive rechecks, first and last look, and the latest hold in full) is held in memory per job, replaced whole on every look so that another thread never reads half of one, and dropped when the job is placed or ends. A restart therefore forgets it, as it forgets C-6.8's count: recovery makes every capacity wait due once, since what each was waiting for may have changed while no daemon ran and nothing else could bring a persisted wait forward, at the cost of one decision row per waiting job; `why` reports the record (C-6.11). C-11.5 is unchanged: the decision is still stored per attempt, and a waiting job still has the latest verdict it reached (incident: 2026-09-20, three jobs no lane would admit were each re-evaluated once a second for hours; every look prepared the workspace with git, scored every lane, and wrote a 22 KB decision row whose only new content was fresher readings: 1,628 rows in ten minutes with no attempt reserved, 29,923 rows and 681 MB of a 709 MB store, the file growing about 170 MB an hour, and the daemon at a full core; the decision said `earliest reset: 2026-09-20T22:20:00Z`, more than an hour off, on every one of them; by the next morning the store was 2.3 GB, 2.2 GB of it 98,014 decision rows. Replayed over the 80,996 rows of the six worst jobs, the verdict changed 74 times).
- **C-6.11** A job that is not placed always has a stated reason, and a fleet that places nothing says so. Each admission pass records, per job it leaves unplaced, why: `behind-older-job` with the older job's id and the tier (C-6.9); `fleet-full` with `max_active_attempts`; `slot-kept` with `kept_for`, `live`, and `max_active_attempts`, when a lane would take the job and the fleet is one short of its cap because C-6.9 keeps the last slot for an older waiting job of the tier (it is not reported as a full fleet, which an operator can see it is not); `parent-cap` (these four, and `behind-older-job`, only in a pool with a count cap, C-6.9; in an uncapped pool `no-slot` means a probe or a latched credential holds the lane); `machine-busy` with `class` and the reading that held it (`load_per_cpu` and `load_threshold`, `memory_pressure` and `memory_threshold`, C-6.13); `lease-held` with the lease keys another job holds (and, for a turn, `queued`: free keys kept for an older turn, C-26.9); `probe-pending`; `route-moved` with `tries`, when the job's route could not be settled in C-6.3's `ROUTE_TRIES` reservations in a row (a commit before each check moved the lane its pin names, or removed a reading the decision rested on) and it keeps its place for the next pass; `attempt-live` (an earlier attempt of the job is still live or quarantined, found before the job is looked at or again inside its reserving transaction); `conversation-blocked` with `conversation_id`, `blocked_by` and `legacy_hold` (a turn whose conversation is blocked, C-24.5), or with `error_type` and `error` when its turn manifest is missing, cannot be read, or does not name its conversation, message and provider, or its conversation could not be checked for a reason other than a store error, which holds that job alone (a store error is the pass's, C-6.12); `message-settled` with `conversation_id` and `state` (its message was withdrawn after the job was made; the job is cancelled, C-24.7); `approval`, `uncertain`, `workspace` (C-4.1); `route` with `error_type`, `error`, and `deferrals` (C-6.12), which is reported as that whatever else holds the job while its clock runs; otherwise the commonest first reason lanes rejected it for (`reserve:fable:unmeasured`, `closed:account`, `no-slot`, ...), with the `next_check_at` of any wait that has one. A wait that is a person's or a retry's to end (`approval`, `uncertain`, `workspace`) is reported as that even when the fleet is also full or an older job is also ahead of it. `hold` is the last pass's answer and `recheck` describes the last look (`recheck.label` is what that look found): the reason is the latest look's, not the first's, whether or not the verdict repeated; a look that ends without changing a verdict or a clock still refreshes it; and a pass that does not look at the job repeats the last hold in full (`leases`, `max_active_attempts`), so `why` never degrades between looks. A pass that raises publishes nothing: the holds and the `admission` snapshot stay as the last whole pass left them, because half a hold set would read as nothing left pending, and C-5.10 logs and paces the failure. When every lane has a standing reason the label is the commonest of those and not `fleet-full`: a probe's reservation counts toward the fleet cap, so such a job would otherwise read `fleet-full` for the second each probe runs. The record is in memory and replaced whole each pass; C-26.9's turn pass and the detached pass each replace their own jobs' part, and `hold` is read from the two together. `subfleet why <job>` returns it as `job` (`state`, `tier`, `wait_reason`, `next_check_at`, `hold`, `recheck`, `decision_source`, `decided_at`) and as `queue`, the same in sentences, ahead of the decision. A queued or waiting job with no decision row (admission held it back, or no pass has reached it) is evaluated for the answer and marked `decision_source: evaluated-now`; no decision is recorded and no job changes, because answering is not admission. The evaluation asks who the desktop login is, as every evaluation does (C-10.3), and a newly verified identity is recorded as the `desktop.identity` event it would have been on the next pass. A job that ended without a decision prints its state and `No decision recorded.`, unless admission refused it (C-6.12), which prints `Refused at admission: <message>` in its place The CLI never prints `null`, also against a daemon that predates `queue`. `daemon.status` carries `admission`: `pending` (unplaced jobs other than those held as `approval`, `uncertain`, `workspace`, `attempt-live`, `conversation-blocked` or `message-settled`, which are a person's or a retry's to end), `placed_at`, `idle_for_s` and `idle_since` (null unless jobs are pending and none has been placed), `reasons` (count per reason), and `open_lanes`; it is one snapshot, replaced whole at the end of a pass, so a status request never reads half of an update. `open_lanes` is the lanes owned by v2, enabled, not the desktop login while Claude Code uses it (C-10.3), identity not mismatched, under no account-wide closure, with a slot free (always, while no per-lane cap is set) and no probe holding it. Open means capacity exists, not that it fits: a job can still be refused an open lane by a model-scoped closure, the reserve, or its own exclusions, and the reasons say which. `subfleet status` prints one `admission:` line while `idle_for_s` is set, and its `running jobs:` count and table cover live jobs only. When jobs have been pending with none placed for 60 s, `daemon.log` gets one line (count, seconds idle, open lanes by id, reasons by count, and the first job in admission order), and one line when placing resumes or nothing is left pending. The line is a warning when a lane is open and some job is held for a reason other than ordinary queueing (`fleet-full`, `slot-kept`, `parent-cap`, `no-slot`, `lease-held`, `probe-pending`, `behind-older-job`, `route-moved`, `machine-busy`); otherwise it is information, because with no lane open or a fleet at its cap waiting is the expected answer. The fleet is looked at again every 600 s while the stretch lasts: a warning is written each time, information at most every 3600 s, so a wait that was expected when it was first logged becomes a warning within ten minutes of becoming one (incident: 2026-09-20, fifteen jobs from six sessions sat queued for more than three hours beside open lanes; `subfleet why` printed `null` for every one of them, because a job admission skips gets no decision row and the CLI printed the missing value instead of the daemon's text; `subfleet status` said `running jobs: 519`, the size of the store, because `daemon.status` carries every job as `jobs`; and `daemon.log` had not gained a line since the daemon started).
- **C-6.12** A job whose route cannot be evaluated is that job's problem and never the pass's. Evaluating one job (`scheduler.evaluate`, and `scheduler.probe_required`, which checks an unmeasured-reserve authorization) is isolated from the rest of the pass, both where the route is prepared and inside the reserving transaction, which rolls back before the job is settled; a `ValueError` (a `PolicyError` is one), `KeyError`, `TypeError`, `AttributeError`, or `IndexError` from it settles that job and the pass goes on to the next, in its tier and every other. What it settles to depends on whose the error is. A `scheduler.RouteError` is the job's own: its pin names several lanes, its pin and its model are of different providers, or its authorization is not whole. No wait can fix that and only the caller can say what was meant, so the job is `failed` with rc 2, what submit would have answered, its `wait_reason` and `next_check_at` cleared (as for any job `_fail_queued` ends); its notice and a `job.route_refused` event carry the message (`error_type`, `error`), `daemon.log` gets one line naming the job and the message, `why` prints `Refused at admission: <message>` ahead of any decision recorded before it (`refused` in its result), and a worktree admission cut for it under `worktrees/<job id>/` that no attempt used is removed, since `jobs.worktree` is set only at reservation and retention would never collect it. Two of those errors can also come from a policy edit rather than the job: a provider conflict (a tier's chain moved to another provider under a job already pinned to a lane) and an authorization's model check. Those are refused only under the policy the job was accepted with (`jobs.policy_hash` equal to the running policy's); under any other they are treated as below. Anything else is not the job's: bad capacity data, a policy that no longer knows the job's task, tier, or model (submit checked each against the policy it ran under, so a policy edit is the operator's to fix), or a defect. That is never terminal, because a restart can bring the fix and failing it could fail every queued job at once: the job waits with `wait_reason` `route`, 5 s out doubling per consecutive failure to a 300 s ceiling, each deferral a `job.route_deferred` event carrying `error_type`, `error`, `deferrals`, and `next_check_at`, and a `daemon.log` line naming the job and the error's type only (C-5.10: the message is in the event and in `why`). A route wait is not a capacity wait: it holds back no other job (C-6.9) and no released lease brings it forward (C-6.10). While its clock runs its hold is `route` with the error (C-6.11), whatever else would hold the job; once the clock is due the job goes through the pass like any other, and a pass that evaluates its route resets the count. `why` names the error, from the hold and, when `why`'s own evaluation raises, in place of the decision (`route_error` in its result); `daemon.status` counts the hold under `admission.reasons`. The count is in memory; recovery makes every route wait due, as it does capacity waits. Route holds are not ordinary queueing, so beside an open lane the idle line (C-6.11) is a warning. A store error is not isolated: that is the pass's, and C-5.10 retries it. An accepted job is always evaluable as far as submit can tell: an empty task or tier is stored as none. A transient retry (C-4.5, C-9.5) is the daemon's choice of pair, not the job's, and is pinned to the last attempt's lane and model id only while that pair could run: the running policy resolves the id (a current id or a `retired` alias) to a model of the lane's provider, and the lane (or its re-enrolled successor) is enabled, v2-owned, and not identity-blocked. While it is pinned, its C-6.9 demand is that one model on that one lane; once a look has let the pin go, the job's demand is its own on that pass and while its clock runs, so it neither passes an older job it competes with nor is passed by a younger one (held behind one after a look, it waits on a C-6.10 capacity clock like any other held look, so the passes before that clock prepare no workspace and score no lane), and the next due look evaluates the pair again (a lane that recovered takes its one retry; a restart, which forgets the look, changes nothing). When the job is due, the pair is evaluated as admission would evaluate it. If the lane refuses it only for want of a slot (in flight, the fleet or a parent at its cap, a probe holding it), the retry waits for that lane. If the lane refuses it for anything a slot will not end (a closure, the desktop login, the job's own exclusions, a latched credential, the floor, the reserve), or the pair cannot be evaluated, the job routes as submitted, which is C-4.5's "then next candidate". - **C-6.13** (the machine guard, 2026-09-27; off by default, Max's to turn on) With no count cap (C-6.4), admission can hold the detached jobs of a class at the door while this machine is saturated, and never holds a conversation turn. Policy `admission.machine_guard` names, per class (`background`, `session`), a `load_per_cpu`, a `memory_pressure` (`warn` or `critical`), or both; it is null by default, which holds nothing (2026-09-28, Max: "remove *all* caps", "nothing should be queued"), and a class it does not name is never held. The proposed setting (`policy.MACHINE_GUARD_PROPOSAL`) holds `background` jobs at 6.0 per logical CPU or `warn`, and `session` jobs at 10.0 or `critical`. A job is held while the larger of the 1- and 5-minute load averages divided by the logical CPU count is at or above its class's `load_per_cpu`, or while `kern.memorystatus_vm_pressure_level` (1 normal, 2 warn, 4 critical) is at or above its level: the larger average holds as soon as load rises and lets go only as it stays down, so a dip does not release a burst. The reading (`subfleet/machine.py`: `os.getloadavg`, `os.cpu_count`, `sysctlbyname`) is taken once per pass, costs no subprocess, and holds nothing where it cannot be read. The check (`scheduler.machine_hold`) comes before workspace preparation, so a held job costs no git and records no decision; its hold is `machine-busy` (C-6.11), ordinary queueing that is never logged as a warning, and it holds no other job back. It never counts attempts. ## 7. Cancellation

- **C-7.1** `kill` inserts a cancel request in the job row (`cancel_requested_at`) in one transaction and returns; the daemon performs C-5.6 asynchronously. `kill --wait` blocks until terminal.
- **C-7.2** If the cancel commits before acceptance, the job becomes `cancelled` even if an attempt later reaches `finalizing`; that attempt's artifacts are kept and it is marked `interrupted`. If acceptance commits first, `kill` returns 0 and prints "already finished".
- **C-7.3** A parent's cancel cancels every child job not submitted with `--independent`, in the same transaction that records the parent's request.
- **C-7.4** A job that is `queued` when cancelled becomes `cancelled` immediately and releases its leases.

## 8. Artifacts and export

- **C-8.1** Every file the daemon publishes (deliverable, `-o` export, `manifest.json`, receipts) is written as: temp file in the destination directory, `os.fsync(fd)`, `os.rename`, `os.fsync` on the directory descriptor.
- **C-8.2** The deliverable is captured once at `finalizing` from the adapter (C-12.6) and recorded in `artifacts` with role `deliverable`, path, bytes, and SHA-256. The raw stream, stdout, stderr, and lane log are recorded with their own roles. Nothing appended to a transcript after the attempt's exit changes the deliverable.
- **C-8.3** The `-o` export is a copy of the accepted deliverable published by C-8.1 after acceptance. A failed export sets `export_error` on the job and emits an event; the job stays `succeeded`.
- **C-8.4** Retention: newest 500 jobs or 2 GiB (policy `retention.jobs`, `retention.bytes`), whichever binds, counted over jobs that are not conversation turns (turn jobs have their own budget, C-26.12), computed outside transactions in a maintenance pass; jobs that are active, `quarantined`, have unread notices addressed to a session, hold salvage refs referenced nowhere else, or are a gate's evidence are never pruned. A notice with no session can never be read, so it pins nothing (review IR-17). Probe and keepalive results live in `readings` and `events`, not in `jobs`.

## 9. Evidence labels and classification

- **C-9.1** Reading labels: `provider` (a server reported it; source and age recorded), `stale-provider` (the same beyond `reading_ttl_s`), `admission-observed` (this model recently succeeded or was rejected on this lane; remaining quota unknown), `local-backoff` (a routing decision with an explicit expiry and reason), `unknown`. No other label exists. A percentage is rendered only from a `provider` or `stale-provider` reading, and a stale one is marked stale.
- **C-9.2** Classification precedence is authentication, then admission, then quota, and the classifier records which evidence answered each. Outcome classes: `ok`, `limited`, `auth-dead`, `cli-too-old`, `content-filter`, `transient`, `unknown`. The raw rc and signal are always kept beside the class. An attempt the daemon signalled (`killed_by` set: an operator's kill, the wall limit, recovery of a dead guardian's group) is never `ok`, whatever its rc and deliverable, except a conversation turn whose driver recorded `complete` (C-24.4: that is the provider's own end-of-turn event, not an exit status, so a stop that came after it does not undo it): finalization records it `unknown` with the detail `stopped by <killed_by>: exit <rc> after the daemon's signal is not a finished deliverable`. The daemon decides this, not the adapter, so it holds for every provider; like C-12.6's empty-deliverable rule it is recomputed from the attempt row on every finalization while `finalization.json` keeps the adapter's verdict, and whenever either rule overrides that verdict the attempt's evidence keeps it as `provider_verdict` (incident: 2026-09-24, three running Codex jobs were cancelled; Codex exited 0 after the SIGTERM and left its last interim progress message, 32 to 61 words such as "I am checking the newer validation code before finalizing", in `last.md`, which the adapter classified `ok`, "Codex completed with a deliverable").
- **C-9.3** `auth-dead` requires a 401 from a usage endpoint, an explicit organisation-block message, a refresh-token-revoked event, or the provider's refusal of the lane's own key ("Incorrect API key provided", `invalid_api_key`; codex-1, -3 and -6 failed every job that way on 2026-09-25 while classed transient). For Codex any other 401 is `transient`. For Claude, a credential-failure signature (a 401, `authentication_error`, a revoked token) in a run that never reached `system/init` is `auth-dead`, because the credential never authenticated; after `system/init` it is not auth evidence. A 403 from the Claude usage endpoint on a setup token is expected scope and is not evidence. A limit-looking phrase with a successful `system/init` is `limited`, not `auth-dead`. A Codex conversation turn's `unauthorized` error is not evidence on its own: the turn is `unknown` and the lane's usage endpoint decides (design §7).
- **C-9.4** `limited` carries scope (`account` or a model id), the provider's reset clock when reported, else a guessed clock of now + 3600 s marked `clock_source: guessed`, and the evidence (event, stderr line, or rc). It writes a closure (C-9.6).
- **C-9.5** `transient` covers 5xx, stream disconnects, DNS and TLS failures, and "model at capacity" messages. It never writes a closure; it allows one same-lane retry after 60 s.
- **C-9.6** A closure is (lane, scope, until, reason, clock source, source event). A new closure on the same lane and scope extends `until` but never shortens it. Closures expire by clock; nothing else releases a provider-limit closure except a later `provider` reading that shows the window reset.
- **C-9.7** Codex windows are classified by duration (`window_minutes` 300 is `five_hour`, 10080 is `seven_day`, anything else keeps its minute count as the key), never by slot position.
- **C-9.8** Claude `rate_limit_event`: `unifiedWindows.<window>.utilization` is a fraction in [0, 1] and `resetsAt` is epoch seconds; `status: allowed` yields `provider` readings for the shared five-hour and weekly windows with scope `account`, and a scoped weekly Fable reading when `seven_day_overage_included` is present; over-cap utilization is stored as exhausted (1) with the original retained in evidence; `status: rejected` yields no utilization reading; it yields one `admission-observed` reading for the requested model whose `window` is the literal `admission` (the only value of `window` that is not a duration key), with `resetsAt` as the closure clock when present, and `errorCode` recorded. Named rejection types `seven_day_overage_included`, `seven_day_opus`, and `seven_day_sonnet` close their respective model scopes; shared and unknown limit types close the account. `overageStatus` is parsed independently and never treated as admission evidence.

## 10. Lanes and credentials

- **C-9.9** The Claude usage sensor that costs no model turn is `https://api.anthropic.com/api/oauth/usage`, read with the lane's own credential (source `oauth-usage`). It yields `provider` readings for the account windows `five_hour` and `seven_day` (scope `account`) and one `provider` reading per `limits[]` row of kind `weekly_scoped`, scope = the policy model id for the row's `scope.model.display_name`, window `seven_day`; utilization is normalised to a fraction. HTTP 429 yields no reading and the server's `Retry-After`, which the timer honours before asking that lane again; 401 is auth-dead; 403 is no-scope; anything else is unavailable and yields no reading. Reads are paced `reserve.usage_spacing_s` apart (3) because the endpoint penalises bursts (2026-09-06: fourteen back-to-back reads earned `Retry-After: 3035`). C-10.6 holds: the readings count only when the profile endpoint, asked with the same credential, binds the lane. The timer's periodic Claude probe is this read; a model turn is spent only by the pre-launch probe (C-11.4) and keepalive. A Claude home lane's login lives in the config directory's `.credentials.json` or, on macOS, in the keychain item `Claude Code-credentials-<sha256(CLAUDE_CONFIG_DIR)[:8]>` (observed 2026-09-06); its access token expires within hours and carries a refresh token the CLI renews when it runs. An access token past `expiresAt`, or a 401 on a home lane with a refresh token, is `expired-token`, never auth-dead: the timer spends one minimal turn under that home (C-23.47's heal, at most once per 20 minutes per credential epoch) and reads usage again.
- **C-10.1** A lane row is an immutable binding of provider, account key, credential reference, credential epoch, optional home, `owner` (`v1` or `v2`), and `desktop` flag. The credential reference is a keychain item name (`claude-quota-<email>`, as v1) or a home directory path; the store never holds a secret.
- **C-10.2** Enrolment probes before recording: Codex reads `auth.json`, refuses an API-key login and a free plan, and probes the usage endpoint; Claude runs one Haiku turn under the token with `--output-format stream-json --verbose` and reads the `rate_limit_event`. A re-enrollment runs only that turn through its process fence; the keychain reads that resolve a keychain-token credential run outside it.
- **C-10.3** A lane whose Claude identity (C-10.6) equals the identity of the desktop app's keychain credential is `desktop`. It is refused while Claude Code is using the desktop login, unless the job has `allow_desktop`, and is otherwise a candidate that sorts after every other lane (C-11.3) (2026-09-27, Max: excluding it "makes sense if we're using sf thru the cc app but not if thru the sf app"; until then it was never a candidate without `allow_desktop`). Claude Code uses the login while its own registry, `~/.claude/sessions/<pid>.json`, has a row that is alive, is not a Subfleet run, and shows use. Alive: its pid is live and, where it records `procStart`, that process started then (`registry.validated`, against one process-table read; a stale row whose pid another process reuses is dead, and one without `procStart`, an older Claude Code, is alive on its pid). Not a Subfleet run: an `sdk-*` row is left out only when a live attempt owns its process (its process group is the attempt's `pgid`, or it is the attempt's child) or runs its session (`native_session_id`); the entrypoint alone proves nothing about the credential, so any other headless run counts like the Claude app's rows (`claude-desktop`) and a terminal's (`cli`). Use: a `busy` status, or a status time (`statusUpdatedAt`, else `updatedAt`) within `admission.desktop_recent_s` (1800) of now; a row with no status, or a status and no time to judge it by, is unknown and counts, whatever its start. A registry directory that cannot be listed is use, and so is each row file whose process is live but whose content cannot be read or whose `pid` is missing, not a number, or not the one the file is named for; an absent directory is none (`registry.listing`, `registry.desktop_login_in_use`). The daemon reads it at most every 2 s, never under the store lock, as part of the one registry read C-6.9's classes use (`Daemon._registry_read`: rows and answer are kept together, reused for 2 s after the read finished however long it took), keeps a read only if none that began later was kept meanwhile (two reads may overlap; the slower never replaces the newer, whatever either found), ages the answer from when that read began, and a reservation treats an answer older than `DESKTOP_IN_USE_MAX_AGE_S` (10 s) as use; and puts the answer on the desktop lane as `desktop_in_use`, a `scheduler.LANE_FACTS` field; a desktop lane without the field is in use. The reservation reads it again: the answer is refreshed off the lock before each reservation try, and `_route_rows` marks the desktop lane with it, so C-6.3's check judges that lane again when Claude Code became active (or idle) since the evaluation (review of the uncap plan: reusing the view's answer reserved the lane after Claude Code became active). The admission-probe reservation refuses the lane only while it is in use, reading the answer refreshed just before its transaction as the attempt reservation does. `status.json` judges the lane with the same signal (`Timers.desktop_in_use`). Each change, and the first answer after a start, is a `desktop.in_use` event (`in_use`, `was`, and the counts of `busy`, `recent`, `unknown` and `subfleet` rows that decided it), written by admission (at the start of the detached pass, and after each refresh a reservation or an admission probe places by, so a change a job was placed by is on record) and never by a read op (`status`, `why`, `lanes`), under a lock of its own: a read op never waits for that write (C-3.7). Timers (usage probes, keepalive, touch) still never use the desktop lane, and `status.json` marks it dispatchable only while it is not in use. The desktop identity comes from the profile endpoint using the keychain credential itself, re-read each probe cycle; `~/.claude.json` `oauthAccount` is a hint that `doctor` compares against the profile and reports when they disagree, never the authority. While the desktop identity cannot be verified, every lane whose label matches either the cached email or the last verified desktop identity is treated as `desktop`. For Codex, `~/.codex` is observed and never a lane, and a numbered lane that shares the app's account is `app_shadowed`: dispatchable, ordered like any other lane, and last for automatic reset credits (C-23.46).
- **C-10.4** A lane with `owner: v1` is never a candidate. Ownership changes only by `subfleet lanes transfer <lane> --to v2` (or `--to v1`), which records an event. For a Codex lane the transfer also relocates the home: `~/.codex-<n>` moves to `<state root>/lanes/<lane id>/` on `--to v2`, before ownership flips, and back on `--to v1`, after it flips, each in one rename. v1 discovers Codex homes by directory glob from every caller (CLI, gates, launch agents) and reads no roster, so the relocation is the fence and the roster entry is the record. The lane keeps its id: the credential is unchanged, only its path moved. A transfer to v2 is refused while v1's ledger shows a run live on that home; a transfer back is refused while a v2 attempt is live on the lane.
- **C-10.5** The credential value is resolved inside the adapter's launch builder and placed only in the child's environment. It is never logged, never written to `lane.log`, never in `manifest.json`.
- **C-10.6** A Claude identity is the pair (`account_uuid`, `org_uuid`) returned by `https://api.anthropic.com/api/oauth/profile` when requested with exactly the credential that produces the lane's usage reading. A usage reading is recorded only when the profile identity equals the lane's recorded identity. When the profile is unavailable, the reading is stored with evidence `identity-unverified` and no windows; when it differs, with evidence `identity-mismatch` and no windows, and the lane is not a candidate until an operator re-enrols it. A setup-token lane whose token lacks profile scope keeps the identity recorded at enrolment, and its stream readings carry evidence `identity-enrolled`. Incident: on 2026-09-05 v1 attributed the Axiom account's usage to RulesAtlas because it trusted `~/.claude.json`; the evidence is `~/axiom-eng-briefs/opus-expiry-20260905/identity-fix-live-result.json`.
- **C-10.7** A desktop credential and an enrolled inference-token lane are distinct lanes even when their labels match; identity, not email, joins two credentials to one account, and `doctor` reports two enabled lanes with one identity as a defect (C-23.45).

## 11. Routing evaluation

- **C-11.1** `policy.json` is the routing data. Required keys: `tiers`, `chains` (task to ordered short-model list, one per tier), `fallback: "upward-only"`, `permissions` (task to sandbox; a submit that names no sandbox, `sandbox: "policy"`, gets its task's entry, else `*`, else read-only, and an isolated review or gate round always reads only; a writable result outside a git repository is refused with the fix `-s read-only`, never downgraded; d261, 2026-09-24), `models` (short name to provider, id, optional effort and scope), `retired` (alias to short name), `desktop_login: "never"`, `caps` (C-6.4), `reset_credits`. Optional `network: {codex_workspace_write: bool}` (d260, default false in code, true in the shipped policy): a writable, non-isolated Codex job gets `-c sandbox_workspace_write.network_access=true`, and a Codex conversation turn under `bypass` gets `networkAccess: true` (under `ask` and `accept-edits` a network command still reaches the person as an approval); wherever the network is granted the launch also carries `-c features.unified_exec=false` (C-23.6), because unified exec's `write_stdin` feeds a shell text the never-rules guard never sees; read-only and isolated launches never get the network. The file's SHA-256 is the policy hash on every job.
- **C-11.2** Evaluation for a `--task`/`--tier` job walks the chain from the tier's index upward. For each model, candidates are lanes of the model's provider that are enabled, `owner: v2`, not `desktop` while Claude Code uses the desktop login (unless allowed, C-10.3), not in the job's exclusions, not under an unexpired closure for scope `account` or the model id, and with a free slot (C-6.4; always, while no per-lane cap is set). The first model with a candidate wins. A `-m` pin evaluates one model and never falls back; `-a` or `-H` evaluates one lane. A pinned job evaluates one model, its `-m` model or else the first model of its task's chain from its tier, and so runs only on that model's provider. The pin is resolved to one lane id by `scheduler.resolve_lane` once, at submit, against the lanes admission evaluates named as the capacity view names them (each lane's row with its latest probe verdict merged in, as `Timers.enrich_view` merges it, so a Codex lane also answers to the email its usage probe reported, and keeps it through a probe that could not read the account; the same roster serves admission and recovery), and the job stores that lane id. The name as typed is kept in the `job.submitted` event (`pin.requested`, `pin.lane_id`) and, except for a job carrying an unmeasured-reserve authorization, in the request digest; a retry of an accepted request whose name no longer resolves to one lane is answered from the lane it was accepted on, so a retry still finds its job (C-6.2). An authorized job's digest binds the lane id it was granted for (C-11.7a), so its retry after the name comes to name another lane is refused as a different payload. A lane id matches only itself, except that a disabled lane whose credential an enabled lane now holds (a re-enrolment, C-10.2: the same account on the same credential) resolves to that lane, so a job pinned before a re-enrolment runs on its successor, and attempts on a lane and on its successor are attempts on one lane when retries and exclusions are counted (C-4.5: one same-lane retry, then the next candidate), a resume included, whose launch accepts the successor of the lane it recorded because the native session lives under the credential's home, not under a lane id (C-12.3); a job carrying an unmeasured-reserve authorization never follows, because the authorization names the lane id it was granted for (C-11.7). Any other name (an account key or its account part, a label, a Codex email, a home) may match several lanes, and narrowing drops only lanes that could never take the job: lanes of another provider than the job's, taken from the job's model or task, else from the flag that pinned it (`-a` a Claude account, `-H` a Codex home, sent as `pinned_provider`), a disabled lane when an enabled lane that also matches is bound to the same credential, and a lane whose credential proved to hold another account (C-10.6) when another lane of the same provider also matches (across providers the name stays ambiguous); such a lane keeps the email its probe read as `observed_email`, never as a name it answers to. A name given with `-a` or `-H` names a lane of that flag's provider only, so a job whose model runs on the other provider is refused at submit (exit 2), as v1 refused `-a` with a Codex model; a lane id says its own provider whatever flag carried it. A name that still matches several lanes is refused at submit with exit 2 naming the lane ids (`-a <lane id>` pins one). Resolving once means no later roster change (a probe reporting an email, a lane enrolled) can make an accepted pin ambiguous. A job accepted before this rule may still carry a name: each daemon start rewrites the pin of every unfinished job whose name resolves to one lane (`job.pin_canonicalized`, from and to; a job carrying an unmeasured-reserve authorization is never rewritten) and logs one line for each it leaves. One that names several lanes is refused at admission (C-6.12). One that names no lane waits as a pin to an unknown lane always has (`pinned lane ... is unknown`, C-17.3), which admission cannot settle, and `subfleet doctor` fails its `unfinished jobs pin lanes by id` row while any job carries such a pin; a repair that raises is logged and skipped, never holding up recovery. Exclusions (`-x`) are not narrowed: a name excludes every lane it matches, which errs toward not running.
- **C-11.3** Every comparator starts with the lane's `desktop` flag, so the desktop login's lane sorts after every other candidate (C-10.3); then, for a turn, its affinity lane first (C-26.2); then the load band, the lane's attempts in flight in the job's pool divided by `admission.lane_spread` (default 2; null, no bands), so with no per-lane cap lanes fill evenly, that many attempts at a time, instead of one lane taking every job until a provider limit stops it and then hits every job on it at once; with a per-lane cap equal to the band every candidate is in band 0 and the choice is the comparator's below, as before (2026-09-27). Within a band: Codex comparator: eligible when every `provider` window has utilization below `1 - headroom_floor` (floor default 0.15); ordered by `seven_day` reset ascending (soonest first), then lane id. In-flight counts reorder Codex lanes only across bands. Claude comparator: eligible for a model by the same floor on the worst window of every scope that applies to that model; ordered first by the stranded term (a lane closed for a model the job does not need, typically Fable, sorts ahead of unstranded lanes so stranded capacity is spent first; C-23.37), then worst-window headroom descending, then in-flight ascending, then lane id. Lanes with no `provider` reading rank after measured lanes on both providers and are "eligible but unmeasured".
- **C-11.4** Before dispatching expensive work (writable, or tier `hard`) to an unmeasured lane, the daemon runs a probe with the model the job wants (C-10.2 style); a `limited` result closes the scope; `ok` records `admission-observed`. For other work the job's first attempt is the probe. A conversation turn never triggers a probe (C-26.9). A probe launch uses the fixed prompt `Reply with exactly OK. Do not use tools.` in a private read-only directory under the state root and carries `SUBFLEET_PROBE=1` in the child environment, so tooling and the fake providers can tell a probe from work. The probe's reservation re-checks, inside its transaction, that the lane is enabled, is not the desktop login while Claude Code uses it (C-10.3, the answer refreshed just before), and has no credential a timer found revoked or unusable since the evaluation (review of PR #72).
- **C-11.5** The decision record is JSON: chain walked, per-model candidate list with each rejected lane and its reason, readings and closures consulted, chosen lane and model, and the policy hash. It is stored per attempt and printed by `subfleet why <job>`; `subfleet run --why` and `--dry-run` print it without dispatching.
- **C-11.6** The observed 06:33 case (excluded desktop lane, Opus chain exhausted) must evaluate to Astra with the reason "opus: no candidate lanes after exclusions; promoted".

## 12. Adapters

- **C-11.7** Reserve rule. A Claude Max account carries a shared weekly window (`seven_day`, all models) and a model-scoped weekly window for each reserved model (`reserve.models`, today `fable`). Use of the reserved model counts against both; use of any other model counts against the shared window only, so the shared window is what ends a week of the reserved model. For a job whose model is not reserved, a lane is a candidate only when fresh complete `oauth-usage` readings, or shared/scoped readings paired by event time and attempt from one `rate_limit_event`, give slack = (1 − shared utilization) − `reserve.cap_ratio` × (1 − reserved utilization) ≥ `reserve.min_slack`: a lane with no fresh paired measurement is rejected `reserve:<model>:unmeasured` unless an active provider-reported model-only exhaustion proves the reserved model cannot use capacity before its reset; that case requires a fresh supervised probe of the requested model and never overrides fresh measured reserve restrictions, a lane below the slack `reserve:<model>:reserved`, and a lane whose usage read shows no reserved window is free. Candidates are ordered by slack, so non-reserved work lands where the reserved bucket is most spent. `cap_ratio` is the reserved bucket's size relative to the shared one; the payload does not state it, so it is set above any ratio the observed accounts allow (2.0 on 2026-09-06, from an account at 94 shared and 49 reserved, which bounds it below 1.92) and lowered only from measurement. Incident: 2026-09-05, Opus lanes on two accounts exhausted their shared window and ended their Fable week with half the Fable bucket unused.
- **C-11.7a** An operator may explicitly authorize only an unmeasured reserve verdict for one new dispatch using `--allow-unmeasured-reserve REASON` with both lane and model pinned. The daemon resolves the lane to its enrolled ID, persists the reason/evidence (nonblank, at most 2,000 characters), includes it in request idempotency and audit data, and requires a fresh same-model admission probe before reserving the work attempt, even for standard read-only jobs or previously observed admissions. The decision continues to call reserve capacity unmeasured. This exception never overrides measured reserve restrictions, account/model closures, identity or desktop protection, ownership, exclusions, or capacity caps; never rotates accounts or promotes models; and is not inherited by subsequent jobs or resumes. Dry-run remains side-effect free. An unsuccessful or identity-unbound probe cannot authorize work. Tests: `tests/unit/test_scheduler.py`, `tests/fake/test_reserve_authorization.py`.
- **C-12.1** `subfleet/adapters/base.py` defines the interface; adapters return data and never touch the store. Methods: `enroll(credential) -> LaneInfo`, `probe(lane) -> list[Reading]`, `build_launch(job, attempt, lane, credential_env) -> Launch`, `classify(attempt_dir, exit_info) -> Outcome`, `attest(attempt_dir, launch) -> Attestation`, `deliverable(attempt_dir, launch) -> bytes | None`, `resume_launch(job, attempt, lane, prompt) -> Launch | None`.
- **C-12.2** A `Launch` is argv, env additions, cwd, and the paths for stdout, stderr, and any raw stream file, plus `native_session_id` when the adapter chose it up front (Claude `--session-id`).
- **C-12.3** Codex launch mirrors v1's `bin/subfleet-codex` argument construction: `codex exec --json -m <model id>`, effort via `-c model_reasoning_effort=<effort>` when the model has one, `--sandbox <read-only|workspace-write>`, `-c hooks=<guard override>` when the guard is armed, `--output-last-message <attempt dir>/last.md`, the prompt on stdin, `CODEX_HOME=<home>`, `CODEX_API_KEY` and `OPENAI_API_KEY` removed from the environment. The thread id is read from the `thread.started` event. `codex exec resume <thread id>` on the same home is the resume launch.

Result is `attested`, `mismatch` (with served model), or `unattested`; never a false positive.

Claude from the transcript's final assistant text within the attempt's range (v1 `prefer_transcript_text` rule), else the stream's `result` text. An empty deliverable with rc 0 is class `unknown`, not `ok`.

## 13. Salvage and workspaces

- **C-13.1** Salvage runs only for a writable job, only at `finalizing`, `lost`, or kill, and only when the worktree's tree hash differs from the baseline recorded at `reserved`. It builds a temporary index from the working tree (tracked and untracked, honouring `.gitignore`), `commit-tree` with the baseline as parent, and writes `refs/subfleet-salvage/<branch>-<utc>-<attempt seq>`. HEAD, the real index, and the working tree are untouched. The ref is recorded as an artifact with role `salvage`.
- **C-13.2** A private salvage ref may be written from any branch. What is refused, at submit, at admission and again at launch, is a writable job that would write in a checkout on `main` or `master`: an in-place job whose workdir is on one, and any job whose allocated worktree has been switched to one between attempts. A job that is not in place never writes where its caller stands: the daemon cuts it a detached worktree from the caller's head (C-6.6), so it may be submitted from a checkout on `main`, and the caller's HEAD, index and files are untouched. Any push of a salvage ref to a branch named `main` or `master` is refused.
- **C-13.3** Before a new attempt on a writable job, the daemon reconciles: salvage if dirty, record the salvage ref and the current head as the checkpoint, and start the next attempt from the same worktree with a prompt suffix naming the checkpoint. A limit hit after an hour of work loses nothing committed or salvaged.
- **C-13.4** Lane worktrees the daemon allocates live under `$SUBFLEET_HOME/worktrees/`, never `/tmp`. They are removed only after the job is terminal, its salvage ref exists if the tree was dirty, and retention selects them.

## 15. Notices and waiting

- **C-15.1** Every terminal job except a conversation turn writes a `notices` row for its caller session in the same transaction as the terminal state, after that transaction has written the state; a notice for a job whose row is not yet terminal is refused. The first line is `<job id>: <state>; rc=<rc>; deliverable=<path>; out=<-o path>`, read from the job row inside that transaction: the job's terminal state and rc, the pair `wait`, `runs` and `runs show` report, never the final attempt's outcome class and rc. The deliverable and `-o` paths name files only for an accepted job (`succeeded` with an `accepted_attempt_id`); for any other job both are `-`, whatever its attempt left on disk. The PostToolUse hook's line for a job with no notice row (C-15.2 layer 2) is rendered from the job row by the same function, so one terminal state has one rendering; likewise `wait`'s line names an `-o` file or deliverable only for a `succeeded` job, and `runs show` falls back to the `-o` path only for one. Then the summary: for a job whose last attempt reached finalization, `attempt a<seq>: <class>, rc=<rc>: <detail>`, and when the job did not accept that attempt's non-empty deliverable, `output kept, not accepted: <path>`, with `; -o <path> was not written` when the job has an `-o` path; for a job that ended without one, why (cancelled before launch, quarantined with its census, the refusal, the workspace error of C-6.8). Then any uncertainty (`quarantined`, export failed, unattested) (incident: 2026-09-24, three running Codex jobs were cancelled and correctly became `cancelled` with rc 130, their attempts `interrupted`, nothing accepted and nothing exported, but each notice was written from the attempt, `ok; rc=0; deliverable=<path>; out=<-o path>` and "Codex completed with a deliverable", so the session was told the job had succeeded and where its output was; the hook fallback later announced the same jobs `cancelled; rc=130` from the job row). A conversation turn's outcome is its message's state (C-24.1), which the app shows.
- **C-15.2** Delivery layers, most to least reliable: `subfleet wait` in a background Bash call; a PostToolUse `asyncRewake` hook (milestone 4); SessionStart and UserPromptSubmit hooks surfacing rows with state `pending` or `offered` (inside a process Subfleet launched, only rows that name a job; C-26.13); a best-effort socket push through the v1 mechanism, kept until tickle, muster, and `ping` have tested replacements.
- **C-15.3** Notice states: `pending` (written), `offered` (a delivery attempt was made; transport recorded), `acknowledged` (`notice.ack` from the session, or the session ran `runs show <job>`), `surfaced` (printed by a hook). A notice may be offered more than once; it is acknowledged once.
- **C-15.4** `wait` is a server-side long poll with a per-call deadline of at most 60 s, counted from when the daemon read the request; the CLI loops until the job set is terminal or `--timeout` expires (exit 124), asking again after a busy answer (C-16.1). `wait` never wakes headless lanes and never targets a lane session.
- **C-15.5** `wait` has one reader, the wait hub (`subfleet/waits.py`). A waiter registers the jobs it waits on before its first read, reads its answer when it starts, and reads again only when the hub wakes it and once more when its deadline passes, so that a job that ended then is answered, not timed out; it never re-reads on another waiter's wake-up, nor on a timer while the hub's thread runs. The hub looks at the store's generation (C-5.11) when poked by `Daemon._notify` and otherwise every `WAIT_POLL_S` (0.1 s). When the generation has moved, a waiter has registered, or `WAIT_RECHECK_S` (1 s) has passed, it reads the state of every watched job and which of them hold an `out:` lease, one statement each whatever the number of waiters, and wakes each waiter whose jobs may all be returned: ended, a succeeded job's export done, or unknown to the store (the waiter then reports the unknown job, as it always did). So a wait whose last job ends by a commit on the daemon's store returns within `WAIT_POLL_S` plus three reads, poked or not: the hub's read in progress when the commit landed, the hub's read that sees it, and the waiter's own; a commit the generation does not count (another process's, C-6.3) is seen within `WAIT_RECHECK_S` plus those reads. No read has a time bound of its own: each takes what SQLite takes, plus up to `READ_WAIT_S` for a read connection (C-3.7). Waiting costs one read per commit for all waiters together, and because registration comes before the first read, no wake-up is lost. A waiter is always woken or times out. A hub pass that raises, in its read or anywhere else, wakes every waiter to read for itself, and the hub goes on. If the hub's thread ends anyway, it wakes every waiter as it goes, and the next registration or the next wait starts another thread. It does not try to start one less than `WAIT_RECHECK_S` after its last try, and a start that fails (no thread to be had) is logged and tried again after that; until a thread runs, each wait is cut to `WAIT_RECHECK_S` and its waiter reads again, and a waiter's registration ends with its wait whatever happened to the hub. `daemon.status` reports the hub under `wait_hub`: its waiters, whether a thread runs, and its reads, deaths, restarts and failed starts. A stopping daemon wakes every waiter, which answers `{"timeout": true}`. Incident: on 2026-09-25 ~21 PostToolUse hooks each held a `wait`, and every worker pass woke every waiter to re-read its jobs behind the store lock.
- **C-15.6** A hook costs one connection per question and no inspection. Its client does not check `daemon.lock` before connecting (`Client(verify_lock=False)`): that check costs a `ps` and a `sysctl` per process, and the PostToolUse hook runs on every Bash call of every session, while a hook exits 0 silently whichever way the daemon is down, which a refused connection already says. Its reads (`list`, `notice.pending`) are C-16.5's lookups.

## 16. Socket protocol

- **C-16.1** Unix domain socket at `daemon.sock`, mode 0600. Newline-delimited JSON, one request then one response per line. Request: `{"v": 1, "id": "<client string>", "op": "<op>", "args": {...}}`. Response: `{"v": 1, "id": "<same>", "ok": true, "result": {...}}` or `{"v": 1, "id": "<same>", "ok": false, "error": {"code": <exit code>, "message": "...", "fix": "..."}}`. The daemon raises its open-file soft limit to 4096 at start (never past the hard limit; launchd starts it with 256) and reads at most 512 connections at once. A connection holds a reader until its client closes, and counts against the 512 only while it does: one whose client has left while its request still runs does not. A connection past the 512, or one for which no reader thread can start, is answered at once with exit 69 and "try again shortly", before its request is read, rather than queued; each such answer is counted and logged at most once a minute, from the daemon's first minute on. Reader admission finishes before the reader can read a request, including when thread creation fails after queuing it. Because the request was never read, asking again is safe: `subfleet wait`, `kill --wait` and `run --wait` ask again, backing off from 0.25 s to 5 s, within `--timeout`, and `subfleet gate`'s poll does so for up to 180 s across all busy retries. Each retry's transport timeout and backoff use only the original deadline's remaining time. `subfleet daemon status` reports a daemon that answered, busy or not, as running (exit 0). When a client has closed its connection, not merely its write half, what it sent that no pool has started is dropped. A `wait` has a thread for every connection that could send one. `daemon.status` reports `connections`: `reading` (against the cap), `open` (not yet closed), `cap` and `refused_busy`. A client whose request write fails because the daemon already answered and closed still reads that answer (the CLI and the app). The socket listens with the system's largest queue (`SOMAXCONN`, 128 on macOS); past it a client is refused as if no daemon ran. `accept` failing for want of descriptors or memory (EMFILE, ENFILE, ENOBUFS, ENOMEM), on a connection its client abandoned, or on an interrupted call, is logged at most once a minute and the daemon keeps serving; the connection it failed on is lost (macOS drops it). Failing without a break for 300 s, the daemon exits so launchd starts a fresh one.
- **C-16.2** Ops: `submit`, `list`, `show`, `wait`, `kill`, `lanes`, `readings`, `why`, `notice.pending`, `notice.ack`, `notice.mark`, `ping`, `daemon.status`, `gate.start`, `gate.poll`, `gate.continue`, `sessions`, `pick`, `operations`, and the section 25 ops. Argument and result shapes are the dataclasses in `subfleet/protocol.py`, except the section 25 ops', which are design §5's (C-25.2); unknown fields are ignored, missing required fields are exit 2.
- **C-16.3** `submit` returns `{job_id, request_id, created: bool}` where `created: false` means an existing job matched the request id. `wait` returns the terminal states of the requested jobs or `{"timeout": true}` after the deadline. A client that connected and sent a request but read no complete, decodable response line (a timeout while sending or reading, a reset or broken pipe, a close with no line, a line past the size cap or one that does not decode) does not know the request's outcome and never reports it as not done: the daemon may have committed it and answered after the client stopped reading, and even a failed send may have delivered the whole line. A refused connection is the one failure that proves nothing was sent (exit 69, C-17.3). `submit` and `kill` are idempotent (C-6.2, C-7.1), so the CLI and the sessions kit send the identical request once more, the same arguments under the same request id, with a 60 s deadline, and its answer is the outcome: `created: false` there is the job the first, unanswered request created, which a request id the CLI minted makes this invocation's own (`created: true` in its output), and a kill answered "already finished" is followed by `show`, because the first kill may be what finished the job, and the CLI prints the job's state and rc. Only if the re-send is also unanswered is the outcome reported as unknown (exit 1, C-17.3), naming the request id and the command that settles it: the same command with `--request-id <id>`, which never creates a second job, or `subfleet kill <job>` again, which is safe; stdout then carries no job id, and a job whose kill is unknown is not waited on. A re-sent submit that is refused does not prove the first created nothing, because submit validates before it looks up the request id and a moved HEAD is a different payload (C-6.2), so the client looks the request id up: `list` accepts `request_id`, and the client filters the rows itself as well, for a daemon that ignores the field (C-16.2). A job found is the answer when the CLI minted the id and is named in the refusal otherwise; none found, the refusal stands; a lookup that fails leaves the outcome unknown. The different-payload refusal names the job that holds the request id. A daemon gone before the re-send leaves a submit's outcome unknown and sends a kill to offline mode (C-17.5). A re-send answered "busy" (exit 69, C-16.1) was not read, so it proves nothing about the first request, which may still be committing: it is repeated with the busy backoff until the 60 s deadline, and a daemon still busy then leaves a submit's or a kill's outcome unknown, never refused and never looked up as "none found" (merge review 2026-09-25). The message also names `subfleet runs --request-id <id>`, which finds the job whoever its caller session is (a revive's job belongs to the session it continues, so `runs --mine` would miss it); every id in a printed command is shell-quoted, so pasting it cannot change the id. A quarantine resolution (`--confirm-dead`, `--force-release`) whose outcome is unknown is to be repeated with its own flag and note, not as a plain `kill`, which would answer "already finished" and resolve nothing. `revive` and `handoff` tell the settle whether their request id was minted for the call, as `run` does; the CLI mints it before calling them, because the staged prompt is named after it, so it says so explicitly, and only `handoff --request-id` is the operator's. A handoff's brief is rebuilt from a transcript that keeps growing, so for it the lookup is named first and a re-run is said to risk a refusal as a different payload, which names the job and creates none. The unknown entry of a batch names the lookup as well. A dry run creates nothing and is not re-sent (incident: 2026-09-24, a `subfleet run --batch` entry printed "no response from the daemon within 15s" and "NOT submitted" while the daemon had committed it at 11:47:04Z, about a second before the client's 15 s deadline (event 581051); a manual `subfleet run` retry minted a fresh request id and created a duplicate job at 11:50:38Z (event 581065); a kill reported failed three times, with "no response from the daemon within 15s" and then "daemon closed the connection without a response", had committed its cancel at 11:59:01Z (event 581283)).
- **C-16.4** The daemon serves requests on a thread pool; a request handler never blocks on a provider process, a probe, or `ps`. Long-running work is queued to workers with deadlines.
- **C-16.5** A liveness question and a hook's reads never queue behind slow requests. `ping` without `text` reads nothing and is answered on the connection's own thread. `list`, `show` and `notice.pending` (`LOOKUP_OPS`) run on their own 8-thread pool, `subfleet-read`; `wait` on the waiters' pool; `submit` and `gate.*` on the workers; conversation ops on the conversation pools; every other op on the 16-thread request pool, where view builds and writes that wait for the store lock stay. With C-3.7 none of the lookups waits for a transaction either, nor longer than `READ_WAIT_S` for a read connection, and snapshots cannot take the connections kept for them. Incident: 2026-09-25, all 16 request threads were busy and a `ping` took up to 90 s.

## 17. CLI

- **C-17.1** Verbs (v1 spellings permanent, plan amendment 1): `subfleet` and `subfleet status` (table), `run`, `runs [--mine] [--running] [--last N] [--kind K | --include-turns] [--request-id ID] [--json]` (turn jobs only when asked, C-26.12; `--request-id` names the job carrying that request id, whoever submitted it and whatever its kind, C-16.3), `runs show <id> [--out|--err|--json]`, `runs reap` (reconcile now), `wait <id>... | --mine | --last [--timeout S]`, `kill <id> [--wait] [--confirm-dead|--force-release]`, `resume <id> [PROMPT]`, `lanes [list|probe|enroll <credential>|hold <lane> --until|release <lane>|transfer <lane> --to v1|v2]`, `why <id> | --task T --tier X`, `daemon [start|stop|status|logs|install]`, `doctor [--live]`, `ping [--session ID] TEXT`. Aliases: `jobs` for `runs`, `show` for `runs show`, `capacity` for `status`, `notify` for `ping`, `resume-codex` for `resume`. Also first-class and permanent, from v1: `gate [pr|plan|continue]` with its 0 to 5 exit codes, `sessions [list|continue|revive|mirror]`, and `handoff <session> --to <model>`; they dispatch to the `subfleet-gate` and `subfleet-sessions` entry points. `doctor --guard-check <payload>` runs the never-rules check as a dry run that writes no denial log (C-23.24). The bare `runs show <id>` keeps v1's output shape, which agents parse today: the metadata object, then a `--- out.md ---` line and the deliverable; `--out`, `--err`, and `--json` are v2's single-artifact forms and print one thing each.
- **C-17.2** `run` flags: `--task`, `--tier`, `-m`, `-a EMAIL` (a Claude account), `-H CODEX_HOME` (a Codex home; either may name a lane id instead, and the flag's provider narrows a name, C-11.2), `-C DIR`, `-p PROMPTFILE`, `-o OUT`, `-n NAME`, `-s SANDBOX`, `-x EMAIL` (repeatable), `--allow-desktop`, `--allow-tmp`, `--in-place`, `--independent`, `--parent JOB`, `--request-id ID`, `--wait`/`--attach`, `-d`/`--detach` (default inside a Claude session), `--batch FILE` (C-17.7), `--json`, `--dry-run`, `--why`, `--no-preamble`, `-I` (isolated review; requires `-s read-only` and `-D`; C-23.2), `-D REVIEW_ROOT`. Deprecated but accepted through milestone 8 with a stderr note: `-t CLASS`, `--overflow`, `-m sol` (remapped to `astra`).
- **C-17.3** Exit codes, one meaning each across every verb: 0 ok · 1 operational error · 2 invalid input · 3 no lane: no attempt could be admitted (message names the earliest reset) · 4 hard limit: the job's final attempt was `limited` and no candidate or attempt remained, whether or not a lane was pinned (message names the closure's clock) · 5 auth dead · 6 provider CLI too old · 7 refused (message names the rule and the fix) · 69 daemon unavailable · 75 queued (only with `--json` and `--no-wait-queue`) · 124 wait timeout · 125 job lost · 130 cancelled. `wait` and `--wait` return the job's rc when it is one of these; a provider rc outside the table maps to 1 with the raw rc in the message. Exit 1 also covers an outcome the CLI could not learn (C-16.3): the message says the outcome is unknown and names the request id, and such an outcome is never reported as refused, failed, or not submitted.
- **C-17.4** Stdout carries the contract (job id on `run`, the table on `runs`, the deliverable on `runs show --out`); human progress goes to stderr; `--json` emits one JSON object per line and no prose.
- **C-17.5** Offline mode: when the daemon is unavailable, `runs`, `runs show`, `status`, and `kill` work by reading the store read-only and the receipts, and `kill` signals the recorded pgid only after C-5.3 identity checks; everything else exits 69 and prints `subfleet daemon start`.
- **C-17.6** `run` inside a Claude Code session (detected as v1 does, by the session registry and env) defaults to detached and prints the four-line hint v1 prints (out path, log path, wait command, status command).
- **C-17.7** `run --batch FILE` submits every job in a manifest in one call and labels them as one batch. The manifest is TOML when the file ends `.toml` and JSON otherwise (both in the standard library; the package takes no dependency): an optional `label` (default: the file's stem), an optional `defaults` table, and `jobs`, a non-empty list of at most 256 tables; a bare JSON list is `jobs`. A table says nothing `run` cannot. Its keys are `task`, `tier`, `model` (`-m`), `account` (`-a`), `codex_home` (`-H`), `workdir` (`-C`), `prompt` (`-p`), `prompt_text`, `out` (`-o`), `name`, `sandbox`, `exclude`, `allow_desktop`, `allow_tmp`, `in_place`, `independent`, `parent`, `no_preamble`, and `allow_unmeasured_reserve`; an unknown key is exit 2. Precedence is the entry, then `defaults`, then the other flags on the same command line. Relative `workdir`, `prompt`, `out`, and `codex_home` paths resolve against the manifest's directory, so a folder of briefs moves whole. A job with no `name` is named after its prompt file. Every entry passes `run`'s own client-side checks before the first submit; if one fails, nothing is submitted and the message names the entry (exit 2, or 7 for a client-side refusal). After that the entries are independent: a submission the daemon refuses is reported (`NOT submitted`, which names only an entry the daemon refused with an error response) and the rest still go, because a caller handing off K threads wants the K-1 that can run to run; the exit code is the first failure's, else 0. An entry whose answer is still lost after its re-send (C-16.3) is reported with its outcome unknown and its request id, and it ends the batch, because a daemon that answered neither is not answering: every later entry is reported as not sent and is not sent, the exit code is 1 unless an earlier failure's code stands, and stderr prints `subfleet run --batch <file> --request-id <batch id>`, which settles every entry and creates none twice. A daemon that refuses the connection ends the batch the same way, with exit 69, the count already submitted, and the same command. A batch that stopped waits for nothing. Stdout carries the job ids, one per line in manifest order, and with `--json` one object per entry (`batch`, `label`, `index`, `name`, `workdir`, `request_id`, `job_id`, `rc`, `outcome` (`created`, `existing`, `refused`, `unknown`, or `not-sent`), and `error` and `fix` for an entry that was not submitted, where the `fix` of an unknown or unsent entry is the command that settles it) (C-17.4); stderr carries the table and the `wait` command for the whole batch. `--wait` and a synchronous `run` wait for every submitted job. `--dry-run`, `--why`, `-p`, and a positional prompt describe one job and are exit 2 with `--batch`. The batch id is `ID` with `--request-id ID` and a fresh UUID4 without it, and entry n is always `<batch id>-n`, which must fit C-1.5's 128 characters (exit 2 before anything is sent), so submitting the same manifest again with `--request-id <batch id>` after a partial failure or a lost answer adds nothing twice (C-6.2) (incident: 2026-09-24, entries of a batch without `--request-id` each had an unrelated fresh request id, so no re-run could name them, C-16.3); an in-place entry whose checkout has since moved is reported as a different payload rather than resubmitted, because the digest covers the git head. The daemon records `{id, label, index, size}` in the `job.submitted` event and in `manifest.json`, returns it as `batch` on `show` and on each labelled row of `list`, and refuses a malformed one with exit 2. It is a label for people and the menu bar app: it is not a column, not part of the payload digest, and never an input to routing; a daemon that predates it ignores the field (C-16.2).

## 18. Timers (milestone 5, interface only here)

- **C-18.1** Probe cycles wait `probe_interval_s` after the preceding cycle completes (default 60 seconds), with one usage read per enabled, unlatched lane per window (an `auth-dead` lane is not probed until re-enrolment and a revoked-token lane not until its credential epoch changes; C-23.44, C-23.47). An idle lane's probe holds `slot:0` from its reservation through the publication of its verdict; a busy Codex lane's is the usage read alone, taken beside its attempts (C-18.3); a busy Claude lane is measured by its own attempts as they end (C-9.8) and is not read. A cycle releases every timer hold it took, whatever raised (review of PR #72: a lane whose probe raised left every other lane's `slot:0` held until a restart). The default leaves refresh headroom within the 120-second reading TTL; configured intervals remain authoritative, and delayed lanes, and busy Claude lanes between attempts, still display stale readings honestly. Keepalive is `admission-observed` evidence every 5 h 05 m; reset-credit policy is an action (C-19) with v1's rule set; alerts fire on transition and at most every 6 h while persisting; retention runs every hour; `status.json` is published for the menu bar app every probe cycle.
- **C-18.2** `status.json` also carries `jobs`, so the menu bar app shows work as well as quota: `live` (every `running`, then `waiting`, then `queued` job, oldest first within a state), `recent` (the 8 most recently finished jobs), and `counts` by live state, all three of detached work only: a turn job (kind `turn`, C-26.1) is its conversation's (C-26.12) and is shown under `conversations` (C-29.6). Each row has `job_id`, `kind`, `name`, `state`, `wait_reason` and `next_check_at` (only while `waiting`, so a finished job never shows a stale reason), `sandbox`, `workdir` (the allocated worktree once there is one), `model` and `lane_id` from the job's latest attempt (the pinned model before any attempt), `attempts`, the three timestamps, `rc`, and `batch` (C-17.7) or null. Batch labels are read from `job.submitted` events for the displayed jobs only. The section is always present, empty when nothing is running. The app keeps a batch's jobs together under one heading (`<label> · <size> jobs`) where the first of them appears, shows a waiting job's reason (`waiting: workspace`; any reason other than `capacity` is a warning), shows a failed job's exit code, and decodes a snapshot that has no `jobs` key, so an app newer than its daemon still works. The section is as fresh as the snapshot, one probe cycle (C-18.1); `subfleet runs` remains the live ledger.
- **C-18.3** A busy Codex lane is read beside its work. A lane is busy when it has an attempt `reserved`, `starting`, `running` or `finalizing`, or any `lane:<lane id>:` lease; one transaction decides whether the lane is never read (disabled, not v2's, the desktop's, or under an open `operator-hold` or `auth-dead` closure, checked first), idle, or busy. A busy lane's read is the usage GET alone: it takes no lease and writes no reservation, so admission never sees it as a slot block or a reserved probe (C-6.10) and the next attempt on the lane takes the slot it would have taken without it; it runs no heal turn, because the lane's attempts renew its token (C-23.47); and it passes the per-lane read fence an idle read passes (one read per lane at a time, four at once, the 15 s deadline, a late answer dropped). Its result is judged when the cycle publishes, after every read has finished, and it is judged and published in one store transaction: no slot keeps the lane's attempts away, so the store's write lock does, and a publication that raises rolls back whole, the settlement with it, leaving the lane as it stood. An `ok` or `limited` answer for the lane's own account (or a credential that names no account) publishes what an idle read of the same answer publishes: the readings, a `provider-limit` closure or its release, the reset-credit settlement that ends a confirmed override (C-23.17), and the verdict. A read whose credential names another account (the home's `auth.json`, whatever the request returned) publishes the identity mismatch as an idle read does (no readings, no settlement, no closure change, the lane disabled in the same transaction); it is not fenced, and a job admitted between the read and that commit runs as it would have had nothing been read; a token refresh keeps the account, and a torn `auth.json` reads as no credential, so rotation cannot produce one. Nothing else a busy read finds is published: not `auth-dead`, `revoked`, `expired-token` or `no-auth` (a 401 on a token the attempts just replaced reads as dead; an attempt that ends `auth-dead` disables the lane itself, C-23.44, and the next idle read sets the latches), and not a failed read. Nothing at all is published for a lane disabled or bound to another account since its read. When a closure was recorded or extended on the lane after its read began, the read publishes its readings and verdict but releases no closure and settles no reset credit, so an older answer never undoes a newer limit; the next cycle reads again. Every read in a cycle, busy or idle, published or not, counts toward whether the cycle was offline, and the cycle's `timer.cycle` event names the busy lanes it read and the status of each busy read it did not publish. Claude lanes are not read busy (C-18.1) (incident: 2026-09-30, codex-4 went from an operator hold straight to work with a fresh week from a reset credit; no cycle read it for 78 minutes, the credit's override stood, and the lane stayed unmeasured at one attempt while every other Codex lane was at its floor; `docs/decisions/2026-09-30-busy-lane-usage-read.md`, MaxGhenis/subfleet-v2#73).

The daemon runs the mirror on the timers' own worker, which `Daemon.close()` waits for (`Timers.stop()`), so the mirror opens what it reads outside its state root (the store's records, transcripts, archived transcripts, the app's log, `cc-mirror.json`), and its own lock, only as regular files and never blocks in `open()`: a FIFO, device or directory there reads as unreadable at once, and one where a transcript belongs is no transcript, which revival leaves in place; a transcript that is a symlink is checked again on every pass, since its target can be replaced without its project directory changing. The flag protocol is specified in `docs/formal/MirrorFlags.tla`; its invariants (convergence, change wins both ways, idempotence, cancellation safety, no lost update, all or nothing, base agreement, intent wins) are checked over every reachable state of its executable twin `tests/mirror_flags_model.py` (TLC has not been run on the spec), and the mirror is held to that model on random interleavings, including writes between two of a publish's writes. A wait for the session's other writer (`external-writer`, and the legacy hold's `legacy-owner`, C-30.4) is re-admitted however often it happens and uses up none of those 3, then or later. [milestone 9; owner fake; module `subfleet/conversations/reconcile.py`]
- **C-24.7** (stop is scoped and ends the turn) `message.cancel` withdraws a message only before its job has an attempt, checked in the transaction that records the cancel, except a message with no job bound, which it withdraws even if a job the dispatcher made for it meanwhile has been given an attempt: the stop recorded with that withdrawal keeps the attempt from ever writing the message (below). Withdrawing an id the daemon never received (naming its conversation) records a tombstone that is cancelled in the transaction that creates it; a later `message.submit` of that id returns the tombstone and nothing is dispatched (review IR-7). The dispatcher claims a message (`waiting`, reason `dispatching`) in the conversation store before it creates the message's job, so a handoff that sees the claim refuses rather than racing the submit (IR-28); `message.cancel` still withdraws a message with no job bound, claimed or not, and the job the dispatcher then creates finds it withdrawn and is cancelled before any attempt (IR-2); `turn.interrupt` of a waiting message with no job bound withdraws it too. A cancel records the person's stop in the transaction that withdraws the message, so a runner admission started for that job meanwhile never writes it: a turn whose message has a person's stop recorded before the relay log shows the message handed over is stopped before it is ever written (a message frame whose send was already under way when the stop was recorded, its answer lost, counts as handed over when the relay's log, read after a fresh `status` answer, holds it). A person's stop is recorded, and a runner hands the message frame to the relay, under one lock per message, and the runner reads the stored stop again under it just before the handover, so a stop recorded after the runner started (while the provider answers `initialize`, say) still keeps the message unwritten, and one made during the handover is recorded after it and stops the turn as below; a stop the runner was asked for before the handover (the daemon's wall limit or kill) keeps it unwritten too. A relay slow to take one message's frame holds up the stops and cancels of that message alone. The withdrawal also cancels such a job while it has no attempt, and admission cancels any turn job whose message has settled (hold `message-settled`, C-6.11). A cancel refused (too late, or the message being handed to its job) records no stop, so nothing it did stops the turn it lost to, and clears none; a person's cancels and stops of one message are taken one at a time. A claim is released (a message that was queued, or whose claim a crash interrupted, goes back to `queued`) when its submit is deferred. `turn.interrupt` targets only that message's attempt and escalates as design D-13: the provider's interrupt, SIGINT to the provider child through its guardian's relay, closing stdin, and only then C-5.6 containment. Each later step is taken only while the turn has no terminal event, at policy `conversations.stop_sigint_after_s`, `stop_close_after_s` and `stop_contain_after_s` seconds after the stop was requested (defaults 10, 20, 30); the policy loader refuses a value that is not a positive finite number and an order other than SIGINT before closing before containment. No other conversation, job, or process is signalled. [milestone 9; owner fake; module `subfleet/conversations/service.py`]
- **C-24.8** (an unfinished Claude turn blocks) A Claude attempt that ends without `result` after its message was delivered (C-24.6: acknowledged, or in the session transcript; review IR-5), including a stop that got no `result` and a driver's own stop (a model mismatch) that no `result` followed, sets the conversation `blocked_by: "unfinished-turn"`; a written message frame whose delivery is unknown blocks it as `delivery-unknown` (C-24.6), and a person's `message.resolve` of a Claude message as `delivered` turns that block into `unfinished-turn`; the next message waits for a person's `conversation.unblock` (`continue` or `leave`), recorded. `leave` sends a one-line note ahead of any queued message, so the next turn does not resume the stopped work; `continue` sends nothing. ## 25. Protocol additions

- **C-25.1** (discovery before mutation) `capabilities` returns protocol version 1, the daemon version, `conversation_schema` 1 (the version of the conversation ops' argument and result shapes, C-25.2, which is not the conversation store's schema, C-26.14), capability names and limits. A client sends no conversation op to a daemon that answers "unknown op", and sends a field whose silent omission would change an outcome only after the daemon advertised it. `PROTOCOL_VERSION` stays 1. [milestone 9; owner unit; module `subfleet/protocol.py`]
- **C-25.2** (the ops) The conversation ops are `capabilities`, `conversation.list`, `conversation.open`, `conversation.create`, `conversation.settings`, `conversation.unblock`, `conversation.history`, `conversation.events`, `conversation.watch`, `message.submit`, `message.status`, `message.cancel`, `turn.interrupt`, `message.resolve`, `approval.list`, `approval.get`, `approval.respond`, `attachment.add`, `catalog.refresh`, `models.list`, `conversation.runs`, `turn.diff` and `conversation.diff`, listed in `subfleet/protocol.py` (`CONVERSATION_OPS`) and answered by `subfleet/conversations/service.py`, with the arguments and results of design §5. Receipts from `conversation.open` and `message.status` carry the message's `text` (at most 20,000 characters, `text_truncated` when cut), so a client that did not send a message can show it. Errors are `ok: false` with an `Exit` code. An op added to this list is advertised by a `capabilities` name (`diff.v1` for the two diff ops, `runs.v1` for `conversation.runs`), not by a new `conversation_schema`. [milestone 9; owner unit; module `subfleet/protocol.py`]
- **C-25.3** (handlers never wait) A conversation op handler validates, writes at most one transaction per store (a worktree conversation's create writes its row, then its worktree), wakes the control loop, and returns. It never waits on a provider, a probe, `ps`, git, or a catalog scan (C-16.4), with two exceptions: `turn.diff` and `conversation.diff` run git (C-26.14), and `conversation.create` of a worktree conversation runs git to cut its worktree (C-26.10, design D-16). Those three ops (`conversation.create` whatever its workspace kind), file copies and transcript reads run on a dedicated bounded pool (the file pool), never on the pool the other ops and the session hooks use. The conversation service's `close()` lets the file ops already running finish before it returns, while the state root and the conversation store are still there, drops the ones not yet started, and the pool accepts none after. A file op writes into the state root as it stands and never creates it: with the root gone it fails `state-root-gone` (exit 1). The conversation service (its ops, its control-loop steps and its turn runners) opens every file it reads only as a regular file, and never blocks in `open()`: what it reads of a native session (a Claude transcript, a Codex rollout, Codex's `session_index.jsonl`, a Claude session-registry file), a workspace's `PROGRESS.md`, the real `.git/index` a diff copies, and in the state root an admission job's `manifest.json`, a message's text, an attachment's stored copy, an approval's request, `catalog.json`, `catalog.lock`, `conversations/models.json` and an attempt's files (`stdout`, `stdin.jsonl`, `turn.json`, the JSON records). Admission reads a manifest through `O_NONBLOCK|O_NOFOLLOW`, checks its descriptor with `fstat`, and reads at most 16 MiB; an unreadable manifest holds that job as `conversation-blocked` with its manifest error, without delaying later admission. A FIFO, device or directory there reads as unreadable at once; a stored attachment or a message's text is read only up to its limit (20 MiB, 1 MiB). Contents of the listed service-owned state files are read through a separate no-follow regular-file reader, including attempt stdout and relay logs; `catalog.lock` is opened only for locking, with its existing nonblocking regular-file check. Native transcript readers retain their existing symlink support. A file it writes it makes as a new file of its own (O_EXCL, O_NOFOLLOW) and puts in place by rename, never opening one that stands there, and an attachment's stored copy that does not hash to its name (a FIFO, a partial copy) is replaced by the new copy. Some of what they read of a native session is capped too: a scan for a first task or a session's prompts reads at most the first 64 MiB; a reader that reads lines forward skips a line longer than 64 MiB rather than hold it, so a page of history reads its budget (C-29.8) and, for results past its cursor, the rows that start within its window, each at most 64 MiB, and looks no further back than its budget for a row's start; a registry file is read up to 1 MiB and Codex's index up to 64 MiB, of which a lookup of one thread parses and scrubs only the rows that name it. Settling a turn scans its session's file from the turn's start to its end, and a diff copies the whole of `.git/index`: those are bounded by the file's size alone. So `close()`'s wait for the file ops already running is bounded by those caps and sizes, git's time limits, and the walks of a provider's session trees that find a rollout, which have no budget of their own; and only on a filesystem that answers: `O_NONBLOCK` bounds a FIFO's open, not a read from a stalled mount. A FIFO where a rollout belonged had held a file op, and with it `close()`, until a writer came. The catalog run (C-30.1), a process of its own, opens those files plainly: a FIFO holds that run until its service stops it, never the daemon. `close()` also stops every turn runner and waits, at most 5 s in all, for each to finish the iteration it is in, so what a runner was writing (its events, an approval, `turn.json`, the model catalog in `conversations/models.json`) lands before `close()` returns; it logs each runner still going when the wait ends. The control loop adopts no runner once `close()` has begun, and keeps none whose thread could not start (a thread limit): its next pass adopts that turn again, and a step `close()` overtook is logged as stopped, not failed. After `close()` the conversation store refuses every read and write (`store-closed`, exit 1), and an op that meets the refusal fails with it (`message.status` answers `unknown` only for an id the store holds no message by, and a cancel makes a tombstone only for such an id); a runner's containment write to the main store (D-13) is refused the same way; and a runner's files, the model catalog and message texts (C-24.3) are written only while the store is open, which `close()` waits for; none of them creates the state root. A runner whose last writes are refused still ends, closes its relay and is marked finished, and `close()` logs one it stopped with its outcome unreported; a later daemon replays the attempt from its stdout (C-26.6), and settles a message whose attempt has ended with no runner of its own by replaying that attempt once, so a turn whose report was cut short is settled whichever of finalization and adoption comes first. A settlement writes the conversation's block before the message's state, so one cut short leaves the message live for that replay. `Daemon.close()` waits for its request pool after the service has closed, so an op still running then finishes before the daemon's `close()` returns, its store work refused. The daemon's other work that `Daemon.close()` waits for (the timers' workers through `Timers.stop()`, and its requests and workers pools: `submit`, `gate.*`, `lanes`, an attempt's finalization) reads a file only as a regular file too, never waiting in `open()`: a lane's or the desktop's login (`auth.json`, `.credentials.json`, `.claude.json`), the guard's TRUST, hook, seed files and cached verdicts, `conversations.sqlite3` for `status.json` (checked by `stat` before SQLite opens it by name: a swap between the two is not covered), an attempt's records and artifacts, a Codex rollout a turn attests, a job's prompt, a gate's brief, plan and state, and v1's rosters, plists and run records (a roster that is not a regular file is refused, never read as an empty one an edit would replace); and a file it writes beside one it does not own (`lanes transfer`'s roster and its backup, a raw stream copied from stdout) is a new file of its own (O_EXCL, O_NOFOLLOW). [milestone 9; owner fake; module `subfleet/daemon.py`, `subfleet/conversations/service.py`, `subfleet/conversations/runner.py`, `subfleet/conversations/store.py`, `subfleet/sessions/transcripts.py`]
- **C-25.4** (a bounded cursor, batched writes) `conversation.events` returns events after a sequence number, long-polls at most 50 s, cuts a page at 256 KiB, and says `reset: true` exactly when the cursor is below the conversation's compaction floor (a cursor of 0 included), the highest sequence number compaction removed; each page carries the floor. ## 26. Turns under admission

- **C-26.1** (a turn is a submission the daemon makes) Each turn is a job of kind `turn` with request id `turn:<message id>:<n>`, created only by the daemon's dispatcher through the ordinary submit validation, with `max_attempts` 1, no parent, `in_place` in the conversation's workspace, and the message digest as its payload digest. It is admitted by `evaluate` inside the reserving transaction like any job (C-6.3; C-23.54's one dispatch path). The socket `submit` op refuses `kind: "turn"` and request ids beginning `turn:`. A turn submit the daemon refuses before the job exists sent nothing: a refusal of the message as it is (exit 2 or 7, such as a checkout on `main` without `allow_main`, a missing attachment, or a model the fleet does not route) fails it `not-delivered: <reason>`; any other refusal (exit 1, such as git timing out while inspecting the workspace, or a store or file error) leaves it in its state with `state_reason` `deferred: <why>`, submitted again after 2 s, then 4 s, doubling to at most 300 s, never on every pass. A message withdrawn while its job is being submitted takes that job with it (C-24.7). [milestone 9; owner fake; module `subfleet/conversations/dispatch.py`, `subfleet/conversations/service.py`, `subfleet/daemon.py`]

- **C-26.4** (the guardian relays, it does not interpret) A turn's guardian owns the provider's stdin as a pipe and accepts connections on `run/<16 hex>.sock` (0600 in a 0700 directory) only from the process `daemon.lock` names (pid, boot id, start time). Frames carry a number, a tag and the SHA-256 of their line; each is logged as an intent with fsync before the pipe write and then as `written` or `failed`. A resent number is acknowledged as a duplicate only when its hash matches a written frame; other content is a conflict; a failed or unfinished write is never reported as applied and ends relaying. It never parses provider messages. The relay advertises its version and frame cap in `start.json` and answers `status`, which is not a frame (no number, never logged, answered only after any frame being applied is logged), with the frames applied, whether stdin is closed, whether the child runs, and the cap. A runner asks for it before it sends or replays anything and then sends nothing on a guess: a relay whose count differs from its log, or whose log shows a frame not written, is not written to; a relay that answers `status` as a malformed frame (version 1) is read from its log as before. `message.submit` refuses a Claude message whose text and images cannot fit one frame (`capabilities` limit `relay_frame_bytes`); a frame over the cap is never sent, stdin is closed instead and the turn is reconciled (C-24.6). [milestone 9; owner process; module `subfleet/relay.py`, `subfleet/guardian.py`, `subfleet/conversations/runner.py`]
- **C-26.5** (a turn's end) The provider's terminal event (Claude `result`; Codex `turn/completed`) ends the turn, after which the daemon closes stdin. Output after it is attached to the same message and never changes the outcome. - **C-26.6** (drivers replay) Turn drivers are pure: the daemon rebuilds one after a restart by replaying the attempt's stdout; a runner that finds the provider gone reads all of stdout before it ends the turn, and ends a Codex turn whose thread went idle as complete (C-26.5); a later runner restores a recorded no-send execution boundary before starting or replaying its driver, keeps the outcome an earlier runner for the attempt recorded in `turn.json` (it knew what a replay cannot: a legacy withhold, a stop's reason, an idle settle), and writes no new provider work for a recorded terminal turn (neither the user frame nor a person's approval answer), adding only what stdout said after it; an interrupt is not new provider work, so the rebuilt driver's interrupt (a model mismatch's, C-26.8), the close and the stop's signals are still sent; a frame whose tag the relay log shows as written is not sent again; replay reconstructs the state and events of a handed-over user frame without rebuilding its image payload, even if attachments have disappeared or the state root moved, and an interrupt it shows written is one the rebuilt driver asked for; a person's or legacy hold's stop recorded after the message was handed over is the rebuilt turn's stop too, its interrupt sent (unless written) once the replay has read the stdout there is, so the turn settles as stopped, as it would have without the restart; events are unique by `(attempt, source, position, ordinal)` with no NULL part and are not stored at or below the attempt's watermark. - **C-26.9** (attended turns: first, not reserved) Turn jobs have an admission pass of their own. `_admit` runs it before the pass over detached jobs (unless the turn worker is in one), and the control loop also runs it alone, beside the detached pass, on its own worker (`admission:turns`), so a turn submitted while a detached pass works through a backlog, prepares a workspace or waits on a probe is placed by the next turn pass, not after the detached pass; a turn half that raises does not stop the detached half, and its error is raised after it (C-6.12) (incident: 2026-09-26, at load 110 to 170 with 48 jobs queued, a turn waited about 725 s to be placed and ran in about 20 s; `why` said no pass had reached it 12 minutes in). The two passes never look at the same job, each keeps its own holds and freed-lease record, placements are noted for C-6.11 as each is made, and C-6.3's reservation finds its job no attempt in flight. With no turn queued and none held by the last turn pass, the turn pass is one indexed statement, so offering it every tick costs a starved daemon nothing it needs. Within a pass, turn jobs sort ahead of detached jobs of the same tier; a turn that is not placed never enters the detached jobs' waiters, holds none of them `behind-older-job`, and causes no `slot-kept`. Among turns, C-6.9's hold applies only while the policy sets a turn cap: with neither cap set (the default), an unplaced turn holds no later turn `behind-older-job` or `slot-kept`, since no turn slot exists for a later turn to take (review of 5549d87d: an older turn waiting on its closed pinned lane, or on a checkout another turn held, kept a third conversation's turn waiting while other lanes were free). A turn skipped on its clock keeps its place for the keys its last hold named under `leases` or `queued`. Turns trigger no admission probe; a lane whose verdict would require one is not a candidate for a turn (`probe-required`). Turns have their own capacity, counted apart from detached jobs: at most `conversations.max_active_turns` turns at once across the fleet and `conversations.turn_slots_per_lane` on one lane, each null by default, which is no cap (2026-09-27; until then 3 and 1), and a positive whole number when the policy sets one; detached jobs count only detached attempts against `max_active_attempts` and `max_in_flight_per_lane`, and a full pool holds back only its own kind, so an attended turn never waits for a background job's slot (the installed daemon's first turn, 2026-09-24, waited on `no-slot` on every open Claude lane while detached jobs held them). The slot leases are numbered apart too: a turn takes the lowest free `lane:<lane id>:slot:turn-<n>`, a detached attempt `lane:<lane id>:slot:<n>` from n = 1 (C-6.9), so no attempt holds `lane:<lane id>:slot:0`, the lease a detached job's admission probe takes (C-11.4). ## 30. Catalog and legacy continuity

- **C-30.1** (catalog out of process) Discovery of existing native sessions runs in a separate process with a 20 s wall-clock cap per run, writes `catalog.json` atomically with titles and prompts scrubbed, re-reads only files whose size or mtime changed, indexes every session (exclusions of lane runs and Codex exec or subagent rollouts come before any limit), and never writes a native store. The daemon never scans the Claude projects tree or Codex session trees on a request or control thread. The conversation service starts a run every `conversations.catalog_interval_s` (default 60 s; 0 means only on `catalog.refresh`) and on request, never waits for one, and stops a run still alive after 60 s by its process group. Before each file it publishes, a run checks that the service that started it is still open and that the state root it locked is still there: it inherits the read end of a pipe (the fence, above descriptor 2) whose only write end the service holds, and reads end-of-file there once the service closes or dies; and the lock it holds must still be `<root>/catalog.lock`. It publishes by path and never creates a root, so a root removed or replaced between a check and the write after it can fail that write (the run then exits 1) or receive it. A run that finds the service gone or the root removed or replaced at a check publishes nothing more and exits 3; one whose fence descriptor is not a pipe writes nothing and exits 4; one that finds another run holding the lock exits 0. A probe of the lock (`conversation.list`'s `refreshing`, the check before a run starts) takes it shared, and a run tries for it for up to a second before it leaves the catalog to the run holding it, so a probe is never taken for a run. The service logs a nonzero exit of a run it still tracks and did not stop itself, naming the reason for 3 and 4. `close()` stops tracking the service's run and closes the fence, sends SIGTERM to the run's process group and, if a bounded wait does not see it end, SIGKILL and a second bounded wait, all before it returns, and starts no run after; a run that declines after `close()` is therefore logged by no one. `conversation.list` answers whether `catalog.json` is absent, damaged or old, and reports its `state` (`absent`, `unreadable`, `stale` when older than three intervals, `fresh`), `age_s`, `stale_after_s` and `refreshing` (design D-23). - **C-30.2** (what continues in place) A Claude session in the catalog is continuable when it is not a lane run; a live process outside Subfleet makes it wait (C-26.3). - **C-30.3** (handoffs are labelled) A cross-provider or out-of-home continuation is a new conversation whose first message is a scrubbed continuity brief (C-23.14; Claude transcripts and Codex rollouts both have brief readers, bounded by C-23.36's caps) and which records `handoff_from` (provider, native id, transcript path, brief SHA-256). Texts are published and each moved attachment's stored file checked (present, hashing right) before any job is cancelled. A source with jobs to cancel is first fenced with `blocked_by='handoff:<request id>'`, which prevents dispatch; each cancellation is guarded by no attempt and audited with that request id (IR-2). The new conversation, moved messages, source withdrawals and fence lift commit in one conversation-store transaction. On failure, prepared files are discarded and messages whose jobs this handoff cancelled return to `queued` in their original positions, unbound from the cancelled jobs under a new turn sequence, in the transaction that lifts the fence. [milestone 9; owner fake; module `subfleet/conversations/service.py`, `subfleet/conversations/store.py`, `subfleet/conversations/codex_brief.py`, `subfleet/sessions/handoff.py`]
- **C-30.4** (legacy cockpit import) The v1 `outbox.sqlite3` is the legacy cockpit's message outbox, not a notice outbox, and `cockpit-client/pending-messages.json` its client's journal of unacknowledged sends (manifest rows `outbox` and `cockpit`, milestone 9). Each outbox message is classified individually by its row status, the cockpit's own: `finished`, `error` and `cancelled` are terminal, every other status is not. A session is named in one spelling: a UUID in lower case, and a Codex id (`codex:<home>:<id>`) by its thread id. A terminal message of a Claude session whose transcript is found becomes a read-only history row of that session's one conversation (C-24.1): the one it already has, whatever its origin, while that has no message of its own; otherwise one the import creates with origin `legacy`, bound to the native id and created from the transcript as `conversation.open` creates a native conversation (workspace as C-30.2, design D-9's settings); the row keeps the legacy message id, has origin `legacy`, state `complete` (finished), `failed` (error, or a cancelled unknown delivery a person marked handled) or `cancelled` (withdrawn before dispatch), no job and no predecessor, and settings holding only what the outbox recorded. A history row is never queued or dispatched, and is written only ahead of every other message of its conversation. A non-terminal message, and every journal entry whatever the outbox says of its id (an entry is a send the cockpit app has not seen acknowledged), keeps its legacy owner and is reported, and so does every message of its session. So does a session a live cockpit worker holds now (a pid in `native-workers.json` that is alive), whatever its outbox rows say. A session a live Claude process outside Subfleet is registered for (no `SUBFLEET_ATTEMPT` in its environment) gets no history this pass, but its conversation is not held for it: dispatch and launch already make a turn there wait while the process lives (C-26.3), and a hold would outlast it. A journal that cannot be read (an OS error, not JSON, not an object keyed by provider-qualified session ids with requests naming such ids, or an entry with no request or whose request's message id is not a string or image paths not a list, or any text UTF-8 cannot hold, a lone surrogate a JSON escape made, each checked before anything is counted) is never read as empty: it holds every session, while a missing journal holds none. The same holds for an outbox that exists and cannot be read (`unreadable-database`: not a database, or not the cockpit's columns, a `sequence` that is no integer included; `no-messages-table`), for a workers file that cannot be read (a lone surrogate included), and while the cockpit broker holds `broker.lock` (probed with a shared, non-blocking lock on a read-only handle, released at once; the file is never created), since a running broker may dispatch into any session. A missing outbox holds nothing, and the journal, the cockpit's activity and the fence are read and run whether or not the outbox can be. A `--v1-state` holding none of the manifest's entries (missing, empty, another directory), or holding a v2 state root's files (`state.sqlite3`, `conversations.sqlite3`, `daemon.lock`), is not read as a cockpit that holds nothing: `--legacy-cockpit` refuses it (exit 7) before it takes `daemon.lock` or opens a store (unless a store exists, which may record a retirement), and a milestone pass reads nothing from it and changes no hold. `--legacy-cockpit` and a milestone pass also refuse a `--state-root` that looks like a v1 state directory, so no `daemon.lock` lands in one. `--legacy-cockpit --cockpit-retired` reads no v1 state and, in one transaction, lifts every legacy hold, forgets every held session and records the retirement (creating the conversation store if there is none), for a cockpit that will never run again; every later pass then reads nothing from the cockpit, neither its outbox nor its journal, holds nothing, and is not refused for a v1 state that is gone. The import never moves, queues or sends a legacy message. Every conversation bound to a native session a pass finds held, whatever its origin or provider, gets the import's hold: its `legacy_hold` column, set to the reason, beside and never in `blocked_by`. The hold keeps every turn off the conversation (C-24.5). A turn that kept running across the daemon restart is stopped when the daemon adopts it: one whose message the relay log does not show handed over is stopped before any of its output is replayed, so its message is never written, and is re-admitted once the hold lifts unless a person had asked to stop it; any other is stopped through D-13 only after replay restores its delivered state. A durable no-send outcome still fences replay after a crash even when the legacy hold has since lifted. The pass records the sessions it holds (and whether it holds every one), creating the conversation store to do so if there is none yet, and a conversation bound to one of them afterwards (`conversation.open`) is bound held. The pass reports each held conversation `bound-session-held` with its `blocked_by` and every message of it that is not settled, which runs once the hold lifts unless it is cancelled first (with the daemon running, as `message.cancel` is a daemon op). The first pass that finds its session settled lifts the hold and reports `bound-session-released`. Only the import sets or lifts the hold: no turn outcome replaces it, `conversation.unblock` refuses a conversation only the import holds, and `conversation.unblock` and `message.resolve` clear `blocked_by` alone. The fence runs before any history is placed. A terminal message that a pass cannot place is reported with its disposition: its session held, its transcript not found, a session that cannot continue here, or a transcript that raised while it was read (`transcript-unreadable`), each imported by a later pass once that changes; and its conversation already has messages of its own, its id is already a message of the store's own, its row cannot be read (a message id, a payload, the payload's image paths or service tier, text in the payload or receipt that UTF-8 cannot hold, or a timestamp, each checked before anything is written for the row), or a session that is not Claude's, none of which a later pass changes. One session or row never ends a pass. Every message and journal entry appears in the report with its disposition, by id and never by content. Repeated imports create nothing new: history is idempotent by legacy message id. Notices an earlier import made from outbox rows stay as they are. `python -m subfleet.importer --legacy-cockpit [--dry-run]` runs these two rows alone and opens no `state.sqlite3`; a real run holds `daemon.lock` for its whole length and is refused while a daemon holds it; a dry run imports into a scratch copy of `conversations.sqlite3`; neither writes under the v1 state or a native transcript.

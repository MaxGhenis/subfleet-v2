C-28.1 (2026-09-26, found while fixing the entry above): a changed stored copy is repaired, and its name is on disk before its row. `attachment.add` copied only when no file had the copy's name and then refused a hash mismatch, so once `attachments/<sha256>.<ext>` held other bytes (disk damage, a stray write) every re-add failed with `copy-mismatch` and the driver failed every message naming it `attachment-missing`, for good; a copy it could not read failed every re-add with an unhandled error, and a symlink to the same bytes was kept. It now copies whenever the name does not hold a regular file with those bytes. It also never fsynced `attachments/` after the rename, which C-8.1 requires of a published file and `store._publish` does for message text, so a crash could keep the committed row and lose the copy's name. The directory is now fsynced before every row, also by an add that finds the copy in place, which may find it before the add that renamed it has synced.

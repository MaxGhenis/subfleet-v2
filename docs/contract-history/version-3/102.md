C-28.1 (2026-09-26, found while fixing the review of #47): each `attachment.add` copies through a temporary file of its own. Two adds of the same bytes at once (the app resending after its 15 s timeout while the first add still ran, or two clients; an add still queued for the file pool when the app gave up is dropped with its connection) shared `.<sha256>.<pid>.tmp`: the second open truncated the first's file and at least one add failed, in 40 of 40 trials, sometimes both with no row registered, though the stored copy was right. A copy that fails now removes its temporary file where the directory lets it; a temporary name already taken is drawn again; a short write goes on until the copy is whole, and a write that makes no progress fails the copy instead of looping.
